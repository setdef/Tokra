# Plan 054: The config file and `Context`

A Tauri app starts from its config. `tauri::generate_context!()` reads
`tauri.conf.json` when the app compiles and hands `Builder::run` a
`Context` holding the config, the package's name and version, the
decoded icons, the embedded frontend, and the resolved capabilities. The
builder opens the windows the config lists, builds the tray it
describes, and gives each plugin its slice of `plugins`.

A Tokra app starts from nothing. Its `Config` has three fields that no
public method sets (`lib/tokra/app.rb:172-176` at `821a7e2`), so the
identifier, product name, and version are always `nil`; its one window
comes from `Builder#title` and `#size`, which Tauri does not have; and
four plans wait on a config to read: plan 049's config tray (part B),
plan 052's `from_config` constructors (phase 6) and its
`app.macOSPrivateApi` question (question 2), plan 052e-3's data
directory named for the identifier, and plugin configuration.

ADR 014 settles where the config comes from: Tauri's schema, read from
`tokra.conf.json` (and the JSON5 and TOML forms) when the app starts, by
`Tokra.generate_context`, a run-time translation of the macro. This plan
ports it in four phases. Phase 1 is six commits, 054a-0 to 054a-5, each
specified in full; phases 2 to 4 are one commit each, outlined, and each
gets its own section and review when the one before it lands.

| Phase | Commit | What a developer gets |
|---|---|---|
| 054a-0 | the suite builds apps through one helper | nothing: a behavior-preserving test change |
| 054a-1 | `Ipc::Serde` learns aliases, defaults, untagged and adjacently tagged enums | nothing yet; the IPC plugins behave as before |
| 054a-2 | the schema, `parse`, codegen, `Tokra.generate_context`, `Context`, `PackageInfo` | a config file can be read and checked, beside the old path |
| 054a-3 | the builder takes a `Context` | `Builder#build(context)`, `#run(context)`, `App#config` and `#package_info`; `withGlobalTauri` from the config; the old window methods go |
| 054a-4 | `from_config`, and the config's windows | `WebviewWindowBuilder.from_config`; the app opens `app.windows` |
| 054a-5 | `devUrl`, the development flag, `freezePrototype` | `devUrl` loads and may invoke; `freezePrototype` acts |
| 2 (054b) | JSON5 and TOML | `tokra.conf.json5`, `Tokra.toml`, and JSON5 inside `tokra.conf.json` |
| 3 (054c) | icons, and the config's tray | the default window icon, the macOS dock icon in development, and `app.trayIcon` (plan 049, part B) |
| 4 (054d) | the bundle schema, and the GTK app id | every `bundle` struct checked as Tauri checks it; `app.enableGTKAppId` on Linux |

Capabilities and the ACL get a plan of their own, as do the frontend
assets, the asset protocol, and the CLI (out of scope). Each is named
where the inventory meets it.

## Decisions

1. **`generate_context!` becomes `Tokra.generate_context(path = nil)`,
   and the three crates stay three modules** (ADR 014 §2).
   `Tokra.generate_context` is the macro: it resolves the path, checks it,
   and calls `Tokra::Codegen.get_config` and then
   `Tokra::Codegen.context_codegen(ContextData)`. `Tokra::Codegen` holds
   codegen's work, and `Tokra::Utils::Config` holds tauri-utils' schema
   and `parse`. A reviewer checks each file against one crate.

2. **Names follow Tauri's paths.** Tauri re-exports `Config`,
   `WebviewUrl`, `PackageInfo`, and `Pattern` at its root
   (`lib.rs:217-237`, `:311`), and every other config type lives at
   `tauri::utils::config`. So `Tokra::Config` and `Tokra::PackageInfo`
   are constant aliases of `Tokra::Utils::Config::Config` and
   `Tokra::Utils::PackageInfo`, and `Tokra::Utils::Config` holds
   `AppConfig`, `WindowConfig`, `SecurityConfig`, `BuildConfig`,
   `BundleConfig`, `TrayIconConfig`, `FrontendDist`, `PatternKind`,
   `Csp`, `CspDirectiveSources`, `DisabledCspModificationKind`,
   `AssetProtocolConfig`, `FsScope`, `HeaderConfig`, `HeaderSource`,
   `CapabilityEntry`, `BeforeDevCommand`, `HookCommand`, `RunnerConfig`,
   `PreventOverflowConfig`, `PreventOverflowMargin`, and its own
   `LogicalPosition` (`config.rs:519-530`, a separate struct from the
   dpi one). Config types Tokra already defines at its root, because
   Tauri re-exports them where an app meets them, stay there and gain a
   deserializer where they lack one: `Tokra::WebviewUrl`,
   `Tokra::Color`, `Tokra::WindowEffectsConfig`, `Tokra::Theme`,
   `Tokra::TitleBarStyle`, `Tokra::BackgroundThrottlingPolicy`.
   (`Tokra::ScrollBarStyle` is the webview's type, not the config's;
   054a-2's Result has `Tokra::Utils::Config::ScrollBarStyle`.) `Target` is
   `Tokra::Utils::Platform::Target` with `MacOS`, `Windows`, and
   `Linux`; Android and iOS are out of scope. `Target.current` answers
   `MacOS` on Darwin, `Windows` on mingw and mswin, and `Linux` for
   anything else, the BSDs included, as `Target::current` falls through
   (`platform.rs:75-87`). It reads `RUBY_PLATFORM` itself, not
   `App.os_name`, which answers `"unknown"` on the BSDs
   (`app.rb:468-475`). RBS declares the aliases
   with `class Tokra::Config = Tokra::Utils::Config::Config`.

3. **The config is frozen values, and `Context` is an entity.** Each
   struct is a `Data.define` with Tauri's field names in snake case
   (`$schema` is `schema`; `macOSPrivateApi` is `macos_private_api`),
   declared with `self.new` in RBS per AGENTS.md. Each enum with
   payloads is one `Data` class per variant under a module, as ADR 013
   and plan 052's `WebviewUrl` translate them; each enum of unit
   variants is a set of constants. `PluginConfig` is a newtype over a
   map, which Ruby has no use for, so `Config#plugins` is the frozen
   Hash of plugin name to JSON value itself (AGENTS.md precedence 1).
   Its keys, and every object key inside, are Strings, as in Tauri's
   `JsonValue`; ADR 006 §6.2's `symbolize_names: true` is superseded
   (ADR 014 §8).
   JSON values are Ruby's: Hashes with String keys, Arrays, Integers,
   Floats, Strings, `true`, `false`, `nil`. The whole config is
   deep-frozen with `Ractor.make_shareable`, so any Ractor may read it.
   `Tokra::Context` is a `class` with Tauri's accessors: `config`,
   `package_info`, `pattern`, and from phase 3 the icons. Tauri's
   `config_mut` and `package_info_mut` hand out a mutable borrow, which
   Ruby lacks; with frozen values the translation is a writer,
   `Context#config=` and `#package_info=`, taking a copy built with
   `Data#with`. `Context.new` takes keywords named after `Context::new`'s
   parameters (`config:`, `package_info:`, `pattern:`, and from phase 3
   `default_window_icon:` and `app_icon:`), since three of Tauri's eight
   parameters arrive in later plans and positional arguments would shift
   as they do.

4. **Schema errors are serde's, through `Tokra::Ipc::Serde`.** Tauri
   reads the file into a `serde_json::Value` and then calls
   `serde_json::from_value::<Config>` (`tauri-codegen lib.rs:80-93`), so
   every schema error is serde's derive driven by a `Value`, with no
   line or column. That is exactly what `Ipc::Serde` already is
   (`ipc/serde.rb:25-48`): serde 1.0.228's visitors as serde_json
   1.0.145's `&Value` drives them, raising `CommandItem::Mismatch` with
   serde's words. Phase 1 extends it rather than writing a second copy:
   - **Aliases.** `struct_fields` takes `aliases:`, a Hash of field to
     its other names. A key matches a field by any of them. The
     unknown-field error lists, field by field in declaration order,
     each field's name and aliases sorted by byte, because serde_derive
     builds `FIELDS` from each field's `aliases()`, a `BTreeSet` that
     holds the name too (`de/struct_.rs:55-131`;
     `internals/attr.rs:1270-1286`; `internals/name.rs:71-75`). So
     `TrayIconConfig` lists `` `icon-path`, `iconPath` ``, and
     `AppConfig` lists `` `macOSPrivateApi`, `macos-private-api` ``.
     This settles plan 049, decision 7's UNVERIFIED: the list does name
     the aliases.
   - **Defaults.** A missing field with `#[serde(default)]` or
     `default = "..."` takes the default; one without, that is not an
     `Option`, raises `missing field`. Defaults apply whether the struct
     comes as a map or as a JSON array, since serde_derive's `visit_seq`
     fills a short sequence's defaulted fields too (`de.rs:451-505`,
     `expr_is_missing_seq` at `:497`);
     `seq_fields` gains the same `defaults:`.
   - **Untagged enums.** `untagged` tries each variant's reader in
     order and raises serde's "data did not match any variant of
     untagged enum {Name}" when none reads (`FrontendDist`,
     `BeforeDevCommand`, `HookCommand`, `RunnerConfig`,
     `PreventOverflowConfig`, `Csp`, `DisabledCspModificationKind`,
     `FsScope`, `HeaderSource`, `Updater`, `BundleResources`).
   - **Adjacently tagged enums.** `PatternKind`'s `use` and `options`.
     Phase 4's internally tagged bundle enums use the reader
     `Ipc::Serde.internally_tagged` already has. `CspDirectiveSources`
     is untagged (`config.rs:2067-2070`), not tagged.
   - **Key order.** serde reads a map's keys in the order the `Value`
     iterates them, and serde_json's `Map` without `preserve_order` is a
     `BTreeMap`, ordered by byte. So with two bad keys the error names
     the first in byte order. `Ipc::Json` already sorts the keys it
     parses (`json.rb:274-276`), but a Ruby merge appends a platform
     file's new keys at the end, and the JSON5 and TOML parsers of phase
     2 keep source order. So the loader sorts every object by key bytes,
     recursively, after merging and before the schema reads it, and a
     fixture has two bad keys in source order the reverse of byte order.
   - **Rust's quoting.** Messages that print a value with `{:?}`, such
     as url's "{error}: {input:?}" and the CLI's quoted paths, quote as
     Rust's `Debug` for `str` does (`\"`, `\\`, `\n`, `\u{..}` for
     other controls), which `String#inspect` does not (`#{`, `\e`,
     `\u0001`); a small helper renders it.
   - The custom deserializers Tauri writes by hand port by hand:
     `WebviewUrl` (`:88-109`), `Color` (exists), `CapabilityEntry`
     (`:2659-2669`), `PackageVersion` (`:3137-3189`), and in phase 4
     `BundleTarget` and `BundleType`.

   `Tokra::Codegen` rescues `CommandItem::Mismatch` and raises
   `Tokra::Codegen::CodegenConfigError::Json` with serde's message,
   which is what codegen's `#[error(transparent)]` prints
   (`tauri-codegen lib.rs:46-47`). The IPC plugins that use `Ipc::Serde`
   keep their behavior; the extension adds keywords and changes no
   existing call. Tests compare against fixtures the real crates
   produced (Verification).

5. **JSON reads through `Tokra::Ipc::Json`.** Tauri's `do_parse_json`
   is `serde_json::from_str` into a `Value` (`parse.rs:351-356`).
   `Ipc::Json` is serde_json 1.0.145's parser ported step for step, with
   its messages and positions (`ipc/json.rb:22-48`), so a config file
   fails exactly where and how Tauri's fails: "unable to parse JSON
   Tokra config file at /app/tokra.conf.json because expected `,` or
   `}` at line 3 column 5". `read_to_string` refuses a file that is not
   UTF-8 before serde_json sees it, so the loader checks
   `valid_encoding?` first and raises `ConfigError::Io` with Rust's
   "stream did not contain valid UTF-8". A Ruby `SystemCallError` reads
   as Rust's `io::Error` displays one, "{description} (os error
   {errno})", built from `e.class.new.message` and `e.errno`. On
   Windows Rust prints the system's own message ("The system cannot
   find the file specified."), where Ruby maps the error to errno's
   words; that difference is recorded in the RDoc. The missing-file
   case `do_parse` raises itself uses `ErrorKind::NotFound`'s display,
   "entity not found" (`parse.rs:330-333`).

   **Depth.** `Ipc::Json` stops at 128 levels, and so does Tauri's
   config read: `do_parse_json` calls `serde_json::from_str`, whose
   deserializer starts `remaining_depth` at 128
   (serde_json 1.0.145 `de.rs:60-68`, `:1354-1375`). Tauri's lock turns
   on serde_json's `unbounded_depth` (through cargo_metadata 0.19, which
   `tauri-utils/build` pulls in for codegen), but the feature only adds
   `disable_recursion_limit`, which nothing in the parse calls
   (`de.rs:205-217`). So phase 1 keeps the limit, with serde_json's
   "recursion limit exceeded at line L column C". In phase 2 a `.json`
   is read by json5 first, whose recursive parser has no such limit,
   so a deeply nested `tokra.conf.json` that serde_json refuses reads;
   the JSON5 port keeps that, and its own recursion uses an explicit
   stack so Ruby's stack does not set a limit Tauri's does not have.
   serde_json's `from_value` into `Config` has no limit either.

   **Windows paths.** Rust joins and displays paths with `\` on
   Windows, so Tauri's messages read
   `C:\app\src-tauri\tauri.conf.json`. Ruby's `File.join` and
   `File.expand_path` use `/`. Every path a message prints goes through
   one helper that replaces `/` with `File::ALT_SEPARATOR` when Ruby
   has one, so Tokra's messages read as Tauri's on Windows; the paths
   `Context` and `Config` hold stay Ruby's.

6. **The platform file merges as json-patch's `merge` does, and each
   phase enables what Tauri would with its features.** `merge` is
   ported in ten lines (json-patch 3.0.1 `lib.rs:661-678`, with its
   SPDX snippet): an object patch merges key by key, a `null` deletes,
   any other value, an array included, replaces. So a
   `tokra.macos.conf.json` that sets `app.windows` replaces the whole
   list. The merged object is then sorted by key (decision 4). In phase 1 the enabled formats are JSON only, so a lone
   `tokra.conf.json5` or `Tokra.toml` raises Tauri's `DisabledFormat`,
   "supported (but disabled) format encountered .json5 - try enabling
   `config-json5` ", the message Tauri without the features gives.
   Phase 2 enables both, and `DisabledFormat` goes, since no format is
   ever disabled again (ADR 014 §7).

7. **Brand strings are renamed in the messages that name the config;
   nothing else is reworded.** "Tauri config file" reads "Tokra config
   file" in `ConfigError`'s messages (`parse.rs:83-129`);
   "`tauri.conf.json > version`" reads "`tokra.conf.json > version`"
   (`config.rs:3166-3183`); "expected tauri config file" reads "expected
   tokra config file" (`tauri-macros context.rs:51`). The window
   config's default title, Tauri's "Tauri App" (`config.rs:2061-2063`),
   becomes "Tokra App" by the same rule (ADR 014 §4). The runtime's
   default is the same string in Tauri (`tauri-runtime-wry lib.rs:827`),
   which Tokra renamed to "Tokra" (`window_builder.rb:27`), dropping the
   second word. 054a-3 makes `WindowBuilder::DEFAULT_TITLE` "Tokra App"
   too, so both defaults rename Tauri's one string the same way, and the
   CHANGELOG says the default title changed.

8. **Errors keep Tauri's types.** `Tokra::Utils::Config::Parse::ConfigError`
   is a `Tokra::Error` with one subclass per variant, `FormatJson`,
   `Io`, `UnsupportedFormat`, and `DisabledFormat` in phase 1,
   `FormatJson5` and `FormatToml` in phase 2, each with its `path` and
   `error` readers, as ADR 011's table translates an error enum.
   `Tokra::Codegen::CodegenConfigError::Json` carries a schema error.
   Codegen's `ConfigError(#[from] ConfigError)` variant is transparent,
   so Tokra raises the inner `ConfigError` itself; `CurrentDir`,
   `Parent`, and `FormatInline` have no cause in Tokra (decision 9 moves
   no working directory, and decision 11 reads no variable). The
   macro's own refusal of a path is a compile error on its argument, so
   `Tokra.generate_context` raises `ArgumentError` with its words.
   Codegen's panics (phase 3's icons; the assets plan's missing
   `frontendDist`) raise `RuntimeError` with the panic's message, the
   plain Ruby form of `panic!`. That includes the panics Tauri does not
   write itself: an ICO with no entries reaches `entries()[0]`
   (`image.rs:57`) and panics with Rust's "index out of bounds: the len
   is 0 but the index is 0", which phase 3 raises as that
   `RuntimeError`.

9. **`version`, `PackageInfo`, and the config's directory.** The
   `version` deserializer treats its string as a path when a file
   exists there, relative to the working directory, which codegen sets
   to the config's directory for the call (`tauri-codegen
   lib.rs:89-96`; `config.rs:3152-3183`). Moving the working directory
   is process-wide and unsafe beside other threads, so Tokra passes the
   config's directory into the reader and expands the string against
   it; the result is the same, quirk included: a file named `1.0.0`
   beside the config is read as JSON. A version string is checked as
   semver 1.0.24's `Version::from_str` checks it (the version Tauri
   locks; its `parse.rs` is the answer key wherever it and the SemVer
   text could be read differently), and kept as the String Tauri stores
   after `to_string`.
   `PackageInfo` is `Data.define(:name, :version, :authors,
   :description, :crate_name)`. Its Cargo-sourced values translate to a
   Ruby app, which has no manifest: `name` is `productName`, else the
   entry script's base name without extension, the fallback Tokra
   already uses (`window.rb:1488`, `menu.rb:103`); `version` is
   `version`, else `"0.0.0"`, Cargo's version for a package that names
   none; `authors` and `description` are `""`, what `env!` gives for a
   manifest without them; `crate_name` is the entry script's base name.
   `version` is a String, not a `semver::Version`: Ruby's
   `Gem::Version` orders prereleases differently, and Tauri's callers
   only print it.

10. **`devUrl` and `frontendDist` resolve the app URL as Tauri's
    `get_app_url` does, and one development flag picks the arm.**
    Tauri's `dev` is `!cfg!(feature = "custom-protocol")`, read once by
    the macro into codegen's `ContextData.dev`
    (`tauri-macros context.rs:155`) and by the crate as `is_dev()`
    (`lib.rs:313-316`); `tauri build` turns the feature on
    (`tauri-cli interface/rust.rs:483-490`). In development the app URL
    is `devUrl` when set; packaged, it is `frontendDist` when that is a
    URL; otherwise it is the `tokra://` URL (`manager/mod.rs:345-358`).
    A `WebviewUrl::App` joins its path to that URL, leaving `index.html`
    off (`manager/webview.rs:414-430`), and an IPC origin is local when
    it is the `tokra://` origin or the app URL's `make_relative` of it
    succeeds, which is true for any URL with the app URL's scheme,
    host, and port (`webview/mod.rs:1680-1721`). Without that last arm
    a page served from `devUrl` could not invoke; with it, whatever
    answers on `devUrl`'s origin can.

    Where the flag comes from is question 1. 054a-2 and 054a-5 are
    written so either answer fits: `Tokra::Codegen::ContextData` has
    `dev`, as codegen's does; `context_codegen` stores it on the
    `Context` (internal), `App.new` hands it to `AppManager`, and every
    reader (`get_app_url`, later the CSP choice and the macOS dock icon)
    asks the manager. `Tokra.is_dev` mirrors `tauri::is_dev()` and
    answers the flag of the app this process built, or the default when
    none is built yet. Only the default and the way an app sets it
    differ between the answers: under (a) the default is `true` and
    nothing sets it yet; under (c) the default is `false` and
    `Tokra.generate_context(dev: true)` sets it, an opt-in named after
    `ContextData.dev` in code, never in the environment (ADR 011).
    Nothing reads the flag before 054a-5, so 054a-2 carries it with a
    provisional default of `true` and 054a-5, which adds its readers,
    lands with the default you choose.

11. **What the CLI checks, Tokra does not.** The CLI validates the
    merged config against the JSON schema before codegen runs
    (`helpers/config.rs:186-202`); in that schema only `productName`
    has a pattern (`config.rs:3273`). `tauri build` then checks the
    identifier itself: it refuses `com.tauri.dev`, refuses any character
    but alphanumerics, `-`, and `.`, and warns when it ends in `.app`
    (`tauri-cli build.rs:160-186`). Codegen and the runtime check
    neither, so a Tokra app whose config the CLI would refuse starts, as
    a Tauri app compiled without the CLI does. Both checks wait for a
    Tokra CLI or bundler, the identifier's with the rename of
    `com.tauri.dev` to `com.tokra.dev`.

12. **`Builder#build(context)` and `Builder#run(context)` take the
    context first.** `build(context, native: Native)` and
    `run(context, native: Native, &callback)`; `context` is required,
    as in Tauri. `Builder#title`, `#size`, and `#with_global_tauri` go
    (ADR 014 §1), with the builder's `window_config` hash and `App`'s
    `DEFAULT_CONFIG`. `App.new` takes the context and builds
    `AppManager` from its config, package info, and pattern.
    `Rack::Handler::Tokra.run(app, context: nil, invoke_handler: nil,
    native: Tokra::Native, **options)` builds a context when none is
    given: from `File.dirname(options[:config])` when rackup passed
    `:config`, the absolute path of `config.ru` (rackup 2.3.1
    `lib/rackup/server.rb:341`, `:404`), and from the default anchor
    otherwise. Other rackup options (`Host`, `Port`, ...) are ignored,
    as a desktop app listens on nothing. Its `title:`, `width:`,
    `height:`, and `with_global_tauri:` go, since the config holds each.
    `Builder#run` keeps its block for the run callback: Tauri's
    `Builder::run` takes none (`app.rs:2298-2302`), and the block
    predates this plan; it is unchanged here.

13. **`Builder#app` stays.** The Rack app is how a Tokra app serves
    `tokra://`, and nothing in Tauri's config replaces it: Tauri's
    nearest piece, `Context`'s assets, embeds files, where a Rack app
    answers requests. The assets plan decides how embedded
    `frontendDist` assets and a Rack app share the protocol. Until then
    a config's `frontendDist` directory is read and not served.

14. **The config's windows are built where Tauri builds them, and fail
    as Tauri's do.** `App#run` builds each `app.windows` entry whose
    `create` is `true`, in order, through
    `WebviewWindowBuilder.from_config(handle, window_config).build`
    (from 054a-4; 054a-3 builds each with its label, URL, title, and
    size only), after the app menu and before the setup hook, where
    `main` is built

17. **JSON5 is a Ruby port of json5 0.4.1 and of the pest machinery
    its errors come from (phase 2).** No maintained Ruby gem parses
    JSON5: `json5` 0.0.1 is from 2014 and runs JavaScript through
    therubyracer. Ruby's `json` 2.18.0 accepts comments and, with an
    option, trailing commas, but not unquoted keys, single quotes,
    hexadecimal, `Infinity`, or `NaN`. Tauri's json5 0.4.1 is a 123-line
    pest grammar and a deserializer (`src/json5.pest`, `src/de.rs`),
    ported step for step, as `Ipc::Json` ports serde_json.
    - **Values.** An integer literal is an integer, anything else a
      float (`de.rs:52-62`, `:378-383`); `NaN` and `Infinity` become
      `null` once serde_json's `Value` takes them; `-0` is the integer
      0, where serde_json gives `-0.0`. Hexadecimal goes through a
      `u32`, so `0x100000000` fails with "error parsing hex", and a
      negative hex literal is not one to `is_hex_literal` and fails
      `i64` parsing with "error parsing integer" (`de.rs:369-390`); a
      float past `f64` is "error parsing number: too large"
      (`:349-367`).
    - **Errors.** A syntax error is pest's: json5 turns
      `pest::error::Error<Rule>` into its message with `to_string`
      (`error.rs:40-52`), so the text is pest 2.7.15's rendering (the
      version Tauri locks; MIT OR Apache-2.0): the ` --> line:col`
      header, the source line, the caret run, and "= expected {rules}"
      listing the rules attempted at the furthest position, sorted and
      deduplicated, joined as pest's `enumerate` joins them
      (`error.rs:563-680`). Which rules are listed comes from pest's
      attempt tracking (`parser_state.rs:417-520`), so the port tracks
      attempts the same way as it parses: the furthest position reached
      and the rules tried there. The scope is what json5's grammar
      reaches: `ParsingError` with positives (json5 has no negative
      lookahead that reports), one-line and spanning positions, and
      Rule names as pest's derive prints them. Custom errors from the
      deserializer carry json5's own text and no rendering. The port
      carries two SPDX snippets: ISC for json5 and MIT OR Apache-2.0
      for pest.
    - **License.** `LICENSES/ISC.txt` joins the tree. No new dependency.

18. **TOML is tomlrb 3.0.0 (phase 2), with what it cannot match
    recorded (question 2).** Tauri's toml 0.9.10 reads TOML 1.1. Of the
    Ruby parsers, tomlrb 3.0.0 alone reads 1.1 by default and passes
    every 1.0 and 1.1 case of toml-test 2.2.0; it is pure Ruby with no
    dependencies, MIT, and needs Ruby 3.3, below Tokra's floor.
    perfect_toml 0.9.1 calls its 1.1 support preliminary; toml-rb
    depends on citrus; tomlib is a C extension. ADR 005 §3 puts
    configuration parsing in Ruby, and ADR 011 §1 keeps Ferro from
    binding a crate a maintained gem covers, so `tokra.gemspec` adds
    `tomlrb ~> 3.0`, the first runtime dependency beyond `rb_sys`. Where
    tomlrb and toml differ, Tokra closes what it can and records the
    rest:
    - **Numbers.** toml hands an integer to serde as `i64`, else `u64`,
      else `i128` or `u128`, and fails beyond those with "integer number
      overflowed"; a float that is not an `f64` fails with
      "floating-point number overflowed" (`de/deserializer/value.rs:95-113`).
      tomlrb returns any Integer and any Float. Tokra checks the
      ranges: within `i64` or `u64` the value passes, as serde_json's
      `Value` takes it; in the `i128`/`u128` range serde_json's `Number`
      refuses it (`value/de.rs:47-66`) with a message the fixture
      records (UNVERIFIED until the generator runs); past `u128` Tokra
      raises "integer number overflowed". Which float literals toml
      refuses as overflowing (for example `1e400`) comes from the
      fixtures too.
    - **Dates.** toml gives serde a date or time as toml_datetime's
      one-key map, `{"$__toml_private_datetime" => <Display>}`
      (`datetime.rs:98-100`), and its `Display` normalizes: `T` between
      date and time, seconds always shown, a fraction with trailing
      zeros trimmed, `Z` for a `Z` offset and `+HH:MM` or `-HH:MM`
      otherwise, so `-00:00` prints `+00:00` (`datetime.rs:232-284`).
      tomlrb returns a `Time` for an offset date-time and loses whether
      it was written `Z` or `+00:00` (`parser.rb:664-680`). Tokra
      renders tomlrb's local types and `Time`s in toml_datetime's form;
      for a UTC `Time` it prints `Z`, so `+00:00` and `-00:00` written in
      the file read as `Z` where toml prints `+00:00`. Only a plugin's
      config can hold a date, since no schema field takes one.
    - **Errors.** tomlrb raises `Tomlrb::ParseError` ("{message} at
      line N, column M") for bad syntax and `ArgumentError` for an
      impossible offset date-time (`parser.rb:676-678`). Tokra rescues
      both, and only those, and raises `ConfigError::FormatToml` with
      Tauri's "unable to parse toml Tokra config file at {path} because
      {error}" around tomlrb's text. toml prints its own report, with
      the source line and a caret, so that text differs.

    Each deviation is in the RDoc. Question 2 asks whether they are
    acceptable.

19. **The config's icons decode as codegen decodes them, through png
    0.17.16 and ico 0.5.0 in the extension (phase 3; plan 049,
    question 2).** Codegen reads a PNG with png 0.17.16 and no
    transformations and refuses one that is not RGBA
    (`image.rs:74-99`), and takes an ICO's first entry through ico
    0.5.0 (`image.rs:50-72`). Tokra's `Image.from_path` uses the image
    crate, which picks an ICO's richest entry and converts any PNG to
    RGBA, so it cannot stand in. A Ruby port is not small: ico 0.5.0
    decodes a PNG entry of any color type through the png crate, so a
    port needs a whole PNG codec, where Ruby has only Zlib's inflate.
    So phase 3 ports codegen's `CachedIcon` into the extension, over
    `png = "=0.17.16"` (already in Tokra's lock through tray-icon) and
    `ico = "=0.5.0"` (MIT; it needs only byteorder and png 0.17, both
    locked). This is Tauri's own Rust, ported, not a binding of a crate
    for Rubyists at large, so ADR 011 does not send it to Ferro, as it
    did not send `Image::from_bytes`. The decoder takes bytes Ruby read
    and returns a Ruby String it builds after decoding, so no Ruby value
    sits in a Rust buffer, and it never panics: a png or ico error
    returns its message for Ruby to raise in codegen's words ("failed to
    read icon {path}: {e}", "icon {path} is not RGBA", "failed to parse
    icon {path}: {e}", "failed to decode icon {path}: {e}").

25. **The config's URLs are the url crate's, through ferro-url.** Tauri
    reads `build.devUrl`, `app.windows[].proxyUrl`, a URL
    `build.frontendDist`, and a URL `app.windows[].url` as `url::Url`
    (url 2.5.4), whose parser follows the WHATWG URL Standard. Ruby's
    `URI` follows RFC 3986 and disagrees widely: it takes `http://a:99999`,
    refuses `http:/localhost`, IDN hosts, `%zz`, `foo:bar baz`, and
    `C:\dist`, and normalizes neither dot segments nor IPv4 shorthand, so
    the two untagged enums (`WebviewUrl`, `FrontendDist`) would switch
    variant for such strings without a word. ADR 011 sends a crate binding
    to Ferro, and ferro-url binds url one to one, so the core gem depends
    on `ferro-url = 0.1.0.pre.1` (already in the bundle for the
    notification plugin, plan 030), and each URL field holds a frozen
    `Ferro::Url::Url`. `WebviewUrl::External` and `CustomProtocol` take one
    as well as a `URI`, since their one reader calls `to_s`. ferro-url
    binds url 2.5.8 with idna 1.1.0, where Tauri locks url 2.5.4 with idna
    1.0.3; the parser's changes between them read as refactors and
    performance work (Cow hosts, bulk percent-encoding), and every URL
    fixture, answered by 2.5.4, passes through 2.5.8. A difference outside
    the fixtures is UNVERIFIED; the one known is Unicode data, since
    ferro-url's idna_adapter 1.2.2 reads ICU4X 2.4's where Tauri's
    idna_adapter 1.2.0 reads ICU4X 1.5's, so only a hostname with a code
    point assigned since then could read differently. 054a-4 converts `proxyUrl` for
    `WebviewWindowBuilder#proxy_url`, which takes a `URI`.

(`config.rs:132-310`), `Updater`, `BundleResources`, `FileAssociation`,
and the Windows (WiX, NSIS, `WebviewInstallMode`, the sign command),

passes the identifier to tao's event loop as its app id on Linux

## Risks

- **Phase 1 touches every test that builds an app.** About seventy test
  files call `Builder#build` or `#run`. 054a-0 moves them onto one
  helper before anything changes, so 054a-3's diff to them is the
  helper's alone; a test that relied on `main` existing now relies on
  the helper's default window. A reviewer reads `test/support/` first.
- **The generator can drift from Tauri.** It builds from the vendored
  sources with a lock seeded from Tauri's, so a submodule bump needs a
  reseed and a rerun; `rake config:fixtures` does both, and a fixture
  diff after a bump is the signal.
- **Extending `Ipc::Serde` reaches the IPC plugins.** The new keywords
  default to the old behavior, and the existing serde tests stay as
  they are; a changed message there is a regression.
- **Ruby's `URI` decides whether a config string is a URL.** Settled by
  decision 25: the config's URLs are url's own, through ferro-url, which
  binds url 2.5.8 where Tauri locks 2.5.4.
- **The default anchor under a launcher.** With a binstub as the entry
  script, the default path looks beside the binstub (a symlinked
  launcher resolves, and rackup anchors at `config.ru`). The error
  names the path it tried, and ADR 014 tells the developer to pass one.
- **Until question 1 is answered, the development flag is `true`.** A
  config with `devUrl` then loads it in every run, as `tauri dev` would,
  and 054a-5's local-origin arm lets whatever answers on that origin
  invoke commands. An app shipped in that state trusts its developer's
  localhost on its users' machines. That is the reason to answer
  question 1 before 054a-5 lands.
- **Plan 052e-2 is in flight in `lib/`.** Phase 1 starts from the tree
  after it lands, and rechecks every `lib/` citation above.

## Questions for the maintainer

1. **How does a Tokra app tell development from packaged?** Tauri's
   answer is a Cargo feature, `custom-protocol`, that `tauri build`
   turns on and `tauri dev` leaves off (`tauri-cli
   interface/rust.rs:483-490`), which the macro reads into
   `ContextData.dev` (`tauri-macros context.rs:155`) and the crate into
   `is_dev()` (`tauri lib.rs:313-316`). It picks `devUrl` or
   `frontendDist` for the app URL, and with it which origin may invoke
   commands, `devCsp` or `csp`, whether assets are embedded, and whether
   the macOS dock icon is set from `icons/`. Tokra has no build step and
   no bundler, and ADR 011's rule does not settle it: building the
   feature in would make every app "packaged" and `devUrl` dead, and
   leaving it out makes every app "development".
   - (a) **Development until the bundler exists**; the bundler marks a
     packaged app, as `tauri build` does. Every Tokra app runs from its
     sources today, the way `tauri dev` runs one, so this matches how
     apps are run now. But an app shipped before a bundler exists loads
     `devUrl` if its config names one, and trusts that origin, usually
     the developer's localhost, for IPC on every user's machine.
   - (b) Development by default, with packaged an opt-in in code: (a)'s
     risk for any app that forgets the keyword, so it is not
     recommended.
   - (c) **Packaged by default, with development a code-level opt-in
     named after `ContextData.dev`**, such as
     `Tokra.generate_context(dev: true)`, and `Tokra.is_dev` answering
     the flag of the app's context. A shipped app is then safe by
     default, and `devUrl` and `devCsp` act only where the developer
     asked for them in code, which ADR 011's amendment prefers to any
     switch whoever runs the app could flip. The cost is one keyword in
     a developer's script while they work against a dev server.
     **The orchestrator recommends (c)**, pending your decision.

   054a-2 and 054a-5 are written so either answer fits (decision 10):
   only the flag's default and the `dev:` keyword depend on it. Nothing
   reads the flag before 054a-5, which adds its readers, so 054a-5 waits
   for your answer and the commits before it do not.
2. **Are tomlrb's differences from toml 0.9.10 acceptable for
   `Tokra.toml`?** AGENTS.md asks for Tauri's behavior and error
   messages, and none of the precedence tiers covers a cost. tomlrb
   3.0.0 matches toml's TOML version and its values for every key the
   schema reads; decision 18 closes the number ranges and the rescue.
   What stays different: syntax-error text is tomlrb's, not toml's
   report with source line and caret; an offset date-time written
   `+00:00` or `-00:00` reads as `Z`, since tomlrb's `Time` cannot tell
   them apart, where toml prints `+00:00` (only a plugin's config can
   hold a date); and the wording of serde_json's refusal of an `i128`
   integer, until the generator records it. The alternatives: port toml
   0.9.10's parser and messages to Ruby, as `Ipc::Json` ports
   serde_json, a far larger port than json5's; or bind toml 0.9.10 in a
   `ferro-toml` gem first, which ADR 011 §1 discourages while a
   maintained gem exists and which makes the TOML half of phase 2 wait
   for a Ferro release. The JSON5 half does not wait on this answer.
