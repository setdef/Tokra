# Plan 015: The `ipc://` Custom-Protocol Transport, Proven with `@tauri-apps/api`

Serve Tauri's primary desktop IPC transport (`ipc://`) so the frontend's
vendored `ipc-protocol.js` stops falling back to `postMessage`, and prove the
transport by driving it with the real `@tauri-apps/api` loaded through a
faithful `withGlobalTauri` — the mechanism Tauri itself uses to put its API in a
webview without a frontend bundler.

[ADR 009](../adr/009.md) recorded serving `ipc://` as a named follow-up, not an
optimization: it is Tauri's desktop default, and riding the `postMessage`
fallback costs one failed `fetch('ipc://…')` and one console warning per page
load. This phase serves it and, in doing so, delivers [ADR 008](../adr/008.md)'s
promise — that Tauri's npm packages work unchanged — in the direction ADR 008
never demonstrated: a real invoke round trip through a real webview.

## Why the transport and its proof ship together

The `ipc://` request and response format is not Tokra's to define. It is fixed
by Tauri's `ipc-protocol.js` (the client) and `ipc/protocol.rs` (the server this
phase ports). Two facts follow, and they bind the transport to its proof:

1. **The transport is validated only by the client that defines it.** A test
   Tokra hand-writes encodes Tokra's *reading* of the wire format on both ends,
   so it cannot catch a misreading. The vendored `@tauri-apps/api` calling the
   vendored `ipc-protocol.js` is the authority; only it confirms Tokra parses
   and answers the request Tauri actually sends.
2. **The client exercises the transport only once it is served.** Until
   `ipc://` answers, the real `@tauri-apps/api` rejects the fetch, latches
   `customProtocolIpcFailed`, and rides `postMessage` (Context 4). Serving
   `ipc://` is what puts the real client on the real path, so the proof is not
   meaningful without the transport, and the transport is not trustworthy
   without the proof.

## Context

All citations against `vendor/tauri` (pinned submodule) and the vendored
scripts in `lib/tokra/js/`.

1. **Client transport selection** (`lib/tokra/js/ipc-protocol.js.erb:29-93`,
   from `vendor/tauri/crates/tauri/scripts/ipc-protocol.js`). `sendIpcMessage`
   tries the custom protocol first unless `customProtocolIpcFailed` is latched.
   It POSTs to <tt>convertFileSrc(cmd, 'ipc')</tt> with the payload as the body
   and three Tauri headers plus content type: <tt>Content-Type</tt>,
   <tt>Tauri-Callback</tt> (the u32 callback id), <tt>Tauri-Error</tt> (the u32
   error id), and <tt>Tauri-Invoke-Key</tt>. The browser adds <tt>Origin</tt>.
   The command name rides the URL, not the body.
2. **The URL shape** (`lib/tokra/js/core.js.erb:20-28`). `convertFileSrc(cmd,
   'ipc')` yields <tt>ipc://localhost/<i>encodeURIComponent(cmd)</i></tt> on
   macOS and Linux, and <tt>http://ipc.localhost/<i>cmd</i></tt> on Windows and
   Android. The command is the percent-encoded URL path.
3. **Client response contract** (`ipc-protocol.js.erb:49-65`). The client reads
   the <tt>Tauri-Response</tt> response header (<tt>ok</tt> → the callback id,
   anything else → the error id), parses the body by `content-type`
   (<tt>application/json</tt> → `response.json()`, <tt>text/plain</tt> →
   `response.text()`, else `arrayBuffer()`), and calls
   <tt>runCallback(callbackId, data)</tt> **itself**. The server does not eval
   `runCallback` for this transport; it answers the HTTP request.
4. **Fallback fires only on fetch rejection** (`ipc-protocol.js.erb:66-75`). Any
   resolved HTTP response — even a 4xx/5xx — keeps the client on `ipc://`. The
   client falls back to `postMessage` only when the `fetch` *rejects* (the
   protocol is absent or blocked by CSP). Once Tokra serves `ipc://`, the client
   stays on it and the warning disappears.
5. **Server handler** (`vendor/tauri/crates/tauri/src/ipc/protocol.rs:38-183`,
   the `get` async URI-scheme handler; header-name constants at 24-30). A shared
   `respond` closure (48-57) stamps <tt>Access-Control-Allow-Origin: *</tt> and
   <tt>Access-Control-Expose-Headers: Tauri-Response</tt> onto every reply.
   `POST` (60) parses the request (Context 6) and, on success, hands it to
   `webview.on_message` (75). `OPTIONS` (164) returns a preflight adding
   <tt>Access-Control-Allow-Headers: *</tt>; any other method returns 405 (172).
6. **Request parsing** (`protocol.rs:435-538`, `parse_invoke_request`). `cmd` is
   the URL path with the leading `/` removed, **percent-decoded** (443-445).
   `Content-Type` defaults to `application/octet-stream` (452-458).
   <tt>Tauri-Invoke-Key</tt> (483-489), <tt>Tauri-Callback</tt> and
   <tt>Tauri-Error</tt> (numeric, 501-520), and <tt>Origin</tt> (parsed as the
   request URL, 491-499) are **required**; the payload is the body parsed by
   content type — JSON parsed, or an empty object when the body is empty
   (525-538). **Any missing or invalid header, bad JSON, or unknown content type
   returns `Err(String)`, and the handler replies 500 `text/plain` with that
   message** (`protocol.rs:143-151`). This is distinct from a key mismatch
   (Context 7).
7. **The key is verified in the shared dispatch; a mismatch drops, never
   replies** (`vendor/tauri/crates/tauri/src/webview/mod.rs:1724-1744`).
   `on_message` runs for both transports (called from `protocol.rs:75` and the
   `postMessage` handler at `protocol.rs:311`). It compares `request.invoke_key`
   against `manager.invoke_key()` and, on mismatch, logs
   <tt>__TAURI_INVOKE_KEY__ expected {expected} but received {received}</tt> to
   stderr and `return`s — the responder is dropped, never called. On the
   custom-protocol path the dropped responder makes the client `fetch` reject,
   which triggers the `postMessage` fallback, which drops and logs in turn
   (Context 4; Plan 014). A well-formed request thus produces no HTTP reply at
   all on mismatch, unlike a malformed one (Context 6).
8. **The rest of `on_message`** (`webview/mod.rs:1746-1892`). After the key
   check it resolves capabilities (ACL) for the command (1776-1831), then routes:
   `plugin:`-prefixed commands split on `|` to `manager.extend_api(plugin,
   invoke)`, everything else to `manager.run_invoke_handler(invoke)`; an
   unhandled command rejects with <tt>Command {name} not found</tt> (1793-1892).
   Tokra's `dispatch_ipc` already mirrors the routing and rejection; it has no
   ACL layer (see the gap note in D3).
9. **Tokra's native layer already carries the machinery**
   (`ext/tokra/src/webview.rs:97-225`). `new_with_protocol` registers one
   asynchronous custom protocol (`tokra`) whose handler stores the wry responder
   by `request_id` and forwards a `UserEvent::HttpRequest` {request_id, method,
   uri, headers, body}; Ruby replies with `Proxy#respond(request_id, status,
   headers, body)`. An `ipc://` request is the same shape with a different
   scheme, and wry registers each scheme independently
   (`tauri-runtime-wry/src/lib.rs:4974-4983`; `ipc` is its own scheme at
   `manager/webview.rs:274-279`).
10. **The responder is already an opaque callable** (ADR 009 §4; Plan 014 D8).
    `Ipc::Invoke` holds a `lambda { |success, value| … }`. The `postMessage`
    path builds one that evals `runCallback` (`app.rb:319-329`). This phase adds
    one that answers the HTTP request — parsing and the responder differ, the
    dispatch does not.
11. **How Tauri puts its API in a bundler-less webview.** The core
    `@tauri-apps/api` IIFE (`__TAURI_IIFE__`, input `packages/api/src/index.ts`,
    output `crates/tauri/scripts/bundle.global.js`;
    `packages/api/rollup.config.ts:62-67`) is registered as a *global-API script*
    by `crates/tauri/build.rs:347-355`. When `app.withGlobalTauri` is true
    (`tauri-utils/src/config.rs:2762`), codegen collects those scripts
    (`tauri-codegen/src/context.rs:430-436`) and the webview manager injects them
    as main-frame initialization scripts, after the core init scripts
    (`manager/webview.rs:210-215`). The result exposes the whole
    `@tauri-apps/api` as <tt>window.__TAURI__</tt>, so a page calls
    <tt>window.__TAURI__.core.invoke(…)</tt> with no build step of its own.

## Design Decisions

1. **Serve `ipc://` as a second async custom protocol, reusing the HTTP-request
   event.** `new_with_protocol` gains a second
   `with_asynchronous_custom_protocol("ipc", …)` whose handler is identical to
   the `tokra` one — store the responder by `request_id`, forward
   `UserEvent::HttpRequest`. No new event variant: an `ipc://` request arrives as
   a `Native::HttpRequestEvent` whose `uri` begins `ipc://` (macOS/Linux) or
   `http://ipc.localhost/` (Windows), and Ruby routes on the scheme. wry
   registers each scheme independently (Context 9), so this is additive. The
   binding stays thin (ADR 001/005): one added registration, no new response API.

2. **Reuse `Proxy#respond`; Ruby supplies the Tauri headers.** The reply is an
   ordinary custom-protocol HTTP response, so the existing
   `proxy.respond(request_id, status, header_pairs, body)` suffices. Ruby stamps
   the CORS pair on every reply and adds <tt>Tauri-Response</tt> +
   <tt>Content-Type</tt> on invoke replies, mirroring `protocol.rs`'s `respond`
   closure (48-57) and response builder (107-139).

3. **One dispatch, two transports — the routing shape of `on_message`.** Tauri
   routes both transports through `webview.on_message`. Extract the command
   routing (the plugin-vs-invoke_handler branch and its
   <tt>Command {name} not found</tt> rejection, Context 8) out of `dispatch_ipc`
   into a private method both front ends call. Each transport supplies only what
   differs: how it reads the raw key (JSON member vs. `Tauri-Invoke-Key` header),
   how it parses the payload (Context 6), its responder (D4), and its drop action
   (D5). `dispatch_ipc` stays the postMessage front end; a new
   `dispatch_ipc_protocol(event, proxy)` is the `ipc://` front end.
   **Gap, stated:** `on_message` also resolves ACL/capabilities (Context 8);
   Tokra has no capability system (TODO 001 #9), so this dispatch omits it,
   exactly as the current `dispatch_ipc` does. This phase does not close that
   gap and does not widen it — both transports are equally unguarded until the
   capabilities phase lands.

4. **The `ipc://` responder answers the request; it does not eval.** Per Context
   3 the client evals `runCallback` after reading the response, so the `ipc://`
   responder replies over HTTP: on success,
   <tt>proxy.respond(request_id, 200, [Tauri-Response: ok, Content-Type:
   application/json, Access-Control-Allow-Origin: *, Access-Control-Expose-Headers:
   Tauri-Response], JSON.generate(value))</tt>; on failure, the same with
   <tt>Tauri-Response: error</tt>. `FormatCallback` stays on the postMessage
   path. JSON values and errors both serialize as `application/json`
   (`protocol.rs:112-125`, 343-345); raw (octet-stream) bodies are out of scope
   with the rest of the raw/channel path.

5. **Two failure modes, ported distinctly.** A **malformed** request — missing
   or non-numeric `Tauri-Callback`/`Tauri-Error`, missing `Tauri-Invoke-Key` or
   `Origin`, unparseable JSON, or an unimplemented content type — replies **500
   `text/plain`** with the message (Context 6; `protocol.rs:143-151`), which the
   client surfaces as a rejection. A **key mismatch** on an otherwise well-formed
   request **logs Tauri's exact message and drops with no reply** (Context 7;
   `webview/mod.rs:1730-1744`). For the postMessage transport the drop is a bare
   return (nothing was stored), matching `on_message`. For `ipc://`, Tauri drops
   the owned responder by returning; Tokra's responder lives in a map keyed by
   `request_id` (a bridge adaptation, Context 9), so the faithful equivalent is
   to remove and drop it — add a minimal `Proxy#drop_response(request_id)`.
   Dropping reproduces Tauri's chain (fetch rejects → postMessage fallback →
   drop-and-log); Tokra uses the same wry, so the client's reaction to a dropped
   responder is Tauri's behavior, not a Tokra choice.

6. **Prove the transport with the real API through a faithful `withGlobalTauri`.**
   The way to run `@tauri-apps/api` in a webview without a frontend bundler is
   Tauri's own `withGlobalTauri`, which injects the API's `bundle.global.js` as a
   global-API initialization script (Context 11). Port it: a `Builder` config
   that, when set, appends the vendored `bundle.global.js` after the core init
   scripts, mirroring the injection at `manager/webview.rs:210-215`. Tauri gates
   this at build time from `config.app.with_global_tauri`
   (`context.rs:430-436`); Tokra has no build-time codegen for it, so the gate
   moves to `Builder` and `App`'s runtime script assembly — a tier-1 language
   adaptation (no Rust codegen in Ruby), noted as such. Extend `rake sync:tauri`
   to vendor `bundle.global.js` from `vendor/tauri/crates/tauri/scripts/` into
   `lib/tokra/js/` with an SPDX snippet header, aborting if it is absent — the
   same extract-and-abort discipline the task already uses. Producing that
   artifact is the API package's own rollup build; the sync task consumes it, so
   Tokra stays pinned to the submodule and never hand-bundles Tauri's JavaScript.

7. **Deterministic coverage drives the exact request the real client sends.**
   New `test/builder/test_ipc_protocol.rb` injects a `Native::HttpRequestEvent`
   modeling `ipc-protocol.js` precisely — `uri: "ipc://localhost/ping"`, `method:
   "POST"`, headers `Tauri-Callback`/`Tauri-Error`/`Tauri-Invoke-Key` (from
   `app.invoke_key`) + `Content-Type` + `Origin`, JSON body — and asserts the App
   replies through `StubNative` with `Tauri-Response: ok`, `application/json`, the
   JSON-encoded value, and the CORS headers; plus a `plugin:` round trip
   resolving a rid; an unhandled command rejecting with `Tauri-Response: error`;
   a **malformed** request (missing `Tauri-Callback`) → 500 `text/plain`; a
   **key-mismatch** request → dropped (no reply, `drop_response` called);
   `OPTIONS` → preflight; a non-POST → 405. Header names and URL shape come from
   the vendored client and `protocol.rs`, so the test mirrors Tauri rather than
   Tokra's assumptions.

8. **The real API round trip is a manual smoke test in `verify_ping_pong`.** The
   example enables `with_global_tauri` and calls
   <tt>window.__TAURI__.core.invoke('ping', { message })</tt> — how a
   bundler-less Tauri app invokes — rendering the resolved value. Success plus
   the **absence** of the "IPC custom protocol failed" console warning proves the
   real `@tauri-apps/api` rode `ipc://` (Context 4). This mirrors Tauri's own
   `examples/api`, which consumes the real package; automated browser execution
   is not part of the `verify_*` apps, and the deterministic mirror is D7.

   handler body so `tokra` and `ipc` do not duplicate (D1).

   `drop_response(request_id)` (D5).

   extract the shared command router from `dispatch_ipc`; append
   `bundle.global.js` to `initialization_scripts` when `with_global_tauri` is set

   SPDX snippet header; abort if absent (D6).

   the ACL gap, and `withGlobalTauri` as the API-delivery mechanism. Supersede

## Out of Scope

- **ACL / capabilities** (`webview/mod.rs:1776-1831`; TODO 001 #9). Neither
  transport is ACL-guarded today; this phase keeps that status and does not add
  the capability system.
- **Raw / ArrayBuffer request bodies and Channels**
  (`plugin:__TAURI_CHANNEL__|fetch`). Bodies stay JSON-only, as in Plan 014;
  `String::from_utf8_lossy` on the native side is lossy for binary and is
  acceptable until channels land.
- **Isolation pattern and CSP.** The encrypted `ipc/protocol.rs` isolation arm
  (247-286) is not ported; Tokra runs the brownfield pattern only.
- **Events / `@tauri-apps/api/event` `listen`.** Inbound event delivery is a
  separate phase; this phase proves `invoke`.
- **Worker-Ractor migration** (ADR 001; ADR 009 §4). Dispatch and the responder
  still run synchronously on the Main Ractor.

## Risks

- **Building `bundle.global.js`.** The vendored submodule ships the API as
  TypeScript with no prebuilt `dist/`; producing the artifact runs the API
  package's own rollup build once. `sync:tauri` consumes the result and aborts if
  it is missing, so a stale or absent bundle fails loudly rather than silently
  shipping hand-written JavaScript.
- **Custom-protocol POST bodies and headers across platforms.** wry already
  surfaces request headers (used for cookies since Plan 003); the same path
  carries the `Tauri-*` and `Origin` headers. Confirm the body arrives intact for
  `ipc://` POSTs, not only `tokra://` ones.
- **Two active transports.** Serving `ipc://` must not regress the postMessage
  path (hand-rolled messages, tests). The shared router keeps one routing; both
  responders and both failure modes are exercised by tests.
