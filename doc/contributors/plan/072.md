# Plan 072: Precompiled gems of tokra for Ruby 4.1

## Context

Installing tokra compiles its Rust extension: the source gem needs Rust,
libclang, and on Linux WebKitGTK's and GTK's development packages. Fledge
keeps an example Rails and Tokra app in its own repository, and its CI
builds that app on each platform. It takes Tokra's gems from one GitHub
Release, puts them in the app's `vendor/cache`, and pins them by SHA-256.
With only the source gem, every one of its runs compiles wry and tao.

Fledge embeds Ruby 4.1.0-preview1 on macOS (arm64) and on Linux (glibc
and musl, x86_64 and aarch64), and on Windows a RubyInstaller build of
Ruby's master of 2026-11-10 (4.1.0dev, its library folders named
`4.1.0+6`, where the preview's are `4.1.0+5`; Fledge's
`runtime/sources.yml`).

## Problem

Tokra had no way to build a gem with its extension already compiled, and
nothing that showed such a gem installs and loads.

## Decided

### Each platform builds its own gem, natively

`rake package:native` (`tasks/precompiled.rake`) compiles the extension
and builds `pkg/tokra-VERSION-PLATFORM.gem` with `PlatformGem`
(`tasks/platform_gem.rb`), on the platform and Ruby it runs on.

Three ways to build were weighed:

- **Natively, on each platform's own machine or runner.** rove_2d
  (`tasks/native_gem.rb`, its CI's `package:native` jobs) and
  ratatui_ruby (`.github/workflows/build-gems.yml`,
  `tasks/release/platform_gem.rb`) both do this. It builds with the
  toolchain the gate already proves on every system.
- **rb-sys's cross-compilation images** (rb-sys-dock and
  oxidize-rb/actions' cross-gem). They suit a crate that links nothing
  of the system's. Tokra's extension links WebKitGTK, GTK, libsoup, and
  libxdo on Linux, which the images do not carry, and a cross build
  would need each target's copies of them and their development files.
  On Windows it links WebView2 through a loader its build copies, for
  RubyInstaller's MinGW Ruby. Nothing would be gained over a runner of
  the platform.
- **Fledge's own build images** (manylinux). They hold no WebKitGTK.

The first is taken. The gem carries every file the source gem does, the
crate and its `Cargo.lock` among them, so the source of the extension
ships with it, plus the extension and the DLLs installed beside it
(WebView2Loader.dll on Windows). It has no extension to compile and no
`rb_sys` dependency, which only `extconf.rb` loads; its `ferro-url`
dependency stays.

### Platform names

- `arm64-darwin`, with no darwin version: RubyGems installs an
  `arm64-darwin-24` gem only on a Ruby that reports exactly darwin 24,
  the build machine's macOS (ratatui_ruby's `PlatformGem#platform` says
  the same).
- `x86_64-linux-gnu` and `aarch64-linux-gnu`: RubyGems matches a plain
  `x86_64-linux` gem on musl too (rove_2d's `NativeFormat::ELF`), where
  an extension built against glibc does not load.
- Windows keeps Ruby's own platform, `x64-mingw-ucrt` or
  `aarch64-mingw-ucrt`.

### The Ruby requirement follows the ABI

A Ruby release keeps its ABI across teeny versions, so a gem built on
4.1.x requires `>= 4.1, < 4.2.dev`, the source gem's floor kept, as
rake-compiler bounds its native gems. A preview or a build of master
defines `RUBY_ABI_VERSION` (`include/ruby/internal/abi.h`), and on every
system but Windows Ruby refuses an extension whose `ruby_abi_version`
differs (`dln.c`, `dln_load_and_init`); rb-sys exports that symbol
(`crates/rb-sys/src/ruby_abi_version.rs`). RubyGems and Bundler see a
preview's version as `4.1.0.preview1` and master's as `4.1.0.dev`
(`Gem.ruby_version`; Bundler's `RubyVersion.system`). So a gem built on
a preview or on master requires exactly that version. Bundler skips it
on any other Ruby and compiles the source gem.

rake-compiler's own bound, `>= 4.1, < 4.2.dev`, would never pick a
preview: `4.1.0.preview1` sorts below `4.1`. rove_2d's bound, the source
gem's floor and `< 4.2.dev`, would pick the preview1 gem on master too,
where Ruby then refuses it.

`4.1.0.dev` does not tell one master build from another. A gem built on
Fledge's 2026-11-10 snapshot (ABI 6) would be offered to any later
master build; on Linux and macOS Ruby refuses it if the ABI moved, and
on Windows, which has no ABI check, it would load. That is acceptable
only because the one Ruby that build serves is Fledge's pinned snapshot.

### Where they are built

The Platform gems workflow (`.github/workflows/platform-gems.yml`) runs
on a manual dispatch and on a `tokra/v*` tag, builds on `macos-15`,
`ubuntu-22.04`, and `ubuntu-22.04-arm`, with the Ruby `mise.toml` pins
on Linux and macOS, runs `rake package:deliver` on each, and keeps each
gem and its SHA-256 as an artifact. It creates no release, pushes no
tag, and pushes nothing to RubyGems.org. Ubuntu 22.04 is the oldest
runner with WebKitGTK 4.1, and a Linux gem needs at least the glibc of
the system it was built on.

### The check

`rake package:deliver[GEM,...]` (`PackageCheck#precompiled`) refuses a
gem that is for every platform, has an extension to compile, or lacks
its compiled extension; installs its git-sourced dependencies from their
checkouts as `package:install` does (ferro-url, which compiles); installs
the gem into an empty `GEM_HOME` with no directory holding `cargo` or
`rustc` on `PATH`, failing if RubyGems built anything; and runs the
packaging check's smoke script against the installed gem, which requires
`tokra`, builds an app, and calls into the extension and ferro-url.
Neither task is in the gate, which stays as fast as it was.

## Platforms

Built and checked: see "Proof".

Left out:

- **musl Linux.** No pool machine and no GitHub runner runs musl, and
  WebKitGTK on Alpine is a separate build. An Alpine app compiles the
  source gem.
- **Windows.** No Ruby 4.1 builds the extension soundly there yet (Plan
  069). The tasks need nothing more: on a Windows Ruby 4.1 that builds,
  `rake package:native` names the gem `x64-mingw-ucrt` and carries
  WebView2Loader.dll, and the workflow gains one matrix entry. Its Ruby
  must be the RubyInstaller build Fledge embeds.

## ferro-url

tokra's precompiled gem depends on `ferro-url = 0.1.0`, a source gem
with a Rust extension (Ferro's `gems/url/ferro-url.gemspec`, line 36,
`spec.extensions`, and line 38, `rb_sys`), so an app's install still
compiles it. Ferro has no task that builds a precompiled gem. It would
need its own `PlatformGem`, for each gem with an extension, the same
platform names and Ruby requirement, a release step that keeps those
gems, and a published `ferro-url` 0.1.0 built that way; `extconf.rb`'s
`--enable-test-hooks` stays off in it, as for any install.

## Proof

On 2026-11-22, each from an empty workspace, `bin/setup --gate`, then
`rake package:native`, `rake test:core` for `TestPlatformGem` and
`TestPackageCheck` (35 runs, no failures), and `rake package:deliver`:

- **arm64-darwin**, macOS 27 on Apple silicon, mise's Ruby
  4.1.0-preview1: the gem requires `>= 4.0.1, = 4.1.0.preview1`; the
  extension links only system libraries and frameworks, not libruby, with
  a minimum macOS of 11.0; it installed with no Rust on `PATH` and loaded.
- **x86_64-linux-gnu**, Ubuntu 24.04, mise's Ruby 4.1.0-preview1 (static
  libruby): same requirement; `DT_NEEDED` is the eleven libraries
  packaging.md's "Linux libraries" lists, `libgcc_s`, and libc, no
  libruby, and the newest glibc symbol it needs is `GLIBC_2.34`; it
  installed with no Rust on `PATH` and loaded. The check ran under
  `bin/linux-env`, so the WebKitGTK packages, development files
  included, were laid over `/usr`; nothing compiled.
- **x64-mingw-ucrt**, as a check that Windows slots in: on the Windows
  pin, Ruby 4.0.9, the gem (for `>= 4.0, < 4.1.dev`) carried
  WebView2Loader.dll, installed with no Rust on `PATH`, and loaded. It is
  not a gem for Fledge, whose Windows Ruby is 4.1.

aarch64-linux-gnu has no machine but GitHub's arm runner, so the
workflow's first dispatch is its proof.
