# Plan 025: tokra-global-shortcut on ferro-global-hotkey

Tauri's official global-shortcut plugin registers keyboard shortcuts that
fire while another app has focus. This plan ports it as
`tokra-global-shortcut`, a pure Ruby gem in `plugins/global-shortcut` over
`ferro-global-hotkey`, the one-to-one Ruby binding of global-hotkey that
ADR 011 calls for. The frontend keeps using
`@tauri-apps/plugin-global-shortcut` unchanged.

Sources: `tauri-plugin-global-shortcut` 2.3.1 at plugins-workspace
`d4613ff0`, the commit plans 021, 023, and 024 ported from:
`src/lib.rs`, `src/error.rs`, `guest-js/index.ts`, `api-iife.js`,
`build.rs`, `Cargo.toml`, `permissions/default.toml`. The plugin has no
`commands.rs` and no init script at that commit: its four commands live
in `lib.rs`. The workspace's `Cargo.lock` pins global-hotkey 0.7.0, read
from its crates.io package. Tauri core at `vendor/tauri` (`9f0306fbc`):
`crates/tauri/src/ipc/channel.rs` (Channel), `ipc/format_callback.rs:100-106`
(`format_raw_js`), `ipc/command.rs` (argument errors), `error.rs:64-66`
(`PluginInitialization`), `plugin.rs:995-1010`, `app.rs:485-500`, and
`packages/api/src/core.ts` (the page's `Channel`). The binding:
`ferro-global-hotkey` 0.1.0.pre.1 at its tag `ferro-global-hotkey/v0.1.0.pre.1`
(release commit `ff65d77`; work began on `ef2407b`, and the commits between
changed only tests and docs), which binds
global-hotkey 0.9.0, its README, and Ferro's plan 004.

## Context

On desktop, Tauri's plugin is one file. Its setup closure creates a
`GlobalHotKeyManager`, registers the builder's shortcuts, installs
global-hotkey's process-wide event handler, and manages a
`GlobalShortcut` (`lib.rs:388-435`). The handler looks each event's id up
in the plugin's map and calls the shortcut's own handler, then the
builder's (`lib.rs:416-425`). Every manager call goes to the main thread
through `run_on_main_thread` and waits for the answer (`run_main_thread!`,
`lib.rs:75-86`), since the manager is "run on main thread only"
(`lib.rs:63-66`). The page's `register` passes a `Channel`, and the
command's handler sends `{ shortcut, id, state }` through it
(`lib.rs:268-304`).

Tokra had no `Channel`. Plans 014 and 015 left Channels out of scope, and
ADR 009 and 010 note that Tauri's Channel-carried invoke results are
evaluated instead. The page's `Channel` class (`core.ts`) serializes as
`__CHANNEL__:<id>` and expects `runCallback(id, { message, index })`
calls, and a final `{ end: true, index }` when Rust drops the channel.

global-hotkey reports events on the thread that saw the key: inside the
main thread's run loop on macOS, on the hidden window's thread on Windows,
on its own X11 thread on Linux (Ferro plan 004, decision 5). Tokra's main
thread runs tao's loop holding the GVL, with the hand-off hook ADR 012
describes.

## Decisions

1. **The gem mirrors the crate.** `Tokra::Plugins::GlobalShortcut` holds
   `Plugin`, `Builder`, `GlobalShortcut`, `GlobalShortcutExt`, `Error`
   with `GlobalHotkey`, `RecvError`, and `Tauri`, and the re-exports
   `Shortcut`, `Code`, `Modifiers`, `ShortcutEvent`, and `ShortcutState`,
   which name ferro-global-hotkey's own classes, as Tauri's `pub use`
   names global-hotkey's types. Handlers are blocks that take the app
   handle, the Shortcut, and the ShortcutEvent, as Tauri's `Fn(&AppHandle,
   &Shortcut, ShortcutEvent)` does. Rust's `ShortcutWrapper` is the
   private conversion: a Shortcut passes through, a String is parsed, and
   anything else raises `TypeError`, where Rust would not compile.

2. **Setup is construction.** Tokra has no plugin setup phase apart from
   the constructor (parity checklist: `Plugin::initialize` is the Ruby
   constructor). `Plugin.new(app, builder = Builder.new)` runs Tauri's
   setup closure, and `Builder#build(app)` is `Plugin.new(app, self)`, so
   `build` takes the app handle that Tauri's setup receives. Tier 1.

3. **Events arrive through ferro's `set_event_handler`, as Tauri's do.**
   Tauri calls `GlobalHotKeyEvent::set_event_handler` in setup and
   never reads the receiver (`lib.rs:416-425`). The plugin does the same
   with `Ferro::GlobalHotkey::GlobalHotKeyEvent.set_event_handler`. ferro
   cannot run Ruby on the thread that saw the key, so its native handler
   queues the event and a Ruby thread of its own calls the block (Ferro
   plan 004, decision 5). The main thread never runs a handler: while tao's
   loop holds the GVL, ferro's thread waits for it, ADR 012's hook hands it
   over at the end of the loop's iteration, and the handler runs beside
   the loop, so a slow handler never stalls the window. A handler that
   sends through a Channel evaluates in the webview, which from that
   thread travels to the main thread (`Webview#eval`). Draining the
   receiver from Tokra's loop was rejected: Tauri does not read it, Tokra
   has no per-iteration plugin hook, and the handlers would run on the
   main thread, where a slow one freezes the window. global-hotkey keeps
   the handler in a cell set once per process (global-hotkey 0.7.0 and
   0.9.0 `lib.rs:89`, `118-124`), so only the first plugin in a process
   receives events, as in Tauri; a later plugin's handler is ignored. An
   exception a handler raises is reported with `warn` and the next
   handler still runs, where ferro would end its thread and drop every
   later event. Tier 1: a Rust panic there aborts the process, which no
   Ruby port should copy.

4. **The manager lives on the main thread.** Every manager call runs in
   `RuntimeContext#getter`, which runs it at once on the main thread and
   otherwise queues it for the loop and waits, as `run_main_thread!` does.
   A getter whose loop has ended raises Tokra's `FAILED_TO_SEND_MESSAGE`
   or `FAILED_TO_RECEIVE_MESSAGE`, which the plugin raises as
   `Error::Tauri` and `Error::RecvError` ("receiving on a closed
   channel"), as Tauri's `?` converts them. Setup creates the manager
   through the getter too, so a plugin registered off the main thread
   still makes it there: Tauri's `unsafe impl Send` promises that, and
   on macOS a manager made elsewhere silently never fires (Ferro plan
   004, decision 12). On macOS only one manager lives at a time, so a
   second plugin in the process fails setup with ferro's `OsError` text;
   the README says to register the plugin once.

5. **`Tokra::Ipc::Channel` joins core.** `Channel`, `JavaScriptChannelId`,
   `IPC_PAYLOAD_PREFIX`, and `CHANNEL_PLUGIN_NAME` mirror
   `ipc/channel.rs`. `JavaScriptChannelId.from_str` takes
   `__CHANNEL__:` and a `u32` (an optional `+` and ASCII digits), with
   Tauri's two messages. `channel_on(webview)` returns a Channel whose
   `send` evaluates `runCallback(id, { message: JSON, index: N })` with
   a counter from 0, as `channel_on` does. `Channel.from_command(invoke,
   key)` is the `CommandArg` impl, with Tauri's messages. Deviations:
   payloads of 8 KiB or more also go through eval, not the fetch path,
   which needs the raw ipc:// bodies and request headers that plan 015
   left out (the page receives the same message); raw byte payloads are
   not ported, since Tokra's IPC bodies are JSON only (ADR 010); and
   Tokra has no channel interceptor (`channel.rs:147-151`), which Tauri
   offers apps through its builder. Rust
   sends `{ end: true, index }` when the last clone drops; Ruby frees
   objects when the collector runs, so the owner calls `Channel#drop`,
   once, where Rust would drop the last clone. A send after the drop does
   nothing, as Rust cannot send through a dropped channel
   (`channel.rs:80-86`); one lock covers both, so the end message always
   follows the last message, even when decision 6's race sends late. The plugin does so when no
   registered shortcut holds the handler any longer: after `unregister`,
   `unregister_all`, a replacement, or a `register` that stored nothing.
   Tier 1. Invoke results still do not travel over a Channel (ADR 009,
   ADR 010).

6. **Handlers run outside the lock.** Tauri calls each handler while
   holding the map's lock, so a handler that registers or unregisters
   deadlocks. The plugin reads the entry under its lock and calls the
   handlers after releasing it; Ruby's `Mutex` would raise `ThreadError`
   on re-entry instead of deadlocking. Likewise `register_multiple` locks
   for each insert rather than across the main-thread calls, so a
   background thread waiting on the main thread never holds the lock the
   main thread wants. The cost is a race Tauri lacks: an event read just
   before its shortcut is unregistered still reaches its handler. Tier 1.

7. **Errors keep Tauri's Display.** `Error::GlobalHotkey` carries
   global-hotkey's message: ferro-global-hotkey's `Error` and
   `HotKeyParseError` messages are global-hotkey's own Display texts.
   A command rejects with that text, as `Error` serializes to its Display
   (`error.rs:18-25`). `is_registered` the method answers false for a
   string that does not parse; the command rejects with the parse error,
   as Tauri's do.

8. **A core `CommandItem` reads typed arguments.** The Channel argument
   needs serde's messages in core, and this plugin needs `String` and
   `Vec<String>`. `Tokra::Ipc::CommandItem` (Tauri's `CommandItem`)
   reads one key of an invoke's payload and raises `ArgumentError` with
   Tauri's `invalid args `key` for command `name`: ...` and the missing
   key message. Its description of a JSON value moves from the
   notification plugin, whose oracle checked it (plan 024, Results), into
   `Tokra::Ipc::Unexpected`, and the notification plugin calls it. Moving
   dialog onto it would change dialog's messages for floats and
   non-printing characters, so that waits for the follow-up plan 024
   named.

9. **The dependency is the release tag.** Both Gemfiles name
   `ferro-global-hotkey` as a git source at tag
   `ferro-global-hotkey/v0.1.0.pre.1` (release commit `ff65d77`) with the
   glob `gems/global-hotkey/*.gemspec`, so Bundler keeps taking the other
   Ferro gems from their own tags. Work began on commit `ef2407b`; the tag
   adds only tests and docs. The gemspec pins `= 0.1.0.pre.1`.

10. **global-hotkey 0.9.0, not 0.7.0.** ferro-global-hotkey binds 0.9.0;
    Tauri locks 0.7.0. The differences reach the page: 0.9.0 writes
    `meta+` where 0.7.0 wrote `super+` in a shortcut's string, keeps the
    `META` bit where 0.7.0 stored `SUPER` (so ids of shortcuts with
    Command or Windows differ), parses more key names, and registers
    F13 to F35 and more keys on Linux, which 0.7.0 refused. A port can
    only use the binding that exists.

## Verification

- Core: Channel ids, messages, indexes, drop, and argument errors against
  a real Webview whose native webview records evaluations.
- Plugin, in process: registration, errors, and commands on one shared
  app and plugin per test process (macOS allows one manager), with only
  Control, Alt (Option), Shift, and Meta (Command) with F17 to F19, and
  everything unregistered after each test. Event dispatch feeds the
  plugin's handler real `ShortcutEvent` values, so the store, the
  handlers, and the Channel are real.
- Children, each its own process: the Builder's shortcuts and handler,
  setup failures, and on macOS the one-manager limit.
- Linux: everything that talks to X runs against a private Xvfb, as
  Ferro's tests do. A child registers a shortcut, xdotool presses it, and
  the handler receives the press and the release from global-hotkey.
- A real window calls the plugin through Tauri's `api-iife.js`. On Linux
  it runs on the private Xvfb: the page registers, the test presses the
  keys with xdotool, and the page's Channel handler receives both events.
  On macOS the page registers and unregisters without a key press.
- Manual mutation checks, listed in Results.
- `bundle exec rake` from a clean build.

## Untested without a person

- A macOS event: it needs a key press from a person, or synthesized
  input, which needs the Accessibility permission.
- Windows: no Windows machine has run any of it; CI's in-process tests
  register and unregister only.

## Results

Every decision above is done; decision 5 defers the fetch path, raw
payloads, and the channel interceptor, and decision 8 defers moving dialog
onto `CommandItem`, with their reasons.

- macOS, in process: registration, both systems' refusals (Carbon's
  `RegisterEventHotKey failed for F19` for a second registration, `Unknown
  scancode for F24`), parse errors, the commands and their argument errors,
  handler order, a raising handler, a handler that unregisters itself, a
  call from another thread waiting for the main thread, and the loop's
  end as `Error::RecvError` and `Error::Tauri`. In children: the Builder's
  shortcuts and handler, a refused shortcut failing setup with
  `PluginInitialization`, and the second manager's `OsError`.
- Linux, in the `ruby:4.0` container plan 024 used, under xvfb-run with
  the tests' own Xvfb: all runs pass (1 skip: the macOS test) four times,
  40 runs in the last.
  xdotool presses reach the shortcut's handler, then the Builder's, on a
  thread other than the main one; the register command's Channel delivers
  `Pressed` and `Released` at indexes 0 and 1 and ends at 2; a second
  plugin in the process hears nothing; and the real window receives both
  events through `api-iife.js`'s Channel.
- The first Linux run found what the design missed: a child that grabs a
  combination the test process had just unregistered fails with
  `AlreadyRegistered`, since the X server keeps the grab until that manager
  next waits for a reply (Ferro's plan 004, Results). Children now use
  their own combinations.
- Manual mutation checks, each reverted after: counting channel indexes
  from 1 fails `test_a_channel_on_a_webview_sends_each_message_with_its_index`;
  calling the Builder's handler first fails
  `test_an_event_calls_the_shortcuts_handler_then_the_global_one`; dropping
  a channel a shortcut still holds fails
  `test_the_channel_ends_when_its_last_shortcut_is_unregistered`; raising
  `Error::Tauri` for a closed channel fails
  `test_after_the_loop_ends_calls_from_another_thread_raise_tauris_errors`;
  answering `is_registered` for an unparsed string fails
  `test_is_registered_rejects_a_shortcut_that_does_not_parse`; swapping the
  state names fails `test_each_event_reaches_the_page_through_its_channel`;
  keeping the channel after a parse error fails
  `test_a_shortcut_that_does_not_parse_rejects_and_ends_the_channel`;
  raising global-hotkey's error from setup fails
  `test_a_shortcut_the_system_refuses_fails_setup`; calling handlers under
  the lock fails `test_a_handler_may_unregister_its_own_shortcut`; dropping
  either `rescue Tokra::Error` fails
  `test_an_event_after_the_loop_ends_is_dropped_quietly` or
  `test_dropping_a_channel_after_the_loop_ends_raises_nothing`; sending
  after a drop fails `test_dropping_a_channel_ends_it_once`; releasing
  outside `ensure` in `unregister_all` fails
  `test_unregister_all_drops_the_handlers_when_the_loop_has_ended`; and on
  Linux, never calling `set_event_handler` fails both delivery tests and
  the window's press check.
- `bundle exec rake` from a clean build on Ruby 4.0.9 (macOS): 555 core
  runs (4 skips), 60 clipboard, 57 dialog (11 skips), 40 global-shortcut
  (5 skips: the Linux tests), 83 log, and 36 notification runs (7 skips)
  pass; RuboCop, Steep, RBS validation and parity, RDoc (100%), REUSE,
  Clippy, fmt, and the packaging check pass. `rake package:install` builds
  ferro-global-hotkey from its tag, and the smoke parses a
  shortcut through the installed gems.
- One gate run on macOS hung every dialog window test with no output from
  the fixture; the same tests passed alone and in the next full runs. A
  review traced a likely cause to the dialog fixture: it found the sheet
  through `NSApp.mainWindow`, which AppKit reports as nil while the app is
  not active, so under load the helper could wait forever; and its stdout
  was buffered, so the lines it printed died with the kill. The fixture now
  searches `NSApp.windows` for an attached sheet and syncs its stdout (only
  there: exit_paths relies on Ruby's exit flushing buffered output). The
  hang was not reproduced, so the cause is unconfirmed; the window tests
  pass with the change.
- Untested: `release_at_setup`, which unregisters what a failed setup had
  registered, is observable only on Windows; on macOS one manager per
  process hides it, and on Linux the X server keeps the grabs until the
  manager is freed.
- UNVERIFIED until CI runs: all of Windows.
