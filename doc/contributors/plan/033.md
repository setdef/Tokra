# Plan 033: raw invoke bodies and responses

A Tauri command can take bytes and give bytes back without JSON. The page
calls `invoke(cmd, uint8Array, { headers })`; the client sends the bytes as
an `application/octet-stream` `ipc://` body, with any `options.headers`
beside Tauri's own. The command reads them through `tauri::ipc::Request`
(`body()` and `headers()`) and answers with `tauri::ipc::Response::new(bytes)`,
which `ipc://` returns as `application/octet-stream` and the page receives
as an `ArrayBuffer`. The fs plugin's `write_file` and `read_file` work this
way, and it is the way out Plan 032 named for large binary arguments, which
otherwise pay for the pure-Ruby JSON parser.

Plans 015 and 032 deferred it, and ADR 010 records bodies as JSON only.
Tokra answers a non-empty `application/octet-stream` body with a 500
`raw request bodies are not implemented`.

Sources: Tauri at `vendor/tauri` `9f0306fb`; http 1.3.1 (Tauri's
`Cargo.lock:3271-3273`, the crate read from crates.io); plugins-workspace
at `d4613ff0` for the fs plugin, fetched into scratch.

## Decisions

1. **One translation of `Vec<u8>`: a binary String.** A String in
   `Encoding::BINARY` (ASCII-8BIT) stands for Rust's `Vec<u8>` everywhere
   the IPC meets bytes, and any other String is text. That is the only
   way Ruby, which has one String class, can tell `From<Vec<u8>>` from
   `From<String>` (AGENTS.md precedence 1, Ruby the language). So
   `InvokeBody` is a JSON value or a binary String, with no wrapper class:
   `Ipc::Json` makes every string UTF-8, so the two never collide.
   `Ipc::InvokeBody.raw?` holds the rule in one place.
2. **`Invoke#payload` is Tauri's `InvokeMessage::payload`**: the body as
   it came, raw bytes or any JSON value, and `#body` is the same value
   under `Request::body`'s name. `Invoke.new(payload:)` takes it, as
   `InvokeMessage::new` does, and `#headers` is `InvokeMessage::headers`.
   *Amended 2026-10-27, after review:* the first draft kept `#payload` a
   Hash, `{}` for any other body, following Plan 016 #15, which mapped a
   non-object to `{}` so that `payload["key"]` never runs `String#[]`.
   Tauri fidelity outranks that Ruby-culture guard (AGENTS.md precedence
   2 over 3), and CommandItem now gives Tauri's messages for raw and
   non-object bodies, so Plan 016 #15's decision is overturned. The usual
   object body is still a Hash, so `invoke.payload["message"]` reads as
   before.
3. **Headers are a frozen Hash of lowercase names to values.** The http
   crate stores names lowercased and `HeaderMap::get` folds case; Ruby's
   Hash does not fold, so names are stored and looked up lowercased, as
   Rack does. On `ipc://` every request header is there, the first value
   of a repeated name winning as `HeaderMap::get` returns the first. On
   `postMessage` they come from `options.headers` and are checked as the
   http crate checks them.
4. **`Ipc::Request` and `Ipc::Response`.** A text body is encoded to UTF-8
   when the Response is made, since a Rust String is UTF-8 by type
   (`ipc/mod.rs:100-104`); text UTF-8 cannot hold raises there.
   `Invoke#reject(response)` raises TypeError, as Rust's compiler refuses
   a Response where `T: Serialize` is wanted. `Request.from_command(invoke)`
   gives `body` and `headers`, the `CommandArg` impl for `Request`.
   `Response.new(string)` carries a binary String as a raw body and any
   other String as JSON text, sent verbatim, as `From<String>` does.
   `Invoke#resolve(response)` sends that body, as `IpcResponse for
   Response` does; any other value is serialized as before. Tauri's
   `From<InvokeBody>` is not ported, since a UTF-8 String body would be
   ambiguous with `From<String>`.
5. **The responder receives the body String.** `ipc_responder` keeps its
   `(success, String)` shape: a binary String is a raw body, any other is
   JSON text, by decision 1. The `ipc://` responder answers a raw body
   as `application/octet-stream`; the `postMessage` responder evaluates
   it as a JSON number array.
6. **`CommandItem` reads from the body.** Its `payload` may be any
   `InvokeBody`; a raw body fails with Tauri's bytes message and a
   non-object JSON value is a missing key. In-tree callers pass
   `invoke.body`.
7. **Large raw bodies never touch JSON.** A raw body goes straight to the
   command, so Plan 032's escape hatch (a) holds: a 1 MB `Uint8Array`
   travels as bytes both ways.

## Deviations

- Over `postMessage` a raw response is always a JSON number array, never
  Tauri's Channel `ArrayBuffer`, as JSON object and array results already
  always evaluate `runCallback` (ADR 009). The real client reaches
  `postMessage` on desktop only after `ipc://` failed, when it sets
  `customProtocolIpcBlocked` and Tauri evaluates the array too.
- `postMessage` header errors leave out serde's line and column, as the
  `cmd` check does (Plan 032 decision 4). Tauri iterates a HashMap, so
  which bad header it names first is random; Tokra names the first sent.
- `options` that is not an object, and a `customProtocolIpcBlocked` that
  is not a bool, are ignored where serde would fail the message (ADR 009).
- `Channel#send` of raw bytes is not ported (decision deferred below).

## Changes

- `lib/tokra/ipc/invoke_body.rb`: `InvokeBody.raw?`.
- `lib/tokra/ipc/request.rb`, `lib/tokra/ipc/response.rb`: the two types.
- `lib/tokra/ipc/invoke.rb`: `body`, `headers`, raw resolve.
- `lib/tokra/ipc/command_item.rb`: the bytes message; non-object bodies.
- `lib/tokra/app.rb`: raw `ipc://` bodies, request headers on both
  transports, `options.headers` checks, raw responses on both responders.
- In-tree `CommandItem` callers pass `invoke.body`.
- Signatures, RDoc, ADR 010 amendment, CHANGELOG.

## Verification

- Unit (`test/builder/test_ipc_protocol.rb`, `test_ipc_response.rb`,
  `test/ipc/*`): raw bodies empty and not, the default content type,
  request headers on both transports, `options.headers` errors, raw
  responses on both responders, the bytes message, `Request`, `Response`.
- Real window (`ipc_transport` fixture): the real client invokes with a
  1 MB `Uint8Array` and a header, the command answers with
  `Response.new(bytes)`, and the page gets an `ArrayBuffer` with the same
  bytes; the elapsed time is recorded.
- Mutations, each failing a test: the octet-stream branch, the raw
  Content-Type, the binary check, the bytes message, header lowercasing.

## Results

- The real client's 1 MB `Uint8Array` invoke, reversed by the command and
  returned with `Response.new`, round-trips in 4 to 6 ms on macOS
  (`performance.now()` in the page, three runs). The same bytes as a JSON
  number array take 1,352 ms in `Ipc::Json.parse` alone.
- Header values cross the native layer with their bytes
  (`String::from_utf8_lossy` in `ext/tokra/src/webview.rs`; wry builds
  them from Rust Strings, so nothing is replaced). The real-window
  fixture sends `X-Probe: café` over both transports, the second after
  making `ipc://` fail so the client falls back to `postMessage`, and the
  command sees the same value both times.
- Ten hand mutations each failed a test: the binary `body.b`, the raw
  Content-Type, the bytes message, header lowercasing, first-value-wins,
  the header value check, the `postMessage` number array, the encoding
  test in `InvokeBody.raw?`, a `Response` sent unserialized, and reading
  `options.headers` before the key check.

## Out of scope

- Raw `Channel` messages and Tauri's channel-data fetch command
  (`channel.rs:162-183`): Tokra's Channel evaluates every message (Plan
  025 decision 5), and a raw message would need the fetch queue too.
- The isolation pattern's encrypted raw payloads (`ipc/protocol.rs:247-286`).
- Android's JSON-only bodies (`InvokeBody::into_json`).
