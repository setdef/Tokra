# Plan 053: Hand the GVL over while a Windows menu tracks

Windows CI run 41617252499 (plan 051, "What run 41617252499 showed")
found every other Ruby thread frozen while a tray menu tracked. The
closer thread of the tray fixture first ran when the 8 s fallback had
closed the menu. tray-icon 0.21.0 opens that menu with `TrackPopupMenu`
inside its own window procedure (`platform_impl/windows/mod.rs:459-464`,
`509-523`). tao's `run_return` dispatches that procedure from its
`GetMessageW` loop (tao 0.34.5 `platform_impl/windows/event_loop.rs:256-269`),
and the main thread holds the GVL throughout (ADR 012).

This plan settles why nothing hands the GVL over during that menu, picks
a mechanism that hands it over whatever the cause, and adds counters
that let the next Windows run confirm the cause.

## What is confirmed and what is guessed

Tokra hands the GVL over in exactly two places: `Thread.pass` at
`MainEventsCleared` (`event_loop.rs`, `Turn::yield_gvl`), and around the
context menu, which runs inside `without_gvl` (`menu.rs:1520`). Windows
has no READY thread hook (Ruby v4.0.9 `thread_win32.c:33-38`), so there a
ticker posts `UserEvent::Yield` every 10 ms while other threads exist
(`gvl_handoff::poll_tick`).

**Confirmed from the source.** tray-icon's `TrackPopupMenu` does not run
inside tao's event handler. The handler is taken out of its cell only
while `call_event_handler` runs (`event_loop/runner.rs:240-254`), and
`should_buffer` is true only then (`runner.rs:143-148`). So inside the
tray's menu loop tao does not buffer: a `USER_EVENT_MSG_ID` that the menu
loop dispatches reaches `thread_event_target_callback`
(`event_loop.rs:2422-2427`), which calls the handler at once and then
`RedrawWindow(RDW_INTERNALPAINT)`. The `WM_PAINT` that follows calls
`flush_paint_messages`, whose `main_events_cleared` delivers
`MainEventsCleared` (`event_loop.rs:2357-2380`, `819-824`), and tao's
comment there says it is meant for modal loops. If the menu loop
dispatches both messages, the existing hand-off runs every 10 ms. The
context menu differs: muda's `TrackPopupMenu` runs inside the handler,
which is why it needed `without_gvl` (plan 042, decision 15).

**Confirmed from CI.** The menu loop dispatches `WM_TIMER`: the fixture's
50 ms timer printed `main-timer-saw` and its 8 s fallback fired while the
menu tracked. A Fiddle call on the main thread inside the menu loop lets
other threads run: the older tray runs passed on the timer's Fiddle
calls alone (plan 051).

**Guessed.** Which link of the chain from the ticker's posted message to
`Thread.pass` fails. The candidates:

1. The menu loop does not dispatch the internal `WM_PAINT` of tao's
   thread target, so `MainEventsCleared` never comes. Wine and ReactOS
   dispatch every message they do not handle (Wine
   `dlls/win32u/menu.c:4167-4185`, `4349-4354`; ReactOS
   `win32ss/user/ntuser/menu.c:4108-4160`, `4338-4344`), but neither is
   Windows. Both are read at their `master` branches as of 2026-11-03.
2. The posted `USER_EVENT_MSG_ID` is not dispatched in the menu loop.
3. `Thread.pass` does not yield. Ruby v4.0.9 yields on Windows by
   `ReleaseMutex`, `Sleep(0)`, and a wait for the mutex again
   (`thread_win32.c:128-153`), which grants the GVL to a waiting thread.
   Background threads do run on Windows while the loop idles, where only
   this `Thread.pass` lets them, so this is the least likely.
4. The handler is skipped or re-entered in some way the source does not
   show.

Decision 4 adds counters that tell these apart. Decision 1 does not
depend on which one it is, unless it is the third.

Windows CI run 41622185416 then confirmed the starvation itself: a thread
that only sleeps 10 ms and counts advanced 3 to 5 times in the 8 s the
tray menu tracked, against about 800 expected, and the thread that runs
the menu was the main thread (plan 051's `tray:sleeper` and
`tray:threads`). Which link fails is still open.

## Decisions

1. **A thread-level `WH_MSGFILTER` hook hands the GVL over inside a
   menu loop.** While `EventLoop#run` runs on Windows, a hook
   (`SetWindowsHookExW(WH_MSGFILTER, …, None, GetCurrentThreadId())`)
   watches the loop's thread. A menu's modal loop calls
   `CallMsgFilter(&msg, MSGF_MENU)` for each message it peeks, before it
   decides what to do with it (ReactOS `menu.c:4111-4116`, Wine
   `menu.c:4169-4173`; Microsoft documents `CallMsgFilter` as called
   "during internal processing of dialog boxes, message boxes, menus,
   and scroll bars"). The poll ticker now also marks a hand-off owed in a
   `Pending` of its own each tick, before it posts. So the posted message
   it sends every 10 ms reaches the hook whether or not the menu loop
   dispatches it or the paint after it. The hook, for `MSGF_MENU` only,
   calls `Thread.pass` when this thread holds the GVL
   (`ruby_thread_has_gvl_p`, public in Ruby v4.0.9
   `include/ruby/thread.h:336-341`, `thread.c:2103-2113`), it is not
   already inside its own hand-off, its state is set, and either a
   hand-off is owed or Ruby has an interrupt pending for the main thread
   (`rb_thread_interrupted`, the check `MainEventsCleared` makes). The
   second lets a signal's handler run while a menu tracks even with no
   other Ruby thread, since the interrupt ticker posts every 100 ms
   (`interrupt_check.rs`) and the hook hears that message too. It then passes
   the message on with `CallNextHookEx`, and never claims it, so the menu
   loop goes on as before (a nonzero answer would make the loop drop the
   message, ReactOS `menu.c:4113-4115`).

   It meets the rules of plans 042 and 043:

   - *Ruby runs only where Ruby may run.* The hook calls Ruby only with
     the GVL held, on the loop's thread. In the context menu, where
     `without_gvl` released it, `ruby_thread_has_gvl_p` answers false and
     the hook does nothing. Where it does hold the GVL, the main thread is
     either inside tao's handler (a menu a Ruby callback opened while
     holding the GVL), the same place `MainEventsCleared` passes, or in a
     window procedure that tao's pump dispatched, where tao would call
     the handler, and so Ruby, itself. `Thread.pass` runs under magnus's
     `rb_protect`, so a raise never `longjmp`s across user32's frames,
     and the hook's body runs inside `catch_unwind`, so no panic unwinds
     into them.
   - *It cannot re-enter tao.* The hook calls neither tao nor anything
     that posts to tao. The other Ruby threads it lets run reach tao only
     through `Proxy`, since `ThreadBound` refuses them (ADR 012,
     decision 1). Plan 042's decision 19 was about a message that starts
     an iteration from inside the handler. The hook sends no message.
   - *It keeps no Ruby value natively.* An exception from `Thread.pass`,
     which comes from an interrupt (a signal's handler, `Thread#raise`),
     goes into a `Cell` in `EventLoop#run`'s own frame, on the main
     thread's machine stack, which Ruby's GC scans as it scans the loop's
     `raised`. The hook's thread-local state holds only a pointer to that
     cell, which the hook's guard clears before the frame ends.
     `MainEventsCleared` takes the exception and treats it as a failed
     `Thread.pass` there: a `SystemExit` ends the loop with its status,
     and anything else ends the loop and `run` raises it. A menu that
     kept tracking would hold that exception, and the loop, until someone
     dismissed it, so once one waits the hook passes no more and calls
     `EndMenu`, which ends the calling thread's active menu (Microsoft's
     `EndMenu` reference: "Ends the calling thread's active menu"). The
     menu loop returns, and the loop reaches `MainEventsCleared`. The
     loop calls `EndMenu` too, on Windows, after any event that leaves
     its control flow at `Exit` or `ExitWithCode`, whatever set it: a
     `Thread.pass` that raised, an exception from a callback that ends
     the loop, an exit, or `AppHandle#exit` from another thread arriving
     as the `Exit` user event. tao can call its handler from inside a
     menu its pump dispatched, and its loop cannot end until that menu
     does. That is the one place the loop ends a menu; the hook's own
     call covers an exception that waits for `MainEventsCleared`. With
     no menu active `EndMenu` does nothing.
   - *No native callback holds a pointer Ruby can free.* The hook's state
     is an `Arc<Pending>`, the cell's pointer, and a busy flag. None of
     them is a Ruby object.
   - *It is removed on every path.* A guard owns the `HHOOK`. Its `Drop`
     unhooks and clears the state, and runs when `run_return` returns or
     unwinds, before the cell it points to goes. A thread hook is called
     only on its own thread, so once `UnhookWindowsHookEx` returns
     nothing reads the state. If installing fails, the loop runs as it
     did before this plan.

   Pending interrupts behave as at `MainEventsCleared`: `Thread.pass` runs
   them (Ruby v4.0.9 `thread.c:1513-1518`). A signal's handler may now run
   while a menu tracks, as it already runs between tao's events.
   `rb_thread_call_without_gvl2`, which skips the interrupt check, cannot
   serve: on Windows `RUBY_VM_INTERRUPTED_ANY` raises the timer interrupt
   whenever the VM clock has moved (`vm_core.h:2221-2233`,
   `thread_win32.h:19`), nothing clears it until interrupts run, and
   while it is set `unblock_function_set` refuses (`thread.c:319-343`).

   A signal's handler or a finalizer that runs inside the hook's
   `Thread.pass` runs outside tao's callbacks, where the loop lends no
   window target (`event_loop_target.rs`). There `Native::Window#open`, and
   so `Window#open` and a `WebviewWindowBuilder` at run time, cannot build
   a window. They raise `Error::Runtime` with "the event loop is tracking
   a menu, outside its callbacks", not the "the event loop has ended"
   they raise once the loop is down: the hook marks its hand-off for that
   (`event_loop_target::outside_callbacks`). The monitor and cursor
   getters answer `nil` there, as they do after the loop. Code that must
   build a window from a trap should send it to the main thread with
   `run_on_main_thread`, which runs in a callback.

2. **The rejected options.** *(b) A subclass of tray-icon's window that
   handles `WM_ENTERIDLE`* would need one subclass per owner window
   (tray-icon's, each tao window for the menu bar and the system menu),
   installed and removed with each. It would hear only the owner's
   messages, and `WM_ENTERIDLE` is sent once per idle spell after a
   non-timer message (ReactOS `menu.c:4129-4158`). The hook covers every
   owner on the thread at once. *(c) Releasing the GVL for tray-icon's
   whole dispatch* is unsound. The menu runs outside tao's handler, so
   tao calls the handler for any event the menu loop dispatches (decision
   above, `runner.rs:208-227`), and the handler calls Ruby. tray-icon's
   and muda's own callbacks only send through the loop's proxy
   (`tray.rs` `attach_loop`, `menu.rs` `attach_loop`), but tao's do not.

3. **The menu bar and the system menu share the cause and the fix.** A
   click on muda's menu bar, or on the window's system menu, makes
   `DefWindowProc` run the same modal menu loop inside the window
   procedure that tao's pump dispatched, outside the handler. The hook
   watches the thread, not one window, so it covers them. The move and
   size loops are not menus and call no `MSGF_MENU` filter. tao handles
   them with its `WM_PAINT` path. They are out of scope here, as is a
   message box or dialog run while holding the GVL (`MSGF_DIALOGBOX`).

4. **Counters say which link failed.**
   `Tokra::Native::EventLoop.gvl_handoff_counts` answers a Hash of four
   process-wide counts: `cleared` (`MainEventsCleared` events),
   `loop` (hand-offs there), `menu_messages` (the hook's `MSGF_MENU`
   calls), and `menu` (hand-offs from the hook). The tray fixture prints
   them as the menu is opened, when the closer finds it, when the main
   timer sees it or the fallback fires, and in its report.
   A run where `menu_messages` grows but `cleared` does not, while the
   menu tracks, confirms candidate 1 or 2. A run where `loop` grows and
   the closer still starves confirms candidate 3. The native-loop fixture
   prints them too, so a Mac test shows `loop` counting.

5. **macOS and Linux need no change.** On macOS tao's run-loop observers
   and its wake-up source are added in `kCFRunLoopCommonModes`
   (tao 0.34.5 `platform_impl/macos/observer.rs:219`, `277`;
   `event_loop.rs:336`), which include the event-tracking mode an
   `NSMenu` runs in. So `cleared()` delivers `MainEventsCleared` while a
   tray menu or the menu bar tracks, and the READY hook's wake-up reaches
   it. The macOS tray tests pass on that (plan 043). On Linux the tray's
   menu belongs to the desktop's StatusNotifierItem host, in another
   process, and GTK's menu bar tracks through grabs in the main loop
   tao's `gtk::main_iteration_do` already runs, not in a nested loop.
   muda's context menu is the one nested loop, and it is already inside
   `without_gvl` (`menu.rs:1527`). The hook is compiled only on Windows.

## Tests

- Rust, every platform: the hook's decision (`menu_loop::hand_over`).
  Nothing is asked or passed without the GVL, nothing when nothing is
  owed and no interrupt pends, nothing inside its own hand-off, once per
  owed request, and a pending interrupt passes alone. A failed pass keeps
  its exception and ends the menu, and while one waits the hook only ends
  the menu. The counters count, and the no-target message names a menu
  hand-off only inside one.
- Rust, Windows only: a real `TrackPopupMenu` on a test thread, with the
  hook installed and its Ruby calls stubbed, while another thread marks a
  hand-off owed and posts `WM_APP + 1` to the owner, as the poll ticker
  does. A second `WH_MSGFILTER` hook counts only those posted messages
  under `MSGF_MENU`, and the test asserts it heard at least three and the
  hook handed over. This is the doubt decision 1 rests on, checked by
  count and not by time: the poster gives up after 1000 posts, stops as
  soon as `TrackPopupMenu` returns, and the test asserts that
  `TrackPopupMenu` succeeded, so a runner with no desktop fails at once
  and says so.
- Ruby: the native-loop fixture's CPU-bound run reports at least one
  `loop` hand-off and as many `cleared` events. Removing the `loop` count
  fails it.
- Real windows on Windows CI: the tray tests
  (`test_other_ruby_threads_run_while_the_tray_menu_tracks`,
  `test_on_windows_the_closer_thread_alone_finds_and_ends_the_menu`,
  `test_the_menu_reports_its_progress_in_order`) are the proof. They fail
  on trunk and must pass. A new one,
  `test_on_windows_an_exception_raised_while_the_menu_tracks_ends_it_and_the_loop`,
  runs the fixture with `--raise-main`: once the closer finds the menu it
  calls `Thread.main.raise` with an `Interrupt` subclass, and the main
  thread must rescue it from `App#run` with the fallback never fired.
  That proves the exception path and `EndMenu` by order, not by time.

The loop's own `EndMenu` on exit is covered only through the
`--raise-main` test's path (the hook's exception, then `end_with`). No
test ends the app from a callback or `AppHandle#exit` while a menu
tracks: whether tao delivers that callback inside the menu at all is
the open question of candidates 1 and 2, and where it does not, Tauri
waits for the menu too, so such a test would fail on parity, not on
this plan.

Only Windows CI proves the production half of the hook: the ticker's
mark, `ruby_has_gvl`, `ruby_interrupted`, and `ruby_pass`. The Rust tests
stub all three Ruby calls, and on macOS and Linux the hook is not built.

## What the next Windows CI must show

The tray tests pass: `dismissed_by` is `"thread"` in both runs, and no
`fallback-fired`. The report's `gvl_handoffs` shows `menu` of at least
one, and `tray:sleeper` advances far more than 3 to 5 times. The
`--raise-main` run reports `raised` and `fell_back` false. The
`tray:handoffs` lines at `popup-called`, at `shown`, and in the report
tell which candidate link failed. If `cleared` grew during the menu, the
existing path was dispatching after all and only the `Thread.pass` link
remains suspect. The Windows cargo test passes.

## Risks

- Microsoft documents the menu loop's `CallMsgFilter` in general terms.
  The line-by-line evidence that it covers posted, non-input messages is
  Wine's and ReactOS's. The Windows-only Rust test checks it on the real
  system.
- With a CPU-bound thread, each hand-off inside a menu costs up to one
  time slice, as each turn of the loop does (ADR 012), so a menu tracks
  more slowly then. The ticker bounds it to one hand-off per 10 ms tick,
  plus one per message while an interrupt pends.
- `EndMenu` on an exception closes a menu the user did not dismiss. That
  is the point: the exception must end the loop, and Tauri, which has no
  GVL, never meets the case.
