# Plan 031: tokra-notification reads dates with ferro-time

Tauri's notification plugin reads `Schedule::At`'s `date` as a
`time::OffsetDateTime` through `time::serde::iso8601::deserialize`
(plugins-workspace `d4613ff0`, `plugins/notification/src/models.rs:100-105`),
with time's `serde`, `parsing`, and `formatting` features
(`plugins/notification/Cargo.toml:32`). Plan 024 hand-ported time
0.3.41's ISO 8601 parser into `Iso8601` to give the same answers. Ferro
now binds time one to one as `ferro-time`, so this plan replaces the
port with the crate itself, as plan 030 did for url, and moves
tokra-notification to `ferro-notify-rust` 0.1.0.pre.3.

Sources: time 0.3.41 (plugins-workspace `d4613ff0`'s `Cargo.lock`) and
time 0.3.55 (ferro-time's `Cargo.lock`), each read from Cargo's registry
copy; `ferro-time` 0.1.0.pre.1 at tag `ferro-time/v0.1.0.pre.1` (its
README and Ferro's plan 007); `ferro-notify-rust` 0.1.0.pre.3 at tag
`ferro-notify-rust/v0.1.0.pre.3` (its CHANGELOG).

## What changes between the two time releases

time's serde path is unchanged: `deserialize` hands a string to
`OffsetDateTime::parse` with `Iso8601::<SERDE_CONFIG>`, time's default
configuration with six-digit years, and passes time's error to serde as
its message (0.3.55 `serde/iso8601.rs:24-48`, `serde/visitor.rs:432-502`;
0.3.41 `serde/visitor.rs:300-355`). The parser ignores the
configuration (0.3.55 `parsing/parsable.rs:894-954`, unchanged from
0.3.41's `742-800`). Reading every hunk of the parser and its errors
from 0.3.41 to 0.3.55 finds three changes a page can see:

- **Range messages.** `ComponentRange` no longer prints its range: 0.3.41
  writes `day must be in the range 1..=28 for the given month and year`
  and `second must be in the range 0..=59 because leap seconds are not
  supported`, 0.3.55 writes `day was not in range` and `second was not in
  range` (`error/component_range.rs`: 0.3.41 `60-74`, 0.3.55 `52-57`).
  This reaches a date through `TryFrom<Parsed>` for an impossible day,
  ordinal, or week, and a leap second off the end of a UTC day.
- **Offsets of 24 and 25 hours.** `Parsed`'s offset hour widens from
  `-23..=23` to `-25..=25` (`parsing/parsed.rs`: 0.3.41 `160`, 0.3.55
  `175`), the range `UtcOffset` always had, so `+24:00` and `-25:59`
  parse where 0.3.41 stops at the offset and reports trailing input.
- **A leading `T` without a date.** `parse_time` consumes a leading `T`
  even when no date came first (0.3.55 `parsing/iso8601.rs:125-129`), so
  `T12:00Z` fails for want of a date rather than with 0.3.41's
  `the 'year' component could not be parsed`.

The rest of the diff is refactoring that keeps behavior: `try_likely_ok!`
in place of `?`, slice patterns in place of `first_match`, `NonZero`
generics, and the dropped renaming of `UtcOffset::from_hms`'s component
names, which an ISO 8601 date cannot reach because `Parsed` checks the
offset first.

## Decisions

1. **The argument reader calls `Ferro::Time::OffsetDateTime.parse`**
   with `Iso8601.new(Config::DEFAULT.set_year_is_six_digits(true))`,
   time's `SERDE_CONFIG`. A string time refuses raises a
   `Ferro::Time::Error::Parse` with time's message, and the reader passes
   that message through as serde does. The expecting text for a value
   that is not a string stays serde's visitor's. `Iso8601` and its
   signatures are deleted.
2. **`Schedule::At` holds a `Ferro::Time::OffsetDateTime`.** Tauri's
   field is `time::OffsetDateTime`, and plan 024 held a Ruby `Time` only
   because Ruby had no such type. `Schedule::At.new` raises `TypeError`
   for anything else, as Rust's types refuse it; an app with a Ruby
   `Time` converts it with `OffsetDateTime.from`. Desktop systems ignore
   the schedule, so nothing downstream reads the date.
3. **The version difference is a deviation.** Ferro binds a crate's
   latest release (plan 030, decision 4), and the three changes above
   make some dates read as time 0.3.55 reads them, recorded in the
   plugin's RDoc and README, until Tauri's lock moves past time 0.3.41.
4. **`large-dates` stays off, now checked.** No manifest in
   plugins-workspace `d4613ff0` enables it, nor does any registry crate
   in the notification plugin's tree that depends on time (cookie
   0.18.1, cookie_store 0.21.1, plist 1.7.1, mac-notification-sys 0.6.4,
   serde_with 3.12.0, tauri-codegen 2.5.2), so years run from -9999 to
   9999 in both, as ferro-time builds time. This closes plan 024's
   UNVERIFIED note.
5. **The dependencies are release tags.** Both Gemfiles take
   `ferro-time` from tag `ferro-time/v0.1.0.pre.1` with the glob
   `gems/time/*.gemspec`, and `ferro-notify-rust` from tag
   `ferro-notify-rust/v0.1.0.pre.3`, whose macOS `schedule` checks for
   `::Time`: with ferro-time loaded, pre.2's bare `Time` inside `Ferro`
   names `Ferro::Time` and refuses every Ruby `Time`. The gemspec pins
   `= 0.1.0.pre.1` and `= 0.1.0.pre.3`. No Tokra code opens `module
   Ferro`, so a bare `Time` in Tokra still names Ruby's. Steep's RBS
   validation reads ferro-time's signatures; the packaging smoke reads a
   date through ferro-time. CI needs nothing new: time builds without
   system libraries.

## Verification

- The plan 024 oracle, a scratch crate compiling Tauri's `models.rs`
  with the locked serde, serde_json, and time 0.3.41, printing each
  accepted date's nanoseconds and offset, and a twin locking time 0.3.55.
- Through the plugin's real argument reader, on plan 024's 4,066 dates
  and 35,000 new fuzzed ones (20,000 mutations of the old corpus, 15,000
  built from random components, many out of range), Tokra matched the
  0.3.55 oracle, value and message, on all 39,066, and the 0.3.41
  oracle on all but 890. Each of the 890 is a date where the two oracles
  differ: 123 range messages, 296 dates with an offset hour of 24 or 25,
  and 471 that start with `T`.
- `test_each_date_parses_as_time_parses_it` keeps the 60 of plan 024's
  66 chosen dates on which both versions agree, plus two more, each now
  held as an `OffsetDateTime`; `test_a_date_reads_as_time_0_3_55_reads_it`
  pins decision 3 with 11 dates and both oracles' answers;
  `test_a_schedule_refuses_a_date_that_is_not_parsed` pins decision 2.
- Manual mutation checks, in Results.
- `bundle exec rake` from a clean build.

## Results

Every decision above is done.

- Manual mutation checks, each reverted after: dropping `At`'s type
  check fails `test_a_schedule_refuses_a_date_that_is_not_parsed`;
  holding the string in place of the parsed date fails
  `test_each_date_parses_as_time_parses_it` and
  `test_a_date_reads_as_time_0_3_55_reads_it`; replacing time's message
  with the error's class name fails both; parsing with Ruby's
  `Time.iso8601` fails both and `test_each_value_reads_as_serde_reads_it`;
  dropping the string check fails `test_each_value_reads_as_serde_reads_it`.

## Out of scope

- Serializing a date: Tauri's custom `iso8601::serialize`
  (`models.rs:127-146`) serves mobile, and Tokra writes no
  `NotificationData` back.
