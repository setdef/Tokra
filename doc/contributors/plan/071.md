# Plan 071: Tokra builds soundly on Windows' Ruby 4.1

## Context

Fledge, the packager Tokra apps ship with, embeds only Ruby 4.1. On
Windows its runtime is RubyInstaller's build of Ruby's master of
2026-11-10, x64 (`ruby 4.1.0dev (2026-11-10 master 0e25874222)
[x64-mingw-ucrt]`), which Fledge keeps as a release of its own because
RubyInstaller replaces its head build every day. Plan 069 left Windows on
Ruby 4.0, since no Ruby 4.1 there built Tokra's extension soundly, and
said Tokra builds nothing on a Windows Ruby 4.1 until magnus and rb-sys
change. This plan replaces that section.

The maintainer decided on 2026-11-21 that Tokra moves to Ruby 4.1 on
Windows now, without waiting for upstream, and that a patched magnus may
be carried but not forked: each change Tokra would send upstream lives in
`doc/contributors/upstream/` as the pull request's text in Markdown and a
`.patch` beside it that the upstream maintainers would accept, and
nothing is filed.

## The fault, traced

Ruby 4.1 adds `rb_len_t`, the type of String's, Array's, and MatchData's
lengths and indices in the C API (ruby/ruby 03e3376643). It is `int64_t`
when `SIZEOF_RB_LEN_T` is defined wider than `long`, and `long`
otherwise. RubyInstaller's head build defines `-DSIZEOF_RB_LEN_T=8` in
`RbConfig::CONFIG["CPPFLAGS"]`, not in `config.h`, where `SIZEOF_LONG`
is 4. So there every length is 64 bits and `long` is 32.

- **Plain cargo** (`cargo test`, Clippy) gives bindgen RbConfig's
  `CPPFLAGS`, binds `rb_len_t` as `i64`, and magnus 0.9.3 does not
  compile: it casts each length `as c_long`.
- **rb_sys's Makefile** (`rake compile`, `gem install`) hands the build
  script each RbConfig entry as an `RBCONFIG_<key>` variable, which
  rb-sys reads before RbConfig itself. RbConfig has `CPPFLAGS` and an
  empty `cppflags`. Windows' variable names ignore case, so the two are
  one variable, and the build script got `RBCONFIG_CPPFLAGS` empty: its
  `RB_SYS_DEBUG_BUILD` dump shows `"RBCONFIG_CPPFLAGS": ""` beside an
  RbConfig that holds the flags, and its bindgen arguments hold none of
  them. So bindgen bound `rb_len_t` as `c_long`, magnus compiled, and the
  extension passed every length and index to Ruby as 32 bits where Ruby
  reads 64. That is the unsound build Plan 069 met; it could not say
  where the define was lost.

Both need fixing. Fixing only the Makefile path makes every magnus gem
stop compiling; fixing only magnus leaves a gem install mistyped.

## Decided

### The pin

`mise.toml` pins, on Windows only, what Fledge's `mise.toml` pins there
(at d48f365f): RubyInstaller's head build of 2026-11-10 from Fledge's
copy, by its SHA-256, through mise's http backend; the MSYS2 packages of
the two DLLs that build lacks, `libz-1.dll` and `libgcc_s_seh-1.dll`,
with `RUBY_DLL_PATH` naming their folders; and the MSYS2 with its UCRT64
compiler that ruby/setup-msys2-gcc built on 2026-11-12, with
`MSYS2_PATH`, `RI_DEVKIT`, and the rest of what `ridk enable` sets
(`.config/mise/windows-x64.env`). It needs mise 2026.10.11, since the
`[env]` is a template. Linux and macOS keep 4.1.0-preview1. The tables go
when RubyInstaller releases RubyInstaller-4.1.0-1.

Pinning the MSYS2 makes Windows' setup whole: `bin/setup` no longer needs
a machine whose MSYS2 has the compiler (Plan 061's "Left for later"),
and `bin/setup.ps1` names `mise install` where it named `ridk install`.
`bin/windows-env` keeps its search for the MSYS2 that runs it, for a Ruby
outside mise, where `MSYS2_PATH` is unset.

Weighed: the head build of the day, as setup-ruby's `head` gives it,
moves every day and is not the Ruby Fledge embeds; a released
RubyInstaller 4.1 does not exist yet.

### magnus, patched and vendored

`vendor/magnus` is magnus 0.9.3 as crates.io serves it (unpacked from the
`.crate` whose SHA-256 is the one `Cargo.lock` recorded,
40ef4244...c713) with one change: a crate-private alias `Len`, which is
`rb_sys::rb_len_t` on Ruby 4.1 and newer and `c_long` before, and each
length or index cast to it where magnus cast to `c_long`. The root
`Cargo.toml` takes it with `[patch.crates-io]` and excludes `vendor` from
the workspace, so it is never a member: the gate neither tests, formats,
nor lints it. `Cargo.lock` names it as a path package, so `--locked`
holds. The gemspec ships the folder, so `rake package:install` and
`gem install` build the same. `REUSE.toml` gives it magnus's MIT license,
and RuboCop leaves it alone.

`doc/contributors/upstream/magnus-rb-len-t.md` and `.patch` are the same
change against magnus's main branch. Where `rb_len_t` is `long`, which is
everywhere but RubyInstaller's 4.1 and 64-bit mswin, `Len` is `c_long`,
so nothing changes on Linux, macOS, or Ruby 4.0.

Weighed: a fork (refused); a git dependency on an unmerged branch (also a
fork); moving to magnus 0.9.4 first (one unrelated fix, and Ferro locks
0.9.3); applying the `.patch` to Cargo's registry copy at build time,
which an installed gem cannot do without the network and which `--locked`
would not see.

### rb-sys's Makefile, worked around

`ext/tokra/extconf.rb`, on Windows, leaves every `RBCONFIG_` key that
differs from another only in case out of the Makefile, by setting it to
`nil` in `create_rust_makefile`'s `env` (rb_sys 0.9.130 writes no line
for a `nil` value: `mkmf.rb`, `env_line`). rb-sys then reads those keys
from RbConfig, as plain cargo does. The workaround ships in the gem, so a
gem install is sound too.

`doc/contributors/upstream/rb-sys-rbconfig-env-on-windows.md` and
`.patch` make the same change in the rb_sys gem's `rb_config_env`, with a
test. When a release has it, the workaround goes.

This also gives bindgen `-D_WIN32_WINNT=0x0600`,
`-D__MINGW_USE_VC2005_COMPAT`, and `-D_FILE_OFFSET_BITS=64` on Ruby 4.0
on Windows, which it lost the same way; Ruby builds its own extensions
with them.

Weighed: a vendored rb_sys gem, which would mean vendoring a gem Bundler
resolves; `RBCONFIG_CPPFLAGS` set by hand in `bin/windows-env`, which a
gem install never runs.

### CI

The matrix runs 4.0 and 4.1 on all three runners, six jobs. Windows' 4.1
job installs Ruby with jdx/mise-action from `mise.toml`'s pins, and runs
`.github/scripts/windows-ruby-env.sh` for what setup-ruby would have set
beyond them (TMPDIR above all), both after Fledge's CI at d48f365f.
Every other job keeps setup-ruby. `test/tasks/test_ruby_pins.rb` reads
the Windows pin from the head build's table.

`ruby-head.yml` still leaves Windows out; ci.yml's Windows 4.1 job runs
one pinned day of the head build.

## What the runs showed

Each run went through `bin/setup --gate` with `CI=true` in MSYS2's bash
on the Windows build machine.

- mise installs the head build, which answers `ruby 4.1.0dev (2026-11-10
  master 0e25874222) +PRISM [x64-mingw-ucrt]`, with Bundler's path
  `vendor/bundle/ruby/4.1.0+6`. Its RbConfig `CPPFLAGS` holds
  `-DSIZEOF_RB_LEN_T=8`; `config.h` has `SIZEOF_LONG 4`.
- Before the workaround, `rake compile` bound `rb_len_t` as `c_long`, and
  the build script's environment held `RBCONFIG_CPPFLAGS` empty.
- With it and the patched magnus, `compile:strict` passes with no
  warning and binds `rb_len_t` as `i64`; `test:rust` and `lint:rust`,
  through plain cargo, pass and bind it as `i64` too.
- `test:core` passes: 2363 runs, 0 failures, 119 skips.
- The real-window tasks, `plugins:test`, the rest of the gate, and Ruby
  4.0 on Windows with the `extconf.rb` change were left to the pre-push
  hook and CI.

## Left for later

- The Ferro gems Tokra and its plugins use (ferro-url, ferro-time,
  ferro-rfd, ferro-arboard, ferro-notify-rust, ferro-global-hotkey, each
  at v0.1.0) lock magnus 0.9.3 and build through rb_sys's Makefile, so on
  Windows' Ruby 4.1 they compile with `rb_len_t` bound as 32 bits. Each
  needs the patched magnus and the `extconf.rb` workaround in a release
  of its own; Tokra cannot change how another gem builds.
- When magnus and rb_sys release the changes: `vendor/magnus`, the
  `[patch]`, and the workaround go.
- When RubyInstaller releases 4.1.0: `mise.toml` pins it with mise's
  ruby, and the head build's tables go.
- rb-sys compiles its stable API's C fallback without `CPPFLAGS`
  (`rb-sys-build`, `src/cc.rs`). It reads nothing wrong today, as the
  rb-sys text says; it is noted there and not changed.
- Ruby's head on Windows in `ruby-head.yml`.
