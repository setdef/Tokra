# Plan 020: Main-Thread Dispatch

Plan 019's review found that `unsafe impl Send` for `RbEventLoop` and
`RbWebView` is sound only while every use, and the drop, happens on the
main thread, and that nothing enforces it. App code on another Ruby
`Thread` can call `Tokra::Webview#eval`, which reaches wry directly, and a
garbage collection on another thread can free either object. Tauri never
touches a window or webview off the main thread: every call goes through a
dispatcher that runs it there. This plan ports that dispatcher and makes
the native layer refuse, rather than trust, a foreign thread. ADR 012
records the architecture and the alternatives rejected.

Sources: `vendor/tauri` at `9f0306fb`; tao 0.34.5, wry 0.54.1, magnus at
`2370a35`, and rb-sys 0.9.130 as `Cargo.lock` pins them; Ruby `v4.0.1`
(`e04267a1`).

## Context

Ruby threads in the main Ractor share one process and one GVL. Tokra runs
tao's loop on the main thread, so a window or webview call made anywhere
else breaks the invariant the `Send` impls state. Two facts made that
reachable:

- **Calls.** `Webview#eval`, `Window#set_title`, `Window#set_size`, and
  `AppHandle#emit` called the native object on whatever thread called them.
- **Frees.** magnus wraps these types with `free_immediately`, so Ruby
  runs their destructor inside the sweep (`gc.c:1182-1222`, the
  `free_immediately` arm). Lazy sweeping continues on whichever thread
  next allocates (`gc/default/default.c:2062-2120`, `heap_prepare`), and
  without the flag the free becomes a postponed job that any thread can run
  (`gc/default/default.c:2939-2953`). Dropping the flag does not help.

A third fact surfaced while writing this plan: **no other Ruby thread ran
while the loop waited.** `EventLoop#run` calls tao's `run_return` holding
the GVL, so a background thread got the GVL only while the main thread ran
Ruby code in a callback. A probe app whose background thread ticked every
200 ms never ticked once in 20 s of idle loop. Dispatching to the main
thread needs the main thread to give the GVL up while it waits, or a
background caller that waits for a reply waits until some unrelated event
arrives.

## Decisions

1. **`ThreadBound<T>` owns every main-thread value.** A new
   `ext/tokra/src/thread_bound.rs` holds a value with the `ThreadId` of
   the thread that created it. `get` returns the value only on that thread.
   Dropped on any other thread, it forgets the value instead of running its
   destructor. Its one `unsafe impl Send` is sound for any `T`: another
   thread can move it, read the owner id, and leak it, and never reaches
   `T`. `RbEventLoop` and `RbWebView` hold their tao and wry values in it,
   so their own `unsafe impl Send` blocks and the two clippy exceptions are
   gone. `RbWindow` holds its tao window the same way (decision 2). Leaking is the safe failure: a wry `WebView` or tao `EventLoop`
   freed on the wrong thread is undefined behavior; one leaked is memory.
   Rust unit tests prove both halves with real threads.

2. **The native layer refuses a foreign thread.** Each `EventLoop`,
   `Window`, and `WebView` method, and the constructors that take one,
   checks the owner and raises `ThreadError`: "Tokra::Native::WebView can
   only be used on the thread that created it", and likewise per class.
   Ruby raises `ThreadError` for an operation a thread may not perform, and
   Tauri has no counterpart message, since its types are not reachable
   from other threads. tao calls its `Window` `Send + Sync`, and this plan
   first left it unwrapped; review found that wrong. On macOS, tao runs most
   window work on the main thread and makes the caller wait, dropping
   included: `UnownedWindow::drop` closes through `run_on_main`, which is
   `Queue::main().exec_sync` (`platform_impl/macos/window.rs:1734-1739`,
   `util/async.rs:43-48`, `242-249`). A sweep on a background thread holds
   the GVL while the main thread waits for it in `Thread.pass`, so neither
   moves. The window now lives in a `ThreadBound` too, and Tauri likewise
   never calls one off the main thread. `EventLoop#create_proxy` and every
   `Proxy` method stay callable anywhere.

3. **A window or webview freed off the main thread is released on it.**
   `RbWebView` and `RbWindow` keep a loop proxy. Their `Drop`, run by a
   sweep on another thread, moves the `ThreadBound` value into
   `UserEvent::Release` and sends it; the loop drops it on the main thread. If the loop is gone, the event comes
   back in `EventLoopClosed` and drops where it is, which decision 1 makes a
   leak. Undelivered events are dropped with the loop's receiver, on the
   main thread on macOS and Linux (`macos/event_loop.rs:76-82`,
   `linux/event_loop.rs:194-196`); on Windows a lost race can drop one on
   the sender (`windows/event_loop.rs:571-586`), which again leaks. The drop
   path calls no Ruby API, as `free_immediately` demands (magnus
   `typed_data.rs:310-316`). An `RbEventLoop` freed off its thread leaks its
   unrun loop: it cannot be sent to itself.

4. **`RuntimeContext` is the dispatcher, in Ruby.** `Tokra::RuntimeContext`
   mirrors tauri-runtime-wry's `Context`: it records the main thread when
   the app is built, and `send_user_message` runs a task at once on that
   thread or queues it and wakes the loop with `Proxy#send_task`
   (`UserEvent::Task`, delivered as `Native::TaskEvent`). The loop runs one
   queued task per event, in order, on the main thread, as
   `handle_user_message` runs `Message::Task`. `getter` mirrors `getter!`:
   the task answers through a `Thread::Queue`, the Ruby counterpart of the
   mpsc channel, and an exception the query raises re-raises in the
   caller. Tasks queued before the loop exists wake it when it attaches.
   Ruby blocks stay in Ruby: the native event carries no payload, so Rust
   never holds a Ruby object across threads.

5. **The loop keeps the GVL and hands it over once per iteration** (ADR
   012). A READY thread-event hook (`gvl_handoff.rs`) fires whenever a
   thread starts waiting for the GVL (`thread_pthread.c:794-801`), and at
   every time-slice switch (`thread_pthread.c:1128-1141`). It marks a
   hand-off owed and wakes the loop with `UserEvent::Yield` only when the
   mark was clear. At `MainEventsCleared` the loop clears the mark and calls
   `Thread.pass` through magnus's protected `funcall`, inside tao's
   callback, so any exception lands in magnus's `rb_protect`, never across
   tao. Installing the hook marks a hand-off owed, for threads already
   waiting, whose READY events fired before the hook existed. Once an exit
   is set the loop stops handing over, so the exit is not a time slice
   late. The hook skips the main thread's own waits, calls no Ruby API, and
   is removed, under the write lock every hook call reads, before its data
   is freed (`thread_pthread.c:3428-3485`). Ruby has no hooks on Windows
   (`thread_win32.c:34-45`); there the loop wakes every 10 ms while other
   Ruby threads exist and hands over at the same point. Releasing the GVL
   around the loop was the first design and is unsound; ADR 012 says why.
   The second passed the GVL on every `Yield`, inside tao's user-event
   drain: review showed a CPU-bound thread turning each hand-off into the
   next request, so the window froze and `exit` never took effect.

6. **Protocol answers from other threads go through the loop.** The first
   real-window run deadlocked: a background thread holding the GVL called
   `Proxy#respond`, and `-[WKURLSchemeTaskImpl didReceiveResponse:]` waited
   for the main run loop (`WTF::callOnMainRunLoopAndWait`) while the main
   thread waited for the GVL. `Proxy` now records the loop's thread; off it,
   `respond` and `drop_response` send an `Answer` to the loop
   (`UserEvent::Respond`), which delivers it on the main thread. If the
   loop has closed, the answer is forgotten, since WebKit could wait
   forever for a run loop that no longer turns, and the call raises
   "Failed to send response: event loop closed".

7. **Window and Webview dispatch every native call.** `Webview#eval`,
   `Window#set_title`, and `Window#set_size` send fire-and-forget messages
   and return `nil`; the new `Window#title` is a getter. `Webview#eval` logs
   a failed evaluation instead of raising, as Tauri does.
   `run_on_main_thread` lands on `AppHandle`, `App`, `Window`, and
   `Webview`, all through the one context the app handle holds. tao sets a
   macOS title asynchronously even on the main thread
   (`util/async.rs:222-228`), so `title` right after `set_title` can read
   the old title, in Tauri as here.

8. **Ruby's events wait for the end of the iteration.** tao drains its
   user-event channel until it is empty (`platform_impl/macos/app_state.rs:110-121`;
   Linux stays in its `EventQueue` state while events remain). A callback
   inside the drain loses the GVL for a full time slice whenever another
   thread wants it, so with a CPU-bound thread and a 100 ms ticker the drain
   never emptied, and `cleared()` never reached the `stop` an exit needs,
   with or without the hand-off. The drain now acts at once only on what
   needs no Ruby (`Yield`, `Respond`, `Release`, `Exit`) and queues the
   rest; `MainEventsCleared`, and `LoopDestroyed` for any remainder,
   deliver the batch in order. A close request joins the same queue, so it
   reaches Ruby after the user events that arrived before it, the order
   tao's macOS `cleared()` keeps and Tauri sees (`app_state.rs:394-398`).
   No test can raise a real close request here (it takes the window's
   close button); a Rust test pins the shared queue's order, and
   `hands_over` pins that no hand-off happens once an exit is set. Events that arrive meanwhile wait in tao's
   channel for the next iteration.

9. **An interrupt ends the loop the Ruby way.** Before, everything a
   callback raised except `SystemExit` was printed and swallowed, so
   `kill -TERM` printed a `SignalException` and the app stayed up. Now a
   `StandardError` is still reported and the loop keeps running, a
   `SystemExit` ends it with its status, and anything else, a
   `SignalException` from Ruby's default TERM, HUP, or QUIT handler, an
   `Interrupt`, a `Thread#kill`, ends the loop and is raised again by
   `EventLoop#run` once the loop is down. Whatever `Thread.pass` raises
   came from an interrupt, a `Thread#raise` at the main thread included, so
   it ends the loop too. The loop keeps an exit already set rather than
   resetting the flow for each event, as Tauri does (tauri-runtime-wry
   `lib.rs:4029-4031`); tao's Linux loop calls back again after an exit is
   set (`linux/event_loop.rs:1113-1126`).

10. **The loop's end closes the context.** `App#run` closes it in an
   `ensure` once the native loop returns. Closing fails every queued getter
   with `FailedToReceiveMessage`, the way the dropped sender fails Tauri's
   `recv`, and every later off-main call with `FailedToSendMessage`, the
   way the closed proxy fails Tauri's `send_event`. A main-thread call
   after close still runs at once, as `send_user_message` does on the main
   thread. A getter whose query raises closes its reply as well, the way
   Tauri's handler drops its sender, so its caller fails at once instead of
   waiting for the loop to end. Only a `StandardError` from the query
   travels to the caller; anything else, such as a signal's `Interrupt`,
   stays on the main thread, where Ruby raised it.

11. **The loop's thread is the main thread.** The context records the
    building thread and `attach`, which `App#run` calls with the loop's
    proxy, makes the running thread the main one, as Tauri records the
    thread that builds its loop (`lib.rs:2795`).

## Deadlock analysis

- **A main-thread callback that dispatches** runs the task at once, never
  queues it, so it never waits on itself. Test: an invoke handler reads
  `Window#title`.
- **A background caller during exit.** Its task may sit in the queue when
  the loop ends. Closing the context wakes it with
  `FailedToReceiveMessage`. Test: a thread started in the `Exit` handler
  waits on `Window#title`; `at_exit` prints the error it got.
- **A background caller after exit** gets `FailedToSendMessage` without
  queuing. Test: the same `at_exit` makes a fresh call.
- **The main thread blocking on a background caller.** A main-thread
  callback that joins a thread which waits for the main thread deadlocks,
  in Tauri too ("this must be called from a separate thread, otherwise the
  channel will introduce a deadlock", `lib.rs:2633`). `run_on_main_thread`'s
  RDoc says so.
- **A background thread in native code that waits for the main thread.**
  The main thread may be waiting for the GVL that thread holds. The window,
  webview, and loop refuse other threads outright, and `Proxy#respond`
  sends its answer to the main thread (decision 6). `Proxy#wake_up` and
  `send_task` only queue an event.
- **The READY hook** runs with Ruby's scheduler lock held. It does an
  atomic swap and, at most once per hand-off, sends a proxy event, a
  channel send and a run-loop wake-up, which take no lock the main thread
  holds while it waits for the scheduler.
- **A native object freed on another thread.** The sweeping thread holds
  the GVL, and the main thread may be waiting for it in `Thread.pass`. A
  window or webview dropped there could wait for the main thread (tao's
  macOS window close is a synchronous main-queue dispatch). Neither does:
  `Drop` only sends the value to the loop, or leaks it. Test: a background
  thread collects unreachable windows and webviews.
- **CPU-bound threads.** Each turn of the loop hands the GVL over once,
  and Ruby gives each waiting thread one time slice, so the window turns at
  least once per round of slices and an exit takes effect at the next turn.
  Tests: one and three spinning threads, with a 100 ms ticker, keep its
  wake-ups under 2 s and let `exit` end the app.

Review found four liveness bugs the first version had, now fixed and

Three mutations survive, each for a stated reason. MW alone, a window freed
elsewhere and not sent home, leaks it through `ThreadBound`: safe, and not
visible to Ruby. ME, routing `Thread.pass`'s exceptions through the
callback rules, still ends the loop on a `SignalException`, which is not a
`StandardError`; only a `StandardError` from `Thread#raise` would differ.
Resetting the flow unconditionally (decision 9) is harmless on macOS, where
tao hands an exiting loop a scratch flow; the path it guards is Linux's,
untested here.

Two mutations taught something. The first M5 run passed: `getter` had a
main-thread check of its own that duplicated `send_user_message`'s, so it
went. And an early draft dispatched `AppHandle#exit` to the main thread;
reverting it failed only a unit test of that dispatch, because Ruby
already raises a thread's `SystemExit` in the main thread (audit table),
so `exit` stays as it was and the real-window exit test guards it. The
main-thread getter tests now run under a 5 s timeout, so that mutation
fails instead of hanging the suite.

## Out of scope

- `Webview#url` and the other Tauri getters and setters Tokra has not
  ported; each lands through `RuntimeContext` when it does.
- `RunEvent::ExitRequested` and an exit request through the loop.
- Signals other than `SIGINT` while the loop idles with no other Ruby
  thread: nothing wakes the loop for them, before and after this plan.
- `Proxy#drop_response` does not make the page's `fetch` reject on macOS,
  on the main thread or off it: wry drops the responder without failing
  WebKit's scheme task. `App`'s RDoc says a drop makes the client fall back
  to `postMessage`; that path is the ipc:// key mismatch, which this plan
  does not change. A follow-up should check it against Tauri on WebKit.
- The review also asked for a CHANGELOG line saying
  `Native::EventLoop#create_proxy` no longer raises after `run`. It never
  did: the proxy it cloned lived in a `RefCell<Option<_>>` that nothing set
  to `None` (only the loop itself was taken), so nothing observable
  changed.
- Ractor workers calling `run_on_main_thread`: the context lives in the
  main Ractor, and the extension is not Ractor-safe.

## Risks

- **Linux and Windows are unverified locally.** The hook is Ruby's, not the
  platform's, and CI runs the real-window tests on Linux under Xvfb. The
  Windows polling fallback runs nowhere yet: `RealApp` skips Windows.
- **A leaked webview stays on screen** if its last reference dies on a
  background thread after the loop ends. The process is ending then.

## Follow-up: the first hosted run

Tokra's first CI run (40224829414) passed 526 of 527 tests on Linux and
macOS, real windows included, and never reached the gate on Windows.

- **macOS, three CPU-bound threads.** The test asked for at least ten of
  the ticker's forty wake-ups in 4 s, and the runner delivered seven, each
  within 387 ms. How many arrive is how often the ticker itself wins the
  GVL against three spinning threads, which depends on the machine's
  cores, not on the loop. The test now asserts what decision 5 guarantees:
  the loop delivers more than one wake-up, each within one round of time
  slices (one per busy thread, the ticker, and the main thread, doubled
  for timer jitter), with the slice read from `RUBY_THREAD_TIMESLICE` or
  Ruby's default of 100 ms (`thread.c:118`, `5746-5752`), and the exit
  ends the app.
- **Linux, the collection test.** The app ended with status 0 before it
  could report. A trace under Xvfb showed three `CloseRequested` events
  right after the collection, one per dropped webview. Tokra built each
  webview with wry's `build`, which on Linux takes wry's X11 path and,
  without `as_child`, adopts the window's own X window
  (webkitgtk/mod.rs:159-162); dropping the webview destroys that X window
  and closes its GTK wrapper (`mod.rs:77-82`), tao reports the window
  closing, and the first close ended the loop. Tauri never takes that
  path: on Linux it builds into the window's GTK box with `build_gtk`
  (tauri-runtime-wry `lib.rs:5032-5051`). Tokra now does the same, which
  also makes webviews work under Wayland, where the X11 path failed. The
  real-window tests pass under Xvfb in Docker (Debian 13, aarch64).
- **Windows.** The workflow ran setup-ruby twice, the second time to cache
  the bundle once bindgen's settings were in place, and setup-ruby cannot
  run twice on Windows: it links MSYS2's tree beside Ruby again and fails
  on the existing junction (windows.js:133-136). setup-ruby now runs once,
  without the bundle; the bindgen step follows; and the bundle installs
  frozen into `vendor/bundle`, cached with actions/cache by OS, CPU, exact
  Ruby, and lockfile.

Windows reaches the gate for the first time in the next run, and the
extension will likely fail to load there. With the GNU target,
webview2-com-sys 0.38.2 (the locked version) imports the loader
dynamically, `link(name = "WebView2Loader.dll")` for any non-MSVC
environment (`src/lib.rs:13-24`); its build script only copies the DLL
into its own `OUT_DIR/<arch>` for the link search path (`build.rs:39-91`).
Windows looks for a DLL's dependencies beside the executable, not beside
the extension, so `tokra.so` will need `WebView2Loader.dll` beside
`ruby.exe`, on `PATH`, or in a directory added with RubyInstaller's
`RubyInstaller::Runtime.add_dll_directory`. Tauri copies it beside the
executable for GNU builds (tauri-build `src/lib.rs:660-682`). Shipping it
means copying it from webview2-com-sys's build output in extconf and
packaging, and adding its directory before `require`. That waits for the
first Windows log, so the fix answers the error Windows actually reports.
