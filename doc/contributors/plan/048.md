# Plan 048: tokra-notification moves to ferro-time 0.1.0.pre.3 and ferro-notify-rust 0.1.0.pre.4

Plan 031 pinned tokra-notification to `ferro-time` 0.1.0.pre.1 and
`ferro-notify-rust` 0.1.0.pre.3. Ferro has since released
`ferro-notify-rust` 0.1.0.pre.4 and `ferro-time` 0.1.0.pre.3, each
fixing a crash in Ruby's garbage collector interplay. This plan moves
both pins and records which fix the plugin can reach.

Sources: Ferro's `gems/time/CHANGELOG.md` and
`gems/notify-rust/CHANGELOG.md`, and the diffs between the tags the
plugin pinned and the tags it now pins
(`ferro-time/v0.1.0.pre.1` to `ferro-time/v0.1.0.pre.3`;
`ferro-notify-rust/v0.1.0.pre.3` to `ferro-notify-rust/v0.1.0.pre.4`).

## What changes between the releases

**ferro-time pre.1 to pre.3.** pre.2 adds format items
(`FormatDescription.parse_borrowed` and friends), `Parsing::Parsed`,
`try_from(parsed)` and `parse_with_defaults`, makes
`UtcDateTime.parse` raise `RangeError` where it raised "time panicked",
and makes `parse_borrowed` and `parse_owned` accept versions 1 and 2.
pre.3 adds `Timestamp` and fixes the crash below. Reading the diff of
`failure.rs`, `offset_date_time.rb`, `arguments.rb`, and `format.rs`: the error
classes `OffsetDateTime.parse` raises for a refused string are unchanged
(`Error::Parse`, `Error::Parse::ParseFromDescription::*`,
`Error::Parse::TryFromParsed::*`, `failure.rs:109-170`). The new
top-level `Error::ParseFromDescription` and `Error::TryFromParsed`
classes belong to `Parsed`'s own methods, which the plugin does not
call. `WellKnown::Iso8601` and `Config` are untouched, so every date
Plan 031 pinned reads as before. `format.rs`'s
`Description::from_value` now tries `Items::from_value` before the
Iso8601 settings tuple, which does not catch the plugin's description:
`Items::from_value` returns `None` unless element 0 is a Symbol
(`items.rs:442-455` at pre.3), and the Iso8601 settings are
`(u8, bool, bool, u8, u8, u8, u8)`, which start with an Integer
(`format.rs:70-76`).

**ferro-notify-rust pre.3 to pre.4.** One change, to `values.rs`: the
fields of `Hint.from_key_val` and of a Linux notification's `hints`
were held where the collector does not look while the tag array was
allocated.

## Which crashes the plugin reaches

- **ferro-time, an error's arguments freed before the exception read
  them (reached).** `Arguments#date` calls `OffsetDateTime.parse` and
  rescues `Ferro::Time::Error::Parse`
  (`plugins/notification/lib/tokra/plugins/notification/arguments.rb:223-231`).
  Every date time refuses builds one of those errors, and a page can send
  any string as `schedule.at.date`. In pre.1 and pre.2 the error's
  arguments lived in a Rust `Vec`, which the collector does not scan, so
  a collection between allocating the exception and reading them freed
  them. A page could therefore crash the app with a refused date.
- **ferro-notify-rust, `Hint.from_key_val` and `hints` (not reached).**
  Nothing in `plugins/notification/lib` calls `Hint.from_key_val`,
  `Notification#hint`, or `Notification#hints`. The plugin sets a
  sound with `sound_name`, which notify-rust turns into a hint inside
  Rust, and that path does not go through the fixed Ruby-visible
  constructor or reader. The `hints` the Linux tests read belong to the
  test's own D-Bus fixture. So this bump is not needed for a crash the
  plugin can hit today; it is taken so the pin carries no known crash
  for an app that reaches `Ferro::NotifyRust` through `Notification`'s
  handle, and so both Ferro pins move together.

## Decisions

1. **Both pins move**: the root and plugin Gemfiles, both lockfiles
   (`bundle update --conservative`), and the gemspec's `= 0.1.0.pre.4`
   and `= 0.1.0.pre.3`. The plugin's README names the new tags.
2. **The regression test drives the real reader.**
   `plugins/notification/test/test_arguments_gc.rb` runs, in a child
   Ruby so a segmentation fault fails the test and not the suite, the
   plugin's `Commands::Arguments` over three refused dates (a day out of
   range, trailing input, and a string that is no date) with
   `GC.stress = true`. Under stress every allocation collects, so the
   window between allocating the exception and reading its arguments is
   hit on every error, with no timing and no iteration count to tune.
   The child must exit successfully and report an `InvalidArgs` message
   for each date.
3. **No test for the hints fix.** The plugin cannot reach it
   (above); Ferro's own `test_values.rb` covers it.
4. **CHANGELOG.** tokra-notification is unreleased (no tag contains
   it), so a "Fixed" line would record a bug no release shipped. The
   plugin's Added entry names the new versions instead.

## Verification

- Before bumping, the new test ran against the old pins and the child
  crashed three runs out of three (Results).
- After bumping, it passes in about two seconds.
- The plugin's tests and the full `bundle exec rake` gate.

## Results

Before the bump, with `ferro-time` 0.1.0.pre.1 and `ferro-notify-rust`
0.1.0.pre.3 locked, three runs of `test_arguments_gc.rb` each failed:

    the child Ruby crashed or failed: .../Ferro-dac0c6104362/gems/time/lib/ferro/time/error.rb:444: [BUG] Segmentation fault at 0x000065676e615274
    Expected #<Process::Status: pid 88627 SIGSEGV (signal 11)> to be success?.

The fault is in `to_s` called from the exception's `new`, reached from
`Arguments#date`, as the diagnosis above says. With pre.3 locked the
test passes in about two seconds.

## Out of scope

- Tests for `Timestamp` and the format items; the plugin uses neither.
- Moving `ferro-url`, which has no new release this plan needs.
