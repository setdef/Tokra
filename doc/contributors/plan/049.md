# Plan 049: Tray, phase 2

Plan 043 ported the tray icon, its builder, its events, and every command
of the core `tray` plugin, and left three things for later: the config's
`trayIcon`, the rest of `cleanup_before_exit`, and `with_inner_tray_icon`,
which has no Ruby meaning (plan 043, decision 11). TODO 002 names the
first two as the next tray work.

They turn out to be two different sizes. `cleanup_before_exit` is a
dozen lines of Tauri that Tokra now ports one step of, and it can land
whole now. The config's tray is a dozen lines too, but it reads a
`Config` and a `Context` that Tokra does not have: Tokra reads no
configuration file, its `Config` has three fields that nothing sets, and
it has no `Context` to carry the icon Tauri's codegen decodes. So this plan
ports `cleanup_before_exit` (part A) and specifies the config's tray in
full (part B), to be built once a Config and Context plan exists. The
question that plan has to settle goes to the maintainer at the end.

The page's `@tauri-apps/api/tray` commands are not part of this phase:
plan 043 ported all eleven (`new`, `get_by_id`, `remove_by_id`, and the
eight setters; `lib/tokra/tray/plugin.rb:57-70`), with the page fixture
driving them through the vendored API.

## Decisions

### Part A: `cleanup_before_exit`

1. **`App#cleanup_before_exit` and `AppHandle#cleanup_before_exit` are
   public, and replace `cleanup_trays`.** Tauri generates the method on
   both through `shared_app_impl!`, and documents it for apps that run
   their own loop and for code that ends the process itself. `App`
   delegates to its handle, as its other shared methods do. The RDoc
   ports Tauri's warning nearly word for word: exit right after it
   returns, and call nothing else of Tokra's. It returns `nil`.
   `cleanup_trays` goes; `TrayManager#close_all` stays as step 1 and 2's
   tray half.

2. **The steps run in Tauri's order, and the tables are cleared without
   `close`.** First every tray leaves the system tray and the icons list
   empties (`close_all`, unchanged). Then the app's resources table is
   cleared, then for each window its table is cleared and, on Windows, the
   window hidden, then each webview's table is cleared. `clear` drops
   references and calls no `close`, as Tauri's does (`resources/mod.rs:218-222`).
   In Tauri the clear itself is what drops a tray, through its last
   clone; in Ruby a dropped reference frees nothing until the collector
   runs, so trays are closed first, as plan 043 decision 6 and 7 already
   do. That stays the only resource closed: the other resources Tauri
   drops here (images, menus, plugin resources) have no visible effect
   when dropped (`menu/mod.rs:96-105` only frees the muda object on the
   main thread), and Ruby's collector frees them later, on their own
   thread, or leaks them when it runs on another, since `ThreadBound`
   forgets a platform object dropped off its thread
   (`ext/tokra/src/thread_bound.rs:116-126`). The
   observable change is that a rid stops resolving: `resources_table.has?`
   answers `false` and a later `get` raises `Error::BadResourceId`.
   Trays leave before the tables clear, so a menu that only a webview's
   table held cannot be freed while a tray still points at it.

3. **On Windows each window is hidden, and a failure is ignored.** Tauri
   hides each window to stop the white flash a closing WebView2 window
   shows (`6c047aee1`). Tokra calls `Window#hide` for each window in
   `AppHandle#windows`, only when `Menu.os` is `:windows` (Tauri's
   `cfg(windows)`; `Menu.os` is the helper `App` already uses for
   `cfg(target_os)`), and rescues `Tokra::Error`, as Tauri's `let _ =`
   drops the result. On the main thread `Window#hide` runs at once, as
   `send_user_message` runs a message inline there
   (`tauri-runtime-wry lib.rs:234-247`); off it, with the loop gone, it
   raises `Error::Runtime`, which is ignored; a closed native window
   ignores the setter (plan 038, decision 3). The hide runs inside tao's
   `LoopDestroyed` handler, as Tauri's does. Hiding sends the window
   messages synchronously; tao's window procedure hands each to
   `send_event`, which buffers it because the handler is taken
   (`runner.rs:143-148`, `:208-227`), and the buffer is never dispatched
   after `LoopDestroyed` (`event_loop.rs:284-288`; `reset_runner` leaves
   the handler unset, `runner.rs:95-110`). So nothing re-enters tao or
   Ruby; this is the path Tauri takes on the same tao.

4. **Every caller of `cleanup_trays` calls `cleanup_before_exit`.** The
   five places already match Tauri's: `AppHandle#exit` once the loop has
   ended (`:531-538`), `#restart` on the main thread and when its request
   fails (`:546-570`), `#request_restart` when its request fails
   (`:573-582`), and `App` after the run callback hears `RunEvent::Exit`,
   before a requested restart (`:1304-1311`). The last stays inside
   `reporting`, so a raise in one step does not keep the restart from
   following.

5. **It can run twice.** Tauri's callers all end the process, so it runs
   once. In Tokra `restart` on the main thread raises `SystemExit` from
   inside a handler, and the loop's `LoopDestroyed` still follows it
   (`AppHandle#restart`'s RDoc, `lib/tokra/app_handle.rb:446-452`), so
   the cleanup runs again. That `RunEvent::Exit` therefore runs after
   `cleanup_before_exit`, so its handlers find the app's, windows', and
   webviews' resource tables empty (and on Windows the windows hidden);
   Tauri never reaches that state, because its `process::restart` never
   returns (`app.rs:546-550`). Each step is a no-op on
   an empty manager and empty tables, and a second hide is harmless; a
   test calls it twice.

   No Rust changes: every step calls a native method plan 038 or 043
   already binds, and nothing new is stored on the native side, so no
   Ruby value enters a Rust collection.

### Part B: the config's `trayIcon` (once Config and Context exist)

These record what Tauri does so the Config and Context plan can port it
without reading it again. Nothing here is built until that plan lands
(decision 6).

6. **Part B waits for a configuration source.** Tauri's tray comes from
   `config.app.tray_icon`, and its icon from `Context::tray_icon`, which
   codegen fills by decoding `iconPath` at compile time
   (`context.rs:291-300`). Tokra reads no configuration file: `Config` is
   `Data.define(:identifier, :product_name, :version)` built from the
   builder's window hash (`lib/tokra/app.rb:172-176`), and the builder has
   no method that sets any of the three. Porting `TrayIconConfig` alone
   would add a struct nothing can fill, which is code only tests can
   reach (lessons, "Testing"). Inventing a builder method for it would
   break Tauri fidelity, which has none. And ADR 004 (Tokra loads
   configuration "from standard locations (or accept a config hash)")
   and ADR 006 §6 (`tokra.conf.json`) leave open which file, which schema,
   and how the decoded icon travels; the same decision decides
   `app.windows`, `identifier`, `bundle.icon`, and plugin configuration.
   That needs its own plan, and the maintainer (question 1).

7. **The config's struct and its parsing follow serde's derive.**
   `TrayIconConfig` has `id: String?`, `icon_path` (required),
   `icon_as_template` (default `false`), `menu_on_left_click` (default
   `true`, deprecated since 2.2.0), `show_menu_on_left_click` (default
   `true`), `title: String?`, `tooltip: String?`. Keys are camelCase, each
   has a kebab-case alias (`icon-path`, `icon-as-template`,
   `menu-on-left-click`, `show-menu-on-left-click`), and unknown keys are
   refused (`deny_unknown_fields`). serde's error texts for a missing
   `iconPath` and an unknown key, and whether its expected-fields list
   names the aliases, are UNVERIFIED here; the Config plan reads them from
   the serde Tauri locks. A `Data.define` value object, per AGENTS.md.

8. **The icon is decoded as codegen decodes it, not as `Image.from_path`
   does.** Codegen joins `iconPath` to the config file's directory, not
   the working directory, and picks the decoder by extension: `.png` or
   `.ico`, anything else an `InvalidImageExtension` error
   (`image.rs:29-38`). A PNG goes through png 0.17.16 with no
   transformations and must be RGBA, or codegen stops with "icon {path}
   is not RGBA" (`image.rs:74-99`); since the decoder's transformations
   are `IDENTITY` (`decoder/mod.rs:126-139`, `:563-569`), a 16-bit RGBA
   PNG passes the check with eight bytes a pixel. An ICO takes the
   directory's first entry through ico 0.5.0 (`image.rs:50-72`), where
   `Image.from_path`'s image crate takes the entry with the most bits per
   pixel and then the largest area (`ico/decoder.rs:194-213`) and
   converts any PNG to RGBA (`image/mod.rs:76-89`). Tokra has png 0.17.16
   in its lock already (through tray-icon) and no `ico`; the Config plan
   either adds ico 0.5.0, the version Tauri locks, or records the
   deviation. The decoder returns a Ruby String built after decoding, so
   no Ruby value sits in a Rust buffer. Codegen's failures are compile
   errors; Tokra raises when the configuration is read, before any
   window exists, with codegen's texts.

9. **The tray is built where Tauri builds it, and only the app's
   listeners hear it.** Tauri builds it in `Builder::build`, after the
   core plugins (`:2247`) and before `initialize_plugins` (`:2289`), so
   before the setup hook and before any configured window (`setup`
   creates those at `Ready`, `:2370-2375`); on the main thread, where
   `run_on_main_thread` runs inline. Tokra builds trays only once the
   event loop exists (plan 043, decision 3), so the build goes in
   `App#run` right after `install_app_menu` and before the setup hook,
   which keeps Tauri's order: app menu, tray, setup, main window. The
   builder is `TrayIconBuilder.with_id(id || "main")`, then
   `menu_on_left_click`, then `show_menu_on_left_click`, then the icon if
   the Context has one, then `title` and `tooltip` if set, then `build`.
   The tray gets no menu, no menu listener, and no listener of its own:
   its events reach the app's `on_tray_icon_event` listeners, plugins,
   and the run callback (plan 043, decision 4), and the app reaches the
   tray through `tray_by_id("main")`. It sits in the app's resources
   table, so the page reaches it too through `TrayIcon.getById("main")`.
   A build that raises ends `App#run`, as `Builder::build` returns the
   error.

10. **Tauri's quirks are kept.** Both left-click flags set tray-icon's
    one `menu_on_left_click` (`tray/mod.rs:300-324`), and the build sets
    the deprecated one first, so `showMenuOnLeftClick` (default `true`)
    always wins and `"menuOnLeftClick": false` alone changes nothing. An
    icon tray-icon refuses is dropped and the tray is built without one
    (`tray/mod.rs:251-257`). A `Context` whose icon was set to `nil` gives
    a tray with no icon. The default id `"main"` still takes one number
    from tray-icon's counter, since `with_id` starts from `new`
    (`tray/mod.rs:229-233`), as Tokra's `with_id` already does.

## Results

Part A is done. Part B is deferred, not built: Tokra has no
configuration source and no `Context` for the config's tray to come
from, and where they come from is the maintainer's decision (decision 6,
question 1). TODO 002 carries it as the remaining tray work.

Each test was run before the code existed and seen to fail. In
`test/test_cleanup_before_exit.rb` six tests raised `NoMethodError`
(`undefined method 'cleanup_before_exit'` for `AppHandle`, and for
`App`), and the loop's-end test failed on its window table still holding
its rid, since the loop called only `cleanup_trays`. Each of the four
`test/tray/test_tray_exit_paths.rb` tests failed on its
`refute @handle.resources_table.has?(rid)`, and the Exit test in
`test/tray/test_tray.rb` failed on the same refutation after `run`.

With the code in, each mutation the plan lists was made by hand and
turned a test red: moving `close_all` after the window loop (the order
test, and four more that assert a cleared table); dropping the
`Menu.os` check, and inverting it (the platform test and the
twice-called test); dropping the rescue (the failed-hide test raised
`Error::Runtime` from its thread); dropping the app table's clear (three
cleanup tests, all four exit-path tests, the Exit test); dropping the
window's or the webview's clear (the loop's-end test, and the failed-hide
test for the webview); closing each resource before the clear (the
app-table test); emptying `App#cleanup_before_exit` (the delegation
test); and calling the cleanup before the run callback's Exit (the Exit
test).

Three tests from earlier plans read the main webview's table after
`App#run` returned, to find the rid `plugin:image|new` stored
(`test/builder/test_plugin_routing.rb`, `test_ipc_response.rb`,
`test_ipc_protocol.rb`). The cleanup now empties that table as the loop
ends, which is the first risk below meeting the suite; each now reads it
when the run callback hears `RunEvent::Exit`, before the cleanup, as a
Tauri app would.

The integration test passes on macOS before and after the change, as it
expects `VISIBLE true` there; it can fail only on Windows, in CI. To
prove the line reads the window's real state after the cleanup, the
platform check was dropped by hand so the macOS window was hidden too,
and the test failed with `Expected: "VISIBLE true"`, `Actual: "VISIBLE
false"`.

The review of the plan's citations against `vendor/tauri` (`9f0306fbc`)
and tao 0.34.5 found them right but for three: `Window::hide` is at
`window/mod.rs:1774-1776`, not `:1775-1777`; `Config` is built at
`lib/tokra/app.rb:172-176` once `App#cleanup_before_exit` sits above it;
and decision 2 said `ThreadBound` frees a platform object later on its
own thread, where it leaks one dropped on any other
(`thread_bound.rs:116-126`). The plan now says each. The tao analysis in
decision 3 holds: `loop_destroyed` runs the handler through
`call_event_handler`, which takes it, so `send_event` buffers what the
hide causes, and `reset_runner` follows without dispatching the buffer.
Tokra's own Windows subclass procedures (`undecorated_resizing.rs`,
muda's) call no Ruby. No Rust change was needed.

## Out of scope

  002). tray-icon attaches a tray menu's subclass to its window
  (`tray-icon platform_impl/windows/mod.rs:133`, `:176-179`), a Submenu's

  muda's procedure reads that pointer as a `Menu` for `WM_NCACTIVATE` and

  tray-icon calls `SetForegroundWindow` on its window before the menu
  shows (`:512`). The page can reach it through `plugin:tray|set_menu`

  next tray-adjacent Windows work.
- A thread-safe `ResourceTable`: Tauri's tables sit behind a `Mutex`;
  Tokra's do not, so `cleanup_before_exit` from another thread while the
  loop runs races with plugin commands, as any table use from two
  threads already does.
- `with_inner_tray_icon` (plan 043, decision 11).

## Risks

- An app that kept a rid from the app's, a window's, or a webview's table
  and reads it after `RunEvent::Exit` now gets `Error::BadResourceId`.
  That is Tauri's behavior, and the RDoc says to call nothing after the
  cleanup.
- Hiding runs inside tao's `LoopDestroyed` on Windows. The analysis in
  decision 3 says the messages it causes are buffered and dropped; if a
  WebView2 handler answered one by calling back into Ruby, that would be
  a re-entry. None does today: Tokra's own WebView2 focus handlers only
  send a `UserEvent` through the proxy (`ext/tokra/src/webview_focus.rs:43-75`),
  which posts a message no one reads after the loop. The fixture's run
  in CI is the check.
- Clearing the tables lets the collector free menus earlier than
  before. Windows' menu bars are held by their windows (plan 043,
  `WindowMenus`), and trays leave first (decision 2), so no native
  callback should be left pointing at a freed menu; `rake test:replay`
  under cdb in Windows CI is the check.

## Questions for the maintainer

1. **Where does a Tokra app's configuration come from?** Part B, and
   with it `app.windows`, `identifier`, `bundle.icon`, and plugin
   configuration, needs a configuration source and a `Context` to carry
   decoded icons. ADR 004 says Tokra loads configuration "from standard
   locations (or accept a config hash)"; ADR 006 §6 names
   `tokra.conf.json` with Tauri's `plugins` key; Tauri fidelity would read
   `tauri.conf.json` with Tauri's schema. Which file name (or both), and
   whether `Builder#build` takes a `Context` as Tauri's takes one from
   `generate_context!`, decides the Config and Context plan, which Part B
   then follows. The recommendation is Tauri's schema under the file name
   you choose, loaded into a ported `Context`, with codegen's icon
   decoding (decision 8), in its own plan before Part B.
2. **Does ico 0.5.0 join the extension** so the config's ICO icon picks
   the first entry as codegen does, or is the image crate's choice of the
   best entry an acceptable, recorded deviation? Only matters once
   question 1 is answered.
