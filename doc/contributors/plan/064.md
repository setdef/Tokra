# Plan 064: Plugins register and configure the Tauri way

## Interfaces this changes

Other work rebases over these. Each is in `lib/` unless it names a
plugin.

| Interface | Before | After |
|---|---|---|
| `Tokra::Builder#plugin(plugin)` | none | registers `plugin` before the app exists; `App#run` initializes it with its `config.plugins` slice after the menu and the config tray, before the config windows and the setup hook; returns the builder |
| `AppHandle#plugin(plugin)` | registers; returns whether a same-named plugin was replaced | initializes `plugin` with its slice, then registers it; returns `nil`; raises `Error::PluginInitialization` and leaves the store as it was when initialization fails |
| `Tokra::Plugin` | the constructor is setup (`initialize(app, config = {})`) | the constructor's `app` is optional; new hooks `initialize_plugin(app, config)` (Tauri's `Plugin::initialize`), `initialization_script_2`, and `drop`; an existing subclass built with the handle keeps working |
| `PluginStore#initialization_script` | Strings | `[script, for_main_frame_only]` pairs, the form `WebviewBuilder#initialization_scripts` already uses |
| `PluginStore` | `register`, `unregister`, hooks | adds `initialize_plugin(plugin, app, config)` and `initialize_all(app, config)`; `register` and `unregister` call `drop` on the plugin they let go |
| `WebviewManager#initialization_scripts` | Strings | pairs; the global API scripts come from the context, not from `config.app.withGlobalTauri` |
| `Tokra::Context.new` | five keywords | adds `plugin_global_api_scripts:` (default `nil`) |
| `Tokra::AppManager` | 11 members | adds `plugin_global_api_scripts` (default `nil`) |
| `Tokra::Plugin::Builder`, `Tokra::Plugin::TauriPlugin`, `Tokra::Plugin::BuilderError` | none | new |
| `Tokra::PluginApi` | `config` a Hash with Symbol keys | `config` the plugin's slice, deserialized |
| `Tokra::Utils::Plugin` | none | `define_global_api_script_path(path)`, `global_api_script_paths`, `read_global_api_scripts` |
| `Tokra::Ipc::Serde.unit` | none | serde's unit visitor |
| `tokra-dialog`, `tokra-notification` | `Plugins::X::Plugin.new(handle)` | `Plugins::X.init`, registered with `Builder#plugin`; the `Plugin` classes go |
| `tokra-clipboard`, `tokra-global-shortcut` | `Plugin.new(handle)`, global-shortcut's `Builder#build(handle)` | unchanged for now; they still register with `AppHandle#plugin` (State, next steps) |
| `tokra-log` | `Log::Builder#build` | unchanged; registered with `Builder#plugin`; refuses a non-null `plugins.log` |

The core plugins `App.new` registers (`Event::Plugin.new(@handle)` and
the rest) keep their form: `AppHandle#plugin` now also calls their
`initialize_plugin`, whose default only records the handle and config.

## Context

An inventory of what Tokra lacks (`road-to-1` branch,
`doc/contributors/research/2026-11-13-road-to-1.0.md`, rows C-02, C-37,
C-41, CF-20) says plugins cannot be configured or registered the Tauri
way. The code agrees. `Tokra::Builder` has no `plugin`. A plugin's
setup is its constructor (plan 013, decision 2; plan 025, decision 2),
so it cannot exist before the app, and every first-party plugin's RDoc
builds the app, constructs the plugin with `app.handle`, and registers it
before `App#run` (plan 052, decision b1). No plugin reads
`config.plugins` (plan 054, decision 20, deferred here). No plugin ships
its global API script: `WebviewManager#initialization_scripts` appends
only Tauri's own `bundle.global.js`, and says so
(`webview_manager.rb:156-158`), so a page with `withGlobalTauri` has
`window.__TAURI__` but no `window.__TAURI__.dialog`. The plugins'
real-window fixtures vendor each plugin's `api-iife.js` and load it with a
script tag to make up for it.

Of the hooks `Tokra::Plugin` documents, all but one are called:
`window_created` (`window_manager.rb:50`), `webview_created`
(`webview_manager.rb:133`), `on_page_load` (`app.rb:1223`), `on_event`
(`app.rb:556`), `extend_api` (`app.rb:864`), and
`initialization_script` (`webview_manager.rb:166`). `on_navigation`
(`plugin.rb:66-77`) is called nowhere.

Sources: vendor/tauri `9f0306fbc`; tauri-apps/plugins-workspace
`d4613ff0`; serde 1.0.228 and serde_json 1.0.145, the versions Tauri's
`Cargo.lock` pins.

## Decisions

1. **Tauri's `Plugin::initialize` is `Plugin#initialize_plugin`.**
   Ruby's `initialize` is the constructor: `new` calls it, and it is
   always private. A plugin that `Builder#plugin` takes exists before the
   app, so its setup cannot be its constructor, as plans 013 and 025 made
   it. Precedence 1 renames the hook. `initialize_plugin` keeps Tauri's
   word, and reads like Ruby's own later-initialization hooks
   (`initialize_copy`, `initialize_dup`). `PluginStore::initialize` is
   `PluginStore#initialize_plugin` for the same reason, and
   `initialize_all` keeps its name. The rejected options:
   re-running the constructor through `__send__(:initialize, ...)` (the
   former ADR 006 §6.2's sketch), which runs a constructor twice;
   `setup`, which Tauri uses for the builder's closure; and `init`, which
   Tauri uses for a plugin crate's constructor function.

   The hook's default records the handle and config for the `app` and
   `config` readers that `Tokra::Plugin` has always given subclasses,
   where Tauri's default does nothing: the readers are Tokra's, not
   Tauri's, and without this a subclass registered with `Builder#plugin`
   would have no app. The constructor's `app` becomes optional, so a
   subclass built with the handle, as every core plugin is, still works.
   The hook raises to fail; the store wraps any `StandardError` in
   `Error::PluginInitialization` with the plugin's name and the error's
   message, as `plugin.rs:1009` maps the error's `to_string`.

2. **`plugin::Builder` and `TauriPlugin` nest under `Tokra::Plugin`.**
   Tauri's module `tauri::plugin` holds the trait `Plugin`, `Builder`,
   `TauriPlugin`, `PluginApi`, and `BuilderError`. Tokra's class
   `Tokra::Plugin` already stands for both the module and the trait, so
   the rest nest under it: `Tokra::Plugin::Builder`,
   `Tokra::Plugin::TauriPlugin` (a subclass of `Tokra::Plugin`), and
   `Tokra::Plugin::BuilderError` with its variant `ReservedName`.
   `PluginApi` stays `Tokra::PluginApi` where it is. The builder's
   methods return the builder, as `Tokra::Builder`'s do, where Rust's
   consume and return it. `build` raises what `try_build` raises, since
   a panic in Ruby is a raise. A method that takes a block raises
   `ArgumentError` without one, as the global-shortcut builder's
   `with_handler` does.

3. **A config type is an object that deserializes.** Tauri's `Builder<R,
   C>` reads the slice with `serde_json::from_value::<C>`. Ruby has no
   type parameters, so `Builder.new(name, config: type)` takes any object
   that answers `deserialize(json_value)` and raises
   `Ipc::CommandItem::Mismatch` with serde's words, which is how every
   Tokra type Tauri deserializes already reads JSON. With no `config:`,
   the type is `()`, read by the new `Ipc::Serde.unit`: `nil` for null,
   and "invalid type: {unexpected}, expected unit" otherwise. The message
   that wraps it reads "Error deserializing 'plugins.{name}' within your
   Tokra configuration: {err}", Tauri's words with the brand renamed, as
   the config's design (`design/config.md`, "File names") renames every
   message that names the framework's config.

4. **Plugin blocks need not be Ractor-shareable.** `Tokra::Builder`
   refuses a block that is not, because the app's hooks may one day run
   in a worker Ractor (the former ADR 001 (now ADR 020)). A plugin lives in the plugin store, on
   the main Ractor, as every `Tokra::Plugin` subclass and its state
   already does, and the first-party plugins' blocks close over
   unshareable state (the global-shortcut handler). Tauri asks `Send` of
   them, and `Sync` of `invoke_handler` only; requiring shareability here
   would refuse plugins that work today.

5. **`App#run` initializes the builder's plugins where `Builder::build`
   does.** Tokra builds the event loop, the menu, and the config tray in
   `App#run`, because they need tao's loop (plans 041, 042, 043), so
   `App#run` does the rest of Tauri's `Builder::build` too: after the
   config tray, before the Rack adapter, the config windows, and the
   setup hook. A plugin's setup therefore finds the app's tray, and its
   `on_window_ready` hears `main`. `App.new` puts the builder's plugins
   in the app's store first and registers the core plugins after them,
   as Tauri's order is. Tauri's `initialize_all` initializes every
   plugin, the core plugins a second time; their setups have run and
   been taken, so the second time does nothing. Tokra's builds and runs
   in two steps, and an app may add a plugin with `AppHandle#plugin`
   between them, which Tauri has no time for. So `initialize_all`
   initializes every plugin not yet initialized, in store order, which
   is what Tauri's does to every plugin it has not yet initialized.

6. **`drop` is Rust's `Drop`, called by the store.** Ruby frees an object
   when it chooses and calls no destructor that sees it. Tauri drops a
   plugin at three points the store controls: when `unregister` removes
   it, when `register` replaces it, and when `AppHandle::plugin` fails to
   initialize it. `Tokra::Plugin#drop` is a hook the store calls at those
   points, doing nothing by default. `TauriPlugin#drop` runs `on_drop`
   with the app once, and only if the plugin was initialized, as its
   `Drop` does. Tauri also drops every plugin when `Builder::build`
   fails, with the `App`; Ruby keeps the `App` a failed `App#run` leaves,
   so Tokra does not (deviation, tier 1). A Tauri app that ends through
   `run` exits the process without dropping its plugins, and so does a
   Tokra app.

7. **A plugin gem names its global script when it is required.** Tauri
   collects the scripts of the crates an app links, when it compiles;
   what a Tokra app links is what it requires. A plugin's main file calls
   `Tokra::Utils::Plugin.define_global_api_script_path(path)`, the
   tauri-utils function that tauri-plugin's build `Builder` calls. Tokra
   does not port tauri-plugin's build `Builder`, whose other work is the
   ACL. The paths are canonicalized with `File.realpath`, and a missing
   file raises "failed to canonicalize global API script path: {e}",
   Tauri's panic message with Rust's `io::Error` text. A gem required
   twice names its path once, as each crate has one key. Tauri's own
   bundle comes first, as `save_global_api_scripts_paths` inserts it;
   the plugins follow in the order their gems were required, where
   Tauri's follow the order its build sees its dependencies, which no
   app chooses. Each plugin's script only defines its own
   `window.__TAURI__` member, so the order among them does not matter.
   `Tokra.generate_context` reads them when the config sets
   `withGlobalTauri`, so require the plugins first, as an app does at
   the top of its file.

8. **The vendored scripts are upstream's files, unchanged.** Each plugin
   ships `lib/tokra/plugins/<name>/api-iife.js`, copied byte for byte
   from plugins-workspace `d4613ff0`'s `plugins/<name>/api-iife.js`,
   which the plugin's rollup build produces and the repository commits,
   with a `.license` file naming the source, as the dialog and
   notification plugins already ship `init-iife.js`. The real-window
   fixtures stop vendoring their copies and stop loading them: the page
   now gets the script from the plugin, and a second copy would throw,
   since each defines a property that cannot be redefined.

9. **`on_navigation` waits for plan 052e-4.** Calling it needs wry's
   navigation handler, which answers synchronously from inside the
   webview, and Tokra's native layer registers none (`ext/tokra/src/
   webview.rs` has no `with_navigation_handler`). Plan 052e-4 ports it
   with the builder's `on_navigation` and the store's
   `PluginStore::on_navigation` (`plugin.rs:952-962`), which it then
   calls. This plan ports `plugin::Builder#on_navigation` and
   `TauriPlugin#on_navigation`, so the plugin side is ready, and leaves
   `PluginStore#on_navigation` to the plan that calls it.

10. **Plugin URI scheme protocols register on the webview manager.**
    Tauri registers a plugin's protocols on the app's webview manager at
    initialize, after its setup and only if the setup succeeded, and each
    webview registers every scheme with wry (`plugin.rs:793-815`). When
    this plan was written Tokra's webview registered only `tokra` and
    `ipc`, so a plugin's scheme would never have been asked. Plan 067
    landed while this one was under way and gave
    `WebviewManager#register_uri_scheme_protocol(scheme, handler)`, and
    `plugin::Builder#register_uri_scheme_protocol` and
    `#register_asynchronous_uri_scheme_protocol` then landed as a
    follow-up: the synchronous block is wrapped to answer its responder,
    as `Tokra::Builder#register_uri_scheme_protocol` wraps the app's, and
    neither block need be Ractor-shareable (decision 4). The builder's
    plugins initialize after `App.new` holds the app's own schemes, so a
    plugin's scheme replaces the app's of the same name, as Tauri's map
    insert does.

11. **The first-party plugins take Tauri's entry points, and their
    `Plugin` classes go.** Tauri's clipboard-manager, dialog, and
    notification crates export `init()`, and global-shortcut and log a
    `Builder` whose `build()` takes no app; none exports a plugin type.
    `Tokra::Plugins::Dialog.init` and `Notification.init` build a
    `TauriPlugin` with Tauri's name, invoke handler, init script, and
    setup; `Clipboard.init` and a `GlobalShortcut::Builder#build` that
    takes no app are to follow the same way (State). The `Plugin` classes existed because setup was
    construction; precedence 2 (class structure) rules out keeping them
    beside `init`, and keeping them would keep every hook twice. They are
    unreleased (`v0.0.1.pre.2` has no plugins), so the CHANGELOG's
    entries for them are rewritten, as AGENTS.md says of a change undone
    before its tag. Their constants (`COMMANDS`, `INIT_SCRIPT`) move to
    the plugin's module. When clipboard moves, the Ruby methods
    `Clipboard::Plugin` has (`read_text` and the rest) stay only on the
    managed `Clipboard`, as in Tauri, reached as `app.clipboard`.

    The log plugin is mid-port in plan 065, whose `Log::Plugin` is also
    the logger the app calls. This plan changes only how it registers:
    it is built without the app already, `Builder#plugin` takes it, it
    refuses a non-null `plugins.log` as Tauri's `()` config does, and it
    ships its global script. Making `Log::Builder#build` return a
    `TauriPlugin` whose setup acquires the logger with the app handle,
    as Tauri's does, so that `Builder#app_handle` and `#path_resolver`
    can go, is plan 065's.

12. **The global scripts come from the context.** `WebviewManager` used
    to append Tauri's bundle when the config set `withGlobalTauri`. Now
    codegen reads the scripts into the `Context` and the manager runs
    what the context holds, so changing the config with `Context#config=`
    after `Tokra.generate_context` no longer adds or removes them, as
    changing it with `config_mut` does nothing in Tauri. `Context.new`
    takes `plugin_global_api_scripts:` with a `nil` default, where
    Tauri's `Context::new` requires it, so the callers that predate it
    keep working; a `nil` is Tauri's `None`.

## Verification

Each behavior has a test on a real `Tokra::App` built on `StubNative`
(`test/support/test_app.rb`), and each test was seen to fail with its
line reverted. The plugin tests run with each plugin's own `rake test`,
except clipboard's, whose every test writes the clipboard and so is
written and not run here. The real-window fixtures change (decision 8)
and are not run here. Both lists are in the state section below.

## Out of scope

- `on_navigation`'s call site (decision 9).
- `PluginApi#scope` and the plugins' permissions: the capabilities plan.
- `Log::Builder#build` returning a `TauriPlugin`: plan 065.
- Moving the core plugins onto `Plugin::Builder`: they keep their
  subclass form, which the path plugin's plan also uses.

## Risks

- A plugin whose gem is required after `Tokra.generate_context` misses
  `window.__TAURI__.<name>`. The RDoc of `define_global_api_script_path`
  and each README say to require first.
- Other branches register plugins with `AppHandle#plugin` and read its
  old boolean. None in `lib/` or `plugins/` reads it today.
