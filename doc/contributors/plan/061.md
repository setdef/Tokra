# Plan 061: The gate runs where you run it, before a push

Two parts of Tokra's gate worked only on the maintainer's Mac.

Plans 056 and 057 sent the real-window tests to a hidden macOS account,
`tokratest`, through scripts in another project's checkout under the
maintainer's home. On any other Mac the gate stopped at "no hidden-run",
until you learned to set `TOKRA_REAL_WINDOWS=local`. The repository held
one person's account name, home paths, and machine setup.

The commit hook ran the whole gate. A commit took as long as the gate
does and opened every real window, so the only practical unit of work was
one large commit a session, which is the opposite of small steps on a
trunk.

The maintainer's decision, on 2026-11-13: the repository carries nothing
of anyone's own machines, the `tokratest` account goes, and Tokra works
trunk-based. This plan makes the gate an ordinary one, which anyone who
clones Tokra runs the same way, and moves it from each commit to each
push.

## Real-window tests run in the session that runs them

`rake test:gui` runs `test:keyboard`, `test:real_windows`,
`test:real_windows:plugins`, and then `test:console`, on every system,
as CI always has. `RealWindows.where`, `TOKRA_REAL_WINDOWS`, `HiddenJob`,
`test:hidden`, `test:hidden:prune`, and the `test:here` guard are gone,
with their tests.

What Plan 056 built to keep stray windows away stays, since it never
depended on the account:

- The file rule and `RealWindows::NAMED` still sort the real-window tests
  from the rest, so `test:core`, `plugins:test`, and a plugin's own
  `rake test` open no window, write no clipboard, and take no hotkey.
- The tripwire still fails a real-window test outside the tasks that set
  `TOKRA_REAL_WINDOWS_RUN`.

So someone who wants no window on the desktop they are working at runs
`test:core` and `plugins:test` there, and the gate on another machine or
in CI. That arrangement is theirs, and stays out of the repository.

`LinuxGate` named each checkout with `HiddenJob.slug`; the method is now
`LinuxGate.slug`, with its test.

## The console set keeps its span

Plan 057 gave `RealWindows::CONSOLE` two reasons. One is gone: off the
console, macOS starved the dialog fixture's page, so the set ran in the
maintainer's session. The other, from that plan's amendment, stands: a
click on one of those tests' dialog sheets ends it, so they run inside
one spoken span that holds the desktop input lock, apart from the
plugins' other real-window tests. `test:console` and the set stay as
they are, and a file joins the set when a person's click could fail it.

The name is now only history. Renaming it is a later change, if it is
worth one.

## The gate runs before a push

`.githooks/pre-push` runs `bundle exec rake` when a push moves a branch.
It reads the remote side of each line git gives it, which is always a
full ref, and skips tags and deletions. The gate tests the working tree,
so the hook refuses a push unless every branch in it gets the commit that
is checked out, with nothing uncommitted and nothing untracked. Untracked
files count because the tests and the compiler read them: a file you
forgot to add would pass here and be missing on CI. An ignored file does
not count.

On Linux it runs the gate as ci.yml does, under `xvfb-run` and
`dbus-run-session`, and a test pins both commands to ci.yml's. It also
unsets `WAYLAND_DISPLAY` and sets `GDK_BACKEND=x11`, since GTK takes a
Wayland desktop before the X display `xvfb-run` gives it, and the gate's
windows would open there.

From a worktree, git hands a hook `GIT_DIR`. The hook unsets it and its
kin once it has found the working tree, or every git the gate runs would
act on that worktree, the ones in tests that make repositories of their
own included.

`bin/setup` writes a stub into the clone's shared hooks folder that runs
the hook from whichever worktree pushes. It writes the stub only where
none exists or the one there is its own, by a marker line, so a hook you
keep there yourself survives. `.pre-commit-config.yaml` keeps the
`bundle check` and loses the gate.

`bin/setup` is now safe to run again and again, asks nothing, and runs no
sudo, so a CI runner or a build machine can run it before every check.
With `CI=true` it installs the bundle as ci.yml does, frozen into
`vendor/bundle`, and skips the commit hook and the RDoc build.

Where `core.hooksPath` is set, git runs the hooks in that folder and
never the clone's own. `bin/setup` still writes the stub, and says what
follows: a push runs the gate only if the pre-push hook in that folder
hands off to the stub, and pre-commit, which refuses to install there,
is left out.

AGENTS.md's "Committing" now describes small commits on `trunk`, each
complete, with the gate before the push. The `commit-session` skill
follows it.

- Plan 057: "Routing", and evidence of starvation as the test for joining
  the console set.
- Plan 060: the twenty runs under load in step 3, and step 4. Steps 1 and

  before one that could behave differently on Linux.

## Tests

`test/tasks/test_pre_push_hook.rb` drives the real hook in a real
repository, with stand-ins for `bundle` and `xvfb-run`: a branch that
moves to the checked-out commit runs the gate, by any local name; a tag, a
deletion, and an empty push do not; another commit, in any line of the
push, uncommitted changes, staged or not, and an untracked file are
refused before the gate; an ignored file is not; and a gate that fails
fails the push with its status. One test pushes for real from a worktree
to a bare repository, so the hook gets the environment git gives it, and
checks that the gate's command inherits no `GIT_DIR`. On Linux another
checks that the gate is kept off a Wayland desktop. The last checks that
git tracks the hook as executable.

`test/tasks/test_setup.rb` runs the real `bin/setup` in a real
repository with a stand-in `mise`: what it installs for a person, for a
CI runner, and where `core.hooksPath` is set, with what it says there;
that it checks out an empty submodule; that its stub runs the hook of
whichever worktree pushes, and lands in the clone's shared hooks folder
when a worktree runs the script; that it replaces an earlier stub of its
own, makes the hooks folder when there is none, and leaves a hook that
is not its own, even one that quotes the marker. One test goes the whole
way: `bin/setup`'s stub, the hook as shipped, and a real `git push`,
whose refs reach the hook only through the stub's standard input. It
also holds the REUSE tool's version to ci.yml's.

`test/tasks/test_real_windows.rb` checks that `test:gui` runs the four
tasks in order, whatever `CI` and the old `TOKRA_REAL_WINDOWS` say, and
keeps its tests of the file rule, the tripwire, and the console span.
`test/tasks/test_linux_gate.rb` takes over the test of the slug.

## Windows, written but not yet run there

A Windows contributor, or a runner that runs `bin/setup.ps1` before the
hook, now gets the state CI's Windows job builds in. None of it has yet
run on Windows: see "Where it stands" below.

`bin/setup.ps1` does only what PowerShell has to. It runs `mise install`,
asks RubyInstaller's Ruby where its MSYS2 is
(`RubyInstaller::Runtime.msys2_installation`), checks that MSYS2 has its
UCRT64 compiler, and runs `bin/setup` in that MSYS2's bash with
`MSYSTEM=UCRT64`. A missing MSYS2 or compiler is named, with
RubyInstaller's own `ridk install` command, and never installed from an
unpinned download. It needs no administrator rights and asks nothing.

`bin/setup` tells Windows by `OS=Windows_NT`, which Windows sets for every
process. A stand-in `uname` would do for the hook, but in `bin/setup`'s
tests it also misleads git's own `git-sh-setup`. On Windows it adds Rust's
GNU host toolchain of mise.toml's Rust, with ci.yml's components, and the
libclang wheel from PyPI (`libclang==18.1.1`, whose `clang/native/`
holds `libclang.dll`), into mise's Python as the REUSE tool is. It
installs the bundle through `bin/windows-env`, and installs no commit
hook.

`bin/windows-env` runs a command with what CI's Windows steps set:
`RUSTUP_TOOLCHAIN` for the GNU host toolchain, which rb-sys needs for
RubyInstaller's MinGW Ruby, and `BINDGEN_EXTRA_CLANG_ARGS` and
`LIBCLANG_PATH`, at Ruby's MSYS2 (`msys_path` and `mingw_prefix`) and the
wheel's libclang. It works them out each time rather than reading a file
setup wrote, which a cleaned checkout or a moved MSYS2 would leave stale,
and stops with a plain message when the C headers or libclang are
missing.

On Windows the hook runs the whole gate through `bin/windows-env`, with
the variables ci.yml's gate step sets there, `A=--verbose` and
`RUST_BACKTRACE=1`. Whether the whole gate passes on a private desktop,
which refuses input injection, the cursor, the foreground window, and
screenshots, is not known yet. The Windows real-window helpers already
drive their own windows with posted messages (`PostMessageW`, `EndMenu`
in `test/integration/support/platform_tray.rb` and `platform_popup.rb`),
and nothing under `test/` or `plugins/*/test/` calls `SendInput`,
`SetForegroundWindow`, `GetCursorPos`, or takes a screenshot.

`test/tasks/test_windows_env.rb` runs the real `bin/windows-env` with
stand-ins for Ruby and Python that print Windows paths: the command gets
its arguments, its own status, the GNU toolchain of the pin, and ci.yml's
clang arguments at Ruby's MSYS2; missing headers or libclang stop it
first. `test_setup.rb` checks what `bin/setup` installs on Windows, for a
person and for a runner, that the toolchain gets ci.yml's components, and
that both setup scripts are tracked as executable. `test_pre_push_hook.rb`
checks that on Windows the gate runs through `bin/windows-env` with the
gate step's Windows variables.

What a Windows build machine gave a run, measured 2026-11-13:

- mise installs `ruby = "4.0.9"` as RubyInstaller's archive,
  `rubyinstaller-4.0.9-1-x64.7z`: Ruby 4.0.9 `x64-mingw-ucrt`, RubyGems
  4.0.20. Python 3.12.16 comes as python-build-standalone's MSVC build.
  A cold install took about six minutes, downloading at 20 to 60 KB/s.
- `pre-commit = "latest"` failed `mise install` on Windows, since mise
  installs it there only through pipx. mise.toml now pins it to 4.7.0 on
  Linux and macOS only.

### Where it stands

Every Windows run after the first ended before its command started,
after mise had installed the tools, from a fault of the build machine,
not of Tokra. So the facts below are unmeasured, and `bin/setup.ps1`, the
hook's Windows branch, and `bin/windows-env` have run only in their
tests, on macOS, with stand-ins.

Not yet known: whether mise's Rust on Windows uses rustup (which
`bin/setup` calls) and sets `RUSTUP_TOOLCHAIN` itself; whether
`mingw_prefix` names `/ucrt64` as ci.yml's `MSYSTEM_PREFIX` does; where
the machine's MSYS2 is and whether it has the UCRT64 compiler; whether git
checks out `CLAUDE.md` and `.claude/skills/*` as symlinks, which the REUSE
check reads; whether the WebView2 runtime is there; which real-window
tests fail on a private desktop; and how long cold and warm runs take.

The next agent's first steps:

1. Run `bin/setup.ps1` alone on Windows with `CI=true`, from
   `powershell.exe -NoProfile -ExecutionPolicy Bypass -File bin/setup.ps1`,
   and read the facts above from the same run (`rustup show`,
   `git config core.symlinks`, `ls -la CLAUDE.md`, WebView2's registry
   key).
2. Run `bin/windows-env bundle exec rake compile:strict`, then
   `test:core`, then `test:gui`, each narrowly, before the whole gate.
3. Where a test needs input the private desktop refuses, rewrite it to
   post its own messages, or leave it out of the hook on Windows by name,
   with the reason here.
4. Run the hook as the build machine does, on the pushed commit, and
   record the run, its totals, and its cold and warm times here.

## Left for later

- `bin/setup.ps1`, the hook, and `bin/setup` have not yet run on Windows
  (above).
- The tests of `bin/setup`, the hook, and `bin/windows-env` skip on
  Windows, where Ruby cannot run a shell script or its stand-ins as a
  command; they test the Windows branches elsewhere with `OS=Windows_NT`.
  Nothing tests `bin/setup.ps1` itself but its executable bit.
- `bin/setup` brings Linux's system packages on Debian and Ubuntu through
  `bin/linux-env` (Plan 068); elsewhere a missing one fails the compile,
  which names it.
- The REUSE tool's version is written in ci.yml and in `bin/setup`. A pin
  in `mise.toml` that both read would leave one.
