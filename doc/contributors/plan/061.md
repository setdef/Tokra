# Plan 061: The gate runs where you run it, before a push

Two parts of Tokra's gate worked only on the maintainer's Mac.

Plans 056 and 057 sent the real-window tests to a hidden macOS account,
`tokratest`, through scripts in another project's checkout under the
maintainer's home. On any other Mac the gate stopped at "no hidden-run",
until you learned to set `TOKRA_REAL_WINDOWS=local`. The repository held
one person's account name, home paths, and machine setup.

The commit hook ran the whole gate. A commit took as long as the gate
does and opened every real window, so the only practical unit of work was
one large commit a session, which is the opposite of small steps on a
trunk.

The maintainer's decision, on 2026-11-13: the repository carries nothing
of anyone's own machines, the `tokratest` account goes, and Tokra works
trunk-based. This plan makes the gate an ordinary one, which anyone who
clones Tokra runs the same way, and moves it from each commit to each
push.

## Real-window tests run in the session that runs them

`rake test:gui` runs `test:keyboard`, `test:real_windows`,
`test:real_windows:plugins`, and then `test:console`, on every system,
as CI always has. `RealWindows.where`, `TOKRA_REAL_WINDOWS`, `HiddenJob`,
`test:hidden`, `test:hidden:prune`, and the `test:here` guard are gone,
with their tests.

What Plan 056 built to keep stray windows away stays, since it never
depended on the account:

- The file rule and `RealWindows::NAMED` still sort the real-window tests
  from the rest, so `test:core`, `plugins:test`, and a plugin's own
  `rake test` open no window, write no clipboard, and take no hotkey.
- The tripwire still fails a real-window test outside the tasks that set
  `TOKRA_REAL_WINDOWS_RUN`.

So someone who wants no window on the desktop they are working at runs
`test:core` and `plugins:test` there, and the gate on another machine or
in CI. That arrangement is theirs, and stays out of the repository.

`LinuxGate` named each checkout with `HiddenJob.slug`; the method is now
`LinuxGate.slug`, with its test.

## The console set keeps its span

Plan 057 gave `RealWindows::CONSOLE` two reasons. One is gone: off the
console, macOS starved the dialog fixture's page, so the set ran in the
maintainer's session. The other, from that plan's amendment, stands: a
click on one of those tests' dialog sheets ends it, so they run inside
one spoken span that holds the desktop input lock, apart from the
plugins' other real-window tests. `test:console` and the set stay as
they are, and a file joins the set when a person's click could fail it.

The name is now only history. Renaming it is a later change, if it is
worth one.

## The gate runs before a push

`.githooks/pre-push` runs `bundle exec rake` when a push moves a branch.
It reads the remote side of each line git gives it, which is always a
full ref, and skips tags and deletions. The gate tests the working tree,
so the hook refuses a push unless every branch in it gets the commit that
is checked out, with nothing uncommitted and nothing untracked. Untracked
files count because the tests and the compiler read them: a file you
forgot to add would pass here and be missing on CI. An ignored file does
not count.

On Linux it runs the gate as ci.yml does, under `xvfb-run` and
`dbus-run-session`, and a test pins both commands to ci.yml's. It also
unsets `WAYLAND_DISPLAY` and sets `GDK_BACKEND=x11`, since GTK takes a
Wayland desktop before the X display `xvfb-run` gives it, and the gate's
windows would open there.

From a worktree, git hands a hook `GIT_DIR`. The hook unsets it and its
kin once it has found the working tree, or every git the gate runs would
act on that worktree, the ones in tests that make repositories of their
own included.

`bin/setup` writes a stub into the clone's shared hooks folder that runs
the hook from whichever worktree pushes. It writes the stub only where
none exists or the one there is its own, by a marker line, so a hook you
keep there yourself survives. `.pre-commit-config.yaml` keeps the
`bundle check` and loses the gate.

`bin/setup` is now safe to run again and again, asks nothing, and runs no
sudo, so a CI runner or a build machine can run it before every check.
With `CI=true` it installs the bundle as ci.yml does, frozen into
`vendor/bundle`, and skips the commit hook and the RDoc build.

Where `core.hooksPath` is set, git runs the hooks in that folder and
never the clone's own. `bin/setup` still writes the stub, and says what
follows: a push runs the gate only if the pre-push hook in that folder
hands off to the stub, and pre-commit, which refuses to install there,
is left out.

AGENTS.md's "Committing" now describes small commits on `trunk`, each
complete, with the gate before the push. The `commit-session` skill
follows it.

## Tests

`test/tasks/test_pre_push_hook.rb` drives the real hook in a real
repository, with stand-ins for `bundle` and `xvfb-run`: a branch that
moves to the checked-out commit runs the gate, by any local name; a tag, a
deletion, and an empty push do not; another commit, in any line of the
push, uncommitted changes, staged or not, and an untracked file are
refused before the gate; an ignored file is not; and a gate that fails
fails the push with its status. One test pushes for real from a worktree
to a bare repository, so the hook gets the environment git gives it, and
checks that the gate's command inherits no `GIT_DIR`. On Linux another
checks that the gate is kept off a Wayland desktop. The last checks that
git tracks the hook as executable.

`test/tasks/test_setup.rb` runs the real `bin/setup` in a real
repository with a stand-in `mise`: what it installs for a person, for a
CI runner, and where `core.hooksPath` is set, with what it says there;
that it checks out an empty submodule; that its stub runs the hook of
whichever worktree pushes, and lands in the clone's shared hooks folder
when a worktree runs the script; that it replaces an earlier stub of its
own, makes the hooks folder when there is none, and leaves a hook that
is not its own, even one that quotes the marker. One test goes the whole
way: `bin/setup`'s stub, the hook as shipped, and a real `git push`,
whose refs reach the hook only through the stub's standard input. It
also holds the REUSE tool's version to ci.yml's.

`test/tasks/test_real_windows.rb` checks that `test:gui` runs the four
tasks in order, whatever `CI` and the old `TOKRA_REAL_WINDOWS` say, and
keeps its tests of the file rule, the tripwire, and the console span.
`test/tasks/test_linux_gate.rb` takes over the test of the slug.

## Windows

`bin/setup`, run in MSYS2's bash, gives a Windows contributor or a
runner the state CI's Windows job builds in, and the hook runs the whole
gate there; since "The hook alone, in a bare checkout", the hook runs
that setup itself. See "What the runs showed" for what has run.

`bin/setup.ps1` does only what PowerShell has to. It runs `mise install`,
asks RubyInstaller's Ruby where its MSYS2 is
(`RubyInstaller::Runtime.msys2_installation`), checks that MSYS2 has its
UCRT64 compiler, and runs `bin/setup` in that MSYS2's bash with
`MSYSTEM=UCRT64`. A missing MSYS2 or compiler is named, with
RubyInstaller's own `ridk install` command, and never installed from an
unpinned download. It needs no administrator rights and asks nothing.

`bin/setup` tells Windows by `OS=Windows_NT`, which Windows sets for every
process. A stand-in `uname` would do for the hook, but in `bin/setup`'s
tests it also misleads git's own `git-sh-setup`. On Windows it adds Rust's
GNU host toolchain of mise.toml's Rust, with ci.yml's components, the
libclang wheel from PyPI (`libclang==18.1.1`, whose `clang/native/`
holds `libclang.dll`) into mise's Python as the REUSE tool is, and
clang's own headers through `bin/clang-headers`. It installs the bundle
through `bin/windows-env`, and installs no commit hook.

The wheel holds the library and none of the headers clang finds beside a
full LLVM (`stddef.h`, `mm_malloc.h`, the intrinsics), so bindgen stopped
at `mm_malloc.h` in every Rust gem. CI's runner has a full LLVM.
`bin/clang-headers` takes LLVM's clang source release of the wheel's
version, `clang-18.1.1.src.tar.xz` from the llvm-project release
`llvmorg-18.1.1`, whose `lib/Headers` is clang's resource include folder
as it ships. It checks the archive against the SHA-256 it pins (the
archive's signature, `clang-18.1.1.src.tar.xz.sig`, is good from LLVM's
release key 474E22316ABF4785A88C6E8EA2C794A986419D8A), and unpacks only
those headers, once, into `tokra/clang-18.1.1/include` in your cache
(`$XDG_CACHE_HOME`, or `~/.cache`). A full LLVM for Windows would match
too, but it is a gigabyte for a few hundred headers, and MSYS2's clang
package would be an unpinned install into whichever MSYS2 the machine
has. GNU tar reads a name like `C:/...` as another host's file, so the
script gives tar names relative to its folder.

`bin/windows-env` runs a command with what CI's Windows steps set:
`RUSTUP_TOOLCHAIN` for the GNU host toolchain, which rb-sys needs for
RubyInstaller's MinGW Ruby, and `BINDGEN_EXTRA_CLANG_ARGS` and
`LIBCLANG_PATH`, at Ruby's MSYS2 (`msys_path` and `mingw_prefix`), the
wheel's libclang, and `-resource-dir` at `bin/clang-headers`' folder. It
works them out each time rather than reading a file setup wrote, which a
cleaned checkout or a moved MSYS2 would leave stale, and stops with a
plain message when the C headers, libclang, or clang's headers are
missing, or when Ruby finds no MSYS2. RubyInstaller looks for its MSYS2
in `MSYS2_PATH`, beside Ruby, at `C:\msys64`, in the registry, and among
PATH's entries for an MSYS2's root, and mise installs Ruby beside none of
them, so Ruby raised `MsysNotFound` on a machine whose MSYS2 is anywhere
else. When `MSYS2_PATH` is unset and the MSYS2 whose bash runs the script
(`cygpath -m /`) has `ucrt64/bin/gcc.exe`, `bin/windows-env` sets
`MSYS2_PATH` to it. Git for Windows' bash is an MSYS2 with no compiler,
so there Ruby keeps its own lookup.

On Windows the hook runs the whole gate through `bin/windows-env`, with
the variables ci.yml's gate step sets there, `A=--verbose` and
`RUST_BACKTRACE=1`.

RuboCop's `Layout/EndOfLine` runs only off Windows (`.rubocop.yml`,
through RuboCop's ERB pre-processing). goodcop gives it the native style,
which on Windows wants CRLF, while git writes a Windows working tree with
CRLF or LF as each clone's `core.autocrlf` says, so the same commit failed
every file in a clone that does not convert.

### A desktop of the run's own

Windows can run a program on a desktop made for it, as a build machine or
a service does, so its windows open on no one's screen. There Tokra's
windows, WebView2, menus, and focus all work, and two things do not:
`Shell_NotifyIcon` fails with E_FAIL, since the notification area belongs
to Explorer's taskbar on the desktop a person signs in to, and
`GetCursorPos` fails with error 5, since only the desktop that takes the
mouse has a cursor. `test/support/desktop.rb` probes for exactly those,
once and only on Windows: no `Shell_TrayWnd` window, and a failing
`GetCursorPos`. These skip with its reason, as real-window tests skip
without a GUI session on macOS:

- the tray: `TrayTest` (6), `ConfigTrayTest` (3), the six `TestNativeTray`
  tests that make a `Native::TrayIcon`, and `keyboard/tray_menu_test.rb`'s
  `TrayMenuTest` (8);
- the cursor: `WindowStateTest#test_the_cursor_position_is_a_physical_position`.

A Windows machine with a taskbar and a cursor, CI's runner among them,
skips none of them, so CI is where these 24 run on Windows. Driving the
tests' own windows instead cannot reach the platform's tray, and running
them on a person's desktop would put every push's check on someone's
screen.

The hang probe's tests (`real_app_test.rb`) matched only the output of
CI's runner, an administrator with the Windows SDK's `cdb`. On a standard
account the probe says SeDebugPrivilege is not enabled before the wait
chains it can still read, and without `cdb` it says it has no debugger;
the tests now accept both.

## The hook alone, in a bare checkout

A CI runner, a build machine, or a contributor's tool may check out the
commit you push and run `.githooks/pre-push` there, with git's arguments
and ref lines, and nothing before it: no `bin/setup`, and no mise
activated. Until now the hook assumed Ruby and the bundle were in place,
so it passed only after someone ran `bin/setup` by hand and started it
through `mise x --`. On a Mac with no GUI session it could not pass at
all. This section makes the hook enough on its own, on Linux, on Windows
from MSYS2's bash, and on a Mac with or without a GUI session.

### A Mac with no GUI session

launchd runs a process outside any login session, as a build machine's
daemon, in its System session (`launchctl managername` prints `System`,
not `Aqua`). There is no window server there. The core real-window tests
already skip, by `RealApp.unavailable_reason`. The plugins' did not:

- `plugins/clipboard`'s `test_clipboard.rb` failed 37 of its 67 tests
  with arboard's "The selected clipboard is not supported with the
  current system configuration.", since there is no pasteboard. That
  stopped `test:real_windows:plugins` before the other plugins ran.
- `plugins/dialog`'s `test_macos_dialogs.rb` failed all 4: rfd falls
  back to a modal panel that never opens, and each child Ruby ran until
  it was killed at 30 seconds.
- `plugins/notification`'s `test_macos_notifications.rb` failed 1 of its
  4, `test_notify_resolves_while_the_send_waits`, as the notification
  center refused the connection ("Connection to notification center
  invalid"). The 3 that only name the app send nothing, and pass.
- `plugins/global-shortcut` passed: 37 tests, 4 of them skipped by their
  own platform checks.
- `package:check` failed at tokra-clipboard's load check, which opens the
  clipboard. With it left out, every other gem's checks passed.

`Desktop.session_unavailable_reason` (`test/support/desktop.rb`) asks
launchd once, on macOS only, and names the session when it is not Aqua.
`RealApp.unavailable_reason` now asks it too. The clipboard's tests and
the dialog's macOS tests skip with that reason in their `setup`, since
each opens the pasteboard or a panel; the notification test that sends
skips with it, and the three that do not still run. A Mac with a GUI
session, as a person's or CI's runner, gets `nil` and skips nothing.

tokra-clipboard's load check still loads the packaged plugin and
ferro-arboard's extension, and still opens the clipboard where there is
one. Where arboard answers that no clipboard is supported and launchd
names a session that is not Aqua, it takes that answer as proof the
plugin reached the extension, and says why it opened nothing. Anything
else that keeps the clipboard shut fails the check, as before.

`test/test_desktop.rb` checks the reason for a session that is not Aqua
and none for Aqua, and that on macOS the answer is launchd's, asked once.
`test/tasks/test_package_smokes.rb` runs tokra-clipboard's load check
against stand-ins for the plugin and `launchctl`: it opens the clipboard
where there is one, takes arboard's answer on a Mac with no GUI session,
and fails for that answer with an Aqua session or no launchd, and for any
other error.

### The hook sets Tokra up

Once the hook has checked the push, it runs `bin/setup --gate`, then the
gate through `mise x --`, so the tools are mise.toml's whether or not
mise is activated. It writes what setup prints to
`tmp/pre-push-setup.log`, and if setup fails, it shows the last 40 lines
and refuses the push with setup's status. A push the hook refuses, or one
that moves no branch, sets nothing up.

`bin/setup --gate` does what the gate needs: the submodule, `mise
install`, the REUSE tool, on Windows the GNU toolchain, libclang, and
clang's headers, and the bundle, with ci.yml's frozen `vendor/bundle`
when `CI=true`, through `bin/linux-env` or `bin/windows-env`. It leaves
the git hooks and the RDoc, which only a person's clone wants. Any other
argument stops it with its usage before it installs anything.

Three ways were weighed:

- **The hook runs plain `bin/setup`.** With `CI` unset, as on a
  contributor's machine, that ends with `rake rdoc`, which rebuilds the
  whole RDoc whenever a file under `lib/` changed, so nearly every push
  would wait on it. It would also write the pre-push stub and the
  commit hook into whatever clone runs the hook, a build machine's
  among them.
- **The hook sets nothing up and leaves it to whoever runs it.** That is
  how it stood: a checkout where nothing ran first failed at its first
  `bundle`.
- **The hook skips setup when nothing it reads has changed**, by a stamp
  of `mise.toml`, the lockfiles, and the setup scripts. A warm setup
  costs seconds, set against a gate of minutes, and a stamp can be
  wrong where a tool was removed by hand. Not worth its risk yet.

So a warm push pays for each tool's own check that it has nothing to
do; see "What the runs showed" for the times. `tmp/` is ignored, so the
log never counts as an untracked file.

`test/tasks/test_pre_push_hook.rb` now stands in for `bin/setup` and
`mise` too, and checks that a gated push runs `bin/setup --gate` before
the gate, that a failing setup refuses the push with its status and its
last words, before the gate, and that the gate runs through `mise x --`
on Linux, Windows, and elsewhere. Every refused push still runs nothing,
setup included. `test/tasks/test_setup.rb` checks what `--gate` installs
for a person and for a runner, that it writes no stub, that an unknown
argument installs nothing, and, through a real `git push`, that the
shipped hook runs the shipped `bin/setup` before the gate, without the
RDoc.

### Windows' platform in the plugins' lockfiles

On Windows, `plugins:test` added `x64-mingw-ucrt` to every plugin's
`Gemfile.lock`, and nothing else. It installs each plugin's bundle
unfrozen, and Bundler counts a lockfile's `ruby` platform for every
platform but Java's and Windows' (bundler 4.0.3, `rubygems_ext.rb`'s
`GENERICS` and `definition.rb`'s `add_current_platform`), so it adds
Windows' own to a lockfile without it. The tree the gate left was then
changed, and the hook refuses the next push from it. The plugins'
lockfiles hold no gem built for one platform, so each now names
`x64-mingw-ucrt` beside `ruby`, which changes no resolution, and
`test/tasks/test_plugin_lockfiles.rb` holds them to it.

The root `Gemfile.lock` lacks the platform too. ci.yml and `CI=true`
install it frozen, so it never changes there, but a person's unfrozen
`bin/setup` on Windows would add it, with ffi's Windows build. Adding it
changes which ffi CI's Windows job installs, so it is left for a change
of its own.

## Left for later

- `bin/setup.ps1` has not run on Windows (above).
- A Windows machine whose MSYS2 has no UCRT64 compiler gets one only from
  RubyInstaller's `ridk install`, which `bin/setup.ps1` names. Bringing a
  pinned MinGW toolchain and `make` instead is undecided.
- The tests of `bin/setup`, the hook, `bin/windows-env`, and
  `bin/clang-headers` skip on Windows, where Ruby cannot run a shell
  script or its stand-ins as a command; they test the Windows branches
  elsewhere with `OS=Windows_NT`. Nothing tests `bin/setup.ps1` itself
  but its executable bit.
- `bin/setup` brings Linux's system packages on Debian and Ubuntu through
  `bin/linux-env` (Plan 068); elsewhere a missing one fails the compile,
  which names it.
- The REUSE tool's version is written in ci.yml and in `bin/setup`. A pin
  in `mise.toml` that both read would leave one.
- The root `Gemfile.lock` lacks Windows' platform, so a person's unfrozen
  `bin/setup` on Windows rewrites it (see "Windows' platform in the
  plugins' lockfiles").
- The hook runs the whole gate, minutes long, where a pre-push check is
  best kept to about a minute; CI already runs the whole gate after each
  push. Narrowing it is a decision of its own.
- On a Mac with no GUI session, 30 of the clipboard's tests would pass,
  as they never reach the pasteboard, but the file skips as a whole.
  Guarding each test that opens it instead would let them run there.
