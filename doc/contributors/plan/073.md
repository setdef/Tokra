# Plan 073: One setup in Ruby for every system

## Context

`bin/setup` was a bash script with a PowerShell twin, `bin/setup.ps1`,
which ran it in the bash of Ruby's MSYS2 (Plans 061 and 071).
`test/tasks/test_setup.rb` launched `bin/setup` in a repository, with a
`#!/bin/sh` stand-in for mise on `PATH`. Ruby on Windows cannot start a
script or such a stand-in as a command, so every test in the file
skipped there. A change to `bin/setup` passed the pre-push hook on a
Windows machine, which tested less than another system would have, and
turned trunk red on Linux and macOS. Setup had two implementations, one
of which was never run, and a check that tested less on one system.

## Problem

Setup needs one implementation, and tests that run on every system, so a
change to it is checked on whichever system the pre-push hook lands on.

## Decided

### The command

Setup is two lines, the same in sh, cmd.exe, Windows PowerShell 5.1,
PowerShell 7, and Git Bash:

    mise trust -q mise.toml
    mise x -- ruby tasks/setup.rb

They are two lines, not one with `&&`, because Windows PowerShell 5.1 has
no `&&`. `mise x` installs every tool `mise.toml` pins before it runs
Ruby, with no terminal and no prompt, so nothing runs `mise install`
first, and the only things to install by hand are git and mise. The first
run on a clean machine installs Ruby, Rust, and Python, and takes
minutes. The trust line stays because it costs nothing where mise asks
for no trust.

`bin/setup` stays as an sh file holding those two lines, so what people
type is unchanged. `bin/setup.cmd` holds the same two lines for cmd.exe
and replaces `bin/setup.ps1`: a `.ps1` needs PowerShell's execution
policy bypassed on every machine, every run. Both go to the checkout's
root first, and pass their arguments on.

### The Ruby file

`tasks/setup.rb` does every step `bin/setup` did, in the same order, with
the Windows steps as branches of the same file:

1. `git submodule update --init`, when a submodule is not checked out.
2. `mise install`, when `mise ls --missing` lists anything. `mise x`
   has installed it already; this is the safeguard Plan 061 had.
3. On Windows, Rust's GNU host toolchain with CI's components.
4. The REUSE tool at CI's version, and on Windows libclang and clang's
   headers (`bin/clang-headers`).
5. On a CI runner (`CI=true`), the repair of a `vendor/bundle` Bundler
   cannot start from, and Bundler's `path` and `frozen` settings.
6. `bundle install`, through `bin/linux-env`, or on Windows through
   `bin/windows-env`, when `bundle check` says the bundle is not whole.
7. Without `--gate`: the pre-push stub, the note where `core.hooksPath`
   is set, `pre-commit install` (off CI, off Windows), and the RDoc (off
   CI).

It follows these rules:

- It reads only what Ruby ships (`fileutils`, `open3`, `shellwords`),
  since it runs before the bundle exists, and on Ruby 4 `logger`, `csv`,
  and `fiddle` are bundled gems.
- Every command is an argument list, never a string a shell reads. A
  `Setup::Shell` runs them, and it is the only object that does. Tests
  put a recorder in its place. A command that cannot start ends with 127,
  as a shell would end it.
- It is quiet where nothing is missing. A step asks the system first
  (`mise ls --missing`, `pip show`, `rustup toolchain list`, whether
  clang's headers are there, `bundle check`) and prints and runs a command
  only when the answer is no. With nothing missing it prints nothing.
- A failure ends it at once, with the failing command's status, after the
  command and what it printed. A step that changes something streams its
  output, so a long install shows its progress; a question asked of the
  system is captured and shown nowhere.
- What the file installs itself (`mise install`, the Rust toolchain, the
  Python packages, clang's headers) runs under a `File#flock` on
  `tokra/setup.lock` in the cache folder: `XDG_CACHE_HOME` when set, else
  the platform's own (`~/Library/Caches` on macOS, `LOCALAPPDATA` on
  Windows, `~/.cache` elsewhere). Two setups at once in one cache break
  mise's download store. The lock does not cover the first step: `mise x`
  installs the missing tools before the file starts, so two cold setups at
  once in one cache are still unprotected there.
- It reads the system from its environment (`OS`, `CI`, `HOME`,
  `XDG_CACHE_HOME`), which the tests pass in, and from Ruby's `host_os`.
  It knows no machine and no person's computer.

mise's own `mise.toml` pin, `min_version`, is what a person's mise must
meet. The file tests nothing of mise's version.

### The hook

`.githooks/pre-push` runs the two lines itself, with `--gate`, and not
`bin/setup --gate`. The hook already stands in the checkout's root, so it
needs no `cd`; and it no longer depends on a script's mode bits, which a
Windows checkout may not keep. The commit that moves it keeps the hook's
log and its refusal message, now naming `tasks/setup.rb`. The stub that
`tasks/setup.rb` writes into a clone's hooks folder is unchanged, and so
is its marker, so a clone that holds the old stub keeps it.

### Its tests

`test/tasks/test_setup.rb` calls `Setup` in a real repository with a
recorder in place of its runner. The recorder answers each command it is
told to, runs git for real (the stub and the submodule are real), and
records the rest, so the tests assert on the commands each case would run:
a person, a CI runner, the gate, Windows, the repair of a broken bundle,
what is already in place, a failing command, `core.hooksPath`, the stub
and its replacement, and the lock. None launches a script or a stand-in as
a command, none skips on Windows, and the real runner has tests of its own
that run Ruby itself in array form.

The tests that run the hook, `test/tasks/test_pre_push_hook.rb`, still
start `.githooks/pre-push`, an sh script, and skip on Windows; so do the
three tests moved there from `test_setup.rb`, which run the stub that
setup writes. That is the hook's own check, not setup's.

## Not decided here

- mise 2026.10.11, which ci.yml pins for one job, was not run. The
  strategy was measured on 2026.11.7.
- `bin/windows-env` and `bin/clang-headers` are sh scripts, which Windows
  setup runs through `sh`. In an MSYS2 bash, `sh` is on `PATH`. From
  cmd.exe or PowerShell it is not, and the MSYS2 that `mise.toml` pins
  carries none, so setup puts the `usr/bin` of the Git for Windows that
  `git` leads to ahead of `PATH` for those two commands. The gate itself
  (`mise x -- sh bin/windows-env bundle exec rake`) still needs an `sh`
  on `PATH`: the hook runs under git's own.
- The REUSE tool and libclang are still pinned in `tasks/setup.rb` and
  ci.yml both; tests compare them.

## Proof

On 2026-11-23, mise 2026.11.7:

- `test/tasks/test_setup.rb`: 47 runs on Linux and on Windows, no
  failures; one skip on Windows, `bin/setup`'s executable mode, which
  Windows does not record. RuboCop and REUSE are clean.
- The committed hook alone, from empty mise data, state, and config
  folders (so it installed Ruby, Rust, Python, and pre-commit on Linux,
  and on Windows those and the Windows tools, six in all), then the whole
  gate: Linux, no failures; Windows, 2408 runs, no failures. On macOS
  setup ran to its end and the gate stopped at
  `ContextMenuTest#test_popup_at_places_the_menu_at_the_position`, a
  failure of that machine that setup does not touch.
- The two lines from cmd.exe, and from Windows PowerShell 5.1, with a
  `PATH` of the system folders, mise, and Git for Windows' `cmd` folder
  alone, from empty mise folders: both installed the tools, the toolchain,
  the Python packages, and ran the bundle check, and ended with status 0.
- Not run: mise 2026.10.11, which ci.yml pins for one job.
