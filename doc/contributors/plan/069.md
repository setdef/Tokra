# Plan 069: Tokra develops on Ruby 4.1 where it can

## Context

Tokra runs on Ruby 4.0.1 or newer. Ruby 4.1 collects garbage per Ractor,
and Tokra must be easy to use from a Ractor (AGENTS.md, "Goals"). Ruby
4.1.0 comes out at the end of December 2026; its first preview,
4.1.0-preview1 (2026-10-11, master 2d08b5f42f), is out now. Fledge, the
packager Tokra apps will ship with, embeds that preview on Linux and
macOS, and Tokra's pins follow the Ruby Fledge embeds.

## Problem

Nothing in Tokra had run on Ruby 4.1. Its tools, gems, CI, and documents
named 4.0, and the extension did not build on 4.1. Nobody publishes one
build of Ruby 4.1 that installs the same everywhere:

- On Linux and macOS, mise installs `4.1.0-preview1`, and setup-ruby has
  it too (its `ruby-builder-versions.json`, at the v1.335.0 ci.yml pins).
- On Windows, mise installs RubyInstaller's build of a version, and
  RubyInstaller builds no preview: `mise install ruby@4.1.0-preview1`
  fails with `404 Not Found` for
  `RubyInstaller-4.1.0-preview1-1/rubyinstaller-4.1.0-preview1-1-x64.7z`.
  What exists is RubyInstaller's head build of Ruby's master, served in
  place of the day before's every day, which setup-ruby's `head`
  installs. Fledge keeps a copy of one day's build that can be pinned.

## Decided

### Ruby 4.1 on Linux and macOS, 4.0 on Windows

`mise.toml` pins Ruby per system, in a list of one version for each set
of systems, which mise filters by its `os` key:
`4.1.0-preview1` on Linux and macOS, and `4.0.9` on Windows, as before.
`bin/setup`, the pre-push hook, and a contributor's shell all take the
pin of the system they run on.

On Linux and macOS the preview comes from jdx/ruby's precompiled builds,
as Fledge's does (Fledge's `mise.toml` at 70ce470e, its `[settings]`).
mise finds no precompiled build among the releases GitHub marks as
prereleases, and compiles one with ruby-build instead, against whatever
libraries the computer has: on a Mac with no libyaml, psych could not be
configured and the build failed after seventeen minutes.
`ruby.precompiled_url` names jdx/ruby's asset for each version and
platform, and `ruby.compile = false` makes a missing download fail
rather than compile. jdx/ruby's build links libruby statically; Tokra
embeds no Ruby, so nothing here notices.

Windows stays on 4.0 because no Ruby 4.1 there builds the extension
soundly, as "Why Windows stays on 4.0" below shows. The gemspecs keep
`>= 4.0.1`, RuboCop's target stays 4.0, and `bin/windows-env`,
`bin/setup.ps1`, and ci.yml's Windows steps are unchanged, since 4.0 is
still a Ruby Tokra supports and the only one Windows runs.

### CI

The matrix names `"4.0"` and `"4.1"` on all three runners and excludes
`"4.1"` on Windows, so five jobs run, and every one gates. setup-ruby
takes a version it does not list as a prefix, preferring a stable
release and then any but a head build (index.js,
`validateRubyEngineAndVersion`), so `"4.1"` is 4.1.0-preview1 today and
4.1.0 once it ships, with no change here. The bundle cache's key holds
`RUBY_REVISION`, since the preview and 4.1.0 both say `RUBY_VERSION`
4.1.0.

`test/tasks/test_ruby_pins.rb` checks that `mise.toml` pins one Ruby on
each system, that ci.yml's matrix runs that Ruby's series on that
system's runner, and that `tokra.gemspec` admits it.

`rake test:linux`'s image holds one Ruby, `mise.toml`'s Linux pin, so it
runs the 4.1 Linux job; CI alone runs the 4.0 one.
`test_linux_gate.rb` checks the Dockerfile's Ruby is that pin and in a
series of the matrix, where it checked the matrix held one Ruby.

### What Ruby 4.1 broke, and each fix

Each fix stands alone and is correct on Ruby 4.0 too.

**Bundler 4.0.3.** RubyGems runs the Bundler a lockfile names under
`BUNDLED WITH`, and the root lockfile named 4.0.3. Bundler 4.0.11 and
older read `Pathname::SEPARATOR_PAT` (`bundler/source/path.rb`), which
Ruby 4.1 removed (ruby a5996718f3), so the first `bundle install` raised
`NameError`. Bundler 4.0.12 reads `Pathname#absolute?` instead (rubygems
67ce6df4c9). Every lockfile now names 4.0.24, the newest 4.0 release,
which runs on 4.0 too, and the plugin lockfiles that record Bundler's own
checksum record 4.0.24's. `test/tasks/test_bundled_with.rb` holds every
tracked lockfile to the root's Bundler, its Bundler checksum to that
Bundler, and the root's to 4.0.12 or newer. It reads each lockfile as
git's index holds it: the gate installs each plugin's bundle before
`test:core`, and there Ruby 4.1.0-preview1's own Bundler, 4.1.0.beta2,
wrote its version into a plugin's lockfile, as Plan 061 saw Bundler do
on Windows.

**rb-sys's stable API.** rb-sys writes Ruby's inline C helpers
(`RSTRING_PTR` and the like) in Rust for each Ruby up to 4.0
(`src/stable_api/ruby_4_0.rs` at 0.9.130). For any other Ruby its build
script stops, unless the `stable-api-compiled-fallback` feature lets it
compile the C helpers instead (`build/stable_api_config.rs`,
`Strategy::RustThenCompiled`). Tokra's extension took rb-sys and magnus
with default features off, so its build stopped there; Ferro's gems take
rb-sys's defaults, which include it. `ext/tokra/Cargo.toml` now asks for
the feature. On Ruby 4.1 it costs one more C file at install, and each
of those helpers becomes a call into it rather than inlined Rust; on a
Ruby rb-sys has Rust for, it changes nothing.

**magnus's `rb_data_type_t`.** Ruby 4.1 gives `rb_data_type_t`'s
function table seven reserved slots where 4.0 had one. Tokra took magnus
from its git repository at 2370a35, which sized them for 4.0, and failed
with `E0063 missing field reserved in initializer of
rb_data_type_struct__bindgen_ty_1`. magnus 0.9.3 (`src/typed_data.rs`)
sizes them for 4.1, and Tokra now takes it from crates.io, the release
Ferro's gems lock. It holds every commit since 2370a35.

**Default gems newer than the lockfile.** Ruby 4.1.0-preview1's default
gems include uri 1.1.2, fileutils 1.8.1, and strscan 3.1.9.dev, where
Gemfile.lock held 4.0's uri 1.1.1, fileutils 1.8.0, and strscan 3.1.7.

Three tests start a Ruby with `-rrake` or `-rrubocop` under
`RUBYOPT=-rbundler/setup`. Ruby requires a command line's `-r` libraries
before `RUBYOPT`'s, so rake and RuboCop loaded Ruby's own default gems
before Bundler set up, and Bundler refused: "You have already activated
uri 1.1.2, but your Gemfile requires uri 1.1.1". On 4.0 the versions
matched, so the order never showed. Each child now names
`-rbundler/setup` first.

Ruby 4.1's default strscan adds a Ruby entry point, `strscan.rb`, and
Ruby looks for `strscan.rb` along the whole load path before any
`strscan.so`. strscan 3.1.7 ships only the extension, so a bundled
`require "strscan"` loaded both copies, and every test process warned
that `scan_integer` was defined twice. strscan 3.1.8 ships its own
`strscan.rb`, which the bundle finds first. `test/tasks/test_strscan.rb`
checks that one copy loads and nothing warns.

**A plugin's bundle on Windows.** `plugins:test` installed each plugin's
bundle into Ruby's own gem folder, which on a Ruby installed deeper, as
the head build was under mise, pushed ferro-rfd's Cargo files past
Windows' 260-character path limit. Where the root bundle has an install
path, as `vendor/bundle` on CI, each plugin's bundle now installs there
too (`PluginBundle`, `tasks/plugin_bundle.rb`), which also reuses the
Ferro gems the root bundle compiled.

**Nothing in `lib/` or the plugins.** Ruby 4.1's own list of what it
breaks (NEWS.md, "Compatibility issues") is mostly about Ractors. No test
of Tokra or its plugins failed for any of them.

### Why Windows stays on 4.0

Ruby 4.1 adds `rb_len_t`, the type of String's and Array's lengths
(NEWS.md, "Type for lengths and indices", Feature #22400). It is `long`
unless `SIZEOF_RB_LEN_T` is defined wider than `long`, when it is
`int64_t`; with no definition, the headers define `SIZEOF_RB_LEN_T` as
`SIZEOF_LONG` (`include/ruby/internal/value.h`, lines 127 to 150). NEWS
names only 64-bit mswin as 64 bits. But RubyInstaller builds its head
Ruby on MinGW with `CPPFLAGS+=" -DSIZEOF_RB_LEN_T=8"`
(rubyinstaller2-packages, `mingw-w64-ruby-head/PKGBUILD`, line 62), and
`RbConfig::CONFIG["CPPFLAGS"]` there carries the define. So on
RubyInstaller's 4.1, where `long` is 32 bits, every length is 64.

Under plain cargo (`cargo test`), rb-sys-build passes RbConfig's
CPPFLAGS to bindgen (`src/bindings.rs`, `generate`, and
`src/rb_config.rs`, `cppflags`, at 0.9.130), the bindings say
`rb_len_t = i64`, and magnus 0.9.3 does not compile against them: 38
errors (E0308, a `&mut i32` where a `*mut i64` is expected) at its
`as c_long` casts. magnus 0.9.4 and its main branch name no `rb_len_t`
either. Under rake-compiler and `gem install`, the build runs through
rb-sys's Makefile, which hands RbConfig to the build script as
`RBCONFIG_*` variables (rb_sys gem, `mkmf.rb`, `env_vars`), and there
bindgen got no such define and bound `rb_len_t` as `c_long`, 32 bits.
The extension compiles and its tests pass with every length mistyped
against the Ruby it loads into, which is unsound. Where the define is
lost on that path was not traced.

Two upstream changes lift it: magnus using `rb_sys::rb_len_t` where it
now casts to `c_long`, and rb-sys-build giving bindgen the same CPPFLAGS
under its Makefile as under plain cargo. Until both ship, Tokra builds
nothing on a Windows Ruby 4.1.

## Considered

- **Ruby 4.1 everywhere, Windows on Fledge's pinned head build**, with
  the http-backend tables, DLLs, MSYS2, and environment that needs. It
  was built and passed on Windows only because the release build bound
  the wrong lengths; `cargo test` showed the fault.
- **Requiring Ruby 4.1**, with no 4.0. Windows has no sound 4.1, so 4.0
  stays supported everywhere.
- **Ruby's master on Linux and macOS.** It moves every day, so no two
  runs would be sure to test one Ruby.
- **rb-sys from its git repository**, ahead of a release with
  `ruby_4_1.rs`. None exists there either.

## What the runs showed

Each run went through `bin/setup --gate` with `CI=true`, mise on `PATH`
but not activated, and a home of the run's own, on Ubuntu, on Windows 11
from MSYS2's bash, and on a Mac in launchd's System session.

- The fixes above, on Ruby 4.0 on Linux: the pre-push hook alone passed.
- With them, on Ruby 4.1.0-preview1 on Linux: `compile:strict`,
  `test:core`, `plugins:test`, `test:keyboard`, `test:real_windows`,
  `test:real_windows:plugins`, `test:console`, `test:rust`, `lint`,
  `steep`, `lint:rust`, and `package:check` passed, and so did the
  whole hook on Linux and on the Mac.
- jdx/ruby's preview on the Mac answers `ruby 4.1.0preview1 (2026-10-11
  master 2d08b5f42f) +PRISM [arm64-darwin25]`, and `Gem.ruby_version` is
  `4.1.0.preview1`.
- The Ferro gems Tokra's plugins use compile on 4.1 with Ferro's own
  rb-sys 0.9.130 and magnus 0.9.3; nothing in Ferro had to change.
- On Windows, RubyInstaller's head build answers `ruby 4.1.0dev
  (2026-11-10 master 0e25874222) +PRISM [x64-mingw-ucrt]`, its RbConfig
  CPPFLAGS hold `-DSIZEOF_RB_LEN_T=8`, and `cargo test --locked` failed
  in magnus as above.
- `test:real_windows` failed twice in nine runs on Linux on 4.1, each
  time in one test and a different one, and passed on the run after:
  `ExitRequestedTest#test_a_prevented_exit_keeps_the_app_running_with_no_window_until_exit`,
  whose app's output stayed open five seconds after it exited, and
  `TestNativeTray#test_on_linux_ruby_raises_error_menu_for_a_menu_gtk_cannot_build`,
  where gtk-rs said "GTK has not been initialized".

## Left for later

- When magnus and rb-sys-build lift the Windows fault, and RubyInstaller
  releases 4.1: `mise.toml` pins 4.1 on Windows too, and the matrix drops
  its exclusion.
- When Ruby 4.1.0 ships: `mise.toml` and the Dockerfile pin it, and
  `ruby.precompiled_url` goes; setup-ruby's `"4.1"` already resolves to
  it.
- When rb-sys ships `ruby_4_1.rs`: Tokra's rb-sys drops
  `stable-api-compiled-fallback`.
- Whether `lib/` may use anything new in 4.1 waits for Tokra to drop 4.0.
- The two real-window failures above, seen once each on Linux on Ruby
  4.1, need a cause before they can be called flaky or fixed.
