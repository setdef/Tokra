# Plan 042: Menus

Tauri gives an app a menu bar: the app-wide menu at the top of the screen
on macOS, a menu bar inside each window on Windows and Linux, and the same
menus as context menus. Its `menu` module wraps muda, and its JavaScript
API drives the same menus through the core `menu` plugin. Tokra has none
of it. ADR 013 decided that muda joins Tokra's own extension, beside tao
and wry, since muda takes the window's raw handle and keeps process-wide
state (ADR 011's table).

The port is large, so this plan inventories all of it and splits it into
phases. Phase 1 ports the menu tree, its ids and builders, the default
menu, the app and window menus, menu events in Tauri's order, and the
plugin commands the JavaScript API needs for those types. Phase 2 ports
icons: icon items, Submenu icons, macOS's native icons, and the plugin's
icon payloads. Phase 3 ports context menus and the Windows menu theme.
The rest follows in later work, each with its reason. Phases 1 to 3 are
done.

## Decisions

1. **Ruby owns the menu logic; the extension is a thin muda binding.**
   `Tokra::Native::Menu`, `Submenu`, `MenuItem`, `CheckMenuItem`, and
   `PredefinedMenuItem` each hold one muda value in a `ThreadBound`, as
   windows and webviews do (ADR 012). They expose muda's own methods. The
   attach calls live where a stub can stand in for them: the window's
   (`Native::Window#init_menu`, `remove_menu`, `hide_menu`, `show_menu`,
   `is_menu_visible`, on Windows and Linux only) and the app's
   (`Native.init_menu_for_nsapp`, `remove_menu_for_nsapp`,
   `set_windows_menu_for_nsapp`, `set_help_menu_for_nsapp`, on macOS only).
   Each is defined only where Tauri calls it, so `respond_to?` answers the
   platform question Tauri's `cfg` answers. A constructor raises
   `ThreadError` off Ruby's main thread, where muda would panic (macOS's
   `MainThreadMarker`) or GTK would. Tauri's wrappers (stash, listeners,
   builders, the default menu, the plugin) are Ruby.

2. **muda 0.17.1 with Tauri's features, `libxdo` on, one off.** Tauri
   enables `gtk`, by default `common-controls-v6`, and behind its
   `linux-libxdo` feature muda's `libxdo`. Tokra enables `gtk` and
   `libxdo`. A Cargo-gated Tauri feature is simply supported (AGENTS.md),
   and ADR 011's amended rule builds in an additive feature; `libxdo`
   makes the Copy, Cut, Paste, and Select All items work on Linux under
   X11 (Wayland is unaffected). Its cost is `libxdo-dev` at build time and
   `libxdo.so.3` at run time on Linux, which CI installs and the README
   lists (maintainer's decision). Tokra leaves `common-controls-v6` off. With
   `common-controls-v6`, muda's About dialog imports `TaskDialogIndirect`
   from comctl32, which only version 6 exports; a Tauri app embeds the
   manifest that loads version 6, but Tokra's host is `ruby.exe`, whose
   manifest Tokra does not control, and a missing import fails the whole
   extension's load. Without it muda shows `MessageBoxW`. Tier 1: the
   process is Ruby's.

3. **`run_item_main_thread!` is `RuntimeContext#run_main_thread`.** It runs
   the block at once on the main thread and otherwise sends it there and
   waits, as `getter` does, but raises `Error::FailedToReceiveMessage`
   ("failed to receive message", Tauri's `error.rs:95-97`) when no answer
   comes, where the runtime getter's error is the runtime's. Constructors
   run there too, as `run_main_thread!` builds the muda value on the main
   thread. A wrapper that Ruby frees on another thread sends its muda value
   home to be dropped (`UserEvent::Release`), through the proxy of the
   event loop that is running; with none it leaks it, as `ThreadBound`
   does.

4. **The item is its own `MenuItemKind`.** Tauri's `MenuItemKind` wraps
   one item type per variant, as raw-window-handle's enums do; ADR 013's
   translation applies: in Ruby the item is the variant. `Menu#items`,
   `#get`, and `#remove_at` answer `MenuItem`, `Submenu`,
   `PredefinedMenuItem`, or `CheckMenuItem` objects, each with `kind`
   (itself) and `id`, and the `as_*` methods become `is_a?`. Tier 1. Each
   item answers `==` by its id and class, as muda compares children by id.

5. **Menu events go through the loop, as in Tauri.** One muda event
   handler, set once per process (muda's `OnceCell` takes one), sends
   `UserEvent::MenuEvent(id)` through the proxy of the running loop. The
   loop delivers it in arrival order with the other user events
   (ADR 012, decision 4), as `Native::MenuEvent`. `App` calls the app's
   listeners in registration order, then each window listener whose
   window exists, then plugins (the menu plugin sends to the item's
   channel), then the run callback with `RunEvent::MenuEvent`. Tauri
   calls the listeners while holding their mutex; Tokra copies the list
   and calls them outside it, so a listener may register another without
   deadlocking. A listener's `StandardError` reaches the loop, which
   reports it and keeps running, as for every other callback.

6. **`Menu.default` reads Tokra's config.** Tauri's About metadata takes
   the name and version from `PackageInfo` and the copyright and authors
   from the bundle config. Tokra has neither yet; the name is the
   config's product name or the program's file name (Ruby has no Cargo
   package), the version is the config's, and the copyright and authors
   are `nil` until a bundle config exists. Tier 1. The submenus are
   Tauri's per platform, chosen at run time.

7. **The builder's menu is set up when the loop exists.** Tauri builds
   the menu in `Builder::build`, after its runtime made tao's event loop:
   on macOS tao installs its own `NSApplication` subclass, and muda's
   `init_for_nsapp` would otherwise create a plain one first. Tokra makes
   the loop in `App#run` (plan 041, decision 1), so `App#run` builds and
   installs the builder's menu right after it, before the setup hook, as
   Tauri's order has it. Before `App#run`, `App#menu` is `nil`. Tier 1.

8. **Frontend input never panics.** Two of the plugin's paths panic in
   Tauri: `do_menu_item!` for a kind its command excludes
   (`unreachable!()`), and `new` for `Predefined` with no `item`
   (`unwrap()`). A panic in a command would end Tokra's VM. Tokra rejects
   both with Rust's panic text, "internal error: entered unreachable code"
   and "called `Option::unwrap()` on a `None` value". The rest of the
   plugin rejects with serde's words for each payload type: untagged
   enums ("data did not match any variant of untagged enum
   MenuItemPayloadKind"), unknown variants, and missing fields. Three
   more panics sit in muda, and the native layer refuses each first: a
   position past the end (`Vec::insert`, and AppKit's
   `NSRangeException`) raises `IndexError` with std's panic text; a
   submenu added to itself or into a menu inside it (a second `RefCell`
   borrow) raises `ArgumentError`; and an About icon whose bytes do not
   make its size, which muda's GTK backend passes unchecked to
   `Pixbuf::from_mut_slice` (`platform_impl/gtk/icon.rs:27-38`), raises
   with muda's own `BadIcon` text on every platform, as plan 041
   decision 4 did for tao's icons. Tier 1: a panic ends Ruby's VM.

9. **One window, as Tokra has today.** Tokra's app has one window,
   `main`. The window-creation handler runs in `App#run` between the
   native window and its webview, as tauri-runtime-wry runs it
   (`lib.rs:4461-4484`), so on Linux the menu bar sits above the webview
   in the window's box. `Window#on_menu_event` keys its listener by
   label, so a second window later needs no change here. As in Tauri,
   the window records the app's menu as app-wide on macOS too, though
   only NSApp shows it, and `AppHandle#remove_menu` on macOS leaves that
   record (`app.rs:925-962`).

10. **Windows accelerators mirror the stash.** Tauri's message hook asks
    `TranslateAcceleratorW` with each stashed menu's accelerator table.
    Tokra's event loop installs the same hook through tao's
    `EventLoopBuilderExtWindows::with_msg_hook`; it reads a main-thread
    list of muda menus that `MenuManager` replaces whenever its stash
    changes (`Native.set_accelerator_menus`, Windows only). The hook calls
    no Ruby.

### Decisions (phase 2)

11. **`Native::MenuIcon` is Tauri's `TryFrom<Image> for muda::Icon`.**
    `Tokra::Menu.menu_icon` converts a `Tokra::Image` on the calling
    thread, before the call goes to the main thread, and raises
    `Error::BadMenuIcon` with muda's text, as Tauri converts before
    `run_main_thread!`. muda's icon holds bytes on macOS and Linux and an
    `HICON` muda declares `Send` on Windows, so it is made anywhere. The
    About item's icon goes the same way now, so phase 1's `[rgba, width,
    height]` triple is gone.

12. **`NativeIcon` is a `Data` with 56 constants, like `CursorIcon`.** Its
    `new` is private, so only Tauri's names exist; the native layer maps
    a name to muda's variant and raises `ArgumentError` for any other.
    `set_native_icon` on an icon item or a submenu returns `nil` at once
    where menus belong to windows (`Natives#nsapp?`, Tauri's
    `cfg(target_os = "macos")`), without going to the main thread. The
    constructors with a native icon still make the item there, and muda
    shows no icon, as in Tauri.

13. **Icons that would panic raise first.** Tauri's submenu constructors
    unwrap muda's error; Tokra raises `Error::BadMenuIcon` with muda's
    text instead, as `Submenu::set_icon` does. muda's checks run first in
    muda's words, in 64 bits so the product cannot overflow; then an
    image with no pixels (`0x0`, `7x0`), which muda accepts and macOS's
    PNG encoder and GTK's `Pixbuf` panic on, raises with tao's text for
    it, "The specified dimensions (0x0) must be greater than zero.", the
    rule plan 041 decision 4 gave window icons. On Windows muda would
    answer an OS error instead; Tokra gives one answer on every platform.
    Last, an icon wider than 536,870,911 pixels or taller than `i32::MAX`,
    whose row stride GTK's `i32` cannot hold, raises with a text naming
    that limit.
    Tier 1: a panic ends Ruby's VM.

### Decisions (phase 3)

14. **`ContextMenu` is a module.** Tauri's sealed `ContextMenu` trait
    becomes `Tokra::Menu::ContextMenu`, which only Menu and Submenu
    include (tier 1: a Rust trait bound is a Ruby module). `popup` and
    `popup_at` convert the position on the calling thread
    (`Dpi.position_dimensions`, `TypeError` for anything but a
    LogicalPosition or PhysicalPosition) and show the menu on the main
    thread through `run_main_thread`, as `run_item_main_thread!` does.
    The native call is `Native::Window#popup_menu(menu, position)` on
    every platform, where a stub can stand in for it (decision 1); it
    raises `TypeError` for anything but a native menu or submenu and does
    nothing for a closed window (plan 038). `hpopupmenu` exists only on
    Windows, on the native classes and on the module, so `respond_to?`
    answers as Tauri's `cfg(windows)` does. muda's `ns_menu` and
    `gtk_context_menu` stay unbound: Tauri's trait exposes neither.

15. **A popup releases the GVL.** Each platform tracks a context menu in
    a nested loop on the main thread until it closes:
    `popUpMenuPositioningItem:atLocation:inView:` on macOS,
    `TrackPopupMenu` on Windows, and muda's own `gtk::main_iteration`
    loop on Linux. In Tauri only the main thread waits, and an async
    command waits on its channel. Tokra's main thread holds the GVL
    (ADR 012), so held through the popup it would stop every Ruby
    thread. The finding, from the locked sources: tao runs no handler
    while one runs, so no callback of Tokra's, tao's, wry's, or muda's
    reaches Ruby during the popup. macOS's
    `wakeup` and `cleared` return while the handler is in a callback,
    Windows' runner buffers events while its handler is out, and Linux's
    GTK handlers only queue for the loop body. muda's event handler and
    wry's handlers are Rust closures that send through the proxy. So the
    one native call runs with the GVL released
    (`ext/tokra/src/without_gvl.rs`): `rb_thread_call_without_gvl` inside
    magnus's `protect`, since its interrupt checks may raise before and
    after the call, and the call inside `catch_unwind`. Events, blocks
    sent to the main thread, a clicked item's `MenuEvent`, and a signal
    all wait for the menu to close, as in Tauri; other Ruby threads keep
    running, as Rust threads do there. No unblocking function is given: a
    signal or `Thread#raise` waits for the menu, as for any Ruby callback.
    Two exceptions never reach Ruby: on macOS tao's `drawRect:`,
    `open_urls`, and `reopen` skip the check and would block on the
    running handler's lock, as in Tauri; and a foreign callback the app
    registers itself (a GLib timeout, a Fiddle closure) takes the GVL back
    through `rb_thread_call_with_gvl`, whose interrupt check can `longjmp`
    across the platform's frames, as in any region without the GVL. ADR
    012 records the amendment.

16. **The plugin's `popup` reads dpi's `Position` in serde's words.**
    Arguments are read in Tauri's order, so a bad `rid` rejects before a
    bad `at`. A label no window has answers `null` without looking up the
    menu, as Tauri's `if let Some(window)` does. `at` is an externally
    tagged enum of two newtype variants: a bare `"Physical"` rejects with
    serde_json's "invalid type: unit variant, expected newtype variant",
    an unknown name lists the two variants as serde's `OneOf` writes two
    ("expected `Physical` or `Logical`"; `known_variant` now writes one
    and two names as serde does), a physical coordinate is an `i32`, a
    logical one an `f64`, and a struct reads from a map (field errors
    first, then the missing field) or from a sequence (then serde_json's
    "fewer elements in array"). The command answers once the menu closes.

17. **`Window#set_theme` themes the window's menu on Windows.** After the
    window's theme, it sends `Native::Window#set_menu_theme(menu, name)`
    to the main thread when the window has a menu; the native method
    exists only on Windows, maps Light and Dark and makes anything else,
    `nil` included, Auto, and drops muda's error, as Tauri's `let _ =`
    does. Tokra has no `App#set_theme` or `AppHandle#set_theme` yet;
    porting it will re-theme each window's menu the same way, so that
    row of the inventory moves with it.

18. **A context menu GTK cannot build raises first.** muda builds a GTK
    context menu the first time it shows one and unwraps each item's GTK
    item (`platform_impl/gtk/mod.rs:372-389`, `953-970`). GTK has no key
    for an accelerator on the numpad or the volume keys
    (`platform_impl/gtk/accelerator.rs:28-87`, `115-183`), which muda's
    parser accepts, so Tauri panics there on Linux. muda answers no
    item's accelerator, so Tokra remembers, on the main thread, the one
    it gave each item by id. Before it shows a menu on an open window,
    it builds each accelerator remembered for an item in the menu, at any
    depth, on a throwaway item in a scratch menu whose context menu
    already exists, which runs the same build with muda's `?`
    (`mod.rs:98-127`), and raises muda's error, "Couldn't recognize
    "NumpadAdd" as a valid key for accelerator, …", as `Error::Menu`. The
    menu's own items are never built for the scratch menu: that would set
    their accelerator group to the scratch menu's none, so a menu bar's
    accelerators would stop following `set_accelerator`
    (`mod.rs:1004-1072`), and leave the scratch menu's entries in them
    (`mod.rs:155-217`). Once a menu's context menu exists the check is
    redundant, never wrong: a later bad accelerator fails as it is added
    or set, and is not remembered. macOS and Windows build their
    context menus as items are added, so muda answers the error there
    already. Tier 1: a panic ends Ruby's VM.

19. **On Windows the loop waits as Tauri's does.** Tokra's loop polled
    for the GVL hand-off on Windows with `ControlFlow::WaitUntil(now +
    10 ms)` while other Ruby threads existed (ADR 012, decision 3). Windows
    CI then showed every context-menu fixture run dying in tao:
    "either event handler is re-entrant (likely), …"
    (`platform_impl/windows/event_loop/runner.rs:241-245`). The cause: a
    deadline makes tao's wait thread post `Tao::ProcessNewEvents`
    (`event_loop.rs:405-450`); `TrackPopupMenu`'s modal loop dispatches it
    to tao's thread window, whose handler calls `runner.poll()`
    (`event_loop.rs:2435-2468`), which starts a new iteration with
    `call_event_handler` and no `should_buffer` check (`runner.rs:204-206`,
    `295-370`), while the handler that showed the menu still holds it.
    Tauri never sets a deadline (tauri-runtime-wry `src/lib.rs:3075`,
    `4029-4031`), so it never meets this. Tokra now always waits with
    `ControlFlow::Wait`, and on Windows a ticker thread sends
    `UserEvent::Yield` every 10 ms while another Ruby thread exists
    (`gvl_handoff::poll_tick`); a user event arriving inside the nested
    loop is buffered (`runner.rs:208-221`). The other messages that reach
    tao there are guarded too: `WM_PAINT` on either window checks
    `should_buffer` (`event_loop.rs:1115-1130`, `2359-2380`), and window
    events go through `send_event`. macOS and Linux never set a deadline,
    and their re-entry paths are the ones decision 15 lists.

## Risks

- muda keeps one event handler per process; a second app in one process
  shares it. The handler sends to whichever loop runs.
- RubyInstaller's `ruby.exe` manifest is UNVERIFIED; decision 2 avoids
  depending on it.
- GTK casts an icon's width and height to `i32`, and its row stride of
  four bytes a pixel overflows past 536,870,911 pixels wide. Tokra
  refuses such an icon first on every platform (decision 13); only the
  Rust unit test reaches it, since a real one takes more than 2 GB.
- While a context menu tracks, a signal or `Thread#raise` aimed at the
  main thread waits for the menu to close (decision 15). On macOS, tao's
  `drawRect:` handler takes its callback lock without checking for a
  running handler (`platform_impl/macos/view.rs:343-357`,
  `app_state.rs:204-213`); a redraw of tao's own view during a popup
  would block there, as it would in Tauri. wry replaces tao's view as
  the window's content view (wry 0.54.1 `src/wkwebview/mod.rs:614-639`),
  so tao's `drawRect:` should not run.
