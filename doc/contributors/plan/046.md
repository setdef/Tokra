# Plan 046: One desktop input lock for every project's tests

Tokra's keyboard-taking tests (`test/integration/keyboard/`) open real
menus and bring fixtures to the front, so `KeyboardNotice` asks the
person at the Mac to step away while they run. Other projects' tests
share the same Mac and take its keyboard and mouse too: Lota's rove_2d
now, and later Fledge and Deckbuilder. Two such runs at once collide,
since each one's menus and synthetic input land in the other's windows,
and each project speaking its own "step away" and "come back" talks over
the others. This plan replaces Tokra's process-local notice with one
cross-process protocol, agreed with the Lota session, which Lota
implements the same way. Whoever lands first, the other matches it. The
protocol is slated to become a small shared gem once both copies settle.

## The protocol

The lock is an exclusive `flock(LOCK_EX)` on `/tmp/desktop-input.lock`,
literally `/tmp` and not `Dir.tmpdir` (which on macOS is a per-user
directory that need not agree between processes), opened with
`File::CREAT` and mode `0666`. Since the umask still narrows that mode
(to `0644` under the common `022`, which other users' processes could not
open), the process then sets it to `0666` with `chmod`, ignoring
`Errno::EPERM`, which means another user created the file. A process holds it only around each span
that takes the input, and the system releases it if the process dies.
Taking it blocks; while it waits, a process writes one line to standard
error, `waiting for the desktop input lock`.

The spoken notice is shared through a marker file,
`/tmp/desktop-input.away`, containing `<pid> <unix time>`. On taking the
lock for a speaking span, a process looks at the marker. If it is absent,
or names a process that has ended (`Process.kill(0, pid)` raises
`Errno::ESRCH`; `Errno::EPERM` counts as alive), the process writes its
own pid and time there, sets its mode to `0666` the same way so another
user's process can replace it once it goes stale, and says the step-away
line. A speaking span in a process that cannot announce (quiet, or with
neither `osascript` nor `say`) runs as a silent one and writes no marker. A marker naming a
live process means someone has already warned, so it stays silent.

Each process runs a settle watcher. Once three seconds pass with none of
its own spans running, it tries `flock(LOCK_EX | LOCK_NB)`. If it gets
the lock and the marker exists, it deletes the marker, says the come-back
line, and unlocks. If the lock is busy while the marker
exists, it says nothing yet but tries again at each poll for as long as
none of its own spans runs, since the holder may be a silent span, or a
process that never warned, and so may never call the person back. A busy
lock thus only delays the call back. The watcher stops trying once it has
called back or finds the marker gone.

An `at_exit` makes the same non-blocking check, but first waits out
whatever is left of the three seconds since the process last released the
lock, and skips the wait if they have passed. A process that exits right
after releasing would otherwise check at once and could take the lock
ahead of a process already blocked waiting for it, calling the person
back early only for that process to send them away again.

A silent span, `taking_the_keyboard(speak: false)`, takes and releases
the same lock but never speaks, never writes or deletes the marker, and
starts no watcher.

The lock is taken on macOS unless `CI` is set, even when quiet, because
its purpose is that two projects' tests never collide. Announcing
needs neither `DESKTOP_INPUT_QUIET` nor `TOKRA_QUIET` set. Whenever a
process would say the step-away or come-back line, it first posts the
same text as a Notification Center banner, so a muted person still sees
it: `osascript -e 'display notification "<text>" with title "Tests"'`.
The banner needs `/usr/bin/osascript` and the voice needs `/usr/bin/say`;
each is skipped where its command is missing, so a Mac without `say`
still shows the banner. Never use `display dialog` or anything else that
takes focus, and a failing `osascript` (permission denied, missing) is
ignored. Banner first, then `say`. Off macOS and on CI there is neither
lock nor notice.

Lota's session also takes the lock on Linux CI, for its parallel lanes,
while Tokra skips the lock on CI. That is to become a per-project option
in the shared gem.

The wording names no project:

- Step away: "Tests need the keyboard and mouse for a moment. Please step
  away."
- Come back: "The tests are done with the keyboard and mouse. You can
  come back now."

## Tokra's implementation

`test/integration/support/keyboard_notice.rb` keeps the module name and
the block API and adds the `speak:` keyword. A `KeyboardNotice::Desk`
holds one process's share: the lock, the marker, and the watcher, with
the paths, the settle time, the voice, the error stream, the clock, and
the watcher thread injectable, so its tests use a temporary directory
and a recorder, never touch the real files or speak, and drive the
watcher's `tick` on a fake clock instead of waiting on the real one.
Spans nest and may run on several threads: the desk counts how deep it
is and holds one `flock` while any span runs, since a second `flock`
from the same process on a new descriptor would wait on the first
forever. The span releases the lock in an `ensure`, so a block
that raises gives it back.

`test/integration/keyboard_notice_test.rb` covers the marker written and
removed, a stale marker replaced and spoken, a live one kept silent, the
call back only when the lock is free, a watcher that finds the lock busy
and calls back once it is released, an exit that waits out the settle
time so a child Ruby already blocked on the lock takes it first, both
files made `0666` under umask `022`, a quiet speaking span that writes no
marker, silent spans, nesting, release on
raise, and a span in this process waiting on a child Ruby that holds the
lock, proved by order: the child writes `releasing` before it unlocks, so
the span finds that line already written when it starts.

## Amendment, 2026-11-02: the protocol now lives in a gem

The protocol above is now implemented once, by the
[desktop_input_lock](https://github.com/setdef/DesktopInputLock) gem,
which Lota, Tokra, Deckbuilder, and Fledge share. Its files, timing, and
words are unchanged. Tokra's `KeyboardNotice::Desk` and the fake-clock
tests that covered it are gone; "Tokra's implementation" above describes
the copy that was removed.

The gem is also the better implementation. Its call-back watcher is no
longer killed in the middle of a call back, which could leave the marker
deleted and the person never told to come back. And it limits the
banner and the voice to 30 seconds each, so a hung `osascript` or `say`
can no longer hold the lock, and with it every other project's keyboard
tests.

`test/integration/support/keyboard_notice.rb` is now a thin wrapper that
keeps Tokra's policy: it takes the lock on macOS outside CI, and adds
`TOKRA_QUIET` to the gem's `DESKTOP_INPUT_QUIET`. Its tests check that
policy and that mapping against a real `DesktopInputLock` on a temporary
lock, not the protocol.

The gem has no per-project option to skip the lock on CI, which the
protocol section above expected. Tokra's own `locks?` guard in the
wrapper does that job instead, so Tokra still skips the lock on CI.

The gem's default instance also reads `DESKTOP_INPUT_LOCK`, which points
a session at a lock of its own (with its marker beside it), and Tokra
now inherits that.

## Amendment, 2026-11-03: the real-window tests leave the maintainer's session

On the maintainer's Mac the real-window tests, `test:keyboard`
included, now run in the hidden `tokratest` session (Plan 056), whose
jobs each get the account's own lock (`DESKTOP_INPUT_LOCK`, which
`hidden-run` sets) and run with `TOKRA_QUIET=1`, since no one there
hears the notice. Nobody is asked to step away during the gate there.
The lock and the spoken notice above still apply where the tests run
in a person's session: a local run on a Mac with
`TOKRA_REAL_WINDOWS=local`. CI skips the lock as before.

Since Plan 057, `test:console` runs the few tests that need the
console in the maintainer's session, holding this lock as one spoken
span around only those tests; none of them takes the keyboard, but a
click on one of their dialog sheets could end it.

## Amendment, 2026-11-03: one spoken span for each keyboard run

The maintainer's rule, verbatim: "If it could possibly fail if I
continue to use my keyboard/mouse/etc. it should speak and show a
notification. Otherwise, no." And: "it should ONLY wrap the tests that
can fail (which should all happen at once, not scattered multiple times
per run) in such a speaking block-around style run, not the whole
suite."

`test:console` already speaks once, around only its tests. The keyboard
tests did not: each launch took its own span, the gem called the person
back once three seconds passed between them, and the next launch sent
them away again, so one `test:keyboard` run could speak several times.
They now call `KeyboardNotice.take_the_keyboard_for_the_run`, which
takes the gem's shared lock with `DesktopInputLock.acquire` and gives it
back only as the test process exits. `test:keyboard` runs only keyboard
tests, in one Minitest process, so that span runs from the first launch
to the end of the run: one step-away, one come-back, and other projects
wait on the lock throughout. A later call in the same process nests
inside the first span, as the gem's spans do, and says nothing, since
the marker names this live process.

The release is an `at_exit` registered after the gem's own, so it runs
first and the gem's exit handler finds the lock free and calls the
person back. `Minitest.after_run` would not do: Minitest registers the
handler that runs it before any test runs, so it would run after the
gem's, which would find its own process still holding the lock and
leave the person away. Holding the lock in the rake parent around the
Minitest child, as `test:console` does, would not do either: a keyboard
test file run directly, outside `rake test:keyboard`, must still lock,
so the tests themselves take the lock, and a child that took it while
its parent held it would wait on that parent forever.

In tokratest, where every Tokra job shares the account's own lock, the
keyboard runs of gates in parallel checkouts now take turns a whole
process at a time, where before they interleaved launch by launch.

`test:console` keeps the block form, `taking_the_keyboard`, since it is
a rake process whose console tests run in child processes that take no
lock. `TOKRA_QUIET`, `DESKTOP_INPUT_QUIET`, and CI behave as before: the
run's span is silent under either quiet variable and takes no lock on
CI.
