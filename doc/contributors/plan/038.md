# Plan 038: Asking to exit, and keeping the app alive

Plans 018, 020, and 022 deferred `RunEvent::ExitRequested`. Tokra's
`RunEvent::ExitRequested` was a declared shape no code ever emitted, its
`api` member was missing, `AppHandle#exit` raised `SystemExit` at once, and
closing the window ended the loop in Rust before Ruby could object. A Tauri
app answers both moments: it keeps a window open with
`CloseRequestApi::prevent_close`, and keeps running with no windows, a tray
app's usual life, with `ExitRequestApi::prevent_exit`. This plan ports both
requests and the window lifecycle they ride on.

## How Tauri ends an app

A close request runs the window's listeners, then the run callback with
`WindowEvent::CloseRequested { api }`. Unless a handler called
`api.prevent_close()`, the runtime drops the native window
(`on_window_close`). The window's `Destroyed` event follows from the
platform: the run callback hears `WindowEvent::Destroyed` (the manager has
already dropped the window), then the listeners, and the runtime removes
the window and its webviews from its store. If that left no windows, it
emits `RunEvent::ExitRequested { code: None }` and, unless a handler called
`api.prevent_exit()`, sets `ControlFlow::Exit`.

`AppHandle::exit(code)` sends `Message::RequestExit(code)` through the loop
proxy, even on the main thread, and returns. The loop emits
`ExitRequested { code: Some(code) }` and exits unless prevented. If the
proxy is gone, `exit` logs, cleans up, and calls `process::exit(code)`.
The loop's end emits `RunEvent::Exit`. Plugins hear every run event before
the run callback.

The runtime reads the handlers' answer once, right after the callback
returns (`rx.try_recv()`): a prevention sent later is ignored, and no
answer means proceed. `prevent_exit` does nothing when the code is
`RESTART_EXIT_CODE` (`i32::MAX`), so a restart cannot be refused.

## Decisions

1. **The answer travels back as the dispatcher's result.** Tauri's runtime
   passes a channel and reads it after the callback. Ruby owns the window
   store (ADR 005), so Ruby decides; the native loop asks. For
   `Native::ExitRequestedEvent` and `Native::WindowDestroyedEvent` the
   App's dispatcher answers `true` to end the loop, and the loop sets
   `ExitWithCode(code)` or `Exit`. Any other answer, or an exception the
   loop must report, keeps it running. The other events' answers are
   ignored. The loop acts in the same callback, as Tauri's does, so no
   event slips in between the decision and the exit.

2. **A raising handler does not cancel the default.** Tauri proceeds when
   no prevention arrived; a panicking handler aborts the process. Tokra
   reports a handler's `StandardError` and keeps the loop, so the close,
   the destroy, and the exit request report it the way the loop does
   (`full_message`, to `$stderr`) and then proceed unless a handler
   prevented first. Before this plan a raising close handler also could
   not stop the exit. `SystemExit` and signals pass through as before.

3. **The native window closes for real.** `Native::Window#close` and
   `Native::WebView#close` drop the tao window and the wry webview on the
   main thread, as `on_window_close` and the store removal do. A closed
   native window ignores setters, answers `nil` for its title (Tokra::Window
   raises `Error::Runtime` "failed to receive message from webview", the
   getter Tauri leaves unanswered), and `Unavailable` for its handles; a
   closed webview ignores `eval`. tao's `Destroyed` reaches Ruby as
   `Native::WindowDestroyedEvent`, through the same inbox as close requests.

4. **`AppHandle#exit` asks.** It sends the request through the loop proxy
   (`Native::Proxy#request_exit`) on any thread and returns `nil`, so code
   after it runs, as in Tauri. Before the loop exists the request waits
   for `RuntimeContext#attach`, in order with queued tasks. Once the loop
   is gone it falls back to `Kernel.exit(code)`, Tauri's
   `process::exit(code)` in Ruby's form. A `Kernel#exit` of the app's own
   still ends the loop at once with no `ExitRequested`, as
   `process::exit` would in Rust.

5. **The process keeps `code`.** Tauri's loop sets `ControlFlow::Exit`,
   which is `ExitWithCode(0)`, so `exit(7)` ends a Tauri process with
   status 0 on every path but the fallback, which uses 7. That is tao's
   default, not a choice: the API takes a code, documents it as the exit
   code, and uses it whenever it can. A Ruby `exit(7)` that ends with 0
   breaks the language's contract (precedence tier 1), and Tokra has
   ended with `code` since Plan 018, so the loop sets `ExitWithCode(code)`.

6. **`Window#close` uses the close button's path.** It sends
   `Native::Proxy#request_close`, which arrives as the same
   `Native::WindowCloseEvent`, so handlers run on a later turn, never
   inside the caller, as Tauri routes `Close` through the proxy.
   `Window#destroy` closes the native window on the main thread
   (`run_on_main_thread`), skipping `CloseRequested`; on the main thread it
   runs at once, where Tauri queues it, but `Destroyed` comes later from
   the platform either way.

7. **Signals do not ask.** Tauri installs no signal handler, so a signal
   ends its process with no event at all. Plans 018 and 034 chose Ruby's
   semantics: Ctrl-C ends the loop with status 0 and `SIGTERM` unwinds it,
   and both deliver `RunEvent::Exit` the way `ensure` runs. Neither is an
   exit request: no `ExitRequested` fires and neither can be prevented. An
   app that wants to refuse `SIGTERM` traps it.

## Verification

- Stub-native tests drive a real `App`: close then destroyed then exit
  requested then exit, in order; `prevent_close` keeps the window and the
  loop; `prevent_exit` keeps the loop after the last window; `exit(code)`
  emits `ExitRequested(code)` and ends with `code`; a prevented exit
  request keeps running; `prevent_exit` is ignored for `RESTART_EXIT_CODE`;
  a raising handler does not cancel the default; plugins hear each event
  before the callback; `exit` from another thread and before `run`.
- Real-window tests (`exit_requested` fixture, Prohibited policy): the page
  asks Ruby to close the window, and the app (a) exits with status 0 after
  `Destroyed` and `ExitRequested(nil)`, (b) prevents the exit, keeps
  running with no window, answers a later `AppHandle#exit(code)` from a
  thread with `ExitRequested(code)`, and ends with `code`.
- Mutation checks by hand, recorded under Results.

Untested without a person at the machine: the close button itself (the
fixtures use `Window#close`, which shares its path from `WindowCloseEvent`
on), and the Dock behavior of a windowless app with the Regular policy.

## Out of scope

- `AppHandle#restart` and `#request_restart`: they need Tauri's `process`
  module (`Env`, `current_binary`, `process::restart`), and what "the
  current binary and its arguments" means for a Ruby script needs its own
  design. `RESTART_EXIT_CODE` and its `prevent_exit` rule land now, so
  until restart lands `exit(RESTART_EXIT_CODE)` cannot be prevented and
  ends the process with status 255, the low byte of `i32::MAX`.
- `RunEvent::Reopen` and the other macOS app events.
- The `tauri://close-requested` and `tauri://destroyed` events Tauri emits
  to the page (`manager/window.rs:162-176`), and the JS close listener
  that prevents the close; Tokra emits no window events to the page yet.
- `cleanup_before_exit`: Tokra's resource tables hold Ruby objects the
  process frees.

## Risks

- Dropping a tao window inside the callback makes tao emit `Destroyed`
  re-entrantly on macOS and Windows; tao queues events raised during a
  callback, and Tauri drops its window in the same place.
- A windowless app still owns the loop's background threads (the
  interrupt ticker, the GVL hand-off); they behave as with a window.
