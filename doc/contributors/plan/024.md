# Plan 024: tokra-notification on ferro-notify-rust

Tauri's official notification plugin shows desktop notifications and
backs the page's `window.Notification`. This plan ports its desktop side
as `tokra-notification`, a pure Ruby gem in `plugins/notification` over
`ferro-notify-rust`, the one-to-one Ruby binding of notify-rust that ADR
011 calls for. The frontend keeps using `@tauri-apps/plugin-notification`
unchanged.

Sources: `tauri-plugin-notification` 2.3.3 at plugins-workspace
`d4613ff0`, the commit plans 021 and 023 ported from and the one nearest
`vendor/tauri` (`9f0306fbc`): `src/lib.rs`, `src/desktop.rs`,
`src/commands.rs`, `src/models.rs`, `src/error.rs`, `src/init-iife.js`,
`guest-js/index.ts`, `guest-js/init.ts`, `api-iife.js`, `build.rs`,
`Cargo.toml`, `permissions/default.toml`. The workspace's `Cargo.lock`
pins notify-rust 4.11.7, mac-notification-sys 0.6.4, time 0.3.41, url
2.5.4, idna 1.0.3, and serde_json 1.0.140; time, url, and idna were read
from their crates.io packages at those versions. Tauri core:
`crates/tauri/src/plugin.rs:1012-1061` (`PermissionState`) and
`crates/tauri/src/lib.rs:313-316` (`is_dev`). The binding:
`ferro-notify-rust` 0.1.0.pre.1 at its tag
`ferro-notify-rust/v0.1.0.pre.1` (commit `e49610a`; notify-rust
4.18.2, mac-notification-sys 0.6.15), its README, and its plan 003. The
plugins-workspace trunk has since rewritten the plugin (2,084 changed
lines, new desktop actions); this port stays at `d4613ff0` so every
Tokra plugin answers to the same Tauri.

## Context

On desktop, Tauri's plugin is small. Its invoke handler holds three
commands, `notify`, `request_permission`, and `is_permission_granted`
(`lib.rs:224-228`). Permission is always granted (`desktop.rs:61-67`).
`notify` deserializes the whole `NotificationData`, but the desktop
`show` reads only the title (or the product name), the body, the icon,
and the sound (`desktop.rs:26-53`), builds a notify-rust notification,
names the app on Windows and macOS, and spawns the send on the async
runtime, ignoring its result (`desktop.rs:179-221`). Every other command
the guest JS knows (`register_action_types`, `get_pending`, `cancel`,
`get_active`, `remove_active`, the channel commands, `registerListener`)
exists only on mobile, so on desktop the invoke falls through and Tauri
rejects it with `Command NAME not found`.

Tokra dispatches every invoke on the main thread while the event loop
holds the GVL (ADR 012). notify-rust's send blocks: a D-Bus round trip on
Linux, and on macOS a wait of up to two seconds for the notification
center to confirm delivery (mac-notification-sys 0.6.15
`objc/notify.m:160-180`). A send on the main thread would freeze the
window for that long.

## Decisions

1. **The gem mirrors the crate's layout.** `Tokra::Plugins::Notification`
   holds `Plugin` (the commands and init script), `Notification` (the
   managed state, `desktop.rs`), `NotificationExt` (`notification` on
   every manager), `NotificationBuilder`, and the model types
   `NotificationData`, `Attachment`, `Schedule` (`At`, `Interval`,
   `Every`), `ScheduleInterval`, and `ScheduleEvery`, with Tauri's names.
   Builder setters return the builder, as dialog's do; the flag setters
   (`group_summary`, `ongoing`, `auto_cancel`, `silent`) take no argument
   and set the flag, as Tauri's do. `extra` stores the value as JSON
   reads it back, as `serde_json::to_value` does. The private `imp`
   module's `Notification` becomes `Imp::Notification`, marked
   `:nodoc:`, with the build split from the send so tests can read what
   reaches notify-rust without showing anything.

2. **`PermissionState` joins Tokra's core.** It is
   `tauri::plugin::PermissionState`, which every permission-asking
   plugin shares, so it lives beside `Tokra::PluginApi` as
   `Tokra::PermissionState`: `Granted`, `Denied`, `Prompt` (the default),
   and `PromptWithRationale`, serializing as `granted`, `denied`,
   `prompt`, and `prompt-with-rationale`. The plugin re-exports it as
   Tauri's `pub use` does. Its `Deserialize` has no caller in Tokra and
   is left out.

3. **The send runs on a thread; the command does not wait for it.** The
   command checks its arguments and runs `show` on the main thread, where
   the invoke arrives. `show` builds the notification and names the app
   there, as Tauri's async command does on its worker, then starts a Ruby
   thread for notify-rust's `show`, which releases the GVL, and returns.
   The command resolves `null` at once, as Tauri's does after its
   `spawn`. An error from the send is dropped, as Tauri's `let _` drops
   it; only `Ferro::NotifyRust::Error` is rescued, so a bug in Tokra
   still reports. The main thread never waits on D-Bus or the
   notification center.

4. **macOS names the app by its identifier.** Tauri passes
   `com.apple.Terminal` when `is_dev()`, which is true when the app is
   built without the `custom-protocol` feature, and the identifier
   otherwise. Tokra always serves its pages through its own protocol
   (`tokra://`, `App#tokra_protocol_url`), which is what
   `custom-protocol` turns on, so
   `is_dev()` is false and the plugin passes `config.identifier`, or an
   empty string while Tokra has no config file to set one. An identifier
   no installed app has (an app run from source, as Tokra apps are today)
   makes mac-notification-sys answer `CouldNotSet` and send as Terminal
   anyway (`objc/notify.h:25-33`), which is what Tauri's dev builds show.
   An app run from source on a Mac that also has the installed app with
   the same identifier notifies as that installed app, as a Tauri
   release binary run outside its bundle would.
   Tauri ignores the result, and so does the plugin. The call changes
   process-wide state: notify-rust swaps `NSBundle`'s bundle identifier
   once per process and the first `set_application` wins, so an app that
   calls `Ferro::NotifyRust.set_application` first keeps its choice, and
   no other library in the process may link notify-rust or
   mac-notification-sys (ADR 011's table). The README and RDoc say so.

5. **Windows names no app.** Tauri sets the toast's AppUserModelID only
   "when running the installed app", judged by whether the executable
   sits in a Cargo target folder; its crate metadata notes that
   development builds show PowerShell's name and icon. A Tokra app runs
   inside `ruby.exe`, and no installer registers an AppUserModelID for
   it, so the plugin never sets one and toasts come from PowerShell, as
   in Tauri's development builds. Reading Tauri's check literally would
   always set the identifier, and Windows does not show toasts for an
   unregistered ID (UNVERIFIED here; no Windows machine). Deviation, tier
   1, until Tokra packages apps. The `windows7-compat` feature also has
   no port: Rust dropped Windows 7 from Tokra's Windows target in 1.78,
   so `notify` on Windows 7 cannot run, and on every other Windows the
   feature's `notify` is `show`.

6. **Arguments are checked in serde's words.** `notify` reads `options`
   as serde reads `NotificationData`: keys in the order the object gives
   them, unknown keys ignored, missing ones defaulted, and the first bad
   value rejecting the invoke with Tauri's `invalid args `options` for
   command `notify`: ...` and serde_json's text. That covers `i32` and
   `u8` ranges, booleans that are `#[serde(default)]` and so refuse
   `null`, the externally tagged `Schedule`, the custom `ScheduleEvery`
   (`unknown every kind 'x'`), `Attachment`'s `url` through url 2.5.4's
   `Url::parse` (`relative URL without a base: "x"`), and
   `Schedule::At`'s `date` through time 0.3.41's ISO 8601 parser
   (`the 'year' component could not be parsed`, and the rest). The ISO
   8601 parser is ported whole, since its errors depend on the order it
   tries date, time, and offset (retired by plan 031, which reads dates
   with ferro-time and leaves a time-version difference). The URL check
   ports url's error paths:
   the scheme, the authority, ports, IPv4 and IPv6 hosts, opaque hosts,
   and idna's ASCII deny list. Deviations: a host with non-ASCII
   characters or an `xn--` label is accepted without UTS 46 processing,
   which Ruby has no tables for (closed by plan 030, which reads URLs
   with ferro-url and leaves only a Unicode-version difference); time's
   `large-dates` feature is assumed off (years -9999 to 9999), which
   plan 031 confirmed: no manifest in the plugin's dependency tree
   enables it; `-0` reads as the integer 0 in Ruby's JSON, while
   serde_json reads a float, so Tauri rejects `{"id": -0}` and Tokra
   accepts it (core's JSON layer); a float with more digits than a double
   holds may print differently in its last digit, since serde_json's
   parser without `float_roundtrip` rounds some differently; strings in
   messages are escaped by Rust's Debug rules from Ruby's Unicode tables,
   which may be a version apart from Rust's; a JSON array where serde would read a struct field by
   field rejects as a type error, as in plan 023; and floats print as
   Ruby prints them. The values parsed this way are kept, but desktop
   uses none of them beyond the four `show` reads, as in Tauri.

7. **No error is reachable.** Tauri's desktop `Error` has one variant,
   `Io`, reachable only through `current_exe` on Windows, which decision
   5 removes. A failed send is dropped. So `show` raises nothing, and the
   plugin defines no error class.

8. **The init script ships; the global API script waits.** As in plan
   023, decision 9: `init-iife.js` is packaged unchanged under `lib/`
   with a `.license` sidecar, and the plugin substitutes
   `__TEMPLATE_windows__` at load as `lib.rs` does. `api-iife.js` is a
   test fixture only.

9. **The dependency is the release tag.** Both Gemfiles name
   `ferro-notify-rust` as a git source at tag
   `ferro-notify-rust/v0.1.0.pre.1` (release commit `e49610a`) with the
   glob `gems/notify-rust/*.gemspec`, so Bundler keeps taking
   ferro-arboard and ferro-rfd from their own tags. Work began on commit
   `c4b1c5b`; the tag adds only Windows fixes (a Clippy lint and a
   compile error in `windows.rs`). The gemspec pins `= 0.1.0.pre.1`. A
   released `tokra-notification` waits for `ferro-notify-rust` on
   RubyGems.org. Plan 030 moves to `ferro-notify-rust/v0.1.0.pre.2` and
   adds `ferro-url`.

## Results

Every decision above is done; decisions 5 and 8 defer what they name,
with their reasons.

- An oracle checked the argument port: a scratch crate compiled Tauri's
  `models.rs` with the locked serde, serde_json, time, url, and idna and
  deserialized each input with `serde_json::from_value`. The Ruby port
  matched it on 4,066 ISO 8601 strings (66 chosen, 4,000 fuzzed; values
  and messages; the port since retired by plan 031), on 6,057 URLs
  except 6 fuzzed hosts with `xn--` labels
  (decision 6's deviation, since closed by plan 030), and on 5,069 whole
  options objects. The
  oracle found what reading the source had missed: serde_json without
  `preserve_order` stores objects in a BTreeMap, so serde reports the
  first bad field in key order, not the order the frontend sent; and
  serde_json prints floats through ryu (`1e16`, `0.00001`), not Rust's
  `Display`. A float with more digits than a double holds can print
  differently in its last digit, because serde_json's parser without
  `float_roundtrip` rounds some of them differently than Ruby's JSON
  does (517 of 3,000 fuzzed floats). The tests embed 200 of the oracle's
  answers.
- The same oracle shows plan 023's dialog arguments read objects in the
  order the frontend sent them; Tauri reads them in key order. That only
  changes which of two bad fields a message names. Left for a follow-up.
- Linux, in a `ruby:4.0` container under Xvfb with dunst on the suite's
  bus: all 35 runs pass (6 skips: the macOS and Windows tests), including
  the real window, which sent through `invoke`, `sendNotification`, and
  `new Notification`, and dunst received each with its summary, body,
  icon, and `sound-name` hint.
- macOS: the four child tests pass, and the window test passes without
  sending. One early run of the commands test sent a notification from
  the test process before the guard existed; the test support now makes
  the test process refuse to name the app or send on macOS.
- Manual mutation checks, each reverted after: sending on the calling
  thread instead of a new one fails
  `test_notify_resolves_while_the_send_waits`; dropping the product-name
  fallback fails `test_without_a_title_the_product_name_is_the_summary`;
  reading object keys in sent order fails
  `test_the_first_bad_field_in_key_order_is_reported`; naming Terminal
  instead of the identifier fails `test_the_app_is_named_by_its_identifier`;
  dropping `auto_icon` fails
  `test_without_an_icon_notify_rust_picks_the_programs_own`; dropping the
  `__TEMPLATE_windows__` substitution fails
  `test_the_init_script_is_tauris_file_with_the_platform_filled_in`;
  moving ryu's decimal cutoff fails `test_each_value_reads_as_serde_reads_it`
  (it survived until the 1e-5 and 1e15 cases were added); dropping idna's
  deny list fails `test_each_url_parses_as_url_parses_it`; dropping the
  trailing-input check fails `test_each_date_parses_as_time_parses_it`;
  on Linux, dropping the sound fails
  `test_notify_sends_the_title_body_icon_and_sound`; after review,
  skipping the leap-second check fails
  `test_each_date_parses_as_time_parses_it`, dropping the NUL escape or
  narrowing the Unicode escapes fails
  `test_each_value_reads_as_serde_reads_it`, and storing NaN as given
  errors `test_extra_stores_non_finite_floats_as_null`.
- `bundle exec rake` from a clean build on Ruby 4.0.9 (macOS): 536 core
  runs (4 skips), 60 clipboard, 57 dialog (11 skips), 36 notification (7
  skips: the Linux and Windows tests), and 83 log runs pass; RuboCop,
  Steep, RBS validation and parity, RDoc (100%), REUSE, Clippy, fmt, and
  the packaging check pass. `rake package:install` builds
  ferro-notify-rust from its tag and the notification smoke builds a
  notification from the installed gems.
- UNVERIFIED until CI runs: all of Windows, including decision 5.

## Follow-ups

- Review item 6: dialog and notification each carry their own serde
  argument reader; a shared InvalidArgs reader belongs in core once a
  third plugin needs one, and would also fix dialog's key order. Done in
  plan 026: core's `CommandItem` reads every plugin's arguments and raises
  `Tokra::Error::InvalidArgs`, which the plugins rescue in place of any
  `ArgumentError`, and dialog reads objects in key order. The value
  readers stay in each plugin (plan 026, decision 4).
- `NotificationBuilder#data` is a public `attr_accessor`, where Tauri's
  field is `pub(crate)`, and the builder's `id` is not range-checked,
  where Tauri's `i32` type enforces it (review item 11).

## Out of scope

- Mobile (`mobile.rs`): pending, active, cancel, channels, action types,
  listeners, and the `PendingNotification` and `ActiveNotification`
  types only it returns.
- Plugin global API scripts (decision 8).
- Windows 7 (decision 5).

## Risks

- CI on Linux and Windows is unverified until it runs.
- The URL check is a partial port of a large parser (decision 6).
  Retired by plan 030: url itself, through ferro-url, reads the URL.
- The ISO 8601 parser is a port too. Retired by plan 031: time itself,
  through ferro-time, reads the date.
