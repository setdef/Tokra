# Plan 023: tokra-dialog on ferro-rfd

Tauri's official dialog plugin opens the system's file and message
dialogs: open, save, message, ask, and confirm. This plan ports it as
`tokra-dialog`, a pure Ruby gem in `plugins/dialog` over `ferro-rfd`, the
one-to-one Ruby binding of rfd that ADR 011 calls for. The frontend keeps
using `@tauri-apps/plugin-dialog` unchanged.

Sources: `tauri-plugin-dialog` 2.6.0 at plugins-workspace `d4613ff0`, the
commit plan 021 ported the clipboard from and the one nearest
`vendor/tauri` (`9f0306fbc`): `src/lib.rs`, `src/desktop.rs`,
`src/commands.rs`, `src/models.rs`, `src/error.rs`, `src/init-iife.js`,
`guest-js/index.ts`, `guest-js/init.ts`, `api-iife.js`, `build.rs`,
`permissions/default.toml`; `tauri-plugin-fs` `src/file_path.rs` at the
same commit for `FilePath`; dunce 1.0.5 `src/lib.rs` for
`FilePath::simplified`; serde_json 1.0.150 `src/value/de.rs` for the
deserializer's messages (Tauri's workspace locks 1.0.140; the messages
used here have not changed between them, UNVERIFIED line by line);
`ferro-rfd` 0.1.0.pre.2 at its tag `ferro-rfd/v0.1.0.pre.2` (commit
`5f105f4`, rfd 0.17.2; Tauri locks rfd
0.16.0, and 0.17's changes are the removed `tokio` and `async-std`
features and a portal path fix, none observable here); rfd 0.17.2
`src/backend/macos/modal_future.rs` and `utils/user_alert.rs`.

## Context

Tauri's commands are `async`, so each runs on a worker thread. Each calls
a `blocking_*` method (`lib.rs:68-77`), which hands a closure to
`run_on_main_thread`. On the main thread the closure builds rfd's async
dialog, which on macOS opens a sheet on the window and returns a future,
and spawns a thread that blocks on the future and sends the answer back
to the worker (`desktop.rs:142-257`). No thread that runs the event loop
ever waits for the user.

Tokra dispatches every invoke on the main thread, inside the event loop,
holding the GVL (ADR 012). A dialog shown there with a synchronous call
would freeze the window until the user answered, and on macOS a sheet
finishes only on the main thread's run loop, so waiting for it there
never ends.

## Decisions

1. **The gem mirrors the crate's layout.** `Tokra::Plugins::Dialog`
   holds `Plugin` (the commands and init script), `Dialog` (the managed
   state, `desktop.rs`), `DialogExt` (`dialog` on every manager),
   `MessageDialogBuilder`, `FileDialogBuilder`, and the model types
   `MessageDialogKind`, `MessageDialogButtons`, `MessageDialogResult`,
   `PickerMode`, and `FileAccessMode` (`models.rs`, `lib.rs:47-61`), with
   Tauri's names and variants. Builders return themselves from each
   setter, as ferro-rfd's do; Tauri's consume and return `self`.

2. **Threads follow Tauri's, step for step.** A command validates its
   arguments on the main thread, where the invoke arrives, and then runs
   on a new Ruby thread, as Tauri's async command runs on a worker. There
   it calls the `blocking_*` method, which waits on a queue while
   `run_on_main_thread` sends the start to the main thread. On the main
   thread the builder becomes a ferro-rfd `AsyncFileDialog` or
   `AsyncMessageDialog`, its terminal method returns a `Future` at once
   (on macOS after opening the sheet), and a new Ruby thread waits in
   `Future#value`, which releases the GVL, then calls the callback. So
   the main thread never waits for the user, other Ruby threads keep
   running, and on macOS the sheet finishes on the loop it needs.
   ferro-rfd's reviewer warned that a synchronous dialog dispatched to the
   main thread would run its modal there and stall Ruby; this design never
   does that. The callback methods (`pick_file { |path| }`, `show { |ok| }`)
   are Tauri's non-blocking API and work from the main thread; the
   `blocking_*` methods, as in Tauri, must not run on the main thread,
   where on macOS they would wait forever. An exception from rfd (a panic
   ferro-rfd turns into `Ferro::Rfd::Error`) ends the waiting thread in
   Tauri, and the blocked caller panics on the dropped channel; here the
   `blocking_*` caller raises it, and a command rejects with its message,
   so every invoke settles. A blocking caller sends the start as a
   `RuntimeContext` getter, so a loop that has ended, or ends with the
   start still queued, fails the caller with Tauri's runtime messages
   instead of leaving it on its queue forever (Tauri's caller panics on
   the dropped channel). The block forms send it with
   `run_on_main_thread` and drop a start the loop cannot take, as
   Tauri's `let _ =` does. Each terminal method builds rfd's dialog from
   the builder when it is called, as Tauri consumes the builder then.

3. **No parent window, for now.** (Superseded by ADR 013 and plan 028:
   the commands now parent dialogs on Windows and X11; and by plan 035:
   on macOS too, where each dialog is a sheet on the window.) Tauri parents
   every dialog to the command's window through raw-window-handle
   (`commands.rs:129-132`,
   `231`, `278-281`). ferro-rfd binds only Win32 and X11 handles, never
   AppKit or Wayland, whose handles are pointers rfd follows. Tokra has no
   port of Tauri's `HasWindowHandle` for its windows yet, and a native
   getter in `ext/tokra` is not enough on its own: it needs Ruby values
   for each raw-window-handle variant in Tokra's core, its threading rules
   (the handle is valid only on the main thread and only while the window
   lives), and tao's X11 display handle opens a new X connection on every
   call (tao 0.34.5 `platform_impl/linux/window.rs:975-999`). That is its
   own port, best done with the windowing ADR that ADR 011 §1 defers, and
   this machine cannot run its Windows half. So the commands pass no
   parent. Consequences, all documented in the README and RDoc:
   - macOS: rfd puts file dialogs on the app's main window as a sheet
     anyway (`modal_future.rs:69-73`), as Tauri does for a one-window app.
     Message dialogs without a parent become a system alert on a thread of
     rfd's own (`message_dialog.rs:171-183`, `user_alert.rs:177-196`),
     not a sheet on the window. Deviation, tier 1: ferro-rfd cannot take
     an AppKit handle safely.
   - Windows and X11: the dialogs are not owned by the window, so the
     window still takes input behind them. Deviation; deferred to the
     `HasWindowHandle` port.
   - Wayland: no parent, as for any Wayland handle in ferro-rfd.
   The builders keep Tauri's `parent` and `set_parent`, taking any object
   that answers `window_handle` and `display_handle` with ferro-rfd's
   handle values, and, as Tauri's do, keep it only when both answer
   (`lib.rs:287-302`, `460-478`).

4. **Backends are ferro-rfd's.** ferro-rfd builds rfd's portal backend on
   Linux (zenity for message dialogs and as the fallback) instead of
   Tauri's default `gtk3`, and leaves out `common-controls-v6`, so Windows
   message dialogs show the standard button labels for custom ones. Tauri
   supports the portal through its `xdg-portal` feature; the Windows
   labels are a deviation inherited from ferro-rfd's reasons (its README).
   Tauri's mapping of standard results to custom labels
   (`desktop.rs:227-253`) still makes the command return the label the
   frontend asked for.

5. **Arguments are checked in serde's words.** Each command reads its
   arguments by their camelCase wire names and rejects a missing required
   argument or a wrong type with Tauri's `invalid args `key` for command
   `name`: ...` and serde_json's text: `missing required key`,
   `invalid type: integer `1`, expected a string`, `missing field `name``,
   `unknown variant `x`, expected one of ...`, and the enum shapes of
   `MessageDialogButtons`. `MessageDialogKind` takes any string, ignoring
   case, and anything unknown as `info` (`models.rs:20-33`).
   `pickerMode` and `fileAccessMode` are checked and kept, and do nothing
   on desktop, as in Tauri. A JSON array where an options object belongs
   rejects as a type error; serde would read it field by field, which no
   client sends. Strings in messages are quoted as Rust's Debug quotes
   them. Floats use Ruby's formatting, which differs from serde_json's
   for exponents (`1.0e+20` where serde_json writes `1e20`); matching
   zmij's rules is not worth it for a type error no client provokes.

6. **Paths are Strings.** Tauri returns `FilePath`, whose desktop variant
   is always a path and serializes as one. Tokra has no fs plugin and no
   `FilePath`, so builders yield and commands resolve path Strings, after
   `FilePath::simplified`: dunce's rule that drops a `\\?\` prefix from a
   Windows path when that is safe, and nothing elsewhere.

7. **Scope side effects wait for the fs plugin and the asset protocol.**
   Tauri adds each picked path to the fs plugin's scope, when that plugin
   is registered, and to the asset protocol scope. Tokra has neither yet,
   so there is nothing to widen. The RDoc says so; the fs plugin port adds
   it back.

8. **The default title is the product name.** Tauri titles a message
   dialog with the package name, which is the configured product name or
   the crate's name. Tokra's `Config#product_name` has no setter yet and
   Tokra has no crate name, so the title is the product name or an empty
   string. Deviation until Tokra ports `PackageInfo`.

9. **The init script ships; the global API script waits.** `init-iife.js`
   is the plugin's `initialization_script`, packaged unchanged under
   `lib/` and read at run time. Tauri also injects `api-iife.js`, which
   defines `window.__TAURI__.dialog`, when the app sets `withGlobalTauri`.
   Tauri's build scripts collect those from every linked plugin crate;
   Tokra has no such step and no plugin ships one (App's RDoc, plan 016),
   so a page imports `@tauri-apps/plugin-dialog` through its bundler.
   The real-window test loads a copy of `api-iife.js` itself.

10. **The dependency is the release tag.** Both Gemfiles name `ferro-rfd`
    as a git source at tag `ferro-rfd/v0.1.0.pre.2`, as plan 021 names
    `ferro-arboard`; the root Gemfile globs only `gems/rfd`, so Bundler
    keeps taking `ferro-arboard` from its own tag. The gemspec pins
    `= 0.1.0.pre.2`. Work began on commit `1625415`; the tag adds only a
    test fix and the version bump. A released `tokra-dialog` waits for
    `ferro-rfd` on RubyGems.org.

## Verification

- Pure mappings (results, buttons, `ask`/`confirm` labels,
  `set_default_path`, dunce) run against ferro-rfd's real values.
- Argument validation runs through the real plugin on a real handle.
- Linux: every command runs end to end through rfd and a fake zenity, in
  a child process whose test thread plays the event loop for
  `RuntimeContext`, as Ferro's tests do.
- macOS: a real window serves a page that calls the real
  `api-iife.js`; the fixture ends each sheet through AppKit's
  `endSheet:returnCode:` on the main thread and the page checks the
  results.
- Manual mutation checks, listed in Results.
- `bundle exec rake` from a clean build.

## Untested without a person

- Message dialogs on macOS: rfd shows a system alert that only a person
  can dismiss, so the macOS suite checks their mapping, not the alert.
- Windows: no Windows machine has run any of it.

## Results

Every decision above is done; decisions 3, 7, and 9 defer what they name,
with their reasons.

- Real dialogs ran on macOS 27: the window fixture saved through a real
  sheet to `<tmp>/out.txt`, cancelled an open and a multiple open (both
  `null`), and answered `plugin:answer|ping` while a folder sheet stayed
  open for a second. `-[NSSavePanel ok:]` raises "not implemented" for
  the out-of-process panels of recent macOS, so the fixture ends sheets
  with `-[NSWindow endSheet:returnCode:]`. The windowless macOS tests
  cancel the fallback modal for open, folders, and save.
- Manual mutation checks, each reverted after:
  awaiting the future on the main thread instead of a new thread fails 4
  window checks (the macOS child tests still pass, since their fallback
  modal is synchronous); dropping the Cancel-to-label mapping fails
  `test_a_standard_result_for_custom_buttons_becomes_the_label`; defaulting
  `can_create_directories` to false fails
  `test_a_file_dialog_may_create_directories_unless_told_otherwise`;
  making `defaultPath` always the folder fails 4 default-path tests and 2
  window checks; dropping the worker's reject fails
  `test_a_failure_opening_the_dialog_rejects`, as does not forwarding a
  main-thread failure; narrowing the plugin's `ArgumentError` rescue
  errors 7 command tests.
- A review added tests and fixes: commands reject with the runtime's
  messages when the loop has ended or drops their queued start (not
  forwarding the getter's failure fails 2; starting through
  `run_on_main_thread` fails 1); the block forms run on the main thread
  (a cancelled `pick_file` block on macOS, and `show`, `show_with_result`,
  and every file block form on Linux; yielding the wrong value fails 2 on
  macOS); strings in messages are quoted as Rust's Debug does (`inspect`
  fails 1); the init script is checked against the upstream file's
  SHA-256; the window check confirms a sheet is attached before it
  pings; and the dunce code carries its own SPDX snippet and licence.
- `bundle exec rake` from a clean build on Ruby 4.0.9 (macOS): 532 core
  runs (4 skips), 60 clipboard, 57 dialog (11 skips: the Linux zenity tests
  and the Linux message checks), and 83 log runs pass; RuboCop, Steep,
  RBS validation and parity, RDoc (100%), REUSE, Clippy, fmt, and the
  packaging check pass. `rake package:install` builds `ferro-rfd` from its
  tag and the dialog smoke builds an rfd dialog from the installed gems.
- UNVERIFIED until CI runs: every Linux test (the fake zenity, the window
  fixture under Xvfb with D-Bus pointed nowhere, `libwayland-dev`) and all
  of Windows, including the Windows path rules in decision 6 and
  `set_default_path`.

## Out of scope


- Mobile (`mobile.rs`, Android and iOS).
- A native window-handle getter and Tauri's `HasWindowHandle` (decision 3).
- Plugin global API scripts (decision 9).
- fs and asset scopes (decision 7).

## Risks

- CI on Linux and Windows is unverified until it runs.
- A `blocking_*` call on the main thread hangs on macOS, as Tauri warns.
