# Plan 027: JsImage reads, then resolves

Plan 026 narrowed every plugin's rescue to argument errors, but left one
gap (its Follow-ups): `JsImage#into_img` both checked the payload's shape
and resolved it, and reported a bad shape as a plain `ArgumentError`. So
clipboard turned that one call's `ArgumentError` into `InvalidArgs`, and
core's `image` plugin, whose own argument readers raised `ArgumentError`
with messages Tauri never sends, still rescued any `ArgumentError`. A bug's
`ArgumentError` in either became a rejection that looked like the
frontend's fault. Core's `resources` plugin had the same invented message
for its `rid`.

## Fidelity audit

|---|---|---|---|

## Decisions

1. **`JsImage.deserialize` is serde's `Deserialize`.** It reads a JSON
   value as one of the four variants, in serde's order (Path, Bytes,
   Resource, Rgba), and raises `Ipc::CommandItem::Mismatch` with serde's
   <tt>data did not match any variant of untagged enum JsImage</tt>, so
   `CommandItem#deserialize` wraps it in `InvalidArgs` as Tauri's
   `CommandArg` does. `JsImage.new` is private, as Tauri's non-exhaustive
   variants cannot be built outside the crate. The variant is held as a
   Ruby value of its own class: the `String` itself for `PathBuf`, an
   `Array` of u8 for `Vec<u8>`, an `Integer` for `ResourceId`, and an
   `Image` for `Rgba`. Nothing is built from the path while reading it,
   since a `PathBuf` takes any string and `Pathname.new` raises
   `ArgumentError` for a NUL byte.

2. **`into_img` only resolves.** It raises what Tauri's does:
   `Error::BadResourceId`, `Error::Image`, or `Error::Io`. None is an
   `InvalidArgs`: Tauri's `into_img` runs in the command body, and
   clipboard's `?` turns its `tauri::Error` into the plugin's transparent
   `Error::Tauri`, whose Display is the core error's. Clipboard reads the
   argument with `deserialize`, then resolves it outside the block, and
   rescues no `ArgumentError`.

3. **No sequence form.** Plan 016 read `[rgba, width, height]` as the
   `Rgba` variant, reasoning from a plain struct's visitor. serde_derive
   omits `visit_seq` for untagged struct variants, and the locked serde
   rejects every such array. Tokra now does too.

4. **`Tokra::Error::Io` is Tauri's `Error::Io`.** `Image.from_path`
   raises it, displayed as the I/O error alone, as `#[error("{0}")]` is.
   A file Ruby cannot read keeps Ruby's `SystemCallError` message for now
   (Follow-ups). A path with a NUL byte gets Rust's message, checked
   before Ruby touches the path: Rust hands a Unix path to the OS as a C
   string and fails with <tt>file name contained an unexpected NUL
   byte</tt> (`small_c_string.rs:13-14`), and a Windows path as a wide
   string, failing with <tt>strings passed to WinAPI cannot contain
   NULs</tt> (`windows/mod.rs:99-104`, reached through `File::open`'s
   `maybe_verbatim`). Tokra picks the text by `Gem.win_platform?`. Image
   and clipboard rescue `Error::Io` in place of `SystemCallError`, which
   only `from_path` raised.

5. **The image plugin reads as Tauri's commands do.** `new` reads `rgba`
   (`Vec<u8>`), `width`, and `height` (`u32`) in order; `from_bytes` reads
   `bytes`; `from_path` reads `path` (`PathBuf`, whose visitor expects a
   <tt>path string</tt>); `rgba` and `size` read `rid` (`u32`), as
   `resources` reads `close`'s `rid`. Each goes through `CommandItem`, and
   the plugins rescue `Error::InvalidArgs`, so a bug's `ArgumentError`
   reaches `App#route_invoke`.

6. **`CommandItem.integer` is the shared integer reader.** Plan 026's
   decision 4 kept value readers in their plugins until a third needed the
   same one. Notification, image, and resources now read integers, and
   all three need serde's primitive visitors exactly: an integer out of
   range is <tt>invalid value: integer `256`, expected u8</tt>, anything
   else <tt>invalid type</tt>, and an integer past serde_json's range a
   float. That is one rule about serde, not about any plugin, so it moves
   to core: `CommandItem.integer(value, type)` for `u8`, `u32`, and
   `i32`, the types Tokra reads, raising `Mismatch` for use inside
   `deserialize` (a byte, a struct field), and `CommandItem#u32` for a
   whole argument. Notification's reader delegates to it. The struct and
   enum readers stay in dialog and notification, which still disagree on
   their shape.

## Steps

Each behavior change starts with a failing test.

1. `JsImage.deserialize` and a private `new`; mismatch tests call
   `deserialize` alone, and resolution failures come only from `into_img`.
2. Clipboard reads, then resolves (test: an `ArgumentError` while resolving
   reaches the caller).
3. The sequence form rejected (test: four arrays the oracle rejects).
4. The image plugin's readers and rescue (tests: 20 new messages and 4
   changed ones from the oracle, the largest u32 accepted, and a bug's
   `ArgumentError` raised).
5. `Error::Io` and the NUL path (tests: `Error::Io`'s message,
   `Image.from_path`, `JsImage`, the image plugin's `from_path`, and
   clipboard's `write_image`).
6. `CommandItem.integer` and `#u32` (test: 57 oracle answers for `u8`,
   `u32`, and `i32`); notification onto it (refactor, its 442 assertions
   unchanged); resources' `rid` (tests: 6 oracle messages, and a bug's
   `ArgumentError` raised).
7. Plan 026's follow-up marked; CHANGELOG's unreleased entries edited.

## Follow-ups

- `std::io::Error`'s Display. Tauri's `Error::Io` sends it, and Tokra
  sends Ruby's `SystemCallError` message instead
  (<tt>No such file or directory @ rb_sysopen - PATH</tt> where Tauri sends
  <tt>No such file or directory (os error 2)</tt>), in `Image.from_path`,
  so in the image plugin's `from_path` and `JsImage#into_img`. On Unix,
  Rust's format is <tt>{strerror} (os error {code})</tt> (core
  `io/error.rs:519-531`), and the strerror text matches what
  `SystemCallError` holds, so it is a matter of formatting. On Windows,
  Rust formats the Win32 error code with `FormatMessageW`, while Ruby maps
  that code to a POSIX errno, so the text differs and needs its own
  decision. It needs its own plan.
