# Plan 051: Honest closers and progress lines for the popup fixtures

The keyboard tests for context menus (plan 042, phase 3) and the tray
menu (plan 043) prove that other Ruby threads run while a menu tracks.
Each fixture opens a real menu, a second Ruby thread waits for a third
to tick and then closes it, and a fallback timer on the main thread
closes a menu that thread never reached. The test asserts that the
thread, not the fallback, closed each menu. This plan changes only
`test/`: no `lib/`, `ext/`, or `examples/` file.

## What Windows CI showed

On run 41555365228, attempt 1, the context-menu fixture's one launch
hung for 60 s on Windows and was killed. Its stdout and stderr were
empty (`status=0 termsig=nil timed_out=true seconds=60.01`; Ruby on
Windows reports a killed child as status 0). The rerun passed in
4.3 s. The fixture prints only its final `REPORT` line
(`fixtures/context_menu/app.rb:197`, `:200`), so nothing says where
it stopped.

Two more facts come from past Windows jobs. Across 16 of them, the
fixture's launch time splits in two: fast runs take 2 to 4 s, while
eight took 9.4 to 11.9 s and one took 22 s. A slow run matches the
8000 ms fallback timer (`app.rb:68-73`) closing a menu after the closer
thread's cross-thread `WM_CANCELMODE` (`support/platform_popup.rb:329`)
failed to. The tray fixture uses the same pattern and shows the same
slow runs (8.25 s on the rerun above).

The test cannot see this. The closer pushes `"thread"` onto
`dismissed_by` right after `PostMessageW` returns (`app.rb:96-97`),
before the menu has closed, so `dismissed_by.pop` answers `"thread"`
even when the fallback did the work. The same holds on macOS and
Linux: a closer whose close does nothing still passes, eight seconds
later.

The hang itself has three candidate causes, and the logs cannot tell
them apart: both closers failed, so `TrackPopupMenu` never returned;
WebView2 creation blocked in wry's `wait_with_pump` before the menu
ever opened; or the GVL and Fiddle's `TIMERPROC` callback deadlocked.

## Decisions

1. **Each fixture prints its progress.** `FixtureApp.progress(stage)`
   writes `PROGRESS <stage> <seconds>` and flushes. The seconds come
   from the monotonic clock, counted from when the fixture loaded, so
   two lines' gap is a duration. The tray fixture already printed
   `PROGRESS <stage>` with no time (plan 043, CI follow-ups); both
   fixtures now share the helper. The stages are `ready` (the Ready
   event, once the window and its webview exist), `menus-built`, and
   for each menu `<menu>:timers-set`, `<menu>:popup-called`,
   `<menu>:shown`, `<menu>:cancel-posted`, `<menu>:returned`, and
   `<menu>:fallback-fired`. On Windows the closer thread prints
   `<menu>:close-asked` too (decision 3). A hang then names its stage.
   Stuck after `ready` and before `<menu>:shown` points at the popup
   never showing. Stuck after `fallback-fired` with no `returned`
   means neither closer ended the menu. No `ready` at all points at
   window or WebView2 creation.

2. **The harness keeps what a hung app printed.** `Run#describe`
   already prints all of stdout. But `RealApp.launch` collected each
   stream inside its reader thread and handed it over only when the
   stream ended. A stream still open after the kill (a grandchild that
   inherited the pipe) came back as `(stream still open after 5 s)`,
   losing every line read so far. The readers now append to a buffer
   the harness owns, and `drain` returns what arrived, followed by
   that note.

3. **The proof is honest.** A fixture records which closer ended each
   menu. The fallback sets a flag when it fires while the popup has
   not returned. After the popup returns and the closer thread is
   joined, the fixture reports `"fallback"` if that flag is set,
   `"thread"` if the closer thread issued its close, and `nil`
   otherwise. So `"thread"` means the closer's request ended the
   menu, not the fallback. A menu can close some other way too: a
   Windows menu also closes when the app loses the foreground. So on
   Windows the main thread's timer checks that the menu is still up
   before it calls `EndMenu` and prints `cancel-posted`, and the test
   asserts `cancel-posted`, which a menu closed that way never
   prints. The fallback fires 8 s
   after the timers are set. The menu then shows on screen, so the
   order is causal, not a race the test could lose to a loaded
   machine.

4. **On Windows the closer asks, and the main thread ends the menu.**
   `EndMenu` ends the calling thread's menu, and the fallback has
   always ended the menu that way from a timer on the main thread,
   which the menu's modal loop runs. Every slow run shows that it
   works. So the closer thread now sets a flag, `close_asked`, and
   prints `close-asked`. The main thread's 50 ms timer, which already
   finds the menu, keeps running on Windows after it does. Once it
   sees the flag, it calls `EndMenu`, and on the tray it posts the
   chosen item's `WM_COMMAND`. Then it prints `cancel-posted`. The
   proof keeps its order: the menu closes only after the other thread
   has run, ticked, and set the flag while the menu tracked. Both
   fixtures change. `PlatformPopup::Win32.cancel` and
   `WM_CANCELMODE` have no caller left and go. macOS and Linux keep
   their closers (`-[NSMenu cancelTracking]` through GCD's main queue,
   GTK through `g_timeout_add`), which never needed the fallback.

   Why `WM_CANCELMODE` failed only sometimes is not settled.
   `DefWindowProc` cancels menu processing on it, but a posted message
   reaches a window only once the menu loop dispatches it. The
   decision rests on what CI shows: `EndMenu` on the main thread
   always worked, and the posted message sometimes did nothing.

5. **The stack dump on a timeout is deferred.** Running cdb
   non-invasively (`cdb -pv -p <pid> -c "~*kn 40; q"`) before
   `kill_group` would show each thread's stack in a hung app. It is
   cheap to write but cannot be verified here. It runs only on a
   Windows hang, which came once in about seventeen jobs. The gate
   step does not export the debugger path that the replay step builds
   (`ci.yml:205-213`, `tasks/test.rake:86-94`). Ruby and the extension
   on that runner are MinGW builds, so their frames have no PDB
   symbols. Only the system DLLs' frames would resolve, through
   Microsoft's symbol server, inside the bounded wait. The progress
   lines alone tell the three candidate causes apart (decision 1),
   and decision 4 may remove the first one. If a hang recurs and its
   last stage leaves the cause open, a follow-up adds the dump with
   that stage as its reason.

## Verification

- `test_other_ruby_threads_run_while_a_menu_tracks` and the tray's
  matching test keep their assertions: `"thread"` and one tick.
  Mutation, on macOS: make the closer thread's close a no-op
  (`close_appkit` returning at once when `on_main` is false). Before
  this plan the context-menu test passes anyway, after about 8 s per
  menu, because the closer reports `"thread"` regardless. After it,
  the test fails on `"fallback"`. The same mutation of the tray
  fixture's close fails its test. Linux runs the same `track` code
  through GTK's closer, so the mutation fails there too.
- A new test in each file checks the progress stages each menu
  passes, in causal order (`timers-set`, `popup-called`, `shown`,
  `returned`), and that the close was issued (`cancel-posted`).
  Deleting a progress call fails it.
- `test/integration/real_app_test.rb` checks that `drain` keeps the
  lines read from a stream that is still open, and drives
  `RealApp.launch` itself with `fixtures/open_stream`, a child that
  prints and exits while a grandchild holds its stdout open, with
  `launch`'s drain limit cut to 0.2 s. With launch's readers collecting
  into their own strings again, as before, that test fails, its stdout
  only `(stream still open after 0.2 s)`.
- Windows runs only in CI. The fix is confirmed when the Windows job's
  `ContextMenuTest` and `TrayMenuTest` launches take 2 to 4 s, with
  no 9 to 12 s runs, over several jobs, and when a failure's stdout
  shows `<menu>:returned` right after `<menu>:cancel-posted` (well
  under a second), with no `<menu>:fallback-fired`. A run whose
  fallback still fires now fails the test with `"fallback"` instead of
  passing slowly, and its progress lines say which stage stalled.
