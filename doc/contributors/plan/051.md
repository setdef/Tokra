# Plan 051: Honest closers and progress lines for the popup fixtures

The keyboard tests for context menus (plan 042, phase 3) and the tray
menu (plan 043) prove that other Ruby threads run while a menu tracks.
Each fixture opens a real menu, a second Ruby thread waits for a third
to tick and then closes it, and a fallback timer on the main thread
closes a menu that thread never reached. The test asserts that the
thread, not the fallback, closed each menu. This plan changes only
`test/`: no `lib/`, `ext/`, or `examples/` file.

## What Windows CI showed

On run 41555365228, attempt 1, the context-menu fixture's one launch
hung for 60 s on Windows and was killed. Its stdout and stderr were
empty (`status=0 termsig=nil timed_out=true seconds=60.01`; Ruby on
Windows reports a killed child as status 0). The rerun passed in
4.3 s. The fixture prints only its final `REPORT` line
(`fixtures/context_menu/app.rb:197`, `:200`), so nothing says where
it stopped.

Two more facts come from past Windows jobs. Across 16 of them, the
fixture's launch time splits in two: fast runs take 2 to 4 s, while
eight took 9.4 to 11.9 s and one took 22 s. A slow run matches the
8000 ms fallback timer (`app.rb:68-73`) closing a menu after the closer
thread's cross-thread `WM_CANCELMODE` (`support/platform_popup.rb:329`)
failed to. The tray fixture uses the same pattern and shows the same
slow runs (8.25 s on the rerun above).

The test cannot see this. The closer pushes `"thread"` onto
`dismissed_by` right after `PostMessageW` returns (`app.rb:96-97`),
before the menu has closed, so `dismissed_by.pop` answers `"thread"`
even when the fallback did the work. The same holds on macOS and
Linux: a closer whose close does nothing still passes, eight seconds
later.

The hang itself has three candidate causes, and the logs cannot tell
them apart: both closers failed, so `TrackPopupMenu` never returned;
WebView2 creation blocked in wry's `wait_with_pump` before the menu
ever opened; or the GVL and Fiddle's `TIMERPROC` callback deadlocked.

## Decisions

1. **Each fixture prints its progress.** `FixtureApp.progress(stage)`
   writes `PROGRESS <stage> <seconds>` and flushes. The seconds come
   from the monotonic clock, counted from when the fixture loaded, so
   two lines' gap is a duration. The tray fixture already printed
   `PROGRESS <stage>` with no time (plan 043, CI follow-ups); both
   fixtures now share the helper. The stages are `ready` (the Ready
   event, once the window and its webview exist), `menus-built`, and
   for each menu `<menu>:timers-set`, `<menu>:popup-called`,
   `<menu>:shown`, `<menu>:cancel-posted`, `<menu>:returned`, and
   `<menu>:fallback-fired`. On Windows the closer thread prints
   `<menu>:close-asked` too (decision 3). A hang then names its stage.
   Stuck after `ready` and before `<menu>:shown` points at the popup
   never showing. Stuck after `fallback-fired` with no `returned`
   means neither closer ended the menu. No `ready` at all points at
   window or WebView2 creation.

2. **The harness keeps what a hung app printed.** `Run#describe`
   already prints all of stdout. But `RealApp.launch` collected each
   stream inside its reader thread and handed it over only when the
   stream ended. A stream still open after the kill (a grandchild that
   inherited the pipe) came back as `(stream still open after 5 s)`,
   losing every line read so far. The readers now append to a buffer
   the harness owns, and `drain` returns what arrived, followed by
   that note.

3. **The proof is honest.** A fixture records which closer ended each
   menu. The fallback sets a flag when it fires while the popup has
   not returned. After the popup returns and the closer thread is
   joined, the fixture reports `"fallback"` if that flag is set,
   `"thread"` if the closer thread issued its close, and `nil`
   otherwise. So `"thread"` means the closer's request ended the
   menu, not the fallback. A menu can close some other way too: a
   Windows menu also closes when the app loses the foreground. So on
   Windows the main thread's timer checks that the menu is still up
   before it calls `EndMenu` and prints `cancel-posted`, and the test
   asserts `cancel-posted`, which a menu closed that way never
   prints. The fallback fires 8 s
   after the timers are set. The menu then shows on screen, so the
   order is causal, not a race the test could lose to a loaded
   machine.

4. **On Windows the closer asks, and the main thread ends the menu.**
   `EndMenu` ends the calling thread's menu, and the fallback has
   always ended the menu that way from a timer on the main thread,
   which the menu's modal loop runs. Every slow run shows that it
   works. So the closer thread now sets a flag, `close_asked`, and
   prints `close-asked`. The main thread's 50 ms timer, which already
   finds the menu, keeps running on Windows after it does. Once it
   sees the flag, it calls `EndMenu`, and on the tray it posts the
   chosen item's `WM_COMMAND`. Then it prints `cancel-posted`. The
   proof keeps its order: the menu closes only after the other thread
   has run, ticked, and set the flag while the menu tracked. Both
   fixtures change. `PlatformPopup::Win32.cancel` and
   `WM_CANCELMODE` have no caller left and go. macOS and Linux keep
   their closers (`-[NSMenu cancelTracking]` through GCD's main queue,
   GTK through `g_timeout_add`), which never needed the fallback.

   Why `WM_CANCELMODE` failed only sometimes is not settled.
   `DefWindowProc` cancels menu processing on it, but a posted message
   reaches a window only once the menu loop dispatches it. The
   decision rests on what CI shows: `EndMenu` on the main thread
   always worked, and the posted message sometimes did nothing.

5. **The stack dump on a timeout is deferred.** Running cdb
   non-invasively (`cdb -pv -p <pid> -c "~*kn 40; q"`) before
   `kill_group` would show each thread's stack in a hung app. It is
   cheap to write but cannot be verified here. It runs only on a
   Windows hang, which came once in about seventeen jobs. The gate
   step does not export the debugger path that the replay step builds
   (`ci.yml:205-213`, `tasks/test.rake:86-94`). Ruby and the extension
   on that runner are MinGW builds, so their frames have no PDB
   symbols. Only the system DLLs' frames would resolve, through
   Microsoft's symbol server, inside the bounded wait. The progress
   lines alone tell the three candidate causes apart (decision 1),
   and decision 4 may remove the first one. If a hang recurs and its
   last stage leaves the cause open, a follow-up adds the dump with
   that stage as its reason.

## Verification

- `test_other_ruby_threads_run_while_a_menu_tracks` and the tray's
  matching test keep their assertions: `"thread"` and one tick.
  Mutation, on macOS: make the closer thread's close a no-op
  (`close_appkit` returning at once when `on_main` is false). Before
  this plan the context-menu test passes anyway, after about 8 s per
  menu, because the closer reports `"thread"` regardless. After it,
  the test fails on `"fallback"`. The same mutation of the tray
  fixture's close fails its test. Linux runs the same `track` code
  through GTK's closer, so the mutation fails there too.
- A new test in each file checks the progress stages each menu
  passes, in causal order (`timers-set`, `popup-called`, `shown`,
  `returned`), and that the close was issued (`cancel-posted`).
  Deleting a progress call fails it.
- `test/integration/real_app_test.rb` checks that `drain` keeps the
  lines read from a stream that is still open, and drives
  `RealApp.launch` itself with `fixtures/open_stream`, a child that
  prints and exits while a grandchild holds its stdout open, with
  `launch`'s drain limit cut to 0.2 s. With launch's readers collecting
  into their own strings again, as before, that test fails, its stdout
  only `(stream still open after 0.2 s)`.
- Windows runs only in CI. The fix is confirmed when the Windows job's
  `ContextMenuTest` and `TrayMenuTest` launches take 2 to 4 s, with
  no 9 to 12 s runs, over several jobs, and when a failure's stdout
  shows `<menu>:returned` right after `<menu>:cancel-posted` (well
  under a second), with no `<menu>:fallback-fired`. A run whose
  fallback still fires now fails the test with `"fallback"` instead of
  passing slowly, and its progress lines say which stage stalled.

## Amendment, 2026-11-03: the stall is WM_TIMER's, not WM_CANCELMODE's

Run 41608591153 failed the Windows job on both attempts. On attempt 1
the submenu printed `submenu:popup-called` at 3.30 s and `submenu:shown`
only at 11.28 s, then `close-asked`, and then nothing until the 60 s
kill. On attempt 2 the submenu printed `popup-called` at 1.30 s,
`shown` at 9.29 s, and `fallback-fired` at 9.34 s, and the report said
`"dismissed_by": "fallback"`. Each `shown` came at the 8 s fallback's
due time, 8 s after `timers-set`. So inside TrackPopupMenu's modal loop
the main thread stopped delivering WM_TIMER to the fixture's 50 ms
TIMERPROC for the whole 8 s. No Ruby thread could hold the GVL that
long: the closer was blocked on a queue and the ticker sleeps, so this
was not a GVL deadlock. Decision 4 made the Windows close need two such
deliveries, one for `shown` and one for `EndMenu`, so it failed.

That corrects decision 4's reading. The 9 to 12 s runs it took for a
cross-thread `WM_CANCELMODE` that sometimes did nothing are explained
by this same stall, before the closer ever acted: the closer waited for
`shown`, which only the stalled timer could deliver. Both the submenu
and the tray menu open at the pointer, and both stall.

Why the timer stalls is still open. A parallel look ruled out the poll
ticker starving WM_TIMER (posted messages are handled in microseconds,
and on attempt 2 the 8 s timer on the same window fired). Two leads
remain: an
exception or pending interrupt raised inside the Fiddle TIMERPROC,
which would unwind across DispatchMessage, and which DispatchMessage
also swallows from a TIMERPROC by default; and the closer's
`Thread.pass` spin competing with the TIMERPROC for the GVL. The
fixtures now rule out both, below, and report the first.

### Decisions

6. **On Windows the closer thread finds, reads, and ends the menu.**
   It looks for a visible window of class `#32768` among the main
   thread's own windows with `EnumThreadWindows`, every 10 ms, so
   another process's menu cannot match, as a desktop-wide `FindWindowW`
   could. A candidate matches only if it answers `MN_GETHMENU` (0x01E1)
   with the fixture's own HMENU; any other menu window of the thread is
   passed over. So the labels, which it reads from that HMENU with
   `GetMenuStringW`, are the window's. It reads the offset with
   `GetWindowRect` and `ClientToScreen`, from its own thread, against
   the owner window's handle read before the popup. After its one
   proven tick it checks that the menu is still up and sends
   `WM_CANCELMODE` to the owner window with `SendMessageTimeoutW`
   (`SMTO_ABORTIFHUNG`, 2000 ms). A sent message is handled inside any
   `PeekMessage` or `GetMessage` the menu loop makes, whatever its
   timers do, and `DefWindowProc` cancels menu processing on it. The
   closer prints `cancel-posted` only once the main thread took the
   message, and `cancel-unanswered` otherwise, and `"thread"` is
   reported only for a send the main thread took. The owner is the tao
   window for the context menu and tray-icon's window for the tray,
   each the window muda passes to `TrackPopupMenu`. The tray's closer
   then posts the chosen item's `WM_COMMAND` and prints `tray:returned`
   once the menu window is gone, which says only that: not that
   `TrackPopupMenu` has returned or that the click was handled. If the
   window is still there after 20 s it prints `tray:gone-timeout`
   instead, and if the closer never found the menu it prints
   `tray:never-found` and reports at once. The 8 s fallback and the honest
   `dismissed_by` of decision 3 stay. This supersedes decision 4.

7. **The main thread's 50 ms timer only witnesses on Windows.** It
   prints `<menu>:main-timer-saw` the first time it sees the menu, so a
   run shows whether WM_TIMER reached the fixture while the menu
   tracked. `--no-main-timer` skips it. The Windows-only test
   `test_on_windows_the_closer_thread_alone_finds_and_ends_each_menu`,
   and the tray's matching test, launch the fixture with that flag and
   assert `"thread"`, one tick, the labels, `cancel-posted`, no
   `main-timer-saw`, and no timer errors. They run only in Windows CI.

8. **A diagnostic says whether the main thread pumps.** If the closer
   has not found the menu about 2 s after it starts looking, just
   before `popup-called`, it sends `WM_NULL` to the owner with
   `SendMessageTimeoutW(owner, WM_NULL, 0, 0, SMTO_ABORTIFHUNG, 2000,
   &r)` and prints `PROGRESS <menu>:main-pumping <true|false>`. A
   `false` means the main thread took no sent message for 2 s, so the
   loop itself is stuck; a `true` with no `shown` means it pumps but no
   menu window is on its thread.

9. **Each TIMERPROC rescues its block and defers interrupts, and no
   closer spins.** Each Win32 timer's block rescues every exception,
   which it records, as `"<interval>: <class>: <message>"`, in the
   report's `timer_errors`, killing that timer. Every test asserts
   `timer_errors` is empty on Windows. The block also runs under
   `Thread.handle_interrupt(Object => :never)`, which only defers an
   interrupt from another thread: it still fires when the block exits,
   or at the interrupt check where `rb_thread_call_with_gvl` returns,
   and can still unwind across `DispatchMessage`. The risk is low, since
   nothing interrupts the main thread. The closer prints
   `<menu>:timer-errors <n>` after its cancel when there are any, so a
   hang still shows them. The
   closer waits for the ticker's next tick on a queue
   (`PlatformPopup::Ticker#ticks_until_next`) instead of spinning on
   `Thread.pass`, on every platform: the ticker reads the request before
   it counts, so the answer is at least 1 whenever a tick came, and the
   wait never competes for the GVL.

Fiddle's GVL handling makes the sends safe. Fiddle 1.1.8 releases the
GVL around every foreign call unless the function was made with
`need_gvl: true` (`ext/fiddle/function.c:381-386`, where `need_gvl`
defaults to false), so a `SendMessageTimeoutW` waiting up to 2 s for
the main thread leaves every other Ruby thread running, the main
thread's own callbacks included. A callback such as `EnumThreadWindows`'s
retakes the GVL through `rb_thread_call_with_gvl` when the caller does
not hold it (`ext/fiddle/closure.c:229-233`). The Win32 signatures
follow windows-sys 0.59.0 (`Win32/UI/WindowsAndMessaging/mod.rs`,
`Win32/System/Threading/mod.rs`), the crate tao and muda link.

### What the next Windows CI must show

Each `ContextMenuTest` and `TrayMenuTest` launch takes 2 to 4 s. Each
menu's lines run `popup-called`, `shown` within a fraction of a second,
`cancel-posted`, and `returned` right after, with no `fallback-fired`,
no `cancel-unanswered`, `main-pumping`, `gone-timeout`, or
`never-found`, and `timer_errors` empty.
Whether `main-timer-saw` appears tells whether WM_TIMER still stalls;
the tests no longer depend on it. If a run fails, its lines now say
which of these held: a `main-pumping false` points at a main thread
that stopped pumping, a `cancel-unanswered` at a loop that took no sent
message, and a non-empty `timer_errors` at a TIMERPROC that raised.

### What run 41617252499 showed (2026-11-03)

The context menu passed every test on Windows, the closer-only one
included. The tray failed. The timings show only this: no GVL hand-off
reached another Ruby thread while the tray menu tracked. In the
`--no-main-timer` run, `main-pumping` came 2.1 s after `fallback-fired`
(8.39 s), and `never-found` came 20.07 s after it. So the closer's 2 s
and 20 s clocks started only once the fallback had closed the menu. In
the default run the closer printed `shown` 1 ms after `fallback-fired`.
The thread id and the HMENU were right; the closer found the menu as
soon as it ran.

Which link fails is not settled. One hypothesis is that Tokra hands the
GVL over only at `MainEventsCleared` (`ext/tokra/src/gvl_handoff.rs`),
and that a nested menu loop never gets there. tao's modal-loop design
argues against it. tray-icon calls `TrackPopupMenu` from its own window
procedure (tray-icon 0.21.0 `platform_impl/windows/mod.rs:459-464,
509-523`), which `run_return`'s `DispatchMessageW` reaches outside tao's
handler, so `should_buffer()` is false. tao's thread-target `WM_PAINT`
path calls `main_events_cleared()` during modal loops (tao 0.34.5
`platform_impl/windows/event_loop.rs:2357-2378, 2421-2426, 822-824`).
So if the menu loop dispatches posted messages and `WM_PAINT`, a `Yield`
should reach `MainEventsCleared` and `Thread.pass` every 10 ms. Some
other link must fail. The older tray runs most likely passed because
the fixture's own 50 ms timer, polling as long as the menu tracked,
released the GVL in each of its Fiddle calls.

The tray now gathers evidence for the next run:

- It reads the main thread's id with `GetCurrentThreadId` on the main
  thread and prints it beside the window's thread (`tray:threads`).
- The `fallback-fired` and `main-timer-saw` lines print how many times
  the closer has looked (`closer-looks=<n>`).
- A plain Ruby thread, started before `popup-called`, only sleeps 10 ms
  and counts. It advances only when the main thread lets go of the GVL,
  through Tokra's `Thread.pass`, a Fiddle call, or IO. Its count prints
  on the same lines (`tray:sleeper=<n>`).

Read together, near-zero counts mean the main thread never let go of
the GVL while the menu tracked. The Windows tray tests will keep
failing until that link is found and fixed. If the fix belongs in
`lib/` or `ext/`, it is outside this plan's test-only scope.
