# Plan 059: The first release with Ferro's gems and Tokra's plugins

RubyGems.org has tokra 0.0.1.pre.1 and 0.0.1.pre.2, from January 2026,
and no Ferro gem or Tokra plugin. Core tokra now pins ferro-url, and each
plugin pins one or more Ferro gems, so a tokra pushed alone would not
install. This plan records what must be true before the next release, and
the order the gems go to RubyGems.org, so it survives the session that
worked it out (2026-11-04). Publishing is the maintainer's decision; agents
prepare it.

## Status

Open, waiting on Ferro's gems reaching RubyGems.org.

Done:

- Item 1. `lib/rackup/handler/tokra.rb` registers the handler with
  `Rackup::Handler`, and `test/test_rackup_handler.rb` resolves it as the
  `rackup` command does.
- Item 3, the release tasks (2026-11-13). See "How a gem is released".
- Item 5, the metadata (2026-11-13).
- Item 2 is built but not yet run: `rake bump:tokra:minor` moves every
  plugin's `tokra ~> 0.0` to `~> 0.1` in the commit that releases tokra
  0.1.0. Nothing changed a version number ahead of that commit.

Left: items 4, 6, and 7, then the commands under "The 0.1.0 release".

## What is ready

`rake package:install` passes in both repositories: every gem compiles from
its packaged sources and loads outside the checkout, with no warnings.
CI is green on Linux, macOS, and Windows at Tokra 11f426f and Ferro
f610b7d. Every gem name, Ferro's and Tokra's plugins', is free on
RubyGems.org.

## What must change first

1. **`rackup -s tokra` fails.** Done. `lib/tokra/rack/handler.rb` defines
   `Rack::Handler::Tokra`, but rackup 2.3.1 looks a handler up only in
   `Rackup::Handler`: its registry, its constants, then a require of
   `rackup/handler/tokra` or `rack/handler/tokra`
   (`lib/rackup/handler.rb`, `self.get`). Tokra shipped neither file and
   never registered, so rackup raised `LoadError: cannot load such file --
   rack/handler/tokra`.
2. **The plugins accept an older tokra.** Each plugin gemspec says
   `tokra ~> 0.0`, which admits tokra 0.0.1.pre.1 and 0.0.1.pre.2. Neither
   has the plugin hooks the plugins call. The bound moves to `~> 0.1` in
   the commit that releases tokra 0.1.0, not before: until that commit the
   repository's tokra is 0.0.1.pre.2, which `~> 0.1` would refuse, and
   every plugin bundle would fail to resolve. `rake bump:tokra:minor` does
   both at once.
3. **Release tasks.** Done. Tokra had only Bundler's `gem_tasks`, whose
   tags (`v0.0.1.pre.1`) cannot tell its six gems apart.
4. **Pins and Gemfiles.** Pin the Ferro versions Ferro's plan 011
   publishes, in the gemspecs and the plugin READMEs, which today agree on
   each Ferro gem's 0.1.0 tag. Once they are on RubyGems, replace the Ferro git sources in the root and
   plugin `Gemfile`s, which also removes the wide `gems/*/*.gemspec` glob
   in the root and clipboard Gemfiles. The plugin CHANGELOG entries say
   apps take each Ferro gem "from its git tag until it is on RubyGems.org";
   that clause goes in the same change.
5. **Metadata.** Done.
   - `tokra.gemspec` commented out `changelog_uri` and pointed it at a
     `stable` branch that does not exist. It now names
     `blob/trunk/CHANGELOG.md`, as Ferro's gemspecs name theirs.
   - The plugin gemspecs had no `changelog_uri`. Each now names its own
     CHANGELOG, which it ships.
   - The homepage was `https://www.tokra.app` in `tokra.gemspec` and
     `https://tokra.app` in the plugins. `https://tokra.app` answers with
     a 301 to `https://www.tokra.app/`, so every gem names the latter.
   - `test/tasks/test_tokra_gems.rb` checks all three.
6. **Docs.**
   - CHANGELOG `[Unreleased]` (about 580 lines, now without the plugin
     entries) is read through as one release. Each plugin's CHANGELOG is
     read with it.
   - README.md's Installation section, which tells readers to clone while
     RubyGems lags, is rewritten for RubyGems.
   - README.rdoc, which is frozen into the gem as its description, is
     rewritten too.
   - Each Gemfile line names a range that reaches 1.0 (Ferro's plan 011,
     Versioning).
7. **Checks.** `rake package:install`, `rake test:linux`, and the gate, then
   CI, the release commits, and the tags.

## Versions

Plain 0.x releases, with no prerelease label. This replaces the rule this
plan first gave, that every version before 1.0.0 carries a label. Ferro's
plan 011 (Versioning) showed why: a SemVer prerelease is an opt-in preview
of a coming release, which Bundler offers only to a user whose Gemfile or
lockfile already names one, so labelling every 0.x would strand users on
the previews. SemVer's major version zero already says the API is
unstable.

tokra 0.1.0 sorts above 0.0.1.pre.2, so no old tag is deleted. The
plugins are new gems at 0.0.1.pre.1, never published; each releases as
0.1.0 with `rake bump:<plugin>:minor`, which takes a dotted
0.0.1.pre.N to the plain 0.1.0. A later plugin can start at 0.1.0 and
release it with `rake bump:<plugin>:current`.

Versions are written as SemVer (`0.2.0-beta.1`) in `version.rb`, in tags,
and in CHANGELOG headings; RubyGems stores that as `0.2.0.pre.beta.1`,
which is how `Gemfile.lock` and the built package's file name spell it.
The tasks read the dotted form tokra's old tags use, too.

## How a gem is released

The tasks are Ferro's (`tasks/bump.rb`, `tasks/release.rb`,
`tasks/gem_version.rb`, and `tasks/changelog.rb` there), ported with
their tests, so both of the maintainer's repositories release the same
way. `tasks/tokra_gems.rb` lists the seven gems, in publishing order, and
the tasks build every name from it.

1. `rake bump:<gem>:minor` (or `:patch`, `:major`, `:exact[X.Y.Z]`,
   `:current`; a label such as `minor[beta]` makes an opt-in prerelease)
   refuses unless trunk is checked out and clean. It turns the gem's
   CHANGELOG's Unreleased entries into a dated section, moves the links at
   the bottom, rewrites every file that names the version, runs the gate,
   and commits `chore(<gem>): release X.Y.Z`. A failing gate leaves the
   changes uncommitted for inspection.
2. A push of trunk runs the gate again, in the pre-push hook (Plan 061).
3. `rake release:<gem>:tag` refuses unless trunk is clean and matches
   origin's, the tag is absent here and on origin, the CHANGELOG has the
   version's section, and trunk's first-parent history holds the release
   commit. It tags that commit, annotated, and pushes only the tag, which
   the pre-push hook lets through without the gate.
4. `rake release:<gem>:push[X.Y.Z]` refuses unless origin has the tag and
   RubyGems.org does not have the version. It checks the tag out into
   `tmp/push/` as a git worktree, runs the gem's prepare commands there,
   builds the gem, reads the package back, pushes it with `gem push`, and
   removes the checkout.
5. `rake release:<gem>` is the one-step form: from a clean trunk, build
   the gem from the working tree, read it back, push trunk, tag, push the
   tag, and push the gem. Trunk goes before the tag, so a push the gate
   refuses leaves no tag behind for the next try to trip over.

Tokra's layout forced these differences from Ferro's tasks:

- **Tags.** Each tag names its gem, `tokra/v0.1.0` and
  `tokra-dialog/v0.1.0`, as Ferro's do. tokra's two old tags,
  `v0.0.1.pre.1` and `v0.0.1.pre.2`, stay as they are.
- **Bundler's tasks are gone.** The root Rakefile and every plugin
  Rakefile loaded `bundler/gem_tasks`, whose `rake release` would tag
  `v0.1.0` for whichever gem ran it first. The root's `task build:
  :compile` hooked Bundler's build and went with it.
- **One CHANGELOG per gem.** tokra's stays at the root; each plugin's is
  `plugins/<name>/CHANGELOG.md`, which the gem ships. A shared file would
  have put each plugin's 0.1.0 under a heading no reader could tell from
  tokra's, and a tokra bump would have released the plugins' entries as
  tokra's. The five entries that introduced the plugin gems moved from
  the root unchanged. The root's Changed entry "`tokra-dialog`'s
  `FileDialogBuilder#set_can_create_directories` raises `TypeError` at the
  setter for anything but `true` or `false`, as Tauri's `bool` parameter
  allows nothing else (breaking)" was dropped rather than moved:
  tokra-dialog was never released, so there is nothing for that behavior
  to have changed from. Item 6 may restore it as part of the Added entry.
- **tokra's first link.** tokra's CHANGELOG has no section for the
  prereleases it shipped, only an Unreleased link that compares from
  `v0.0.1.pre.2`. `Changelog` now links a new version from wherever the
  Unreleased link compared from, so 0.1.0's link is
  `compare/v0.0.1.pre.2...tokra/v0.1.0`.
- **The plugins bundle the tokra beside them.** A tokra bump also
  rewrites `tokra (X)` in each plugin's `Gemfile.lock`.
- **The plugins' floor follows tokra's minor version.** A tokra release
  that is not a prerelease sets each plugin's `tokra ~> X.Y` to its own
  major and minor version, in the gemspec and in the plugin's
  `Gemfile.lock`, in the same commit, and says so in the commit message.
  A plugin is only ever tested against the tokra beside it, so it cannot
  promise to work with an older one. A prerelease leaves the floor alone:
  `~> 0.2` would refuse 0.2.0-beta.1 itself. The bump does not yet add a
  CHANGELOG entry to each plugin for the raised floor; no plugin has been
  released, so none is owed until tokra 0.2. Add one then, by hand or in
  the task.
- **tokra's crate.** Ferro's bump insists the crate's version already
  equals the gem's. tokra's crate (`ext/tokra/Cargo.toml`, `publish =
  false`) stood at 0.1.0 while the gem was 0.0.1.pre.2, so the bump sets
  the crate's version and its `Cargo.lock` entry to the gem's whatever
  they held. At 0.1.0 they already agree, and that commit leaves them
  untouched.
- **Generated files.** tokra's gemspec packs `lib/tokra/js/*`, which
  `rake sync:tauri` extracts from the Tauri submodule and git ignores. A
  clean checkout of a tag has neither, so the push runs
  `git submodule update --init --reference <root>/vendor/tauri
  vendor/tauri` and `bundle exec rake sync:tauri` there first, borrowing
  the repository's own submodule objects. Every release, from the working
  tree or a checkout, reads the package back and refuses one that holds
  another version or lacks a generated file, before anything is pushed.
- **Who runs them.** Ferro lets agents run its tag task once the gate and
  CI pass. Tokra's AGENTS.md keeps every bump and release the
  maintainer's.

## The 0.1.0 release

Once Ferro's gems are on RubyGems.org and items 4, 6, and 7 are done, each
on trunk, in the main checkout, with nothing uncommitted. Only the
maintainer runs these.

1. `bundle exec rake bump:tokra:minor`: tokra 0.0.1.pre.2 becomes 0.1.0,
   its CHANGELOG's Unreleased becomes the 0.1.0 section, every plugin's
   floor moves to `~> 0.1`, the gate runs, and the commit is
   `chore(tokra): release 0.1.0`.
2. `bundle exec rake bump:log:minor`, then `bump:clipboard:minor`,
   `bump:dialog:minor`, `bump:notification:minor`, and
   `bump:global-shortcut:minor`: each plugin 0.0.1.pre.1 becomes 0.1.0
   the same way, one commit each. Each runs the gate.
3. `git push origin trunk`: the pre-push hook runs the gate once more on
   the last of those commits. Wait for CI to pass on it.
4. `bundle exec rake release:tokra:tag`, then `release:log:tag`,
   `release:clipboard:tag`, `release:dialog:tag`,
   `release:notification:tag`, and `release:global-shortcut:tag`: each
   tags its release commit, `tokra/v0.1.0` and so on, and pushes only that
   tag.
5. `bundle exec rake "release:tokra:push[0.1.0]"`, then the same for
   `log`, `clipboard`, `dialog`, `notification`, and `global-shortcut`, in
   that order: each builds its gem from a clean checkout of its tag and
   pushes it to RubyGems.org, asking for a one-time code. tokra goes
   first, since every plugin requires it.

Steps 4 and 5 for one gem can also be `bundle exec rake release:<gem>`,
which builds from the working tree instead and pushes trunk first.

The tasks were exercised end to end on 2026-11-13 in a scratch clone with
a bare origin and a stand-in gate: the six bumps made the six commits
above, with `Gemfile.lock` files that `BUNDLE_FROZEN=true bundle check`
accepts, and the six tag tasks pushed `tokra/v0.1.0` and the five plugin
tags. In a checkout of `tokra/v0.1.0` the prepare commands restored the
submodule and the templates, and `gem build` made a tokra 0.1.0 package
holding them. Nothing was pushed to RubyGems.org.

## Order of publishing

1. Ferro's gems, once plan 011's fixes, README rewrites, bumps, and tags are
   done. They do not depend on each other, so any order works, but all go
   before Tokra. Core tokra needs only ferro-url, which compiles the idna
   crate in and does not depend on ferro-idna.
2. An agent switches Tokra's Gemfiles from git sources to RubyGems and
   confirms CI against the published gems.
3. tokra, then tokra-log, tokra-clipboard, tokra-dialog, tokra-notification,
   and tokra-global-shortcut.

Each gem requires MFA, so each push takes a one-time code. Installing any
of them compiles Rust, so users need Rust and libclang; the READMEs say so.

## Found on the way

  one shared version and an exact `tokra` pin. The gems never used it, and
