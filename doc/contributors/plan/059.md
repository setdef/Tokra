# Plan 059: The first release with Ferro's gems and Tokra's plugins

RubyGems.org has tokra 0.0.1.pre.1 and 0.0.1.pre.2, from January 2026,
and no Ferro gem or Tokra plugin. Core tokra now pins ferro-url, and each
plugin pins one or more Ferro gems, so a tokra pushed alone would not
install. This plan records what must be true before the next release, and
the order the gems go to RubyGems.org, so it survives the session that
worked it out (2026-11-04). Publishing is the maintainer's decision; agents
prepare it.

## Status

Open, waiting on Ferro's plan 011, whose completeness audit found fixes
that belong in the first versions published.

Done: item 1 of "What must change first". `lib/rackup/handler/tokra.rb`
registers the handler with `Rackup::Handler`, and
`test/test_rackup_handler.rb` resolves it as the `rackup` command does.

## What is ready

`rake package:install` passes in both repositories: every gem compiles from
its packaged sources and loads outside the checkout, with no warnings.
CI is green on Linux, macOS, and Windows at Tokra 11f426f and Ferro
f610b7d. Every gem name, Ferro's and Tokra's plugins', is free on
RubyGems.org.

## What must change first

1. **`rackup -s tokra` fails.** `lib/tokra/rack/handler.rb` defines
   `Rack::Handler::Tokra`, but rackup 2.3.1 looks a handler up only in
   `Rackup::Handler`: its registry, its constants, then a require of
   `rackup/handler/tokra` or `rack/handler/tokra`
   (`lib/rackup/handler.rb`, `self.get`). Tokra ships neither file and
   never registers, so rackup raises `LoadError: cannot load such file --
   rack/handler/tokra`. Register the handler with `Rackup::Handler` and
   ship `lib/rackup/handler/tokra.rb`, with a test that resolves it through
   `Rackup::Handler.get`. The CHANGELOG entry "`rackup -s tokra` no longer
   raises on the options rackup passes" and ADR 009's "`rackup -s tokra`
   remains viable" are true only once this lands.
2. **The plugins accept an older tokra.** Each plugin gemspec says
   `tokra ~> 0.0`, which admits tokra 0.0.1.pre.1 and 0.0.1.pre.2. Neither
   has the plugin hooks the plugins call. Bound each to the release that
   has them.
3. **Release tasks.** Tokra has none, and its tags (`v0.0.1.pre.1`) cannot
   tell its six gems apart. Add per-gem tasks after Ferro's
   (`tasks/release.rb` there), with tags named for the gem, such as
   `tokra-dialog/v0.0.1-pre.1`, and the version handling Ferro's plan 011
   describes (SemVer in `version.rb` and tags, the RubyGems form only for
   ordering).
4. **Pins and Gemfiles.** Pin the Ferro versions plan 011 publishes, in the
   gemspecs and the plugin READMEs (the dialog README still names ferro-rfd
   0.1.0.pre.2 where the gemspec pins pre.3). Once they are on RubyGems,
   replace the Ferro git sources in the root and plugin `Gemfile`s, which
   also removes the wide `gems/*/*.gemspec` glob in the root and clipboard
   Gemfiles.
5. **Metadata.**
   - `tokra.gemspec` comments out `changelog_uri` and points it at a
     `stable` branch.
   - The plugin gemspecs have no `changelog_uri`.
   - The homepage is `https://www.tokra.app` in `tokra.gemspec` and
     `https://tokra.app` in the plugins.
6. **Docs.**
   - CHANGELOG `[Unreleased]` (about 580 lines) is read through as one
     release.
   - README.md's Installation section, which tells readers to clone while
     RubyGems lags, is rewritten for RubyGems.
   - README.rdoc, which is frozen into the gem as its description, is
     rewritten too.
   - Each Gemfile line names a range that reaches 1.0 (plan 011,
     Versioning).
7. **Checks.** `rake package:install`, `rake test:linux`, and the gate, then
   CI, the release commit, and the tags.

## Versions

Every version before 1.0.0 carries a prerelease label, for the reason
plan 011 gives under Versioning. The next tokra must sort above
0.0.1.pre.2. The plugins are new gems; each starts at its first prerelease.

## Order of publishing

1. Ferro's gems, once plan 011's fixes, README rewrites, bumps, and tags are
   done. They do not depend on each other, so any order works, but all go
   before Tokra. Core tokra needs only ferro-url, which compiles the idna
   crate in and does not depend on ferro-idna.
2. An agent switches Tokra's Gemfiles from git sources to RubyGems and
   confirms CI against the published gems.
3. tokra, then tokra-log, tokra-clipboard, tokra-dialog, tokra-notification,
   and tokra-global-shortcut.

Each gem requires MFA, so each push takes a one-time code. Installing any
of them compiles Rust, so users need Rust and libclang; the READMEs say so.
