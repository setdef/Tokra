# Plan 045: Window effects, the taskbar, the title bar, and the app's theme

Plans 040 and 041 ported every window getter and setter that is a thin
call into tao, and Tauri's own window code where it had one. They left
the effects, the taskbar's progress bar, badges, and overlay icon, and
the macOS title bar style deferred as "out of scope", and plan 040 left
`set_theme`'s menu half until menus existed. Plans 042 and 043 brought
menus and trays, and `Window#set_theme` now themes the window's menu on
Windows. This plan takes up the rest: each is a thin call into tao, or,
for effects, Tauri's own `vibrancy` module over the window-vibrancy
crate. It also ports `App#set_theme` and `AppHandle#set_theme`, which
re-theme the whole app and every window's menu, and `Window#webviews`.

## Decisions

1. **window-vibrancy joins Tokra's extension.** Tauri's `vibrancy` module
   hands the window to window-vibrancy, which follows the `NSView` and
   the `HWND`. ADR 013 keeps such crates in this extension, so Tokra
   depends on window-vibrancy 0.6.0, the version Tauri locks, on macOS
   and Windows, the two platforms Tauri adds it on. Its dependencies are
   versions tao and muda already lock. The module is ported whole into
   `ext/tokra/src/vibrancy.rs`: the effect is chosen in Rust, as in
   Tauri, from the names Ruby sends. `#![allow(deprecated)]` becomes an
   `#[allow(deprecated)]` on the functions that name the deprecated
   materials.

2. **The effect types are Tauri's.** `Effect` and `EffectState` are
   closed enums (`ClosedEnum`) with Tauri's variant names.
   `WindowEffectsConfig` is a `Data` of `effects`, `state`, `radius`, and
   `color`, each defaulting as Tauri's `Default` does (`[]` and `nil`);
   anything of another type raises `TypeError` where Rust would not
   compile. `EffectsBuilder` keeps Tauri's methods; a Rust builder that
   consumes itself becomes one that changes itself and answers +self+
   (tier 1). `From<WindowEffectsConfig> for EffectsBuilder` becomes
   `EffectsBuilder.from(config)`.

3. **`set_effects` is fire and forget.** Tauri runs it on the main thread
   and drops window-vibrancy's result, so an effect a platform or version
   lacks does nothing. Tokra does the same. A closed window ignores it, as
   every setter does (plan 038). Tauri has no `clear_effects` on
   `Window`; `set_effects(nil)` clears, and `EffectsBuilder#clear_effects`
   empties a builder's list.

4. **The progress bar and the badge count take Tauri's desktop file
   name.** Tauri names it `"#{package_info.name}.desktop"`. Tokra has no
   `PackageInfo` (plan 042, decision 6), so the name is the config's
   product name or the program's file name, as `Menu.default` takes it.
   `ProgressBarStatus` is a closed enum; `ProgressBarState` is a `Data`
   of `status` and `progress`, each `nil` unless given, as Tauri's
   `Deserialize` reads a missing field; a progress that is not an Integer
   from 0 up raises `TypeError` or `RangeError`. tao clamps it to 100.

5. **Platform-only methods exist only on their platform.** Tauri compiles
   `set_badge_label` only for macOS and `set_overlay_icon` only for
   Windows. ADR 011's table defines such an item only where the native
   window has it, as `App#set_activation_policy` does: each lives in its
   own file (`lib/tokra/window/macos.rb`, `windows.rb`) that returns
   early elsewhere, with its own signature file the RBS gates exclude
   elsewhere. The overlay icon is built on the calling thread with
   `Native::Icon.from_rgba`, as `set_icon` builds one. Tauri drops its
   icon as soon as `SetOverlayIcon` returns (tauri-runtime-wry
   `lib.rs:3504-3507`), so the taskbar does not depend on it afterwards,
   and the native call hands tao a clone of the icon that lives only for
   the call; the Ruby object may then be collected.

6. **`TitleBarStyle` is a closed enum of Tauri's three.** Tauri's enum is
   non-exhaustive and its runtime warns on an unknown style; a closed
   enum has none, so the warning has nothing to port.

7. **The app's theme reaches the loop whenever it exists.** Tauri's
   `AppHandle` sends the theme to its event loop; its `App` sets it on
   the loop directly, which exists from `Builder::build`. Tokra builds
   its loop in `App#run` (plan 041, decision 1), so a theme set before
   then is kept and `App#run` hands it to the loop it builds, as it hands
   over the activation policy. A thread that keeps a theme just as
   `App#run` builds the loop looks for the loop again afterwards, and
   whichever of the two takes the kept theme, under one mutex, sends it,
   so it is neither lost nor sent twice. Afterwards it travels to the main thread
   as any setter does, and failures are dropped, as Tauri drops them. On
   Windows each window's menu bar follows first, through the same muda
   call `Window#set_theme` makes.

8. **`Window#webviews` is Tauri's inherent method.** Tauri's `Window`
   answers its own webviews as a `Vec`, which shadows the `Manager`
   trait's map of every webview. Tokra's `Window` inherited
   `Manager#webviews`, a Hash of all of them; it now answers an Array of
   the webviews in this window, as Tauri does. This is a breaking change,
   recorded in the CHANGELOG.

## Verification

- Stub-native unit tests: each setter's arguments as the native window
  receives them, the desktop file name, closed windows, the argument
  errors, the icon's failure path, the value types, the builder, the
  app's theme before and after the loop exists, and the menus it
  re-themes.
- Real-extension tests (`test/native/`): a closed window ignores each new
  setter; the event loop takes a theme before it runs; unknown names
  raise `ArgumentError`.
- Real window (`window_effects` fixture, Prohibited policy, no focus):
  on macOS an `NSVisualEffectView` with the material, state, and radius
  asked for appears in the content view, the Dock tile's badge label
  reads back for a count and a label, the Dock tile's progress indicator
  reads back its value and hides for `None`, the title bar styles read
  back through `titlebarAppearsTransparent` and the full-size content
  view style bit, and the app's theme reads back through the window's
  `theme`; on Windows the backdrop type DWM reports after Mica and after
  clearing, where the build has one, and the app's theme; on Linux the
  app's theme, and every setter runs without error.
- Rust unit tests: the effect each platform picks.
- Mutation checks by hand, recorded under Results.

Untested without a person at the screen: how an effect, a badge, a
progress bar, or an overlay icon looks; Linux's badge and progress go
over D-Bus to a Unity launcher, which neither CI nor Xvfb has, and
Windows' taskbar keeps no state Tokra can read back.

## Out of scope

The rows the inventory leaves deferred; the core `window` plugin's
JavaScript commands, which Tokra has not ported for any window method.

## Risks

- The Dock tile is the test process's own. A Prohibited app has no Dock
  icon, so nothing shows, and the fixture clears what it set.
- The Windows code cannot be built here: it is checked with Clippy for
  `x86_64-pc-windows-gnu` in a scratch crate, as plans 040 and 041 were.
  The Linux code is built, Clippied, and run under Xvfb in a Debian
  container with CI's packages.

## Results

Every item above is done; the inventory names what stays deferred and
why. The clean-build gate passed on macOS with zero errors and zero
warnings (core suite 1075 runs, 3963 assertions, 0 failures, 0 errors,
19 skips), with the RBS, RDoc, REUSE, Clippy, and packaging checks.

The gate's Steep check caught one regression the tests had not reached
yet: `Window#inner_size` found its webview through `webviews.each_value`,
which decision 8 makes an Array; it now searches the Array.

Linux: in a `ruby:4.0.9` Debian container with CI's packages the
extension built and passed Clippy with `-D warnings` and its Rust tests,
after one fix the first run found: the Linux `apply_effects` could not be
a `const fn`, since its argument has a destructor. Under Xvfb the new
stub, native, and real-window tests passed, as did `window_state_test`.
GTK takes the app's theme on a later turn of its main loop, so the
fixture waits for GTK's dark preference to change rather than reading it
at once. Windows: the `vibrancy` functions, the overlay icon, the badge
count, the title bar style, the progress bar, and the loop's theme passed
Clippy for `x86_64-pc-windows-gnu` with the crate's lints in a scratch
crate with the same tao and window-vibrancy; nothing of it has run on
Windows. Its window events reach tao's handler through `send_event`,
which buffers them while a handler runs (plan 042, decision 19), as
`Window#set_theme`'s already do.

macOS read-backs: window-vibrancy's tagged `NSVisualEffectView` with
Popover's material and the Active state, still there after `nil`; the
Dock tile's badge label for a count and a label, cleared by `nil`; tao's
Dock progress indicator at 40 and hidden for `None`; each title bar
style's pair of `titlebarAppearsTransparent` and the full-size content
view bit; and NSApp's appearance for each app theme. tao's window
`theme` on macOS follows only the system's theme notifications
(`window_delegate.rs:659-680`), so the fixture reads NSApp's appearance
instead.

Mutations checked by hand, each failing the named test and then
restored: in Ruby, `AppHandle#set_theme` not keeping a theme for the
loop (`test_a_theme_set_before_run_reaches_the_loop_before_it_runs`),
the desktop file name without `.desktop`
(`test_set_badge_count_sends_the_count_or_nil`), `Window#webviews`
answering every webview (`test_webviews_are_the_ones_in_this_window`),
`AppHandle#set_theme` skipping the menus
(`test_on_windows_each_windows_menu_bar_follows`), and `set_effects`
dropping the state (`test_set_effects_sends_the_config_by_name`); in
Rust, against the real window, macOS taking the last material instead of
the first
(`test_on_macos_the_first_material_shows_behind_the_webview_and_stays`),
Visible's full-size content view turned off
(`test_each_title_bar_style_reaches_appkit`), the badge count not reaching
the Dock (`test_on_macos_the_badge_count_and_label_are_the_dock_tiles`),
and the loop ignoring the theme
(`test_the_apps_theme_reaches_the_platform`).
