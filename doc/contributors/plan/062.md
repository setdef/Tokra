# Plan 062: Capabilities, permissions, the ACL, and scopes

Status: written 2026-11-13. No step has started. The decisions (D1 to
D12) are the orchestrator's, recorded in
[config.md](../design/config.md), "Access control"; the questions
at the end are the maintainer's. A step may start once the decisions it
names are made.

## Context

A Tauri app says which of its windows may call which commands. It
writes capabilities, in files beside its config or inline in it. Each
capability names windows or webviews by label, the origins it trusts
(the app's own pages, remote URL patterns, or both), and a list of
permissions. Permissions come from the plugins the app depends on, from
Tauri's core, and from the app itself. Some permissions carry scopes,
data a command reads to decide what it may touch, such as the paths the
fs plugin may read. Tauri resolves all of it when the app compiles and
checks every plugin command against the result before the plugin sees
it.

Tokra has none of it. The road-to-1.0 inventory ranks this first among
what keeps Tokra from being a port of Tauri: "Every command is open to
the app's own pages and closed to all others, and every plugin that
needs a scope (fs, shell, http, opener, the asset protocol) has nothing
to stand on." The stopgap that stands in for it
([ipc.md](../design/ipc.md), "Only the app's own origin may invoke"), rejects an
invoke from any origin that is not the app's own, with Tauri's release
message, `Command <cmd> not allowed by ACL` (`lib/tokra/app.rb:850-861`).
Plan 050's question 1, the window and webview plugins' default sets,
every plugin with a scope, the asset protocol, the dialog plugin's
scope widening, and the drag-drop scope plan 047 deferred all wait on
this plan.

The stopgap is not simply stricter than Tauri, as the former ADR 010 §6 and the
RDoc on `route_invoke` said (the design document now says both). It is stricter for remote origins, and
looser for the app's own pages: Tauri rejects a plugin command from a
local page when no capability grants it (`webview/mod.rs:1801-1831`),
and Tokra answers every one. So this plan changes behavior for every
app, in Tauri's direction, and says so where it does (step 9).

This plan is cut so that several agents can work at once. Each step is
one agent's work and lands with the gate green. Until step 9, an app's
behavior does not change unless it already has capabilities, and then
only where Tauri would refuse to compile it.

## What Tauri's access control is

### Permissions and permission sets

A permission (`acl/mod.rs:217-260`) has an `identifier`, an optional
`version` and `description`, `commands` with `allow` and `deny` lists of
command names (`:172-185`), a `scope` with optional `allow` and `deny`
lists of ACL values (`:187-215`), and optional `platforms`. A
permission set (`:262-274`) groups permissions under a new identifier.
A permission file (`manifest.rs:32-46`) holds an optional `default` set,
`set` entries, and `permission` entries. None of these structs refuses
unknown fields, so a file's `"$schema"` key passes.

A plugin's manifest (`manifest.rs:48-98`) merges its permission files:
every permission and set by identifier, and the last file's `default`
as a set named `default`, described "Default plugin permissions." when
the file gives no description.

ACL values (`value.rs:13-61`) are null, bool, a number that is an `i64`
or else an `f64`, a string, a list, or a map. Deserialized from JSON,
an integer stays an `Int`. Converted from a `serde_json::Value`, as
`CapabilityBuilder#permission_scoped` converts, every number becomes a
`Float`, because `Number::as_f64` answers for integers too
(`value.rs:84-97`; serde_json 1.0.145 `number.rs:162-171`).

Identifiers (`identifier.rs:11-209`) are ASCII alphanumerics and inner
hyphens, at most 116 bytes (51 + 1 + 64), with one colon separating a prefix,
except that an identifier starting `core:` may have two
(`core:window:allow-destroy`), and none may start `tauri-plugin-`. The
prefix is everything before the last separator. Seven errors, each with
its own message (`:114-147`).

### Where permissions come from

- **A plugin crate.** Its `build.rs` calls `tauri_plugin::Builder::new
  (COMMANDS).build()` (`tauri-plugin/src/build/mod.rs:95-153`). That
  refuses a name with an underscore or the names `core` and `tauri`,
  requires `package.links`, writes `permissions/autogenerated/commands/
  <command>.toml` for each command, holding `allow-<command>` and
  `deny-<command>` with underscores turned to hyphens
  (`acl/build.rs:254-320`), reads every `./permissions/**/*.*` file
  with a `json` or `toml` extension outside a `schemas` folder
  (`acl/build.rs:69-111`), writes `permissions/schemas/schema.json` and
  `permissions/autogenerated/reference.md`, and publishes the file list
  to the app's build through a Cargo `links` variable. Plugins commit
  the generated files; plugins-workspace does.
- **Tauri's core.** `crates/tauri/build.rs:16-225` lists nine core
  plugins, each command with a flag for its default set: `core:path`,
  `core:event`, `core:window`, `core:webview`, `core:app`, `core:image`,
  `core:resources`, `core:menu`, `core:tray`. Its build script writes
  their permissions into `OUT_DIR` only, with a default set described
  "Default permissions for the plugin." (", which enables all commands"
  when every command is default), and a `core` manifest whose default is
  the nine plugins' defaults: `core:default` (`:366-481`). Only the
  reference pages are committed (`crates/tauri/permissions/*/
  autogenerated/reference.md`). Their manifest keys are `core:window`
  and so on, and `core` (`acl/build.rs:98-108`, `:114-146`).
- **The app.** tauri-build reads the app's `./permissions/**/*`, beside
  `Cargo.toml`, into the manifest keyed `__app-acl__`, plus
  autogenerated permissions for commands the build script lists with
  `AppManifest::commands`. An app may also declare inlined plugins with
  their own permission folders (`tauri-build/src/acl.rs:25-114`,
  `:160-335`). The app manifest counts only when it holds a permission,
  a set, or a default (`:408-413`).

### Capabilities

A capability (`capability.rs:77-216`) has an `identifier`, a
`description`, an optional `remote` with `urls`, `local` (default
`true`), `windows` and `webviews` (glob patterns over labels),
`permissions`, and optional `platforms`. A permission entry is an
identifier, or an object with an `identifier` and a flattened `allow`
and `deny` that extend the permission's scope (`:18-75`). A capability
file is one capability, a list of them, or an object with a
`capabilities` list (`:251-323`), in JSON, JSON5, or TOML by extension
(`:267-283`).

tauri-build reads every file under `./capabilities/**/*` with one of
those extensions, outside a `schemas` folder, refusing a second
capability with an identifier already read: "capability with
identifier `{identifier}` already exists" (`acl/build.rs:203-244`). It
checks each active capability's permissions against the manifests and
fails the build with "Permission {id} not found, expected one of
{list}"; a `default` permission always passes, whether the manifest has
one or not (`tauri-build/src/acl.rs:337-398`). It writes the manifests
and capabilities into `gen/schemas/` for the CLI, with a capability
schema that enumerates every permission (`acl/schema.rs:197-344`).

Codegen then takes the capabilities from the files, unless the config's
`app.security.capabilities` lists some: then exactly those, a name
taken from the files ("capability with identifier {id} not found" when
none matches) and an inline one as written. Files named by the
`generate_context!(capabilities: [...])` argument are added either way
(`acl/mod.rs:352-401`; `tauri-codegen/src/context.rs:395-415`).

### Resolution

`Resolved::resolve` (`resolved.rs:83-197`) walks each capability active
on the target platform. Each permission identifier expands through its
manifest (`get_permissions`, `:339-430`): `default` to the default set
(or nothing), a set to its members, recursively, a member with another
plugin's prefix through that plugin's manifest. An unknown manifest
raises "unknown ACL for {key}, expected one of {available}", an unknown
permission "unknown permission {permission} for {key}", and an unknown
set member "permission {permission} not found from set {set}"; the app
key displays as "app manifest" (`:432-439`). Each resolved permission
inactive on the platform is skipped. A permission's scope is the
entry's extension followed by its own.

A permission with no commands contributes its scope to the plugin's
global scope. One with commands gets a scope id, counting from 1, when
it has a scope, and each allowed or denied command becomes a
`ResolvedCommand` per execution context (local if `local`, one remote
per URL pattern), carrying the capability's window and webview patterns
sorted, the scope id, and, in debug builds, the capability and
permission that referenced it (`:210-248`). Command names become
`plugin:<name>|<command>`, with `core:` stripped from core keys, and
stay bare for the app (`:128-160`). An unparsable remote URL pattern
panics, failing the build (`:221-228`).

A remote URL pattern follows the URLPattern standard (urlpattern 0.3.0),
with an empty search or hash, and an empty or `/` pathname, widened to
`*` (`acl/mod.rs:276-317`).

### The runtime authority, and what each invoke meets

`Context` carries a `RuntimeAuthority` built from the manifests and the
resolution (`lib.rs:367`, `:486-488`; `authority.rs:103-130`), which
the manager holds behind a mutex (`manager/mod.rs:182`, `:277`).

`Webview::on_message` (`webview/mod.rs:1724-1893`), after the invoke
key check, classifies the origin with `is_local_url` (`:1680-1721`) and
calls `resolve_access(cmd, window_label, webview_label, origin)`
(`authority.rs:438-471`):

1. A command with any entry in the denied list is refused, whatever its
   context or window: the check is `.map(..).is_some()`, so the origin
   test inside it has no effect (`:446-452`).
2. Otherwise the allowed entries whose context matches the origin, and
   whose webview patterns match the webview label or window patterns
   the window label, are the answer; none is a refusal.

The check applies to every `plugin:` command, and to app commands only
when the app has an app manifest; `plugin:__TAURI_CHANNEL__|fetch` is
exempt (`webview/mod.rs:1801-1806`). So with no capabilities, no page,
local or remote, can call a plugin command, `plugin:event|listen`
included, and every page can call every app command unless the app
defines app permissions.

A refusal rejects the invoke. A release build says `Command {cmd} not
allowed by ACL` (`:1826-1829`). A debug build says what
`resolve_access_message` builds (`authority.rs:228-436`): "explicitly
denied on origin", "not allowed on window ..., webview ..., URL: ...",
"not allowed on origin [...]. Please create a capability that has this
origin on the context field.", or "not allowed. Plugin not found",
"Command not found", or "Permissions associated with this command:
...", each pinned by Tauri's own test (`:1045-1192`). The resolved
entries ride the invoke as `Invoke#acl` (`ipc/mod.rs:219`).

### Scopes

A command reads its scopes as arguments. `CommandScope<T>` gathers the
command scopes of the resolved entries; `GlobalScope<T>` the plugin's
global scope (`authority.rs:474-665`). Each raw value deserializes
through `ScopeObject` (any `DeserializeOwned` type, or a custom one
given the app handle), cached per type, failing with "error
deserializing scope: {0}" (`:667-815`; `error.rs:151-153`).
`CommandScope::matches` refuses input any deny matches, and accepts it
when there is no allow or one allow matches (`:546-607`). A plugin
reads its global scope with `PluginApi::scope` (`plugin.rs:169-180`);
code reads a command's resolved scope for a webview with
`Webview::resolve_command_scope` (`webview/mod.rs:1421-1458`;
`webview_window.rs:1512`).

The fs-style scope (`scope/fs.rs`) is not an ACL scope. It is glob 0.3.2
patterns over paths, built from an `FsScope` config with path variables
resolved by `PathResolver::parse`, each pattern added as written and
canonicalized, matched with `require_literal_separator` and, by default,
`require_literal_leading_dot` on Unix only. Forbidden beats allowed;
`allow_directory`, `allow_file`, `forbid_*` widen and narrow it at run
time and emit events. The core `Scopes` state holds one, the asset
protocol's, built from `app.security.assetProtocol.scope` at startup
(`scope/mod.rs`; `app.rs:2252-2258`); the asset protocol answers 403
outside it (`protocol/asset.rs:43-48`). Plugins such as fs keep their
own.

### At run time

With `dynamic-acl`, a default feature, `Manager::add_capability` takes a
capability as a JSON or TOML string, or a `CapabilityBuilder`, resolves
it against the kept manifests, and merges it in
(`authority.rs:148-226`; `capability_builder.rs`; `lib.rs:776-827`). It
panics on an unknown permission (`.unwrap()`, `:174-179`). Its scope
ids start again at 1 and merge into the authority's existing ids, so a
runtime capability's scope joins whatever compile-time command already
held that id, and the other way round (`:198-223`). That reads as a
Tauri bug; question 3 asks what Tokra does.

### Config keys, and where the line with CSP is

`app.security.capabilities` (`config.rs:2618-2641`, `CapabilityEntry`
`:2648-2669`) and `app.security.assetProtocol` (`:2217-2286`) feed the
ACL and the asset scope. `csp`, `devCsp`, and
`dangerousDisableAssetCspModification` do not: they shape the
Content-Security-Policy header on the app's own assets, which the
assets plan owns (plan 054's inventory). The ACL decides which commands
a page may call; the CSP decides what a page may load. Neither reads
the other. `build.removeUnusedCommands` feeds only dead-code removal at
compile time (`acl/build.rs:389-500`), which Ruby has no use for.

## What translates, and how

Tauri does most of this before the app runs. Tokra reads its config
when the app starts (ADR 014) and its plugins are gems. AGENTS.md's
precedence decides each row: Ruby the language first, then fidelity.

| Tauri | When | Tokra | When |
|---|---|---|---|
| A plugin's `build.rs`: autogenerated permission files, `reference.md`, the permission schema | the plugin compiles | a Ruby port of `autogenerate_command_permissions` and `generate_docs`, run by a rake task in each plugin gem, files committed and packaged (D3) | while the plugin is developed |
| The `links` key and `DEP_*` variables that tell the app's build where each plugin's files are | the app compiles | D2: gem metadata on the gems Bundler activated, or a declaration on the plugin class | at start |
| `crates/tauri/build.rs`'s core table | Tauri compiles | the same table in Ruby, manifests built from it (D3) | at start |
| tauri-build's `acl::build`: manifests, app manifest, capability files, validation | the app compiles | `Tokra::Build::Acl` (D1), called by `Tokra.generate_context`, raising before any window | at start |
| `gen/schemas/*.json` written into the project | the app compiles | not at start: a CLI command ([cli.md](../design/cli.md) lists `permission` and `capability`) | deferred |
| `allowed-commands.json`, `removeUnusedCommands` | the app compiles | never: nothing to remove | |
| codegen's `get_capabilities`, `Resolved::resolve`, `runtime_authority!` | macro expansion | `Codegen.context_codegen`, filling `Context#runtime_authority` | at start |
| `generate_context!(capabilities: [...])` | macro | `Tokra.generate_context(path, capabilities: [...])`, a keyword ([config.md](../design/config.md), "The loader") | at start |
| `tauri_build::Attributes` (`capabilities_path_pattern`, `app_manifest`, `plugin`) | the app's `build.rs` | D11 | |
| `cfg(debug_assertions)`: which message a refusal carries, and whether `ResolvedCommand` keeps `referenced_by` | compile | question 1 | at start |
| the `dynamic-acl` and `protocol-asset` features | Cargo | built in (the former ADR 011 (now ADR 020)): they add behavior | |

Every failure Tauri reports at compile time, Tokra raises from
`Tokra.generate_context` with the same message (ADR 014). Where
Tauri reaches the message through `expect` or `unwrap`, which print a
Rust `Debug` form, Tokra raises the error's `Display` text instead
(precedence 1: a `Debug` struct dump has no Ruby meaning).

## What exists in Tokra

- **The stopgap.** `App#route_invoke` (`app.rb:850-872`) rejects an
  invoke whose origin `local_url?` (`:955-961`) refuses, unless it is
  the channel fetch, with `Command <cmd> not allowed by ACL`, before
  dispatch. Both transports reach it: `dispatch_ipc` after the invoke
  key check (`:727-760`), passing the postMessage URL, and the `ipc://`
  path, passing the `Origin` header (`:1019-1098`). `local_url?` is the
  first arm of `is_local_url`; Tokra serves no `devUrl` and routes
  custom protocols through `tokra://`, so the other arms wait for `tokra
  dev` ([cli.md](../design/cli.md)). Tests:
  `test/builder/test_ipc_protocol.rb:616-660`; the real-window
  `test/integration/origin_acl_test.rb` and its fixture.
- **The config.** `Tokra::Utils::Config` reads `app.security`
  whole: `capabilities` as `CapabilityEntry::Reference` (a String) or
  `CapabilityEntry::Inlined` holding the raw JSON Hash, a recorded
  deviation until this plan types it (`capability_entry.rb`); and
  `assetProtocol` typed as `AssetProtocolConfig` with an `FsScope`
  (`fs_scope.rb`). The `Field` and `deserialize` machinery, with
  serde's words through `Ipc::CommandItem::Mismatch`, is what the ACL
  types reuse. JSON and JSON5 read; TOML waits on plan 054's question 2
  (`parse.rb:35-42`).
- **The context.** `Tokra::Context` holds config, package info,
  pattern, and icons; its RDoc says the capabilities "join with the
  plans that port them" (`context.rb:35-36`). `Codegen.context_codegen`
  builds it, and `ContextData` names `capabilities` as waiting
  (`codegen.rb:70-80`). Tests build contexts through
  `TestApp#build_test_context`, from a config Hash and the fixture
  directory `test/fixtures/test_app` (`test/support/test_app.rb`).
- **`Utils::Platform::Target`** knows MacOS, Windows, and Linux only.
  A capability's `platforms` may name `android` and `iOS`, which must
  parse.
- **Plugins.** A plugin subclasses `Tokra::Plugin`, answers `name`, and
  dispatches in `extend_api(invoke)`; the clipboard, dialog,
  global-shortcut, and notification plugins keep a `COMMANDS` list. The
  names match Tauri's manifest keys: `clipboard-manager`, `dialog`,
  `global-shortcut`, `log`, `notification`. Apps register plugins on
  the handle in `setup`; another agent is porting `Builder#plugin`, a
  plugin builder, and the `config.plugins` hand-off, which bears on D2.
  `PluginApi` is `Data.define(:app, :config, :name)`, with a note that
  scopes may join it.
- **Core plugins.** `App.new` registers `event`, `resources`, `image`,
  `__TAURI_CHANNEL__`, `menu`, and `tray` (`app.rb:198-212`). `path`
  is being ported by another agent; `window` and `webview` are plan
  050's; `app` is not ported. Their permissions all come from Tauri's
  table regardless (step 6).
- **The JavaScript.** The vendored scripts know nothing of the ACL. A
  refusal is a rejected invoke whose error is the message string; over
  `ipc://` it is a JSON string body with `Tauri-Response: error`, over
  `postMessage` the error callback (`scripts/ipc-protocol.js:40-56`).
  Nothing in the JavaScript changes.
- **Paths.** `Tokra::Path::Resolver` answers `app_log_dir` only today;
  `PathResolver::parse`, which the fs scope needs, comes with the `path`
  core plugin another agent is porting.
- **No glob matcher, no URLPattern.** Ruby's `File.fnmatch` is not glob
  0.3.2 (it never refuses a pattern, and treats `**` and leading dots
  differently), and Ruby has no URLPattern.

## Decisions for the orchestrator

Each has its options and costs. The orchestrator records the choices in
[config.md](../design/config.md), "Access control", which also replaces
the stopgap ([ipc.md](../design/ipc.md), "Only the app's own origin may invoke") and TODO 001 #9 once the check is on.

**Decided, 2026-11-13.** [config.md](../design/config.md), "Access
control", records D1 (a), D2 (a), D3 (c), D7 (a),
D10 (a), D11 (a), and D12 (a). The rest are detailed design, decided
here: D5 (a), a Ruby port of glob, as `Tokra::Json5` ports json5; D6
(a), a `ferro-urlpattern` gem, with `remote` refused at start until it
exists; D8 as listed; D9 (a). D4 is (b): Tokra's own files are JSON
until Tokra reads TOML, since TOML has no parser yet that gives toml's
messages (plan 054's question 2). No step has started.

**D1. Where tauri-build's ACL work runs.**
(a) `Tokra.generate_context` calls it, before any window: errors
surface where Tauri's compile errors would, and `Context` arrives
resolved, as Tauri's does. Plugins registered later in `setup` must
already be known, which D2 settles.
(b) `Builder#build` does it, from the plugins the builder holds:
simpler discovery, but `generate_context`'s `Context` then has no
authority, unlike Tauri's, and a plugin added in `setup` has no
manifest.
(c) A rake or CLI task resolves ahead of time and writes JSON the app
reads: a real build step, which ADR 014 chose against; it may still be
how the packaged context ([packaging.md](../design/packaging.md))
carries the result.
Recommended: (a), with (c)'s output as the packaged form later.

**D2. How Tokra finds a plugin's permissions.**
(a) Gem metadata: each plugin gem names its manifest key and permission
folder in `spec.metadata` (for example `"tokra_plugin" =>
"clipboard-manager"`), and `generate_context` reads them from the gems
Bundler or RubyGems activated (`Gem.loaded_specs`). This is Cargo's
`links` key and `DEP_*` variables translated: every plugin the app
depends on contributes, registered or not, as in Tauri. Cost: a
contract on gemspecs, and a plugin that is not a gem (code in the app)
needs D11's inlined plugins.
(b) A class-level declaration on `Tokra::Plugin` subclasses, gathered
from the plugins `Builder#plugin` holds: no gemspec contract, but it
depends on the plugin-registration work in flight and misses plugins
registered on the handle later.
(c) A list passed to `generate_context`: explicit, and a new API Tauri
does not have.
Recommended: (a).

**D3. Generated permission files.**
(a) Files everywhere: core and plugins alike as committed TOML or JSON,
generated by rake tasks, with a gate check that regenerating changes
nothing.
(b) Nothing generated: manifests built in memory from command lists.
No TOML needed for them, but no `reference.md` and nothing an editor's
schema can read.
(c) Core in memory (Tauri writes core's files only into `OUT_DIR` and
commits only the reference pages), plugins as committed files (as
plugins-workspace commits them).
Recommended: (c), with core's `reference.md` pages generated and
compared against `vendor/tauri/crates/tauri/permissions/` in a test.

**D4. File format, given that TOML waits on plan 054's question 2.**
Tauri reads permission files in TOML or JSON, and capability files in
JSON, JSON5, or TOML, unconditionally (`acl/build.rs:54-67`;
`capability.rs:267-283`).
(a) Wait for plan 054b's TOML and mirror upstream's TOML files.
(b) Write Tokra's own plugin files as JSON now and read TOML once 054b
lands; an app's TOML files fail with the `DisabledFormat`-style refusal
until then.
Recommended: (a) if the maintainer answers plan 054's question 2 before
step 7 starts; otherwise (b), converting the files to TOML afterwards.

**D5. Glob patterns.**
(a) A pure Ruby port of glob 0.3.2's `Pattern` (`new`, `escape`,
`matches_with`, `matches_path_with`, `MatchOptions`, `PatternError`),
about 400 lines of Rust, as `Ipc::Json` ports serde_json and
`Tokra::Json5` ports json5.
(b) A `ferro-glob` binding: exact, but native code and a Ferro release
for a small, pure algorithm; [plugins.md](../design/plugins.md), "Plugins over Ferro", has Ferro skip what Ruby can do.
(c) `File.fnmatch`, with documented differences: no `PatternError`, a
different `**`, different dot handling. Wrong for the fs scope, whose
security advisory (GHSA-6mv3-wm7j-h4w5) turns on exactly these rules.
Recommended: (a).

**D6. URL patterns.**
(a) A `ferro-urlpattern` gem binding urlpattern 0.3.0, as ferro-url
binds url (plan 055), taking a `Ferro::Url::Url` to `test`. Exact, and
Rust's regex dialect comes with it. Cost: Ferro work in another
repository, a release, and a pin.
(b) A pure Ruby port: 3,500 lines of Rust plus a translation of Rust
regex syntax to Onigmo's, with no test suite to prove it.
(c) Never: refuse a capability with `remote` at start, naming the
missing feature. Remote content then never reaches the IPC.
Recommended: (a). Until it lands, step 5 refuses `remote` as (c) does.

**D7. Where the `capabilities/` and `permissions/` folders are.**
Tauri reads them from the crate root, where `Cargo.toml` sits. In every
project `tauri init` makes, that is also where `tauri.conf.json` sits,
and Tauri's own `generate_allowed_commands` reads
`<config directory>/capabilities` (`acl/build.rs:410-411`).
(a) The config file's directory.
(b) The entry script's directory, the anchor of
[config.md](../design/config.md), "Where the loader looks", which stands
for `CARGO_MANIFEST_DIR`.
Recommended: (a). The two agree for an app whose script sits beside its
config; for `Tokra.generate_context("src-tokra/tokra.conf.json")`, (a)
keeps the folders beside the config, as a Tauri project lays them out.

**D8. Module names.**
`Tokra::Utils::Acl` for tauri-utils' `acl` (with `Capability`,
`Manifest`, `Resolved` in their own files, as Tauri splits them);
`Tokra::Build::Acl` for tauri-build's (D1 calls it); the runtime types
in `Tokra::Ipc` (`RuntimeAuthority`, `Origin`, `CommandScope`,
`GlobalScope`, `ScopeValue`, `ScopeObject`, `CapabilityBuilder`) as in
Tauri's `ipc` module; `Tokra::Scope::Fs::Scope` and `Tokra::Scope::Scopes`
for `scope`. The alternative is folding tauri-build's work into
`Codegen`; [config.md](../design/config.md), "The loader", keeps one
module per crate. Recommended: as listed.

**D9. `ScopeObject` in Ruby.**
Rust picks the scope type by generic. (a) The caller passes a class
that answers `deserialize(app, raw)`; without one, the raw JSON value
comes back as Ruby reads JSON, the counterpart of `DeserializeOwned`.
The caches key on that class. (b) Raw values only, each command parsing
its own: simpler, and every scope plugin repeats the work Tauri's cache
saves. Recommended: (a).

**D10. How enforcement lands.**
(a) Steps 1 to 8 resolve and hold the authority, refusing a broken
capability at start, but check nothing; step 9 turns the check on and,
in the same commit, gives every example, fixture, and plugin test the
capabilities it needs. (b) A code-level switch, off until every caller
is ready. Recommended: (a). Nothing between steps 8 and 9 needs the
switch, and a switch would itself need removing.

**D11. tauri-build's `Attributes`.**
`capabilities_path_pattern`, `AppManifest::commands`, and inlined
plugins are written in an app's `build.rs`. Tokra's app commands go
through one `invoke_handler` block, with no command list to generate
permissions from. (a) Defer all three, recorded as deviations: app
permissions come only from `permissions/` files, capabilities only from
`capabilities/**/*`. (b) Keywords on `generate_context`. Recommended:
(a), revisited when an app needs one.

**D12. The notification plugin's sixteen permissions.**
Upstream's default set grants sixteen commands; Tokra implements three.
(a) Mirror upstream's files exactly, so a Tauri capability naming
`notification:allow-cancel` validates; the unimplemented commands still
answer `Command cancel not found`. (b) Generate only Tokra's three: a
Tauri app's capability then fails validation. Recommended: (a), and the
same for global-shortcut's stale `register_all.toml`, which upstream's
glob reads, so `global-shortcut:allow-register-all` exists in Tauri.

## Questions for the maintainer

   when `resolve_access` is ported.

   app commands until the app defines app permissions, a recorded
   deviation.
   Recommended: (a), as the former ADR 010 §6 committed to (now [ipc.md](../design/ipc.md), "Only the app's own origin may invoke"); the RDoc tells app

3. **`add_capability` reuses scope ids, merging a runtime capability's

4. **Does this plan answer plan 050's question 1 with (a)?** Through
   the ACL itself, not a special case for two plugins.
   Recommended: yes.
5. **Accept that every app needs a `capabilities/` file to call any
   plugin command, the event plugin's `listen` included?** (a) Yes, as
   in Tauri; examples gain the `default.json` that `tauri init` writes.
   (b) No: grant `core:default` when an app has no capabilities, a
   deviation.
   Recommended: (a). Pre-1.0, no external users, and Tauri's docs then
   describe Tokra.
