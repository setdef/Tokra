# Plan 068: Tokra's Linux packages, without root

## Context

On Linux, Tokra compiles and links against WebKitGTK 4.1, GTK 3,
libsoup 3, and JavaScriptCoreGTK. bindgen needs libclang. The
real-window tests run WebKitGTK under Xvfb, press keys with xdotool, and
read notifications through dunst. CI installs all of it with
`sudo apt-get install`, in ci.yml's step "Install GTK, WebKitGTK, and a
display server", and `bin/setup` asks a Linux contributor to do the
same first.

## Problem

Not everyone who works on Tokra can run sudo on the Debian or Ubuntu
machine they build on: a shared build machine, a university account, a
locked-down workstation. Without the `-dev` packages and the runtime
libraries under them, nothing compiles, and the gate stops at its first
step.

## Decided

`bin/linux-env` runs a command with ci.yml's apt packages in place. `bin/setup`
runs `bundle install` through it, and `.githooks/pre-push` runs the
gate through it, as `bin/windows-env` does on Windows. Run any other
command through it the same way:

```sh
bin/linux-env bundle exec rake test:core
```

It runs the command unchanged, and does nothing else, when any of these
holds:

- the system is not Linux;
- it has no `dpkg-query`, so it is not Debian or a system built on it;
- `dpkg-query` says every package ci.yml installs is installed, as on CI
  and on a machine where you ran ci.yml's `apt-get install`;
- the command already runs under `bin/linux-env`, which it knows by
  `TOKRA_LINUX_ENV`.

Otherwise it brings the missing packages itself, without root:

1. `apt-get --simulate --no-install-recommends install` with ci.yml's
   packages lists what `apt-get install` would install: every missing
   package and every missing dependency, at the versions this system's
   package lists name. A simulation needs no root.
2. `apt-get download` fetches each of them from the distribution's own
   mirrors. apt checks every file against the hashes in the package
   lists, and the lists against the distribution's signed `InRelease`
   files, exactly as for `apt-get install`. It downloads into a folder
   of its own and moves the files into `tmp/linux-env/debs/` only once
   apt exits 0, so a download cut short leaves nothing there.
3. `dpkg-deb -x` unpacks each into `tmp/linux-env/KEY/root/`. On a system
   whose `/bin`, `/sbin`, and `/lib` are links into `/usr`, files a
   package ships under them move to `usr/`, where dpkg would have put
   them.
4. A tree of symbolic links, `KEY/farm/usr` and `KEY/farm/etc`, joins the
   system's `/usr` and `/etc` with the unpacked ones. Where both have a
   folder, the tree has a folder and joins their contents; where both
   have a file, the unpacked one wins, as it would after an install;
   anything else is one link to wherever it is. A link either side ships
   is copied as it is, so a relative link resolves as it would in place.
   The system's own `/usr` and `/etc` are bound at `KEY/host/usr` and
   `KEY/host/etc`, and the tree's links to the system point there.
5. The command runs under bubblewrap, `bwrap`, with the trees bound over
   `/usr` and `/etc` in a mount namespace of its own. Everything sits at
   the path it was built for, so pkg-config, the compiler, the dynamic
   linker, and WebKitGTK's helper processes find it with no settings,
   and the command runs as you, with your own user and group.
6. Before the first command, it makes what the packages' install scripts
   would have made, each where a package it unpacked has the files for
   it: GLib's compiled settings schemas (`glib-compile-schemas`) and
   gdk-pixbuf's loader cache (`gdk-pixbuf-query-loaders
   --update-cache`). These run under bwrap with the trees bound
   writable, so what they write lands in the tree.

`KEY` is a digest of the packages ci.yml names, dpkg's status file, and
the folder's path. A second run with the same key finds `KEY/ready` and
goes straight to step 5, in a few milliseconds. When you install or
upgrade a system package, or ci.yml's list changes, the key changes:
the next run resolves again, downloads only the files `debs/` lacks,
builds a new `KEY`, and deletes the old one and any file in `debs/` the
new set does not use. A build cut short has no `ready` file and is
built again. A lock file keeps two runs in one checkout from building
at once.

libclang comes with the rest: ci.yml names `libclang-dev`, and apt
fetches it and its headers like any other package, so bindgen finds it
where it looks by default.

## Considered

- **An overlay filesystem over `/usr`.** bubblewrap 0.10 added overlay
  mounts, and the kernel allows an overlay in a user namespace. A spike
  showed one kernel that refuses any overlay with `/usr` as a layer
  there, through `unshare` and through bwrap alike, while an overlay of
  the user's own folders works; and older bubblewraps have no overlay
  options. Plain bind mounts work everywhere bwrap does.
- **Settings alone, with no namespace.** `PKG_CONFIG_PATH`,
  `LD_LIBRARY_PATH`, and `XDG_DATA_DIRS` would reach most of it, but
  WebKitGTK starts `WebKitWebProcess` and `WebKitNetworkProcess` from a
  folder compiled into the library. A spike set `WEBKIT_EXEC_PATH` and
  `LD_LIBRARY_PATH` to the unpacked packages, outside any namespace: the
  page never loaded, since WebKitGTK still looked for
  `WebKitNetworkProcess` in `/usr/lib/x86_64-linux-gnu/webkit2gtk-4.1`.
- **fuse-overlayfs.** Another fetched tool, a FUSE server to start and
  stop around every command, and the cost of FUSE on every file the
  compiler and the tests open. The tree of links costs nothing once
  built.
- **A whole root filesystem** (mmdebstrap's unshare mode, a container).
  It needs a tool the system does not have, and puts Ruby, Rust, and
  your home in a different system from the one you build on.
- **libclang from PyPI's wheel.** It would be a second source with its
  own pin and checksum. apt fetches and checks libclang with everything
  else.

## Spikes

Each ran on a Debian-family machine with none of the `-dev` packages and
no sudo, with no Tokra code: a dozen lines of C that open a GTK window
with a WebKitGTK webview, load a page, and print the result of a line of
JavaScript.

- Ubuntu 24.04 under WSL2, bubblewrap 0.9: the simulation listed 114
  packages in 2 seconds; `apt-get download` fetched them, 125 MB, in 13
  seconds; unpacking took 2 seconds and 700 MB; the packages shipped
  files only under `usr/` and `etc/`. An overlay with `/usr` as a layer
  failed in a user namespace, as above. The tree of links took 2 seconds
  to build, with 11,000 entries, and under it the program compiled
  through pkg-config, WebKitGTK's helper processes started from the
  tree, and the page's JavaScript answered.
- Ubuntu 26.04, bubblewrap 0.11: the same, with 57 packages missing.
- On the first of these, the same program with only settings, as
  under "Considered", aborted when WebKitGTK could not start its network
  process.

## Tests

`test/tasks/test_linux_env.rb` drives `LinuxEnv` with stand-ins for
`dpkg-query`, `apt-get`, `dpkg-deb`, and `bwrap`, in folders of its
own, on any system and with no network:

- it runs the command unchanged off Linux, without `dpkg-query`, with
  every package installed, and under itself;
- with packages missing, it asks apt for ci.yml's packages without
  recommends, downloads what the simulation lists at its versions,
  unpacks each, and runs the command under bwrap with the binds in
  order;
- a second run reuses the build and downloads and unpacks nothing; a
  changed status file builds again and downloads only what is new, and
  removes the old build and unused files;
- a failed download keeps no file, and says what apt said;
- a build cut short is built again;
- the generated caches are made under bwrap with the trees writable,
  only where a package has the files for them;
- the simulation's `Inst` lines, upgrades among them, become packages,
  and nothing else does; a version with an epoch names the file apt
  writes;
- the tree of links joins folders, lets the unpacked file win, copies
  links as they are, and links everything else once.

`test_pre_push_hook.rb` and `test_setup.rb` check that the hook and
`bin/setup` run their commands through `bin/linux-env`.

## Left for later

- The package lists are the system's. When they are old enough that a
  mirror no longer has the versions they name, `apt-get download`
  fails and says so; `sudo apt-get update` fixes it. Lists of
  `bin/linux-env`'s own, with `apt-get update` and apt's `Dir` settings,
  would not need root.
- Only the two caches above are made. GIO's module cache is not needed,
  since GIO loads a module its cache does not name; the MIME database,
  the icon caches, and fontconfig's cache are not made, since nothing
  in the gate has needed them.
- Debian-family systems only. On another system, `bin/linux-env` runs
  the command as before, and you install the packages the way that
  system does.
