# Plan 022: Recorded Follow-ups

Plans 017 through 021 left follow-ups that need no new feature. This plan
clears the ones that are small, local, and have a clear answer, and says
why each of the others stays open.

## 1. The `rbs:parity` stub rule

Plan 017 recorded that the rule which reports an inherited
`NotImplementedError` stub recognizes one way of writing a stub: a body
that is exactly <tt>raise NotImplementedError</tt>, optionally with a
message. Reading `stub?` against Prism's tree showed that even its
`ConstantPathNode` branch never matched, because Prism's `full_name` for
<tt>::NotImplementedError</tt> keeps the leading `::`. The rule now
accepts `raise` or `fail`, the error as a constant, a `::` path, or a
`.new(...)` call on either, as the last statement of the body (so a stub
that builds its message first still counts), and it checks protected and
singleton methods as well as public instance methods. A conditional raise
is not a stub, because the method can return.

The failure message names the escape hatch, with the first violation's
key filled in: <tt>allow "Klass#meth", lint: :rbs_parity, reason: "..."</tt>
in `rbs_exceptions.rb`. The message moves into `RbsParity.failure_message`
so a test can read it.

The new tests define fixture classes and remove their constants afterward,
and Ruby keeps a removed module's name, so the lint went on reporting them
in later tests. It now skips a module whose name no longer resolves to it:
no signature can describe a class that is unreachable by its name, which
is also true of a reloaded class in an app. It checks this after deciding
the module is ours, since looking up another library's deprecated constant
prints a warning.

## 4. A dropped ipc:// response

Plan 020 recorded that `Proxy#drop_response` never makes the page's `fetch`
reject, while `App`'s RDoc said a dropped response makes the client fall
back to `postMessage`.

| Behavior | Tauri | Tokra today | Verdict |
|---|---|---|---|
| Invoke key mismatch over ipc:// | `Webview::on_message` prints `__TAURI_INVOKE_KEY__ expected … but received …` and returns, dropping the owned responder unanswered (`crates/tauri/src/webview/mod.rs:1728-1744`) | Logs the same line and drops the responder (`App#dispatch_ipc_protocol_post`) | Match |
| What dropping does | wry 0.54.0, which Tauri's `Cargo.lock` pins, holds the responder as a boxed `FnOnce` with no `Drop` (`src/lib.rs:440-455`); on macOS the closure only retains the `WKURLSchemeTask` (`wkwebview/class/url_scheme_handler.rs:180-183`), so nothing finishes or fails the task. Tokra's locked 0.54.1 is identical there. | Same wry code | Match |
| What the page sees | The `fetch` stays pending, so `ipc-protocol.js`'s `.catch` fallback never runs and the invoke never settles | Same | Match; Tokra's docs were wrong |

Tauri answers nothing, so Tokra keeps dropping. The RDoc on
`App#dispatch_ipc_protocol_post` and the Rust doc comments on
`Proxy#drop_response` and `take_responder` now say the request is left
pending. A real-window check in the `ipc_transport` fixture sends an
ipc:// request with the wrong key, sees it still pending after a second
while a correct invoke afterwards resolves, and the test reads Tauri's
message on stderr. Linux and Windows are UNVERIFIED: wry's responder has no
`Drop` there either, but what WebKitGTK and WebView2 do with an abandoned
request was not run.

## 5. Plans 018 to 021

Every other item those plans list is a new feature, a CI run, or a
platform this machine cannot run: Linux and Windows real-window runs (018,
CI), `RunEvent::ExitRequested` (018, 020; a feature), the Worker Ractor
round trip (018; ADR 009 §4), screenshots (018; needs Screen Recording
access), Tauri getters and setters not yet ported (020), signals other
than `SIGINT` while the loop idles (020; needs a design), Ractor workers
calling `run_on_main_thread` (020; the extension is not Ractor-safe),
publishing gems and arboard options Tauri does not use (021), and folding
ADR 007 into ADR 011 (021; an ADR pass). Plan 019's follow-ups were all
closed by Plan 020. None is taken up here.

## Verification

Each changed behavior has a test that fails when the change is reverted:
the stub shapes and the failure message in `test/tasks/test_rbs_parity.rb`,
the checklist copies in `test/skills/test_skills.rb`, and the dropped
response in `test/integration/ipc_transport_test.rb` (which fails if
`drop_response` is replaced by an error reply). Then the clean-build gate.
