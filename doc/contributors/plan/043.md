# Plan 043: Tray Icons

Tauri puts an icon in the system tray: the menu bar's status area on
macOS, the notification area on Windows, and an AppIndicator on Linux. The
icon has a tooltip, a title, a menu, and mouse events. Its `tray` module
wraps the tray-icon crate, and its JavaScript API drives the same icons
through the core `tray` plugin. Tokra has none of it. ADR 013 decided that
tray-icon joins Tokra's own extension beside muda, since tray-icon takes
muda's menus and keeps process-wide state.

This plan inventories the port and splits it into phases. Phase 1 ports
the tray icon, its builder and id, its icon, tooltip, title, menu,
visibility, the macOS template flag, the left-click menu switch, the
Linux temp directory, its rect, its events in Tauri's order, the app's
lookups, and every command of the plugin. The rest follows in later work,
each with its reason.

## Decisions

1. **Ruby owns the tray logic; the extension is a thin tray-icon binding.**
   `Tokra::Native::TrayIcon` holds one tray-icon `TrayIcon` in a
   `ThreadBound`, as the menus do (plan 042, decision 1).
   `Native::TrayIcon.new` takes the id and every attribute and calls
   `tray_icon::TrayIcon::with_id`, as `TrayIconBuilder::build` does, so a
   build takes no second id from tray-icon's counter.
   `Native::TrayIcon.next_id` is `TrayIconBuilder::new().id()`, the id a
   new builder gets, which Ruby's `TrayIconBuilder.new` asks for, as
   Tauri's does. `Native::TrayIcon::Icon` is tray-icon's `Icon`. The
   setters are tray-icon's own; `set_temp_dir_path` exists only on Linux,
   `set_icon_as_template` only on macOS, and `set_show_menu_on_left_click`
   only on macOS and Windows, where Tauri's `cfg` calls them, so the Ruby
   method answers `nil` at once where `respond_to?` says no. Tauri's
   wrappers (builder, manager, listeners, plugin) are Ruby.

2. **tray-icon 0.21.0, with `libxdo` and without `serde`.** Tauri enables
   `serde`, and its `linux-libxdo` feature turns on tray-icon's `libxdo`,
   which forwards muda's. Tokra already builds muda with `libxdo`; the
   feature costs nothing more. `serde` would serialize tray-icon's own
   event, which Tauri converts before serializing; Ruby writes the JSON.
   tray-icon loads libappindicator at run time (`dlopen`), so building
   needs no new package. Running a tray on Linux needs
   `libayatana-appindicator3-1` (or the older `libappindicator3-1`): CI
   installs it and the README lists it.

3. **Every call runs on the main thread, after the loop exists.** Ruby
   builds a tray and calls each setter through
   `RuntimeContext#run_main_thread`, as Tauri's `run_on_main_thread` and
   `run_item_main_thread!` do, with `FailedToReceiveMessage` when no
   answer comes. The constructor raises `ThreadError` off Ruby's main
   thread (tray-icon answers `NotMainThread` on macOS; GTK's objects
   belong to its thread). It also raises before any `Native::EventLoop`
   exists: tao initializes GTK and installs its `NSApplication` subclass
   as the loop is built, and an AppIndicator before GTK, or a status item
   before tao's NSApp, breaks both. Tauri cannot meet this, since a tray
   needs a manager that only a running app has; Tokra's `AppHandle`
   exists before `App#run`. Tier 1. The setup hook runs after the loop
   exists, so a tray built there works.

4. **Tray events go through the loop, as in Tauri.** One tray-icon event
   handler, set once per process beside muda's (tray-icon's `OnceCell`
   keeps the first), converts each event and sends
   `UserEvent::TrayIconEvent` through the proxy of the running loop. The
   loop delivers it as `Native::TrayIconEvent`. `App` calls the app's
   listeners in registration order, then the listener of the tray whose
   id the event names, if `tray_by_id` still finds it, then plugins, then
   the run callback with `RunEvent::TrayIconEvent`. Listeners are copied
   out of the manager's lock and called outside it.

5. **The event's values are dpi's.** The native layer converts with
   dpi's own `From<PhysicalPosition<f64>> for Position`, which rounds to
   `i32`, and sends the event's position as `f64`s and the rect's as the
   rounded `i32`s and `u32` size. `Tokra::Rect` is tauri-runtime's
   `Rect`; its position is a `PhysicalPosition` or `LogicalPosition` and
   its size a `PhysicalSize` or `LogicalSize`, since in Ruby the struct is
   the variant (ADR 013, decision 2). Its JSON tags each with `Physical`
   or `Logical`, as serde writes dpi's enums.

6. **Closing a tray removes it from the system tray at once.** In Tauri
   the icon stays while any clone of the `TrayIcon` lives; the resources
   table holds one, so `remove_tray_by_id` or the page's `close` drops
   it unless Rust code kept another. Ruby frees an object when the
   collector runs, which could leave the icon showing for an unknown
   time. So `TrayIcon#close`, which the table calls, removes the id from
   the icons and drops tray-icon's `TrayIcon` on the main thread, which
   takes the icon off the tray. After that the object's setters do
   nothing, `rect` answers `nil`, and its listener no longer hears
   events, since `tray_by_id` cannot find it. Tier 1: Ruby has no
   deterministic drop. A tray the table still holds stays until the app
   ends, as in Tauri.

7. **The exit removes every tray.** Tauri's `App::run` calls
   `cleanup_before_exit` after the run callback hears `RunEvent::Exit`,
   which clears the icons and the app's resources table and so drops each
   tray; without it Windows leaves a dead icon in the notification area.
   Tokra has no `cleanup_before_exit` yet, so it ports that step alone:
   after the run callback hears `Exit`, and before a requested restart,
   each tray in the manager is closed.

8. **Nothing the page or the platform sends panics.** Four panics are
   refused first. libappindicator-sys panics when it can load neither
   AppIndicator library; on Linux the constructor loads them first, by the
   crate's four names in its order, and raises `Error::Tray` with the
   crate's panic text. muda's GTK context menu panics on an accelerator
   GTK cannot build (plan 042, decision 18), and tray-icon builds it when
   it attaches a menu on Linux; the native layer runs plan 042's refusal
   first. tray-icon checks an icon's pixel count as `width * height` in
   `u32` on macOS and Windows; the product can wrap, and on Windows the
   wrapped icon reaches `CreateIcon` with a buffer shorter than its size,
   which reads past it. Tokra runs tray-icon's two checks first in 64 bits
   with tray-icon's texts, on every platform (Linux's tray-icon checks
   nothing and fails later in the PNG encoder). Tauri's `From` ends in
   `todo!()` for a variant tray-icon adds later; Tokra drops such an
   event. An image with no pixels passes those checks; on Windows tray-icon
   then hands `CreateIcon` its empty buffer with a zero size, for which
   GDI makes a 1-by-1 bitmap from bits nothing owns, so Tokra refuses an
   empty dimension first on every platform with tao's text, "The
   specified dimensions (0x0) must be greater than zero.", as plan 042
   decision 13 does for menu icons (`Error::BadTrayIcon`, which the
   builder drops). Tier 1: a panic ends Ruby's VM.

9. **The plugin reads its arguments in Tauri's order and serde's words.**
   `new` reads `options` (a struct from a map or a sequence of nine, its
   fields camelCase), then `handler`; `menu` is a tuple of the rid and an
   `ItemKind`; a path is a string. Trays go into the app's resources
   table; menus and images come from the calling webview's. The handler
   channel hears each event of that tray as its JSON. The page's
   `TrayIcon.close` reaches `plugin:resources|close`, which falls back to
   the app's table (Tauri `resources/plugin.rs:13-22`) and so removes the
   tray (decision 6).

10. **Builder blocks are Ractor-shareable, tray blocks are not.**
    `Builder#on_tray_icon_event` takes a shareable block, as every
    builder hook does. `TrayIconBuilder#on_tray_icon_event`,
    `#on_menu_event`, and the tray's own run where the app runs, so they
    take any block, as `Window#on_menu_event` does.

11. **`with_inner_tray_icon` has no Ruby meaning.** It hands a closure
    tray-icon's own `&TrayIcon`, a Rust type Ruby cannot hold; every
    method it reaches is already a `TrayIcon` method here. Tier 1.

## Verification

No test opens a tray's menu, clicks, or posts input. On macOS a status
item shows in the menu bar while a test runs and takes no focus.

- Stub-native tests drive the Ruby logic through a real `App`,
  `AppHandle`, and builder with a stub tray class that records each call
  (a real status item in the stub suite would make AppKit's
  `NSApplication` before tao's): the builder's attributes and id, the
  main-thread hop and its `FailedToReceiveMessage`, `register`, the
  lookups, removal, the platform guards, the error mapping, events in
  Tauri's order through an injected `Native::TrayIconEvent`, the exit's
  cleanup, and every plugin command with its rejections.
- Rust unit tests convert tray-icon's own events, built with its public
  constructors, through the handler's conversion, and check the RGBA
  refusal.
- Real-extension tests build real trays on the shared event loop: ids,
  the thread and loop guards, the icon refusal, every setter, `rect`,
  and removal.
- A real-window fixture builds a tray with an icon, a tooltip, a title,
  and a menu, then reads it back from the platform: on macOS the status
  bar's window and its button's image, tooltip, and title through Fiddle;
  on Linux the icon file tray-icon writes into the temp directory; on
  Windows what tray-icon answers. It changes each attribute, hides and
  shows the tray, and reads again. Events come through tray-icon's own
  dispatch, never a click: on macOS `mouseEntered:`, `mouseMoved:`, and
  `mouseExited:` sent to tray-icon's view with an event naming its
  window, on Windows `WM_USER_TRAYICON` messages sent to tray-icon's
  window; Linux's tray-icon sends no events. The fixture reports the
  listeners' order.
- A page fixture drives the plugin with the vendored `@tauri-apps/api`.
- Mutation checks by hand for at least five behaviors.

## Results

Every phase 1 item is done; `with_inner_tray_icon`, the config's
`trayIcon`, and the rest of `cleanup_before_exit` wait with the reasons
above.

- macOS (arm64): the stub, native, real-window, and page tests pass. The
  fixture reads the status item's button back through Fiddle (image,
  tooltip, title), sees it gone when hidden and removed, and hears Enter,
  Move, and Leave from tray-icon's own view in Tauri's order. The rect's
  height reads 0 there: the status bar window's frame before AppKit lays
  it out.
- Linux, in a `ruby:4.0.9` Debian container with CI's packages and
  `libayatana-appindicator3-1`, under `xvfb-run dbus-run-session`: the
  extension passes Clippy with Tokra's lints, its Rust tests pass, and the
  tray stub, native, real-window, and page tests pass with the menu
  tests beside them. No StatusNotifierItem host runs there, so the icon
  file tray-icon writes for the indicator is what the tests read: a new
  file per icon, none for `nil`, unchanged while hidden, and removed with
  the tray. libayatana warns on stderr that it is deprecated. With the
  AppIndicator libraries moved aside, building a tray raised
  `Error::Tray` with libappindicator-sys's four load errors instead of
  its panic.
- Windows: the `cfg(windows)` paths (the icon's `Send`, the attributes,
  `set_show_menu_on_left_click`, `rect`, `remove`, the event conversion)
  pass Clippy for `x86_64-pc-windows-gnu` with Tokra's lints in a scratch
  crate on tray-icon 0.21.0 and muda 0.17.1 from Tokra's lockfile. The
  fixture's `WM_USER_TRAYICON` events and window count run only in CI.

Review follow-ups: `get_by_id` and `remove_by_id` read `id` as Tauri's
`&str` ("expected a borrowed string"); options sent as a sequence longer
than nine reject with serde_json's "fewer elements in array"; the
fixtures read the status item's menu back through `-[NSStatusItem menu]`
without opening it; the AppIndicator probe keeps the library it loads,
as the crate's `LIB` does; and stub tests cover the trays' removal on
every early exit and restart. Off the main thread with the loop gone,
nothing can reach a native tray, which only the main thread may drop, so
`restart` there forgets the trays and restarts with them showing until
the process ends.

Mutation checks by hand, each failing a test: the app's tray listeners
moved after the tray's, `tray_by_id` no longer checking the table,
`TrayIcon#close` not removing the native tray, the builder clearing its
icon on a bad image, the exit's cleanup dropped, the plugin looking the
rid up before naming the kind, the rect truncated instead of rounded
(Rust tests), the 64-bit RGBA check dropped (the native test then gets
tray-icon's own refusal with the wrapped count, "the expected pixel count
is 0", where Tauri's text names 4294967296), and on Linux the native GTK refusal dropped
(muda's panic reaches the native test as `fatal`).

A real tray menu (`test/integration/keyboard/tray_menu_test.rb`, the
maintainer's decision): a platform timer on the main thread, outside
tao's handler as a click is, opens the menu the way tray-icon does for a
click, with `-[NSStatusBarButton performClick:]` on macOS
(`platform_impl/macos/mod.rs:467-488`) and on Windows the
`WM_RBUTTONDOWN` that `Shell_NotifyIcon` posts, after which tray-icon
sends the click and calls `TrackPopupMenu` (`platform_impl/windows/mod.rs:286-396`).
The Fiddle call keeps the GVL, as the main thread holds it when a click
reaches tao's loop. While the menu tracks, a timer reads its items, and
another Ruby thread ticks and then closes it by choosing an item: on
macOS `performActionForItemAtIndex:` and `cancelTracking` through GCD's
main queue (`PlatformPopup::Appkit`), on Windows `WM_CANCELMODE` and the
item's `WM_COMMAND`, which muda's subclass of the tray window turns into
the event. On macOS, under the Prohibited activation policy, the menu
opened with its two items, the other thread ticked while it tracked and
closed it, and the chosen item reached the app's listener and then the
tray builder's `on_menu_event`. Those listeners heard it before the click
handling returned: tao's handler is not running while a click's menu
tracks, so tao keeps delivering events and handing the GVL to other Ruby
threads (ADR 012), as Tauri delivers them. No GVL change was needed,
unlike plan 042's popups, which Tokra starts from inside the handler.
`performClick:` alone sends no `TrayIconEvent`; tray-icon sends the
click from its view's `mouseDown:` (`:313-326`), which the test does not
call. On Windows the test expects tray-icon's `Click` (Right, Down); that
path runs only in CI. Linux's tray menu belongs to the desktop's
StatusNotifierItem host, which shows it over D-Bus, so nothing in the
process can open it and the test skips there. Mutation checks: dropping
the builder's `on_menu_event` registration and the tray's menu each fail
the test.

CI follow-ups (runs 40790996438 and 40792165069):

- The keyboard tests proved the GVL release by a rate, ten ticks while
  a menu tracked, which a loaded macOS runner missed. They now prove it
  by order: the thread that closes the menu waits for one tick of
  another thread, with a deadline, and the test asserts that thread, not
  the fallback timer, closed the menu, and that the ticker ticked. With
  the popup holding the GVL (`without_gvl` removed on macOS) the submenu
  is closed by the fallback and both menus record no tick, so the test
  fails.
- On Windows the tray menu fixture hung with nothing on stdout. It
  opened the menu from a `SetTimer` callback with `SendMessageW`,
  holding the GVL. That callback blocks inside `TrackPopupMenu`, and its
  timer stays set until the callback returns, so its `WM_TIMER` comes
  back inside the menu's modal loop and opens again, re-entering the
  blocked callback. The fixture now posts the click's message, as the
  shell does, from the fixture's thread, and detects the menu's end by
  its window going away. On macOS, where a CFRunLoopTimer cannot re-enter
  its own callout, a flag still lets only the first firing open the
  menu. The fixture prints a progress line at each stage, so a hang
  shows how far it got. This path runs only in CI.
- The Windows core suite died with no status and no message. The new
  native test passed `Native::TrayIcon::Icon.from_rgba` an icon with no
  pixels, expecting tray-icon's error. tray-icon passes that icon's empty
  buffer, a dangling pointer, to `CreateIcon` with a zero size, and GDI
  makes a 1-by-1 bitmap from such bits (the rule `CreateBitmap`
  documents), reading memory nothing owns: an access violation outside
  Ruby's reach, and one the page could cause through `setIcon`. Tokra
  now refuses an empty dimension first on every platform (decision 8).
  This is the cause the code shows; CI confirms it.

- The Windows core suite still died silently after that fix (runs
  40794879230 and 40797820197). Replaying each logged seed over its
  batch's file list (minitest 6.0.1 shuffles the classes once from the
  seed and each class's sorted methods from the seed again) puts the
  crashes at the first test of `TestNativeClosedWindow` twice and at
  `TestMenuIcons#test_the_last_icon_a_builder_is_given_wins` once; the
  predicted Windows skips match the logged progress. None of the three
  touches a tray, and Windows logged no Application Error for it. Rake's
  empty status itself says something: Ruby on Windows gives a status no
  exit code only when it maps the NTSTATUS to a signal, an access
  violation, an illegal instruction, or a floating-point fault (Ruby
  win32/win32.c, waitpid), so a fast fail or a stack overflow would have
  shown a code. An access violation that Ruby did not report points to
  a thread Ruby does not run. UNVERIFIED: the cause. The test task now
  prints a failed process's whole status, and Windows CI sets
  `RUST_BACKTRACE=1`.

## Risks

- tray-icon keeps one event handler per process; a second app in one
  process shares it, as with muda's.
- On Linux the AppIndicator shows only where a StatusNotifierItem host
  runs; elsewhere libayatana falls back to an XEmbed icon that most
  desktops no longer show. Tauri has the same limit.
- On Windows, tray-icon's `Shell_NotifyIconW` fails where no shell runs,
  and the build then raises `Error::Tray` with the OS error.
