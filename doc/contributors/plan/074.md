# Plan 074: No shell script in setup, on Windows too

## Context

Plan 073 moved setup into `tasks/setup.rb`, so that no step of it is a
shell script. On Windows it kept two: `bin/clang-headers`, which unpacks
clang's headers, and `bin/windows-env`, which runs a command with what
Rust and bindgen need. Both were sh. Windows setup ran them through
`sh`, and to do that from cmd.exe and PowerShell, which have none on
`PATH`, it put the `usr/bin` of the Git for Windows that `git` leads to
ahead of `PATH` for those two commands (`sh_env`). The gate itself, which
the hook runs as `mise x -- sh bin/windows-env bundle exec rake`, still
needed an `sh`, which the hook has only because git runs it under its own.

## Problem

Setup should run no shell script, on any system. The point of writing it
in Ruby is that what it runs is Ruby, tested in Ruby, on every system. A
borrowed `sh` is a dependency of Windows setup that nothing declares and
that only one machine in the pool has.

## Decided

### The two files

`bin/windows-env` and `bin/clang-headers` are Ruby executables over
classes in `tasks/`, as `bin/linux-env` is over `tasks/linux_env.rb`:
`WindowsEnv` in `tasks/windows_env.rb` and `ClangHeaders` in
`tasks/clang_headers.rb`. The names stay, so what people type changes as
little as possible. A Ruby file with no extension is not something
cmd.exe or PowerShell starts by name, so on Windows they are started
through Ruby, and everything else keeps its form:

    mise x -- ruby bin/windows-env bundle exec rake test:core
    mise x -- ruby bin/clang-headers

Each does what its sh script did, line for line:

- `ClangHeaders` takes the folder `tokra/clang-VERSION` of
  `XDG_CACHE_HOME`, else of `~/.cache`. If `include/stddef.h` is there it
  does nothing. Otherwise it downloads LLVM's clang source release of the
  libclang wheel's version with `curl` (the same flags, with three
  retries) into a folder beside the destination, checks the SHA-256 in
  Ruby (`Digest::SHA256`, where the script ran `sha256sum`), unpacks only
  `lib/Headers` with `tar`, from inside the folder and with names
  relative to it, since GNU tar reads `C:/...` as another host's file, and
  moves the result into place, unless another setup has put headers there
  meanwhile. A failure removes the folder it made and ends with the
  failing command's status. `VERSION` is a constant of the class, where
  the script's `version=` line was read by `bin/windows-env` with `sed`.
- `WindowsEnv` reads the Rust pin from `mise.toml`, asks `ruby` for
  RubyInstaller's MSYS2 (`msys_path` and `mingw_prefix`), asks `python`
  for the libclang wheel's folder, checks that `stdio.h`, `libclang.dll`,
  and clang's `stddef.h` are there, with the script's three messages, and
  runs the command with `RUSTUP_TOOLCHAIN`, `BINDGEN_EXTRA_CLANG_ARGS`
  (CI's, with `-resource-dir`), and `LIBCLANG_PATH` added. Paths are
  written with forward slashes, as ci.yml writes them. The command's
  status is its own.

Both start commands as argument lists through `Setup::Shell`, the one
runner of `tasks/setup.rb`, which gains `capture_separately`, since the
sysroot and libclang are values read from stdout and a warning on stderr
must not become part of a path.

### The MSYS2 that runs it

The script set `MSYS2_PATH`, where it was unset or empty, to the MSYS2
whose bash ran it (`cygpath -m /`) if that MSYS2 had the UCRT64
compiler. Ruby has no bash to ask. The same case is met from `PATH`: an
MSYS2's bash puts its own `usr/bin` and `ucrt64/bin` there, so
`WindowsEnv` takes the first `PATH` entry that is one of the two, whose
MSYS2 root has `ucrt64/bin/gcc.exe`. Git for Windows' `usr/bin` has no
compiler and is passed over. This differs from the script in one case: an
MSYS2 with a compiler that is not the first of its kind on `PATH` is now
used, where the script used only the one running the shell. RubyInstaller
looks among `PATH`'s entries for an MSYS2's root itself, so that is the
neighbourhood it already searches. Under mise, `MSYS2_PATH` is set and
none of this runs (Plan 071).

### Setup, the hook, and the borrowing

`tasks/setup.rb` runs `mise x -- ruby bin/clang-headers` and
`mise x -- ruby bin/windows-env bundle ...` as commands of its runner,
and `sh_env`, with the tests that put Git for Windows' `sh` ahead of
`PATH`, is deleted. No command setup runs needs a shell, and none needs an
environment of its own. `.githooks/pre-push` is still a sh file, as git
runs hooks through its own sh; its Windows branch runs
`mise x -- ruby bin/windows-env bundle exec rake`.

### Their tests

`test/tasks/test_windows_env.rb` and `test/tasks/test_clang_headers.rb`
are rewritten on the classes, with real temporary folders, and none skips
on Windows. `WindowsEnv` runs against a runner that answers ruby and
python with Windows-spelled paths and records the command and its
environment. `ClangHeaders` runs against a runner that answers `curl` by
copying a small archive shaped like LLVM's and runs `tar` for real, so
the unpacking is checked against the tar each system has. The
executable-mode checks remain. The hook's own test puts a Ruby file where
it had a sh stand-in for `bin/windows-env`.

## Not decided here

- mise 2026.10.11 was not run (Plan 073).
- `curl` and a `tar` that reads xz are needed on `PATH`: Windows 10 and
  later ship both in System32, and an MSYS2 has its own. Ruby has neither
  a decompressor for xz nor a download that follows GitHub's redirects
  as simply as `curl --location`, so they stay commands.

## Proof

On 2026-11-23, mise 2026.11.7:

- `test_clang_headers.rb`, `test_windows_env.rb`, `test_setup.rb`, and
  `test_pre_push_hook.rb`: 89 runs on Windows and on Linux, no
  failures. On Windows 21 skip: the hook's 20 tests, which start an sh
  script and skip there as before, and `bin/setup`'s executable mode. No
  test of the two new files skips.
- `bin\setup.cmd` from cmd.exe, and from Windows PowerShell 5.1, with a
  `PATH` of mise, Windows' own folders, and Git for Windows' `cmd`
  folder, so that `where sh` finds nothing and `curl` and `tar` are
  System32's, and with empty mise data, state, config, and cache
  folders: both installed the six tools, the toolchain, the Python
  packages, ran `bin/clang-headers` (a real download, checksum, and
  unpack), checked the bundle through `bin/windows-env`, and ended with
  status 0.
