# Plan 058: CI's Linux job, in Docker, before a push

The maintainer's gate runs on a Mac. Tests that skip off Linux, and code
behind `cfg(target_os = "linux")`, never run there, so twice Linux CI was
the first place a change failed: most recently two zenity dialog tests in
`plugins/dialog/test/test_linux_dialogs.rb` that still expected an old
empty title. The maintainer has Docker. This plan runs CI's Linux job in
a container on this machine, with `rake test:linux`.

## What it runs

The steps `.github/workflows/ci.yml` runs on `ubuntu-latest`, read from
ci.yml itself: its "Install the bundle" commands, which install the
bundle frozen into `vendor/bundle`, then its "Run the gate under X11"
command, `xvfb-run --auto-servernum dbus-run-session -- bundle exec
rake`. Off macOS `RealWindows.where` is `:local`, so the real-window
tests run in the container, under Xvfb. A Linux window there never
reaches the maintainer's session. `rake "test:linux[TASK,...]"` runs
those tasks instead of the whole gate, for a quicker loop on one
failure.

The container sets `CI=true`, which GitHub Actions sets on every runner
(ci.yml does not), and `TOKRA_QUIET=1`, which CI does not set: it
silences the console tests' notice, which says nothing on Linux anyway.

## The image

`tasks/linux/Dockerfile` starts from `ubuntu:24.04`, the release
`ubuntu-latest` runs today, and adds what the runner image has and the
job relies on (git, a C toolchain, Python 3.12), Ruby built from its
release tarball with `--enable-shared` as setup-ruby's are, rustup at
the toolchain `mise.toml` pins, the REUSE tool, Bundler at the version
`Gemfile.lock` names, and a `tokra` user to run as. The task reads the
pins from the files CI reads them from, and passes them as build
arguments: the Rust toolchain from `mise.toml`, its components from
ci.yml's `dtolnay/rust-toolchain` step, the apt packages from ci.yml's
install step (the `apt-get install` command and the lines its
backslashes continue it onto), the REUSE requirement from ci.yml's, and
Bundler from `Gemfile.lock`. Ruby is the exception: its checksum has to
travel with its version, so both live in the Dockerfile. A test checks
that its version is `mise.toml`'s and lies in the series of each Ruby in
ci.yml's matrix, which names a series such as `"4.0"`, and fails when the
matrix holds more than one Ruby, since the image holds only one. The
build sends only `tasks/linux/` as its context. Docker's layer cache
makes a second build instant; the toolchain lives in the image, keyed by
its pin, rather than in a volume. rustup-init itself comes unpinned from
`sh.rustup.rs` over TLS, as rustup's own instructions give it, so the
image trusts that site and its certificate rather than a checksum.

CI's runner user is not root, and neither is `tokra`: one test checks
that an unreadable file fails to read, and skips as root, who reads
anything. The image sets `LANG=C.UTF-8`, the runner's locale; without it
Ruby reads the Ferro gemspecs as US-ASCII and Bundler fails.

## Where it differs from CI

The container comes close to CI's Linux job, not exactly:

- It runs on arm64 here, where CI's runner is x86_64.
- `ubuntu:24.04` is fixed, while `ubuntu-latest` moves when GitHub moves
  it, and the runner image's preinstalled packages are not all here.
- Ruby is built from source at `mise.toml`'s patch, where setup-ruby
  installs its own build of the latest patch in ci.yml's series.
- The `-target` and `-tmp` volumes persist, so a warm run is an
  incremental build, not a clean one. `CLEAN=1 rake test:linux` removes
  both before the run, for a clean build of everything but the gems.
- A submodule is copied as its working tree has it. When its HEAD is
  not the commit the checkout records, the task says so; CI would check
  out the recorded one.
- It copies the working tree's tracked files, unstaged changes included,
  where CI checks out a commit.
- It adds `TOKRA_QUIET=1`.

## The checkout

The checkout is bind-mounted read-only at `/src`, and the container
never writes there. After the image is built, the task sends a manifest
on standard input: the files git tracks (`git ls-files --stage`), as
they are in the working tree, and for each submodule its own tracked
files. That matches what CI checks out, so an untracked file the Mac
gate would see is not there. `LinuxGate.snapshot`, run by the
container's Ruby from `/src`, copies them into `/work`, keeping modes,
times, and symlinks, and commits them into a fresh git repository, each
submodule as a repository of its own recorded as a gitlink, because the
gate's tasks, the gemspecs, and the REUSE tool all ask git which files
exist. Git takes every path literally (`--literal-pathspecs`): a tracked
name such as `[ab]` would otherwise match, and commit, build output the
warm volumes hold. A file that vanishes between the manifest and the
copy fails the run, saying to run it again.

## Volumes, and several checkouts at once

Each checkout gets five named volumes, keyed by the slug Plan 056 keys
its copies by (`HiddenJob.slug`, the folder's name and eight hex digits
of a digest of its path): `tokra-linux-SLUG-cargo` (`CARGO_HOME`),
`-gems` (`GEM_HOME`, where the plugins' bundles install, as on CI's
system Ruby), `-bundle` (`/work/vendor/bundle`), `-target`, and `-tmp`.
So the second run builds nothing that has not changed, and checkouts run
at once without sharing a writer. Its image is `tokra-linux:SLUG` and
its container `tokra-linux-SLUG`; a second run of the same checkout
refuses while the first's container exists, rather than share its
volumes. The mount refuses a checkout path holding `,` or `"`, which
`docker run --mount` cannot take. Each volume carries a
`dev.tokra.checkout` label naming its checkout, and `rake
test:linux:prune` removes the volumes and image of every checkout whose
folder is gone. A volume it cannot remove fails the prune by name, once
it has tried the rest.

Nothing reads files under the maintainer's home outside the checkout.

## Gate or pre-push

Measured on the maintainer's Mac (Docker 29.8.2, arm64, 10 CPUs and
8 GB for Docker), on trunk `e97bf54` with this plan's files staged,
while other projects' jobs held the Mac's load average between 500 and
950. Each passed: 2077 tests, no failures, 73 skips.

| Run | Time |
| --- | --- |
| The image, built from `ubuntu:24.04` alone | 26 min (Ruby 11, ci.yml's packages 10, export 3) |
| The gate with empty volumes, the image cached | 31 min |
| So a cold run, both | about 57 min |
| Warm: image cached, volumes full, no change | 5 min 42 s |

CI's Linux job took 9 min 54 s on the same commit, with its caches warm.

The gate stays as it is, and `test:linux` is a separate task to run
before each push. A warm run would add six minutes to every commit, on a
Mac whose gate already waits on the hidden session, and a cold one, after
any change to the Dockerfile, a pin, or ci.yml's packages, about an
hour. It also needs Docker running and the network, for the git gems,
neither of which the gate needs today. The failures it exists to catch
are rare enough, twice so far, that once per push catches them before CI
does at a fraction of the cost.


## Tests

`test/tasks/test_linux_gate.rb` checks:

- the image, container, and volume names, keyed by the slug, and that
  two checkouts share none;
- the build arguments read from this repository's own pins, and, from a
  stand-in ci.yml whose every step differs, the Rust components, the apt
  packages up to the end of their continued command (not a later
  `apt-get clean`), the REUSE requirement, and Bundler;
- the bundle and gate commands the container runs, from the real ci.yml
  and from the stand-in, with the given tasks after the gate;
- the Dockerfile's Ruby against `mise.toml` and ci.yml's matrix, its
  checksum, its Python, its base, and an `ARG` for each build argument;
- the build command, which sends only `tasks/linux/`;
- the volume commands' labels;
- the run command: the read-only mount, each volume where it belongs,
  the environment, and the script; and its refusal of `,` and `"`;
- the manifest against a temporary repository with a submodule, a
  symlink, an executable, a deleted file, and an untracked one; a
  submodule not checked out; and a submodule not at its recorded commit;
- the snapshot: a repository whose `git ls-files` lists what the
  checkout's does, with modes, times, and symlinks kept; a tracked `[ab]`
  beside an untracked `a`, which it leaves out; and a file that vanishes;
- the run against a stand-in docker: its order, the manifest on its
  input after the build, the output it passes on, a clean run's removal
  of the build volumes before it creates them, and that a run that is not
  clean keeps them; its refusal while the container exists; a failed
  build and a failed gate by name;
- the prune: only the volumes and image of a gone checkout, said as it
  removes each, and a volume it cannot remove, which it goes on past and
  then names.

The Docker run itself is proved by hand, end to end.
