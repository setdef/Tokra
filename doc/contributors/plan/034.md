# Plan 034: Signals While the Loop Is Idle

A running Tokra app ignored `kill`. The maintainer had to `kill -9` a
leftover `ipc_transport` fixture after a plain `kill` did nothing. Plans
018 and 020 handled Ctrl-C and claimed that Ruby's default `SIGTERM`,
`SIGHUP`, and `SIGQUIT` handlers end the app, but ADR 012 already
recorded the gap in its consequences: "With no other thread and no
events, nothing wakes the loop for a signal alone." This plan closes it,
for every signal Ruby handles and for an app's own `trap` handlers.

Sources: `vendor/tauri` at `9f0306fb`; tao 0.34.5, wry 0.54.1, ctrlc
3.5.1, and rb-sys 0.9.130 as `Cargo.lock` pins them; Ruby `v4.0.1`
(`e04267a1`), the version earlier plans cite (the gate runs 4.0.9).

## Root cause

A probe confirmed it: `exit_paths/app.rb --wait`, sent `SIGTERM` three
seconds after its page reported, was still running 16 seconds later and
ended only by `SIGKILL`. Sent the instant the page reported, while the
page's last requests still reached Ruby, the same signal ended it at once.

Ruby never runs a signal's handler in C signal context. Its `sighandler`
counts the signal and calls `rb_thread_wakeup_timer_thread`
(`signal.c:697-716`), which sets the main thread's trap-interrupt flag and
calls the main thread's unblocking function, if it has one
(`thread_pthread.c:2607-2631`). The timer thread does the same once it
wakes (`timer_thread_check_signal`, `thread_pthread.c:2936-2945`;
`threadptr_set_interrupt_locked`, `thread.c:354-372`). The handler
itself, Ruby's default `SignalException` or the app's `trap` block, runs
later, when the main thread checks its interrupts
(`rb_threadptr_execute_interrupts`, `thread.c:2617-2660`, which calls
`rb_signal_exec`, `signal.c:1095-1134`).

A thread has an unblocking function only inside a blocking region
(`blocking_region_begin`, `thread.c:1523-1543`). Tokra's main thread is
never in one: it waits inside tao's native loop holding the GVL, which
ADR 012 chose because releasing it there is unsound. So a signal sets a
flag that nothing reads, and wakes nothing. The flag is read at the next
Ruby call the loop makes: an event delivered to the callback, or the
`Thread.pass` of a GVL hand-off. The hand-off happens only when another
Ruby thread waits for the GVL (Plan 020, decision 5), which is why the
existing `SIGTERM` test, whose fixture runs a ticker thread, passed. An
idle app with no other thread made no Ruby call until the window got an
event, so the signal waited for a mouse movement or forever.

Plan 020's decision 9 is right about what happens once Ruby sees the
interrupt; this plan makes sure Ruby gets to see it.

## Fidelity audit

| Behavior | Tauri | Tokra before | Verdict |
|---|---|---|---|
| `SIGTERM`, `SIGHUP`, `SIGQUIT` | no handler anywhere: tao, wry, and Tauri's runtime crates never call `sigaction` (grep of `vendor/tauri/crates/{tauri,tauri-runtime,tauri-runtime-wry}`, tao 0.34.5, wry 0.54.1), so the default action ends the process at once; no `RunEvent` fires | ended the app only when an event or a hand-off ran Ruby; idle, ignored | Ruby's semantics, now within one time slice (decision 1) |
| `SIGUSR1`, `SIGUSR2`, `SIGALRM`, other trapped signals | default action (most end the process) | same as above | Ruby's semantics, as above |
| An app's `trap` | not applicable | ran only at the next event | runs within one time slice |
| `SIGINT` | default action | ctrlc ends the loop with status 0 (Plan 018) | unchanged |
| Windows | console control events end the process | ctrlc answers every console control event as Ctrl-C (ctrlc `platform/windows/mod.rs:30-34`); Ruby's `Process.kill` sends only `INT`, `KILL`, and the console break (`win32/win32.c:4973-5034`) | unchanged; the periodic check also runs there |

## Decisions

1. **Ruby's semantics, not Tauri's immediate default.** Precedence puts
   Ruby the language first. A Ruby program sent `SIGTERM` raises
   `SignalException` in its main thread, runs `ensure` clauses and
   `at_exit` hooks, flushes its output, and then ends by the signal, so
   its parent sees `termsig` 15. A `trap` replaces that with the app's own
   block, which may log and keep running, or `exit` with a status. Tauri's
   behavior, the process vanishing mid-write, is what a Rust program gets
   by default, not a choice Tauri made; a Ruby app that installs a `trap`
   expects it to run. As before (Plan 020, decision 9), the unwinding loop
   delivers `LoopDestroyed`, so plugins hear `RunEvent::Exit` the way
   `ensure` code runs; Tauri, whose process dies, emits nothing. That is
   the documented deviation.

2. **The loop wakes once per time slice.** A thread that calls no Ruby
   API sends the loop `UserEvent::Yield` every 100 ms while it runs
   (`InterruptTicker`, `interrupt_check.rs`), and stops when the loop
   ends. 100 ms is Ruby's default time slice (`thread_default_quantum_ms`,
   `thread.c:118`), the latency Ruby already accepts before a busy thread
   sees an interrupt; `RUBY_THREAD_TIMESLICE` changes Ruby's slice, not
   this constant. The first version set a `WaitUntil` deadline instead,
   and review found it does nothing on Linux: tao 0.34.5's GTK loop adds
   no timeout for it and blocks in `gtk::main_iteration_do(true)` until a
   GTK event arrives (`platform_impl/linux/event_loop.rs:1062-1086`,
   `1131`), so a signal sent within 100 ms of the last turn, or with no
   later GTK event, waited. A proxy event wakes every backend, and needs
   no GLib source the loop would have to remove. Ruby's timer thread,
   which wakes for every signal, offers no hook to wake tao with.

   The cost is about ten wake-ups a second on every platform, Windows
   included, each one turn of the loop; macOS counts each as an idle
   wake-up. While Ruby has no other thread, the loop's own flow stays
   `Wait`, so Windows does not pay the spin tao adds before a `WaitUntil`
   deadline, up to about 1 ms per wake
   (`platform_impl/windows/event_loop.rs:2443-2460`), which the
   deadline-based first version would have cost there. Whenever another
   Ruby thread exists, Windows' loop is already in poll mode with a 10 ms
   `WaitUntil` (`gvl_handoff.rs`, unchanged by this plan), and each tick
   there adds one hand-off to the hundred a second it already makes.

   The ticker stops for good on its first failed send, which means the
   loop is gone; on Windows `PostMessageW` also fails once the thread's
   posted-message quota is full, after about a thousand seconds of a main
   thread stuck in Ruby, and an in-process signal then waits for the next
   event again. ctrlc still handles console signals there.

3. **Every turn hands over when an interrupt is pending.** At
   `MainEventsCleared` the loop asks Ruby, through the public
   `rb_thread_interrupted` (`include/ruby/internal/intern/thread.h:375`;
   `thread.c:1483-1487`), whether the main thread has an interrupt
   pending, and if so calls `Thread.pass` even when no thread waits for
   the GVL. `Thread.pass` is `rb_thread_schedule`, which runs pending
   interrupts (`thread.c:1495-1518`), inside magnus's `rb_protect`, so the
   handler runs on the main thread in a protected call, never across tao.
   What it raises is handled as Plan 020 handles it: a `SignalException`
   ends the loop and `EventLoop#run` raises it again once the loop is
   down, a `SystemExit` from `trap { exit 3 }` ends the loop with its
   status, and a handler that returns leaves the loop running. The same
   check also runs postponed jobs and Ractor interrupt tasks, which share
   the trap flag (`thread.c:2640-2665`). No exit is ever made to wait for
   this hand-off (`hands_over`).

4. **Windows signals are unchanged; its idle loop now wakes too.**
   ctrlc's console handler already turns Ctrl-C, Ctrl-Break, and a closed
   console into the loop's exit, and `Process.kill(:TERM)` fails there
   with `EINVAL`. Ruby's Windows timer thread raises the trap flag for any
   queued signal every 10 ms (`thread_win32.c:770-781`), so the same check
   delivers a signal Ruby raises in-process. The ticker runs there as
   everywhere (decision 2). The real-window signal tests skip on Windows,
   whose `kill` cannot send these signals.

## Alternatives rejected

- **Chain a native handler in front of Ruby's**, writing to a self-pipe
  that wakes the loop. It changes what Ruby's `trap` reports: `trap`
  names the old handler from the current disposition, and only Ruby's own
  `sighandler` maps to `"DEFAULT"` (`signal.c:1278-1312`). With a chained
  handler installed, `old = trap("TERM") { ... }` returns `nil`, and the
  idiom `trap("TERM", old)` then ignores `SIGTERM` (`trap_handler`,
  `signal.c:1194-1200`, treats `nil` as `SIG_IGN`). Ruby's `trap` also
  replaces the chained handler, so a trap set while the loop runs would go
  unwatched.
- **Observe deliveries without a handler**: kqueue's `EVFILT_SIGNAL`
  records signals without changing dispositions, but exists only on macOS
  and the BSDs, and its event can reach a watcher before Ruby's handler has
  set the flag the loop then checks. Linux's `signalfd` needs the signal
  blocked, which keeps it from Ruby's handler.
- **Watch Ruby's signal buffer from a native thread.**
  `rb_thread_check_trap_pending` reads it, but Ruby calls it a "hidden
  API for tcl/tk wrapper" with "no guarantee to perpetuate it"
  (`thread.c:1471-1479`) and declares it only in the internal `vm_core.h`.
  Reading the main thread's flag through `rb_thread_interrupted` off a
  Ruby thread dereferences a Ruby object and
  its execution context, which fibers swap, without the GVL.
- **Release the GVL around the loop** so Ruby's unblocking function wakes
  it. ADR 012 rejects it: taking the GVL back runs interrupts, and a trap
  that raises would `longjmp` across tao's frames.

## Changes

- `ext/tokra/src/interrupt_check.rs`: `INTERRUPT_CHECK` and
  `InterruptTicker`.
- `ext/tokra/src/event_loop.rs`: runs the ticker for the life of the
  loop; `interrupt_pending`; the hand-off at `MainEventsCleared` runs when
  an interrupt is pending as well as when a thread is owed the GVL;

- `ext/tokra/src/gvl_handoff.rs`, `user_event.rs`: docs.
- `test/integration/fixtures/native_loop/app.rb`: `--idle`, a loop with no
  other thread and no events after its first, with `--trap-usr1` (prints

  an `ensure` around the loop prints `ENSURE`.
- `test/integration/fixtures/exit_paths/app.rb`: `--run-callback`.
- `test/integration/native_loop_test.rb`, `exit_paths_test.rb`: the
  signal tests below.
- ADR 012's consequence amended; CHANGELOG's signal entry corrected.

## Verification

- Rust: `InterruptTicker` wakes again and again, stops on drop without
  waiting out its interval, and stops once a wake fails;
  `INTERRUPT_CHECK` is 100 ms.
- Real processes, idle loop, no other thread, each held to a 2 s grace:
  `SIGTERM` after a 1 s settle and `SIGTERM` sent the moment the loop
  starts, and `SIGHUP`, each end the app by the signal after `ENSURE`
  then `AT_EXIT`; `SIGUSR1` with a trap prints `TRAPPED USR1` and the app
  keeps running until a later `SIGTERM` ends it; `SIGTERM` with
  `trap { exit 3 }` prints `TRAPPED TERM` and ends with status 3.
- A full app idling after its report: `SIGTERM` ends it by the signal,
  and the fixture plugin and the run callback both hear
  `RunEvent::Exit` before `at_exit` runs.
- Linux, in a container under Xvfb: the first, deadline-based version
  fails the no-settle test; this one passes.
- Manual mutations, and the clean-build gate.

## Results

Before the change, all four idle-loop tests hung until the harness killed
them at 60 s, each still showing only `READY`. After it they pass, and
`exit_paths --wait` sent `SIGTERM` three seconds after its report ends by
the signal in about 30 ms.

The first version woke the loop with a `WaitUntil` deadline. Review found
that tao's Linux loop never wakes for one (decision 2). In an Ubuntu
container under Xvfb that version passed every test that settles before
signalling, since a signal that interrupts the main thread's `poll`
finds the deadline lapsed, but it hung on
`test_a_signal_right_after_another_turn_still_ends_the_app`, whose
`SIGTERM` arrives within 100 ms of the turn the `USR1` trap ran. The
ticker passes all nine there.

Manual mutations, each run alone against a rebuilt extension:

- `INTERRUPT_CHECK` at 30 s: five idle tests outlive their 2 s grace,
  and the Rust constant test fails.
- The ticker's wake made a no-op: the same five fail, and the
  `exit_paths` `SIGTERM` test outlives its grace.
- The hand-off without `interrupt_pending`: the `USR1` trap test hangs.
- `yield_gvl` dropping a `SystemExit` instead of reporting it: the
  `trap { exit 3 }` test hangs.
- `yield_gvl` dropping any other exception instead of ending the loop:
  the idle `SIGHUP` test hangs.

The clean-build gate passes with zero errors and zero warnings: core 664
runs, 2061 assertions, 5 skips; plugin suites 67, 72 (14 skips), 41 (5
skips), 83, and 41 (7 skips) runs; Rust 38 tests; RuboCop, Steep, and
Clippy clean.

## Out of scope

- A zero-cost wake on macOS: a GCD `DISPATCH_SOURCE_TYPE_SIGNAL` source
  on the main queue, which, like kqueue's `EVFILT_SIGNAL` beneath it,
  leaves the disposition alone. A wake that finds no interrupt yet would
  need a short `WaitUntil` re-check, since the source can fire before
  Ruby's handler sets the flag.
- `SIGINT`: ctrlc keeps it (Plan 018), so an app's `trap("INT")` still
  does not run while the loop runs.
