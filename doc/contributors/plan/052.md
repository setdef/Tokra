# Plan 052: More windows, child webviews, and `WebviewWindow`

A Tokra app has one window and one webview, both labeled `main`, made by
`App#run` before the loop starts (`lib/tokra/app.rb:273-297`). Nothing
can make another. A Tauri app makes as many as it likes, at any time,
from any thread: `WebviewWindowBuilder` makes a window holding one
webview, and with the `unstable` feature `WindowBuilder` makes a bare
window and `Window#add_child` puts webviews in it at a position and size.
Each new window and webview is announced to the page as
`tauri://window-created` and `tauri://webview-created`. TODO 002 lists
all of it as one item, with the webview getters and setters plans 040
and 045 deferred and the traffic-light position, which only the
webview-window builder has at the pinned commit.

The obstacle is not the builders. It is that Tokra's native layer
cannot tell windows apart. No event the loop hands Ruby names its window
or webview: `ForRuby::CloseRequested`, `Destroyed`, `Resized` and the
rest carry no id (`ext/tokra/src/event_loop.rs:313-331`, `:370-441`),
the webview's IPC, protocol, page-load and drag-drop events carry none
(`ext/tokra/src/user_event.rs:90-124`), and `App` answers every one of
them for `@handle.windows["main"]` or `@webview` (`app.rb:663`, `:668`,
`:837`, `:1200`, `:1219-1222`, `:1266`, `:1281`, `:1295`). A second
window would have its close button close the first.

So the plan has six phases, each one reviewable commit, with a small
fix first. 052a-0 attaches Windows' WebView2 focus binding where `App`
builds its webview (decision 6). Phase 1 makes every native event name
its window or webview and routes on the name, with no new public API;
both are specified in full. Phases 2 to 6 are outlined, each to get its
own plan section and review when the one before lands.

052a lands before plan 050's 050c. 050c's window plugin reaches a window
by label, and its `close` command needs `Window#close` to close *that*
window, which needs `request_close(label)` (plan 050, decision 12 at
`:437-456`, and its test at `:795`; `runtime_context.rb:146-148` sends
no label today).

| Phase | Commit | What a developer gets |
|---|---|---|
| 052a-0 | WebView2 focus on the app's webview | Windows apps start getting `Focused` (decision 6) |
| 1 (052a) | events name their window or webview | nothing new; `on_page_load` gets the webview, and plugins hear it |
| 2 (052b) | `WebviewWindowBuilder`, `WebviewWindow`, the created events | windows made at run time, from any thread |
| 3 (052c) | the window builder's rows | every desktop row of `WindowBuilder`, the traffic-light position |
| 4 (052d) | `WindowBuilder#build`, `WebviewBuilder`, `Window#add_child` | child webviews, `Rect` bounds, auto-resize, `reparent` |
| 5 (052e) | the webview rows | the webview builder's rows and handlers; `url`, `navigate`, `reload`, cookies |
| 6 (052f) | the page's creating commands | `plugin:window\|create`, `plugin:webview\|create_webview_window`, `create_webview`, `reparent`, `set_webview_auto_resize` |

## What `unstable` gates at `9f0306fbc`

It gates three kinds of thing, and ADR 011's rule (a Cargo feature that
adds behavior is built in) treats them differently:

1. **API.** `WindowBuilder`, `WebviewBuilder`, `Window::builder`,
   `Webview::builder`, `Window#add_child`, the plugin's
   `create_webview`, and the manager's `get_window`, `windows`,
   `get_webview`, `webviews`, and `get_focused_window`. Without the
   feature none of it exists. This adds behavior, and Tokra already
   ships four of the five manager getters, so Tokra has been building as
   `unstable` all along. Port.
2. **A check removed.** Without the feature, `Webview#reparent` refuses
   to move a webview out of or into a webview window, with `cannot
   reparent when using a WebviewWindow` (`webview/mod.rs:1533-1539`).
   The check exists because a webview window's webview is its window's
   content: wry built it with `build`, not `build_as_child`, so on macOS
   it is the window's content view's only subview and its first
   responder (`wkwebview/mod.rs:612-640`), and there is nothing sound to
   move. It falls with item 3, so it belongs to question 1: Tokra keeps
   `Error::CannotReparentWebviewWindow` unless the answer is (a). Plan
   050's phase 3 `reparent` command follows the same answer.
3. **A different webview window.** With the feature, the webview a
   `WebviewWindowBuilder` makes is a child of its window, not its
   content (`lib.rs:4489-4500`): it gets bounds the size of the window
   and auto-resize rates of 0, 0, 1, 1 (`:4807-4823`), its drag-drop
   events become webview events, not window events (`:4695-4700`), and
   no undecorated-resize handler is attached (`:5055-5067`). wry then
   builds it with `build_as_child`, so on macOS it is never the window's
   first responder and never gets the traffic-light inset
   (`wkwebview/mod.rs:612-640`). This replaces behavior Tokra ships
   rather than adding any. It is question 1, with item 2, and only phase
   4 waits on it.

## Decisions

1. **Tokra builds as Tauri with `unstable`, except where question 1
   says otherwise.** The API is ported (see "What `unstable` gates").
   Whether a webview window's webview becomes a child, and with it
   whether `reparent` drops its webview-window check, is question 1.
   Until phase 4 every webview is built as content, as today.

2. **Every native event names its source, by label (phase 1).** Tauri's
   runtime turns a tao window id into its own `WindowId` through
   `window_id_map`, finds the window's label, and calls back with
   `RunEvent::WindowEvent { label, .. }`, dropping an id it does not know
   (`lib.rs:4126-4150`). A webview's events reach the app by the webview's
   label: the IPC handler captures it (`:5169-5192`), the page-load
   handler looks it up (`manager/webview.rs:282-300`), and a custom
   protocol reads the id wry passes, which is the label the runtime gave
   `with_id` (`:4625`; `manager/webview.rs:229-233`). Tokra does the
   same:

   - **Window events** carry the window's label. `RbWindow::new` takes
     the label and records `tao WindowId -> label` in a table on the main
     thread; `Turn::handle` reads the label as it queues the event, drops
     an id the table lacks, and forgets the id when it queues
     `Destroyed`.
   - **Webview events** carry the webview's label. Each webview is built
     `with_id(label)`; the `tokra://` and `ipc://` handlers forward the
     id wry hands them; the IPC, page-load, drag-drop, and (Windows)
     focus closures capture a copy of the label.
   - **The close request** names its window: `Proxy#request_close(label)`.
     Tauri's `WindowMessage::Close` carries a `WindowId`
     (`lib.rs:2143-2149`, handled at `:4229-4231`), which no later window
     reuses, so a request queued for a window that has since closed
     reaches nothing. A label can be reused once its window is gone, so a
     request Tokra queues for `"x"` could close a new `"x"` built before
     the loop handles it. Labels are unique while their windows live
     (decision 7), and Tokra builds no window at run time until phase 2,
     so phase 1 cannot reach this; phase 2 decides whether a request
     carries a creation generation beside the label.

   **Live labels are unique, natively too.** Ruby enforces it from phase 2
   (decision 7), and phase 1 states it as the native layer's invariant,
   because wry's macOS backend keys a process-wide table of each
   webview's protocol handlers by its id (`wkwebview/mod.rs:203-206`,
   `:290-293`), finds a request's handler by that id
   (`class/url_scheme_handler.rs:78-81`), and removes the id's entry when
   a webview drops (`:1292-1294`). Two live webviews built with one id
   share an entry, and dropping either leaves the other with no protocol
   handlers. The window label table has the same shape. So the natives'
   RDoc says a label belongs to one live window and one live webview,
   and every caller keeps it: `App` (only `"main"` in phase 1), the
   examples, and the test fixtures, including `native_loop`'s three
   heartbeat webviews, which Ruby frees while they run and which get
   `"beat-0"` to `"beat-2"` (`fixtures/native_loop/app.rb:92-104`).

   **A label crosses into Rust as UTF-8 without NUL.** wry copies the id
   into a `CString` with `unwrap` on macOS (`wkwebview/mod.rs:274-277`),
   so a NUL would panic inside webview creation, which Ruby sees as
   `fatal`. The native constructors raise `ArgumentError` for a label
   holding NUL, before building anything; magnus's `String` conversion
   already raises for a String whose encoding is not valid UTF-8. Phase
   2's Ruby rule excludes both earlier, so these are backstops for direct
   `Native` callers.

   Ruby finds the window or webview by label in the manager. A webview's
   window-level events (drag-drop and, on Windows, focus) go to the
   webview's *current* window, `webview.window`, as Tauri's synthesized
   window events go to the webview's `window_id`, which `reparent`
   updates (`lib.rs:4097-4122`).

3. **Rust holds no window or webview, only plain values (phases 1 to 5).**
   Today each `Native::Window` and `Native::WebView` owns its tao or wry
   value in a `ThreadBound`; Ruby's manager hashes own the Ruby objects,
   and so the natives; a native Ruby frees on another thread is sent home
   to be dropped (`window.rs:53-71`, `webview.rs:197-216`). That model
   scales to N windows unchanged: no Rust collection holds a window or a
   webview, so nothing native outlives a Ruby object or points into one
   (plan 043's lesson). What Rust keeps is plain data on the main thread:
   the label table (phase 1) and, in phase 5, the web contexts keyed by
   data directory, which are wry values that must outlive their webviews
   on macOS (`lib.rs:4589-4621`, `:2437-2461`). No Ruby `VALUE` enters
   either. Auto-resize rates (phase 4) live on the Ruby `Webview`, and
   Ruby resizes a window's children after the window's `Resized`
   listeners have run, which is Tauri's order (`lib.rs:4126-4150`, then
   `:4188-4208`).

4. **Creation is Tauri's: validate and register at once, build on the
   main thread (phase 2).** `Context::create_window` reserves ids, sends
   `Message::CreateWindow`, and returns a detached window whether or not
   the native one exists yet; on the main thread `send_user_message`
   handles the message before returning, anywhere else the loop handles
   it later (`lib.rs:234-254`, `:299-362`). The manager attaches the
   window at once (`window/mod.rs:384-404`), so later calls queue behind
   the creation. A native failure is only logged (`:3912-3943`). Tokra
   mirrors it:

   - `build` checks the labels on the calling thread (decision 7), makes
     the Ruby `Window` and `Webview` with natives that start empty and
     belong to the main thread, attaches them to the manager, and sends
     the native creation through `RuntimeContext#run_on_main_thread`. On
     the main thread it runs at once; from another thread it queues, and
     every later call on that window queues behind it, in order.
   - The empty natives are owned by the loop's thread, not the caller's.
     `ThreadBound::new` takes the calling thread as owner
     (`thread_bound.rs:70-75`), which is wrong for a native made on a
     Ruby worker thread. Phase 2 adds `ThreadBound::empty(owner:
     OwnerThread)`, and the empty constructors take the owner from the
     loop: `RbProxy` already carries the loop's `OwnerThread`
     (`proxy.rs:37-48`, set by `create_proxy`, `event_loop.rs:106-108`), so `Native::Window.empty(proxy)`
     and `Native::WebView.empty(proxy)` read it there. Only that thread
     can fill or use them, as every native today.
   - The native creation fills the empty natives. It takes the loop's
     window target through `RbEventLoop#with_target`
     (`event_loop_target.rs:66-86`): the loop itself before `run`, the
     target the loop lends while a callback runs. So creation happens
     only inside a loop callback or before the loop starts, never by
     re-entering tao from outside it.
   - A failure is warned, not raised, as Tauri logs it. A main-thread
     call that reaches a native not yet filled behaves as one already
     closed, as Tauri's runtime ignores a message for a window not in
     its store.

   This needs no new waiting and no deadlock warnings beyond Tauri's.
   `add_child` waits for its answer on another thread, as Tauri's does
   (`window/mod.rs:1060-1067`), through `RuntimeContext#run_main_thread`.

5. **Creating a webview inside the running loop is safe on Windows for
   the same reason a popup is (phase 2).** WebView2 creation runs a
   nested `GetMessage` loop (`wait_with_pump`) inside the loop's
   callback, as it does in Tauri. Tauri does exactly this for every app:
   it builds the config's windows inside the loop's callback, on the
   runtime's `Ready` (`app.rs:1297-1303`, `:2370-2384`;
   `lib.rs:4034-4035`). Plan 042's decision 19 found the one
   way such a loop re-enters tao: a `WaitUntil` deadline. Tokra never
   sets one, user events that arrive are buffered, and `WM_PAINT` checks
   `should_buffer`. Tauri's rustdoc warns that building a window in a
   synchronous command deadlocks on Windows (wry #583); that deadlock
   needs the creation to run inside a WebView2 callback, and no Tokra
   command does: the IPC and protocol handlers only send through the
   proxy, and Ruby's commands and listeners run from the loop's inbox in
   `MainEventsCleared` (`event_loop.rs:459-498`), never inside a WebView2
   callback. UNVERIFIED until
   Windows CI runs phase 2's test. The GVL stays held during creation in
   phase 2; releasing it as plan 042's decision 15 does for a popup is a
   phase-2 measurement, not a premise.

6. **Windows finally gets `Focused` (052a-0, its own commit).** Plan
   047's decision 10 took Windows' focus from WebView2's `GotFocus` and
   `LostFocus`, and dropped tao's. The binding was attached in
   `RbWebView::new` (`webview.rs:250`), the URL constructor nothing in
   `lib/` calls, and not in `new_with_protocol`, which App calls. So a
   Tokra app on Windows has never heard `WindowEvent::Focused`, and
   `webview_focus.rs` has never run. 052a-0 moves the attach into
   `new_with_protocol` and deletes the dead `RbWebView::new`
   (`webview.rs:232-258`) and its registration, rather than share a
   build path with it; the example in `native.rb:43` goes too. It lands
   before the label work so a failure on Windows CI points at one
   change. `WindowEvent::Focused` is an Unreleased feature, so its
   entry stands (decision 12); `WebView.new` shipped in
   `v0.0.1.pre.2`, so its removal gets a Removed line marked breaking.
   Where Tauri `unwrap()`s, and so panics, when WebView2 refuses a focus
   handler (`lib.rs:5076-5130`), Tokra raises `RuntimeError` from
   `new_with_protocol`: a panic inside a magnus-bound function would be
   a fatal error Ruby cannot rescue, not an error the app can see.

7. **Labels follow Tauri's checks, in Tauri's order (phase 2).**
   - Characters: `char::is_alphanumeric`, `-`, `/`, `:`, `_`
     (`window.rs:494-498`); the empty label passes. In Ruby,
     `/\A(?:\p{Alphabetic}|\p{N}|[\-\/:_])*\z/`, since Rust's
     `is_alphanumeric` is `Alphabetic` or any `Numeric` category, which
     POSIX `[[:alnum:]]` is not. Rust's tables and Onigmo's follow
     different Unicode versions (the Rust toolchain's, Ruby 4.0's), so a
     character assigned in only one of them is judged differently; the
     RDoc says so. A NUL fails the match. A String with invalid encoding
     makes the match itself raise `ArgumentError`, so the check asks
     `valid_encoding?` first and raises the label error for it too. A failure raises `Error::Runtime` with
     Tauri's text, "Window labels must only include alphanumeric
     characters, \`-\`, \`/\`, \`:\` and \`_\`.", so the message reads `runtime error: Window labels ...` as Tauri's
     wrapped error does, for a webview label too.
   - Uniqueness: `a window with label `x` already exists` and `a webview
     with label `x` already exists`, as new `Error::WindowLabelAlreadyExists`
     and `Error::WebviewLabelAlreadyExists`.
   - Order: `WebviewWindowBuilder#build` prepares the webview first
     (`window/mod.rs:333`, then `:354`), so a webview window whose label
     is taken fails with the *webview* message. A non-String label is a
     `TypeError`, where Rust takes `Into<String>`.

8. **The order of creation's effects is Tauri's (phase 2).** For a
   webview window built on the main thread: the window joins the
   manager and plugins hear `window_created`; the webview joins and
   plugins hear `webview_created`; `tauri://webview-created` is emitted;
   the builder's menu listener is added; then the main-thread task
   applies effects and emits `tauri://window-created`. So the page hears
   `webview-created` before `window-created`. Each payload is
   `{"label": ...}` to every target.

9. **The main window is built the same way, in Tauri's order (phase
   2).** Tauri's `setup` builds the config's windows, then runs the
   setup hook (`app.rs:2370-2384`), so a setup hook can find
   `get_webview_window("main")`. Tokra runs the hook first and builds
   `main` after (`app.rb:256`, `:273-297`). Phase 2 builds `main` with
   `WebviewWindowBuilder`, from `Builder#title` and `#size`, before the
   hook. Tauri runs `setup` on the loop's first event (`lib.rs:4034-4035`)
   and Tokra before the loop starts; that stays, as plan 041's decision 1
   chose, and both are the main thread before any window event.

   Building `main` before the hook needs the loop's proxy, since the
   webview's handlers send through it and the native creation is a
   `RuntimeContext` task. Today `run` calls the hook (`app.rb:256`) and
   only then creates the proxy and attaches the context (`:262-265`).
   Phase 2 moves `create_proxy` and `RuntimeContext#attach` up, right
   after the loop is built (`:243-244`) and before the app menu and the
   hook. `attach` makes the calling thread the main thread, which it
   already is there, and replays anything sent earlier; the activation
   policy still goes to the loop before `run`, as it does now.

10. **Linux children pack into the window's box, as Tauri's do (phase
    4).** wry places a webview by its bounds only inside a `gtk::Fixed`
    (`lib.rs:1898-1925`, `webkitgtk/mod.rs:587-623`, `:847-873`). Tauri
    builds every child into `default_vbox`, a `gtk::Box` (`lib.rs:5017-5023`),
    so on Linux children stack in the box, and `set_bounds` and
    auto-resize do nothing. Tokra ports that; a `gtk::Fixed` would be
    behavior Tauri does not have. The RDoc of `add_child` and
    `set_bounds` says so.

11. **`WebviewUrl::App` resolves against Tokra's app URL (phase 2).**
    Tauri joins the path to `tauri://localhost`, leaving `index.html`
    off (`manager/webview.rs:414-430`). Tokra's app URL is
    `tokra://localhost/` (and `http://tokra.localhost/` on Windows,
    `app.rb:927-935`). `External` loads as given, and `CustomProtocol`
    too. A `data:` URL loads as given: `webview-data-url` adds behavior,
    so ADR 011 builds it in, and its one other effect, injecting the
    app's CSP into the page (`manager/webview.rs:455-469`), runs only
    for an app with a CSP, which no Tokra app has yet. Tauri's refusal
    without the feature (`:448-453`) is not ported.

12. **CHANGELOG: amend, not add (every phase).** Everything this plan
    touches arrived after the last tag (`v0.0.1.pre.2` has no Ruby
    `App`), so each phase rewrites the Unreleased entry it changes:
    the `WindowEvent::Focused` entry (`CHANGELOG.md:25-30`) needs no Fixed
    line; the `Native::*Event` entries (`:44-46`, `:274-276`), the
    `Native::WebView.new_with_protocol` entry (`:397-398`) and

    each takes or carries; `Builder#on_page_load`, which has no entry,

### Decisions (052b)

- **b1. Plugins registered in the setup hook miss `main` (plan
  correction).** Tauri registers plugins on its `Builder`, so they exist
  before any window and every webview gets their scripts. Tokra has no
  `Builder#plugin`: a plugin is built with the handle and registered on
  it, and the first-party plugins' RDoc registers them in the setup hook.
  With `main` built before the hook, as decision 9 says, a plugin
  registered there no longer puts its initialization script into
  `main`'s page or hears `main`'s `window_created`. Tauri's semantics
  are that a script reaches the webviews made after it is registered
  (`manager/webview.rs:116-200` reads the store when the webview is
  prepared), and that is what Tokra keeps; the RDoc of
  `Plugin#initialization_script` and of the dialog and notification
  plugins, the two whose scripts matter, says to register before
  `App#run`. A `Builder#plugin` that builds a plugin before the app
  exists changes every plugin's constructor and is a plan of its own.
- **b2. `WebviewUrl` is three `Data` classes.** `App(path)` holds a
  `Pathname` (Rust's `PathBuf`, which Tauri builds from `&str`), and
  `External(url)` and `CustomProtocol(url)` a `URI::Generic` (the url
  crate's `Url`, which a Rust caller parses first). A wrong type raises
  `TypeError`. Resolution is `prepare_webview`'s: `App` joins its path to
  the app URL, leaving `index.html` off; the other two load as given, a
  `data:` URL included (decision 11). The app URL is Tokra's
  `tokra://localhost/`, or `http://tokra.localhost/` on Windows
  (`App#tokra_protocol_url`), with its path's slash: Tauri's is the bare
  `tauri://localhost`, and changing `main`'s URL to drop the slash would
  change the request every Tokra page has had. A path the url crate would
  percent-encode (a space) is escaped with `URI::RFC2396_Parser#escape` before
  the join, as the url crate's `join` encodes it.
- **b3. The natives start empty and are filled on the main thread.**
  `Native::Window.empty(proxy)` and `Native::WebView.empty(proxy)` make
  natives whose `ThreadBound` is empty and owned by the loop's thread,
  read from `RbProxy` (`proxy.rs:37-48`), whatever thread calls them.
  `Native::Window#open(event_loop, label, title, size)` builds the tao
  window from the loop's window target (`with_target`: the unrun loop
  before `run`, the lent target inside a callback, and an error once it
  has ended) with its title and size, records its label, and fills the
  native. `Native::WebView#open(window, proxy, label, url, scripts)`
  builds the webview `new_with_protocol` builds, loading `url`. Each
  raises `ThreadError` off the owner's thread, `RuntimeError` when
  already open, and `ArgumentError` for a NUL in the label, before
  building anything. An empty native answers as a closed one does, and a
  native that was ever open never opens again: `open` after `close`
  raises as `open` after `open` does (review). A window built by hand
  through `Native::Window.new` and put in `handle.windows` never joins
  the exit store (decision b4), so closing the last builder-made window
  exits while it is still on screen. The
  constructors `Window.new` and `WebView.new_with_protocol` stay for the
  examples and fixtures that build natives by hand; `new_with_protocol`
  and `open` share one build function.
- **b4. `RuntimeContext#create_window` is the runtime's `create_window`.**
  It makes the empty natives and sends their filling through
  `send_user_message`, so on the main thread the window and webview exist
  before it returns and from another thread the filling is queued ahead
  of every later call. Only a window whose window and webview both
  opened joins its store of open labels, Tokra's equivalent of the
  runtime's window store; `Destroyed` removes a label, and the app asks
  to exit when a removal empties the store (`lib.rs:4171-4185`). So a
  failed window never holds the app open, and a `main` that fails leaves
  the app running windowless with nothing to exit on, as Tauri's does
  (`app.rs:1298`, `:2370-2375`). Before `App#run` there is no loop and no proxy, so
  it raises `Error::Runtime` "the event loop does not exist yet"; Tauri's
  `App` has its runtime from `build`, Tokra's from `run` (plan 041,
  decision 1). Inside the filling, a `RuntimeError` from tao or wry is
  warned and the natives stay empty, as Tauri logs `CreateWindow`'s
  error and its window never enters the store. The warnings are Tauri's
  errors' text: "failed to create window" (tao's reason dropped, as
  `map_err(|_| Error::CreateWindow)` drops it, `lib.rs:4440-4442`) and
  "failed to create webview: ..." with wry's. When the webview fails
  after the window was built, `Native::Window#discard` forgets the
  window's label and drops it, so its `Destroyed` names no window and is
  dropped, as Tauri's `create_webview(...)?` returns before the window is
  inserted (`lib.rs:4489-4500`). The menu's `init_menu`
  ignores its error, as Tauri's creation handler does (`let _ =`).
- **b5. `WebviewWindow` holds a `Window` and a `Webview`.** Each method
  goes to the one Tauri's does: the window's methods to `window`, and
  `label`, `run_on_main_thread`, `eval`, `cursor_position`,
  `resources_table`, and `display_handle`'s app handle to `webview`;
  `set_background_color` colors the window, then the webview, as Tauri's
  does (`:2104-2107`); `listen` and `once` target
  `EventTarget::WebviewWindow`. The window methods forward with
  `Forwardable`, one list per Tauri `impl` block, since each is a
  one-line call; the class RDoc names the lists. Two `WebviewWindow`s are
  `==` when their webviews are, as Tauri's `PartialEq` compares webviews.
  The window methods Tokra's `Window` does not have yet are not
  forwarded; each arrives with its `Window` method.
- **b6. The scripts and the attach steps move out of `App`.**
  `WebviewManager` (`:nodoc:`, Tauri's `manager/webview.rs`) takes `App`'s
  script assembly unchanged, `prepare_webview`'s URL resolution, and
  `attach_webview`; `WindowManager.attach_window` takes the builder's
  window listeners and `attach_window`'s steps. `AppHandle` holds both,
  as Tauri's `AppManager` does, so a builder reached from any handle
  finds them.
- **b7. Close requests keep the label alone.** Decision 2 left whether a
  close request carries a creation generation. A queued `close` reaches
  a new window with the label only when the old window's `Destroyed`
  arrives, a listener builds the new one, and only then the request,
  sent from another thread before the old window went. Tokra keeps the
  label and the gap, named in `RuntimeContext#request_close`'s RDoc;
  a generation would change `Native::Proxy#request_close`, the event, and
  every stub, for a race a person has to arrange.

## Risks

- **Phase 1 touches every event.** A label lost on the way makes Tokra
  drop the event silently, as Tauri drops an unknown label. A dropped
  IPC shows as a hung invoke and a test timing out at its backstop, not
  as an error. The stub tests cover each arm, and the real-window test
  covers both kinds of id end to end.
- **tao's macOS window id is the `NSWindow`'s address**
  (`platform_impl/macos/window.rs:80-82`), which a later window can
  reuse. tao queues `Destroyed` from `windowWillClose:`
  (`window_delegate.rs:334-345`), so between that and the loop handling
  it, window A's `NSWindow` can be freed and a new window B allocated at
  the same address. B's registration would then overwrite A's entry, and
  A's queued `Destroyed` would read B's label and remove it, so B's
  events would be dropped and Ruby would think B gone. Tauri's
  `window_id_map` has the same flaw: it inserts each new window's tao id
  (`lib.rs:4459`) and resolves events through it (`:4126-4128`). It needs a window to
  close and another to be built inside one turn of the loop, which
  phase 1 cannot do (it builds no window at run time); phase 2, which
  can, records it as a risk to measure, and a fix (registering by a
  creation counter as well as the address) would be a deviation for
  that plan to argue.
- **`webview_focus.rs` has never run.** It was attached only in the dead
  constructor (decision 6), so 052a-0 is its first execution, on Windows
  CI only. Its `unsafe` handlers, its token, and its `GotFocus` and
  `LostFocus` bookkeeping are unproven; a fault there shows as a crash
  on the first Windows run, which cdb's stack names.
- **WebView2 creation inside the loop** (phase 2) runs a nested message
  loop on Windows. Decision 5 argues it cannot re-enter tao; only
  Windows CI proves it. A failure shows as tao's "event handler is
  re-entrant" panic, which `rake test:replay` and cdb locate.
- **Every new webview activates the app on macOS**
  (`wkwebview/mod.rs:641-648`). Real-window tests that build windows at
  run time take focus the way every fixture's first window already
  does; they synthesize no input, so they stay out of `keyboard/`.
- **WebView2 shares one browser process per user data folder** and
  refuses a second environment with different options. Phase 5's
  `additional_browser_args` and `data_directory` meet it; Tauri does
  too. UNVERIFIED how wry 0.54.1 reports it.
- **Question 1 changes shipped behavior either way** it is answered
  under ADR 011; phases 1 to 3 do not depend on it.

## Questions for the maintainer

1. **Should a webview window's webview become a child, as with Tauri's
   `unstable`?** Tokra already ships `unstable`'s manager getters, and
   ADR 011 builds in a feature that adds behavior. But this part of
   `unstable` replaces behavior. With it, a webview window's webview is
   built as a child with whole-window bounds and auto-resize
   (`lib.rs:4489-4500`, `:4807-4823`), so it loses three things Tokra
   ships: the undecorated-resize handler on Windows and Linux
   (`:5055-5067`); on macOS, first-responder status (wry #739, keyboard
   input before the first click) and the traffic-light inset
   (`wkwebview/mod.rs:612-640`), which makes phase 3's
   `traffic_light_position` a no-op; and its drag-drop becomes
   `RunEvent::WebviewEvent` instead of `WindowEvent::DragDrop`. The same
   answer decides `reparent`: without `unstable`, Tauri refuses to move
   a webview into or out of a webview window
   (`webview/mod.rs:1533-1539`), because that webview is its window's
   content.
   - (a) All of `unstable`. One configuration Tauri ships; the losses
     are Tauri's own under it, and `reparent` has no check.
   - (b) `unstable`'s API, the default build's webview window: a webview
     window's webview stays content; `add_child` children are children,
     beside it if added to a webview window. Keeps today's behavior, but
     that mix is a configuration no Tauri build has. `reparent` keeps
     `CannotReparentWebviewWindow`.
   - (c) As (b), but `add_child` on a webview window raises, so a window
     is either a webview window or a window of children, each as some
     Tauri build has it. `reparent` keeps `CannotReparentWebviewWindow`.

   Phase 4, and plan 050's phase 3 `reparent` command, wait for the
   answer; phases 1 to 3 do not.
2. **Does Tokra build in `macos-private-api`, and if not, how does an
   app turn it on?** The feature turns on wry's `transparent` and
   `fullscreen` (`tauri-runtime-wry/Cargo.toml:67-71`): a transparent
   webview through the private `drawsBackground` key, and the
   `fullScreenEnabled` preference, so a page can use the HTML fullscreen
   API (`wkwebview/mod.rs:354-363`). It adds behavior and relaxes no
   safety default, so ADR 011's amendment says build it in, and its
   opt-in clause, written for features that relax a safety default,
   does not apply. Its cost is distribution: private API, which App
   Store review rejects. Tauri lets each app choose through the config
   key `app.macOSPrivateApi` (`tauri-utils config.rs:2758-2759`), which
   its build maps to the Cargo feature (`:2785-2786`), so the choice
   waits on where a Tokra app's config comes from (plan 049, question
   1). And Tokra ships one compiled gem for every app: a runtime opt-in
   can gate the calls, but the private key strings sit in the binary of
   every app once wry is built with the features, whether or not an app
   opts in.
   - (a) Build both wry features in, gate the calls behind
     `app.macOSPrivateApi` once config exists (or a `Builder` setting
     named after it until then), and accept the strings in every app's
     binary.
   - (b) Leave the features out of the shipped gem: `transparent` stays
     undefined on macOS, and the HTML fullscreen API stays off, until a
     second build of the gem or a plugin can carry them.
   - (c) Never port them.

   Phase 3 ports `transparent` off macOS and defers it on macOS until
   you choose.
