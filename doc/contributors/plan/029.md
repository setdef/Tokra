# Plan 029: Real-window tests that never take the keyboard

Every real-window test launches a fixture app, and on macOS each one came
to the front as it launched and took keyboard focus from whatever the
maintainer was typing in. The suite launches a dozen of them, so typing
while the gate runs was a losing game. This plan keeps every fixture in
the background with the API Tauri has for it, the activation policy, and
holds every fixture to that in the test harness.

## How a fixture took focus

tao builds the app delegate with `activation_policy: Regular` and
`activate_ignoring_other_apps: true` (`app_delegate.rs:98-112`). When
AppKit finishes launching, `AppState::launched` applies the policy, then
calls `activateIgnoringOtherApps:` with that flag (`app_state.rs:285-295`).
The app becomes the active app, its window becomes key, and the keyboard
follows. Tokra never set either field, so every fixture did this.

Measured on this Mac (macOS 26, Darwin 27), with a recorder that polls
the frontmost app while a fixture runs (see Verification):

| Fixture's event loop | Became frontmost |
|---|---|
| as before (Regular) | yes, for the length of the run |
| `set_activation_policy(Accessory)` | yes: AppKit still activates an Accessory app that asks |
| `set_activate_ignoring_other_apps(false)` | yes, alone or with Accessory |
| `set_activation_policy(Prohibited)` | never |

A Prohibited app is one AppKit never activates, so tao's call at launch
does nothing. Its window still opens, draws, and runs its page.

## Decisions

1. **The fixtures use Tauri's own API.** `FixtureApp.builder`'s setup hook
   calls `app.set_activation_policy(Tokra::ActivationPolicy::Prohibited)`
   on macOS, the call Tauri's rustdoc shows in a setup hook. The
   window-handle fixture calls it on its App, and the native-loop fixture,
   which drives `Tokra::Native` directly, calls
   `Native::EventLoop#set_activation_policy("Prohibited")`. No test-only
   hook exists in `lib/`.
2. **Before the loop, the App hands the policy to the loop it builds.**
   Tauri's App holds its runtime from `Builder::build`, so a call before
   `run` sets the field on tao's loop. Tokra's App builds its loop in
   `App#run`, after the setup hook, so `App#set_activation_policy` keeps
   the policy and `App#run` passes it to the new loop before running it.
   The last call wins, as on tao's field. Tauri runs its setup hook at
   `RunEvent::Ready` (app.rs:1296-1302), inside the loop, so a Tauri app
   that sets the policy there sets it after tao has activated the app;
   Tokra's setup hook already runs before the loop (an earlier
   deviation), so the same call there takes the earlier path, which is
   the one that keeps the app in the background.
3. **No `AppHandle#set_activation_policy` yet.** Tauri's runtime path
   needs the event loop's window target in the loop's callback, which
   Tokra's native loop does not pass to Ruby. Nothing here needs a policy
   change after launch. Until it lands, a call to `App#set_activation_policy`
   after `App#run` has started its loop changes nothing; the RDoc says so.
4. **Defined only on macOS.** `ActivationPolicy`, `App#set_activation_policy`,
   and `Native::EventLoop#set_activation_policy` exist only where tao
   defines the method, the way ADR 011 translates a `#[cfg(target_os)]`
   item, so `respond_to?` answers. `lib/tokra/activation_policy.rb`
   returns early elsewhere, and `sig/tokra/activation_policy.rbs` is
   excluded from `rbs:parity` there through `--exclude-sig`, ported from
   Ferro's parity task.
5. **A background window stays in sight and out of the cursor's way.** A
   window that never comes to the front opens behind whatever is in
   front. When it is covered, WebKit counts its page as a background
   view: its unified log shows the web, GPU, and network processes moving
   to background assertions ("GPU for background view(s)"), and `ps`
   shows those processes at priority 4, Darwin's background band, against
   47 for a visible page. On a machine at load 300 to 400, the dialog
   fixture's page then stalled for the full minute; across six runs it
   stalled exactly when the window's `occlusionState` lacked
   `NSWindowOcclusionStateVisible`. So on macOS `FixtureApp.keep_in_sight`
   calls Tauri's `Window#set_always_on_top(true)` and
   `Window#set_ignore_cursor_events(true)` at `RunEvent::Ready`, and the
   native-loop fixture does the same for its windows. The window floats
   above other apps' windows while the fixture runs, so its page stays
   visible and runs; the app still never becomes active, so the keyboard
   stays where it was; and clicks pass through it to the app beneath,
   which also keeps a click from activating the app while rfd has it as
   Accessory for a sheet. The trade is that each fixture's window shows
   on top of your work for the second or two it runs.
6. **`background_throttling` does not fix a covered page.** wry's
   `Disabled` sets WebKit's `inactiveSchedulingPolicy` to none. With it,
   a covered dialog fixture still stalled under load, and with it off a
   covered fixture still passed when the machine was quiet, so it is not
   what decides. It stays unported until something needs it.
7. **The harness holds every fixture to it.** `RealApp.launch` watches
   the frontmost process on macOS (`test/integration/support/frontmost.rb`,
   the Process Manager's `GetFrontProcess`, which answers on any thread
   without a run loop) and records whether the child was ever in front.
   `assert_finished` fails a run that was. Every real-window test calls
   it, so a fixture that takes focus fails its test. The plugins' bundles
   that run real windows carry `fiddle` for it.

8. **Load cannot fail a test that checks order.** The suite runs on a
   machine that other work loads to averages of 200 to 400. The native
   loop's wake-up check held each wake-up to one round of time slices
   (`2 * (n + 2) * 100` ms), which a loaded machine exceeds by starving
   the whole process; it now holds them to 4 s, which a loop that never
   hands the GVL over still fails (its ticker starves outright and the
   fixture never ends), and reports the round of slices in its message.
   The notification plugin's "answers while the send waits" test held the
   answer to 0.5 s; the contract is the order, which it already checked
   (the sending thread is still alive when the answer comes), so the time
   moved into the message and the wait for the answer grew to 10 s.
   `ActivationPolicy.new` is private, so an unknown policy cannot be made,
   as Tauri's closed enum cannot.

## Verification

- Unit: on macOS, the variants carry tao's names; a policy set in the
  setup hook, or on a built App, reaches the loop before `run`; the last
  one wins; no policy, no call; it returns `nil`. Everywhere: the three
  are defined exactly on macOS. The window setters delegate and return
  `nil`. Parity: an excluded signature file is not read.
- Native: each variant name is taken, another name raises
  `ArgumentError`, and the loop's method and both window setters refuse
  another thread.
- Real windows: the window-handle fixture asks for always-on-top and
  pass-through and reads them back through the handle (the window's
  level above 0, `ignoresMouseEvents`; on Windows, `WS_EX_TOPMOST` and
  `WS_EX_TRANSPARENT`). Every real-window test fails if its fixture was
  ever the frontmost app.
- Focus, measured with a recorder that polls
  `NSWorkspace.sharedWorkspace.frontmostApplication` through Fiddle,
  pumping the main run loop, while a command runs. Before: each fixture
  launch made `ruby` frontmost for one to two seconds. After: the full
  gate, twice, in Results.
- Manual mutation checks, in Results.

## Untested here

- Windows and Linux: nothing changes there except the window setters,
  which the window-handle fixture reads back on Windows; Linux has no
  reader for either.
- A sheet clicked by hand while a fixture runs still activates the app,
  since rfd makes it Accessory for the sheet; only a person can click it.
- Apple documents a Prohibited app as one that "may not create windows"
  (`NSApplicationActivationPolicyProhibited`, the policy of an
  `LSBackgroundOnly` app). The fixtures rely on its windows still opening,
  drawing, and running their pages, as measured on macOS 26 (Darwin 27).
  If a later macOS stops showing them, the fixtures' pages never load and
  the real-window tests fail by timing out, not silently.

## Results

Every decision above is done. Deferred, with reasons:
`AppHandle#set_activation_policy` (decision 3), `set_dock_visibility`
(nothing needs it), and `background_throttling` (decision 6).

Focus, with the recorder running across the whole clean gate (`rm -rf
tmp`, every extension rebuilt), at load averages of 200 to 360 from other
work on the machine: three runs, and in none did a Tokra process become
frontmost. Two of the three recorded a frontmost change, both to another
project's Ruby (a different Ruby version and checkout). Before this plan,
one fixture alone made `ruby` frontmost for about 1.5 seconds per launch.
Gates two and three passed with zero errors and warnings. Gate one
failed two of the native loop's GVL latency checks (943 and 980 ms
against a 600 ms bound) at load 257; the same tests then passed nine
times in a row at loads of 270 to 325, and a fixture in the foreground
cannot be compared, since the harness now fails it for taking focus.

Mutation checks, each reverted after: dropping the hand-off in
`App#run` fails the App tests and every IPC real-window test ("came to
the front"); mapping `"Prohibited"` to tao's `Accessory` in the native
layer fails the IPC real-window tests the same way; making both native
window setters do nothing fails the window-handle fixture's two
read-backs; dropping the fixture's own calls fails them too (the fixture
reads them again until they show or two seconds pass, since tao applies
them through the main dispatch queue). Removing the native loop's GVL
hand-over fails all three wake-up tests (the fixture hangs). Making the
notification's send join its thread before the command answers fails
the order check. Making `ActivationPolicy.new` public fails its test.
