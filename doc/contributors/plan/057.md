# Plan 057: The few real-window tests that need the console

Plan 056 moved every real-window test into the hidden `tokratest`
session. That session is off the console, and there macOS does more
than suspend a page's JavaScript, which `FixtureApp::Unthrottled`
already prevents: it lowers WebKit's WebContent process to background
priority 4. Under load a page that drives a long test starves past its
wall-clock bound. No harness fix exists. The maintainer's decision:
"Run the minimal set required in my session." This plan finds that set
from evidence, runs it in the maintainer's session holding the desktop
input lock, and keeps everything else hidden.

## Evidence

Every run below used this checkout's mirror in `tokratest`, through
`hidden-run`, with `TESTOPTS=-v`, except the last row, which is
`rake test:console` in the maintainer's session with `TOKRA_QUIET=1`.
The Mac's load average, from other projects' jobs, was about 120 for
the first run and 300 to 970 for the rest, the two later dialog runs
with no added load included. "Under load" adds twelve
`yes` processes in `tokratest` through a second `hidden-run` job, and,
for one run, a concurrent second hidden run of the core real-window
tests from a second mirror, which also built the extension cold.

| Tests | Hidden, no added load | Hidden, under load | Console, under load |
| --- | --- | --- | --- |
| `test:keyboard` (17) | 1 of 1 passed | 4 of 4 passed | not run |
| `test:real_windows` (269) | 1 of 1 passed | 4 of 4 passed | not run |
| dialog `test_dialog_window.rb` (9) | 1 of 3 passed: 12 s at load 120, then hung twice at load 880 | 0 of 6 passed: each time the fixture hung, and was killed at RealApp's 60 s, failing all 9 | 3 of 3 passed, 10 to 13 s |
| dialog `test_macos_dialogs.rb` (4) | 3 of 3 passed | 6 of 6 passed | not run |
| global-shortcut `test_global_shortcut_window.rb` (4) | 1 of 1 passed | 3 of 3 passed | not run |
| notification `test_macos_notifications.rb`, `test_notification_window.rb` (8) | 1 of 1 passed | 3 of 3 passed | not run |
| clipboard `test_clipboard.rb` (67) | not run | 5 of 5 passed | not run |

The dialog fixture's progress lines show where it stalls: a check ends
its sheet at 2.9 s, and the page asks for the next one only at 57.3 s.
Its page makes many round trips per check (it polls `open` every
100 ms), far more than any core fixture's. A sampler of `ps`'s `pri`
column once a second saw each hung dialog fixture's WebContent process
in `tokratest` at priority 4 for its whole 55 to 70 s, while the same
fixture's WebContent in the maintainer's session, in the console runs
at the same load, stayed at 46 or 47. The 9 plugin failures of the
earlier hidden run were these 9.

The other page-driven fixtures passed every time, though some of their
WebContent processes also fell to priority 4: their pages are short
enough to finish inside their bounds. The dialog fixture's bound is not
wrong on its own terms (12 s of work against 60 s), so it stays.

## The console set

`RealWindows::CONSOLE` in `tasks/real_windows.rb` names it, the way
`NAMED` names files:

- `plugins/dialog/test/test_dialog_window.rb`

A file joins it only with evidence like the above: it fails or flakes
hidden under load, and passes on the console at the same load.

## The clipboard

The clipboard plugin's `test_clipboard.rb` writes the real system
clipboard in every test; no other test does. It ran in `plugins:test`,
so in the maintainer's session, overwriting whatever the maintainer had
copied. It now joins `NAMED`: it is a real-window test, so it runs in
`test:real_windows:plugins`, which on the maintainer's Mac is
`tokratest`, whose pasteboard is its own (5 of 5 passed there), and on
CI runs as before, only in another task. Its `setup` calls
`RealWindowsRun.require!("the system clipboard")`, so outside a
real-window run it fails before it touches the clipboard.

## Routing

Where `RealWindows.where` is `:local` (CI, off macOS, or
`TOKRA_REAL_WINDOWS=local`) nothing changes: `test:gui` runs
`test:keyboard`, `test:real_windows`, and `test:real_windows:plugins`,
and the console set runs among them.

Where it is `:hidden`, `test:gui` runs `test:hidden` and then
`test:console`. The hidden job sets `TOKRA_HIDDEN_JOB=1`
(`RealWindows::HIDDEN_JOB`), and where it is set (`RealWindows.hidden_job?`)
`RealWindows.split` and `RealWindows.plugin_tests` leave the console set
out of the real-window tasks. So each test runs exactly once: a test is
either in the console list, and runs here, or runs hidden.

`test:console` runs the console set in this session: the core ones
through `test:console:core`, when there are any, and each plugin's
through its own bundle (`test:console:plugins`), all with
`TOKRA_REAL_WINDOWS_RUN=1`. It is not one of the tasks that refuse to
open windows where the rest belong hidden, since opening them here is
its purpose. It holds the desktop input lock (`KeyboardNotice`, so on
macOS outside CI) around the whole run, so no other project's synthetic
input lands in its windows. The fixture never takes focus or the
keyboard (its activation policy is `Prohibited`), but a click that
lands on one of its dialog sheets would still end it, so the span
speaks and shows its banner, asking the maintainer to step away, once
per run and around only the console tests (amended 2026-11-03 at the
maintainer's request: a span that a person's input could fail speaks;
one it could not stays silent). The lock is held across
child processes, so a console test that took it would wait on its own
parent forever. Each console plugin's bundle installs before the lock
is taken (`test:console:bundles`), so the lock is never held across a
network install. The tests check that no console file is a keyboard
test or names the lock in its own text.

The tripwire is unchanged: outside the real-window tasks and
`test:console`, `TOKRA_REAL_WINDOWS_RUN` is unset, and `RealApp.launch`,
`NativeEventLoop.shared`, and the named plugin tests' setups raise.

## Tests

`test/tasks/test_real_windows.rb` checks that the console files exist,
are real-window tests, and take no lock; that the hidden job leaves
them out of the core and plugin real-window lists and every other run
keeps them; that every clipboard test file is named, so a real-window
one (the clipboard is the session's own), and each named test checks
the tripwire; that `test:gui` hidden
runs `test:hidden` then `test:console`; and, in a child Rake where the
compile, the plugin installs, the plugin test runs, and the core batch's
command only report what they were given, with the lock pointed at a
temporary file, that `test:console` compiles and installs the dialog
plugin's bundle before it takes the lock, then, holding it on macOS,
gives each plugin its console files (the dialog plugin only
`test/test_dialog_window.rb`, the rest none) allowed to open windows,
and, with a stand-in list naming a core file, runs exactly that file in
one core batch with `TOKRA_REAL_WINDOWS_RUN=1`.
