# Plan 060: Real-window tests that a busy machine cannot fail

On 2026-11-05, at a load average near 400, every check in
`IpcTransportTest` failed with "the app hung and was killed" though the
same code had passed the hidden set an hour before. The page was not
hung: its stderr shows the seventh of its nine checks had run when
RealApp's fixed 60-second limit killed it. The maintainer's rule is that
tests must not be so sensitive to load, so this plan makes them
insensitive without weakening what they check.

## Status

Planned, not started. The investigation behind it is
[the research note of 2026-11-05](../research/2026-11-05-hidden-tests-under-load.md);
read it first.

## What the investigation found

What starves is WebKit's helper processes, not the Ruby fixture. WebKit
holds a RunningBoard Foreground assertion for its WebContent, GPU, and
Networking processes only while `isViewVisible()` is true, and on macOS
that needs the window's occlusion state to include Visible
(`WebPageProxy.cpp:4053-4078`, `PageClientImplMac.mm:208-230`, WebKit
main 827737a). The hidden session is never drawn, so every window there
counts as covered, and the page processes drop to background priority
between loads; plan 057 measured priority 4 hidden against 46 to 47 on
the console at the same load. `backgroundThrottling: disabled` only
stops suspension and never restores the assertion. That RunningBoard maps
the assertion to priority 4, and why priority 4 starves so badly at load
400, are inferences the proof below settles.

RealApp's 60-second limit, and the page's own 20-second and 5-second
waits, are in effect pass conditions under load, not only hang
backstops.

## Steps

1. **A fixture helper, test-only.** `FixtureApp` calls the private
   `-[WKWebView _setWindowOcclusionDetectionEnabled:NO]` on each fixture
   webview, through the window handle and Fiddle as the `window_handle`
   fixture already does, guarded by `respondsToSelector:`, then hides and
   unhides the view so WebKit re-checks its visibility. WebKit's own test
   runner does this (`PlatformWebViewMac.mm:103`). It is called from
   `keep_in_sight` and from the dialog, notification, and global-shortcut
   plugin fixtures. Library code does not change, so an app's behavior and
   Tauri fidelity are untouched.
2. **A limit that measures progress, not time.** RealApp fails a fixture
   when no new progress line arrives for about 90 seconds, with a ceiling
   of 15 minutes for a fixture that loops while printing. A progress line
   is one that proves the app moved: the fixture's "loaded" line, and a
   line at the start and end of each check, sent by the page through Rack,
   which crosses the custom protocol, the event loop, and Ruby. No
   free-running heartbeat, which would hide a real hang. Every fixture sets
   `$stdout.sync`, so a killed fixture's output survives (`ipc_transport`'s
   did not), and the page's per-check timeouts come from Ruby.
3. **The proof,** run in `tokratest` when no gate is running:
   - Sample WebContent's priority hidden, with and without the helper:
     about 4 without, about 46 to 47 with. This decides the one assumption
     the research could not verify, that a Foreground assertion lifts
     priority in a session that is not on the console. If it does not,
     step 1 is dropped and the console set stays.
   - Hold the load near 400 with about 400 default-priority spinners and a
     cold cargo build, then run `test:real_windows` and the dialog window
     test 20 times each; 20 of 20 must pass, and fewer must pass without
     the helper.
   - Prove hangs are still caught: unit tests of RealApp's new limit with
     small bounds, and a fixture whose `ping` handler blocks forever must
     fail about 90 seconds after its last progress line.
4. **If the proof holds,** the console set (plan 057, `RealWindows::CONSOLE`)
   returns to the hidden session, and AGENTS.md's paragraph on it is
   amended, so no test needs the maintainer away from the keyboard.

## Ownership

Everything here is Tokra's test code. The hidden session belongs to the
hidden_session project (`~/Developer/hidden_session`, plan 056); nothing
there needs to change, though a load generator, a priority sampler, and a
note about the private call in its `SETUP.txt` would help the proof, and
are requested of that project, not done here.
