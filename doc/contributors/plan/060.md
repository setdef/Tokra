# Plan 060: Real-window tests that a busy machine cannot fail

On 2026-11-05, at a load average near 400, every check in
`IpcTransportTest` failed with "the app hung and was killed" though the
same code had passed the hidden set an hour before. The page was not
hung: its stderr shows the seventh of its nine checks had run when
RealApp's fixed 60-second limit killed it. The maintainer's rule is that
tests must not be so sensitive to load, so this plan makes them
insensitive without weakening what they check.

## Status

Steps 1 and 2 are done. Step 3 is done in part, and step 4 waits on the
rest of it. A shortened proof ran on 2026-11-05 in `tokratest`:

- With the helper, `ipc_transport`'s WebContent and GPU processes stayed
  at priority 47 in every sample, at load averages of 380 and 267, and
  printed `PROGRESS occlusion-detection off 1`. Without it, all three
  page processes sat at 4, at a load of 22 and again at 381. A Foreground
  assertion does lift priority in a session off the console, so step 1
  stands.
- A fixture whose `ping` handler blocks forever was killed about 91 s
  after it started, at a load near 356, reporting "no progress: no new
  line for 90.6 s" with its last check-start line. The blocked handler
  froze the app, so the page's own timeout never answered; only the
  stall bound ended it. macOS has no probe section, as `HangProbe` probes
  only on Windows.
- `rake test:hidden` passed at normal load: 400 runs, no failures.

Not yet run: the twenty runs under load in step 3, with a control run
without the helper. They need no spinners: the machine is often at a
load of 300 to 500 from other projects' agents, so the gates that run
under that load are the evidence, collected over time. Step 4 waits for
them. The investigation behind it is
[the research note of 2026-11-05](../research/2026-11-05-hidden-tests-under-load.md);
read it first.

How steps 1 and 2 came out:

- `FixtureApp.keep_page_awake`, called from `keep_in_sight`, does step 1
  through `WebKitOcclusion` (`test/integration/support/webkit_occlusion.rb`),
  which checks that WebKit answers both the setter and the getter and
  puts each webview's hidden state back as it found it. The three plugin
  fixtures need no call of their own: each builds on
  `FixtureApp.builder`, whose fixture plugin calls `keep_in_sight` on
  Ready. The `native_loop` fixture, which drives `Tokra::Native` without
  `FixtureApp`, calls `WebKitOcclusion` itself for each window with a
  page. Each prints `PROGRESS occlusion-detection off <count>`, or
  `unavailable` with the reason, and `IpcTransportTest` expects one
  webview off on macOS. A webview added to a window after the call is not
  covered; no fixture does that to a window whose page drives a test.
- The bounds live in `test/support/watched_child.rb` (`WatchedChild`),
  which `RealApp.launch` calls after its tripwire, so their tests run in
  `test:core` against children that open no window, on a clock the test
  moves, so a loaded machine cannot fail them. Only stdout counts as
  progress, since a library may log to stderr while the app is stuck. A
  tripped bound kills the child's whole process group, and so what it
  started; an error anywhere in the run still kills and reaps the child;
  a child that ends just as a bound trips is not called hung; and the
  outcome describes a killed run as the bound saw it.
- One constant, `WatchedChild::PATIENCE` (60 seconds), is how long any
  one of a fixture's own waits may last. `WatchedChild` passes it to
  the child as `TOKRA_FIXTURE_PATIENCE`, which `FixtureApp::PATIENCE`
  reads and `/options.json` serves the page, and a fixture run by hand
  takes the same default. The stall bound, `WatchedChild::STALL`, is
  that and `MARGIN` (30 seconds), and `WatchedChild.run` refuses a stall
  bound no longer than the patience, so a check that times out reports
  before RealApp could kill the fixture for its silence. Each check's
  timeout uses it; the waits for an event inside a check (`event`,
  `menu_plugin`, `tray_plugin`, `global-shortcut`, `ipc_transport`,
  `notification`) wait for the event itself, bounded by the check. Once
  a check times out, the checks after it fail at once without running,
  naming it, so a page that hangs throughout ends after one patience, not
  one for each check. The negative one-second wait in `ipc_transport`
  stays: load can only make it pass, not fail.
- `RealApp::Run#lines` leaves out the PROGRESS lines, which `#progress`
  answers, so the many new lines change no test's view of a fixture's
  contract lines.
- `exit_paths` alone sets `$stdout.sync = false` again, so the lines after
  its report still show that Ruby's own exit flushed them (Plan 018,
  decision 4).
- `RestartTest` holds its restarted runs to `WatchedChild::Bounds`: the
  log may go the stall bound without a new entry, and the wait may last
  RealApp's ceiling in all, so a regression that restarts on every run
  still ends.

The other waits that load could fail, and what became of each:

- Hang backstops, now bounded by the fixture's patience from Ruby:
  `HEARD.pop(timeout: 5)` in the `tray`, `menu`, and `config_tray`
  fixtures, now `FixtureApp.take`, which waits the patience for all the
  items rather than five seconds for each; `tray_menu`'s `until_logged`
  (5 s), `shown.pop` (20 s), `returned.pop` (30 s), and `closer.join`
  (5 s); `context_menu`'s `shown.pop` (20 s) and `closer.join` (5 s);
  `main_thread`'s ten-second join at exit; and, in
  `support/platform_popup.rb`, `Ticker#ticks_until_next` (3 s), which a
  starved ticker would have answered with 0, and the Windows
  `await_menu` and `await_gone` (20 s each) and `cancel_mode`'s send
  (2 s).
- The fallback timers that close a menu the closer thread never reached,
  8 seconds in `tray_menu` and `context_menu`, now fire after the
  patience. At 8 seconds a slow closer would have lost the race, and the
  tests would have failed on `dismissed_by`.
- Waits for something to settle, now waits for the condition: the
  `window_effects` and `window_state` `SETTLE` reads (2 s) already
  stopped once the expected answer showed, so their bound is now the
  patience, each read that ends prints `PROGRESS settled` so a run of
  slow reads is not taken for a hang, and `window_state` reads once,
  without waiting, the answers its platform cannot give and its test
  skips: on Linux maximizable, minimizable, and always on top, and on
  Wayland the position and the constrained width. `window_handle`'s
  two-second wait for always on top and ignored cursor events is now the
  patience. `context_menu`'s 0.3-second sleeps before reading its log are
  now waits for the entries its test expects.
- `native_loop`'s `--gc-drop` slept a second before collecting and two
  more before counting the webviews that beat a second after the
  collection, so a slow main thread could count every collected webview
  as still beating. It now collects once every page has beaten, and
  measures silence in the beats of a fourth, kept webview: a collected
  webview counts as still beating if it beat ten control beats after the
  collection, decided at twenty.
- Latency bounds the product promises, kept: `NativeLoopTest`'s
  `FROZEN_MS` (4 s for one wake-up with busy threads), `IDLE_GRACE` (2 s
  for an idle app to act on a signal) and `TERM_GRACE` (15 s), and
  `ExitPathsTest`'s `TERM_GRACE` (2 s) and `INTERRUPT_GRACE` (15 s).
  ADR 012 promises a signal is acted on within about 100 ms and that
  each busy thread adds about one time slice to an event's wait, and a
  regression of either does not hang: an idle app still ends on some
  later event, and a loop that hands the GVL over rarely still turns, so
  only a time bound can see it, and RealApp's stall bound cannot stand
  in. Load can falsify them in principle: a thread descheduled while it
  holds the GVL stretches every round. No measure free of wall time
  tells a loop that hands over rarely from a starved machine, so they
  stay, at 20 times and more what a healthy idle run takes, and the
  proof run decides: if one fails at a load near 400, it gets a bound
  calibrated against a control measured in the same run, such as a plain
  Ruby child's time to die of the same signal. The one-second `SETTLE`
  sleeps before those signals stay too: load can only make them prove
  less, never fail.

## What the investigation found

What starves is WebKit's helper processes, not the Ruby fixture. WebKit
holds a RunningBoard Foreground assertion for its WebContent, GPU, and
Networking processes only while `isViewVisible()` is true, and on macOS
that needs the window's occlusion state to include Visible
(`WebPageProxy.cpp:4053-4078`, `PageClientImplMac.mm:208-230`, WebKit
main 827737a). The hidden session is never drawn, so every window there
counts as covered, and the page processes drop to background priority
between loads; plan 057 measured priority 4 hidden against 46 to 47 on
the console at the same load. `backgroundThrottling: disabled` only
stops suspension and never restores the assertion. That RunningBoard maps
the assertion to priority 4, and why priority 4 starves so badly at load
400, are inferences the proof below settles.

RealApp's 60-second limit, and the page's own 20-second and 5-second
waits, are in effect pass conditions under load, not only hang
backstops.

## Steps

1. **A fixture helper, test-only.** `FixtureApp` calls the private
   `-[WKWebView _setWindowOcclusionDetectionEnabled:NO]` on each fixture
   webview, through the window handle and Fiddle as the `window_handle`
   fixture already does, guarded by `respondsToSelector:`, then hides and
   unhides the view so WebKit re-checks its visibility. WebKit's own test
   runner does this (`PlatformWebViewMac.mm:103`). It is called from
   `keep_in_sight` and from the dialog, notification, and global-shortcut
   plugin fixtures. Library code does not change, so an app's behavior and
   Tauri fidelity are untouched.
2. **A limit that measures progress, not time.** RealApp fails a fixture
   when no new progress line arrives for about 90 seconds, with a ceiling
   of 15 minutes for a fixture that loops while printing. A progress line
   is one that proves the app moved: the fixture's "loaded" line, and a
   line at the start and end of each check, sent by the page through Rack,
   which crosses the custom protocol, the event loop, and Ruby. No
   free-running heartbeat, which would hide a real hang. Every fixture sets
   `$stdout.sync`, so a killed fixture's output survives (`ipc_transport`'s
   did not), and the page's per-check timeouts come from Ruby.
3. **The proof,** run in `tokratest` when no gate is running:
   - Sample WebContent's priority hidden, with and without the helper:
     about 4 without, about 46 to 47 with. This decides the one assumption
     the research could not verify, that a Foreground assertion lifts
     priority in a session that is not on the console. If it does not,
     step 1 is dropped and the console set stays.
   - Hold the load near 400 with about 400 default-priority spinners and a
     cold cargo build, then run `test:real_windows` and the dialog window
     test 20 times each; 20 of 20 must pass, and fewer must pass without
     the helper.
   - Prove hangs are still caught: unit tests of RealApp's new limit with
     small bounds, and a fixture whose `ping` handler blocks forever must
     fail about 90 seconds after its last progress line.
4. **If the proof holds,** the console set (plan 057, `RealWindows::CONSOLE`)
   returns to the hidden session, and AGENTS.md's paragraph on it is
   amended, so no test needs the maintainer away from the keyboard.

## Ownership

Everything here is Tokra's test code. The hidden session belongs to the
hidden_session project (`~/Developer/hidden_session`, plan 056); nothing
there needs to change, though a load generator, a priority sampler, and a
note about the private call in its `SETUP.txt` would help the proof, and
are requested of that project, not done here.
