# Plan 035: Dialogs Parent to Tokra Windows on macOS

ADR 013 gave Tokra windows raw handles, and plan 028 made `tokra-dialog`
parent its dialogs to the calling window on Windows and X11. It copied each
handle into ferro-rfd's own class, because ferro-rfd 0.1.0.pre.2 checked
classes, and it left macOS and Wayland parentless, because ferro-rfd bound
no handle rfd follows as a pointer. ADR 013 recorded both as Ferro
follow-ups.

ferro-rfd 0.1.0.pre.3 settles two of them (Ferro tag `ferro-rfd/v0.1.0.pre.3`,
`gems/rfd/README.rdoc` "Parent windows", Ferro
`doc/contributors/plan/008.md`). It reads a handle by kind, the last
segment of the name of its class or nearest named ancestor, and by
raw-window-handle's field names (decision 8), so a `Tokra::RawWindowHandle`
value is a parent as it is. And it binds `AppKitWindowHandle` by window
number: on the main thread, when the dialog runs, it asks
`-[NSApplication windowWithWindowNumber:]` for the window, holds its
content view while rfd runs, and hands rfd raw-window-handle's
`AppKitWindowHandle { ns_view }` (decisions 1-3). A wrong number raises
`Ferro::Rfd::Error`; it never reaches rfd as a pointer. Wayland stays
unbound and raises `TypeError` (decision 7).

Before this plan, Tokra's AppKit handle carried `ns_view` only, as
raw-window-handle 0.6.2 does (`src/appkit.rs:86-91`), so ferro-rfd could
not read it.

Citations: plugins-workspace `d4613ff0` (`plugins/dialog/src/`), rfd
0.17.2, tao 0.34.5, raw-window-handle 0.6.2, objc2-app-kit 0.3.2, all as
locked.

## Fidelity audit

| Behavior | Tauri / crates | Tokra before | Verdict |
|---|---|---|---|
| `open` parents to the window | Windows and macOS (`commands.rs:129-132`) | Windows only in effect: the AppKit parent dropped | port: macOS parents |
| `save`, `message`, `ask`, `confirm` parent | every desktop (`commands.rs:229-232`, `281-284`) | Windows and X11 | port: macOS too; Wayland stays parentless (decision 4) |
| macOS file dialog with a parent | a sheet on that window (rfd `backend/macos/modal_future.rs:67-103`) | a sheet on the main window, or the first window, whatever called it (`modal_future.rs:71-75`) | port |
| macOS message dialog with a parent | an `NSAlert` sheet on that window (`backend/macos/message_dialog.rs:172-183`) | a system alert on rfd's own thread (`utils/user_alert.rs:177-196`) | port |
| AppKit window handle | `AppKitWindowHandle { ns_view }` (raw-window-handle `src/appkit.rs:86-91`), tao's content view (tao `macos/window.rs:1494-1503`, `1561-1563`) | `AppKitWindowHandle(ns_view)` | keep `ns_view`; add `window_number` (decision 1) |

## Decisions

1. **`Tokra::RawWindowHandle::AppKitWindowHandle` gains `window_number`,
   beside `ns_view`.** raw-window-handle names an AppKit window only by
   its content view's address. Ruby cannot hold that pointer soundly, so
   ferro-rfd names the window by `-[NSWindow windowNumber]`, which AppKit
   resolves or refuses (Ferro plan 008, decision 1). Tokra exposes
   raw-window-handle faithfully, so `ns_view` stays, with its meaning
   unchanged, and `window_number` is an extra field: the translation
   ADR 013's follow-up anticipated ("Tokra would then add the window
   number to `AppKitWindowHandle`"). Tier 1 of the precedence: what Ruby
   can express soundly. The field order is `ns_view, window_number`, so
   raw-window-handle's field comes first.

2. **The native layer reads the number on the main thread.**
   `Native::Window#raw_window_handle` already runs only on the window's
   thread, the main thread (`thread_bound.rs`). For an AppKit handle,
   `raw_handle.rs` asks tao's `WindowExtMacOS::ns_window` for the window
   (tao `platform/macos.rs:88-92`, `macos/window.rs:1557-1559`, a pointer
   to the `NSWindow` tao keeps retained while the window lives) and calls
   objc2-app-kit's `NSWindow::windowNumber` (`generated/NSWindow.rs:780-782`).
   Turning the pointer into a reference is the one `unsafe` block, with a
   SAFETY comment citing those lines. tao creates the window with
   `defer: NO` (`macos/window.rs:248-251`), so it has a window device,
   and a number, from the start. objc2-app-kit becomes a direct,
   macOS-only dependency at the version and features tao already locks.
   The tagged Array becomes `[:AppKit, ns_view, window_number]`.

3. **`tokra-dialog` passes Tokra's handles to ferro-rfd as they are.**
   `Desktop::WindowHandle` still snapshots both handles when the parent is
   set, as Tauri's `WindowHandle` does (`desktop.rs:51-80`), but keeps the
   values themselves. The copying of Win32 and Xlib values into
   ferro-rfd's classes goes. A parent that is ferro-rfd's own values works
   as before.

4. **Wayland stays parentless, by Tokra's choice.** ferro-rfd raises
   `TypeError` for a Wayland handle, since rfd 0.17.2 follows the surface
   and display pointers to export the surface (Ferro plan 008, decision 7).
   A Tokra window on Wayland would make every save and message command
   fail, where Tauri shows the dialog. So `WindowHandle.of` treats a
   Tokra Wayland handle, of either kind, as no parent, and the dialog
   shows parentless: deviation, tier 1, documented in the builders' RDoc
   and ADR 013. Any other value goes to ferro-rfd, which refuses what it
   cannot take with its own error.

5. **The commands' parents stay as they are.** `Commands::OPEN_HAS_PARENT`
   and the unconditional `set_parent`/`parent` in save and message already
   match Tauri's cfgs; now they take effect on macOS.

6. **Threading needs no change.** Each dialog function builds the rfd
   dialog, `set_parent` included, on the calling thread, and opens it on
   the main thread through `run_on_main_thread` or a `RuntimeContext`
   getter (plan 023, decision 2). ferro-rfd reads only the handle's
   fields at `set_parent` and looks the window up when the dialog runs,
   so the lookup happens on the main thread, directly, inside tao's event
   callback: no hop, no wait. rfd's `ModalFuture::new` finds the app
   running and begins the sheet there, through `run_on_main`, which runs
   at once on the main thread (`modal_future.rs:79-103`). The thread that
   awaits the future waits without the GVL, as before. Only
   `inspect`, or a dialog run directly with ferro-rfd from a worker
   thread, hops: ferro-rfd sends the lookup to the main dispatch queue and
   waits without the GVL. Tokra's main thread sits in tao's run loop,
   which drains that queue, and the block runs no Ruby, so it ends. It
   would hang only if the main thread were blocked in Ruby, which
   `Desktop.blocking` from the main thread already does for any dialog
   (plan 023).

## Verification

- Unit (`test/test_raw_window_handle.rb` or its existing home): the
  tagged Array with three elements builds `AppKitWindowHandle` with both
  fields; the two-element form is `NotSupported`.
- Real window, root suite: on macOS, a real Tokra window answers a
  `window_number` that `-[NSWindow windowNumber]` of tao's window matches,
  read through Fiddle from the content view's `window`.
- Dialog unit (`test_parent.rb`): Tokra's values are kept as they are,
  and reach rfd (Win32 and X11 Debug text as before); on macOS a stub
  window's number reaches ferro-rfd's lookup, which refuses it with
  "no window of this app has window number N"; Wayland handles are no
  parent, alone or paired.
- Dialog real window (`test_dialog_window.rb`): on macOS each file sheet
  is attached to the Tokra window whose number the fixture printed, and
  rfd's Debug text for a dialog parented to the window, built on the main
  thread and on a worker thread, names the window's own `ns_view`.
- Mutations: drop the window number from the Ruby value; pass a constant
  instead of `windowNumber`; restore the AppKit branch that dropped the
  parent; drop the Wayland filter.
- The clean gate.

## Results

- Message dialogs on macOS are not in the real-window test. With a
  parent they are `NSAlert` sheets on the window, as planned: one run of
  the fixture with message, ask, confirm, `window.confirm`, and
  `window.alert` ended all five through `endSheet:returnCode:` with
  `NSAlertFirstButtonReturn` (1000) or `NSAlertSecondButtonReturn` (1001),
  nine sheets on the Tokra window in all, and each answer was right. But
  an alert sheet brings the app to the front (the file panels, shown out
  of process, do not), and the real-window harness refuses a fixture that
  takes focus. So the page keeps message dialogs Linux-only, and the
  Debug-text check covers the macOS parent. A second Tokra window, which
  would make the sheet check tell a parent from rfd's fallback to the
  first window, waits for multi-window support.
- No command test runs a macOS command against a stub window: without a
  parent rfd would open a real modal panel in the test process. The
  commands' parent wiring is unchanged and covered on Linux (portal) and
  by `OPEN_HAS_PARENT`.
- Mutations, each restored: the AppKit value built with
  `window_number: 0` failed `test_each_native_window_handle_becomes_its_value`
  and `test_an_appkit_window_number_is_the_windows_own`; `windowNumber`
  replaced by `1` natively failed the latter and seven dialog window
  tests (ferro-rfd refused the number); dropping the Wayland filter
  failed both Wayland tests in `test_parent.rb`; treating an AppKit
  window as no parent failed
  `test_an_appkit_window_reaches_ferro_rfds_window_lookup_on_macos` and
  `test_on_macos_rfd_gets_the_window_as_parent_from_any_thread`.

## Out of scope

- A Wayland parent. rfd 0.17.2 takes one only as raw pointers; a sound
  route needs an exported `xdg-foreign` handle (ADR 013, Consequences).
- A shared raw-window-handle gem. Reading by kind makes it unnecessary
  for ferro-rfd.

## Risks

- `window_number` is not raw-window-handle's. A reader comparing the two
  finds one more field; the RDoc says why.
- Message dialogs on macOS become sheets on the window where they were
  system alerts. That is Tauri's behavior, and an app that relied on
  the alert's placement sees the change; CHANGELOG says so.
