# Plan 050: The window and webview core plugins

Tokra's `Window` has the whole inherent API tao can serve (plans 038, 040,
041, 045), and its events reach the page as `tauri://` events (plan 047).
The page cannot call any of it. `@tauri-apps/api/window` and
`@tauri-apps/api/webview` send `plugin:window|*` and `plugin:webview|*`,
and Tokra registers neither plugin, so every call rejects with
`Command ... not found`. The worst of it is `onCloseRequested`: plan 047
made a page that listens for `tauri://close-requested` keep its window
open, because the page's handler is meant to call `plugin:window|destroy`
itself. Without the plugin that call fails, and the window cannot be
closed by its close button at all (plan 047, Risks).

TODO 002 names these plugins as the next work. They split cleanly by
what Tokra already has. Every window command but one maps onto a
`Window` method that exists, so the window plugin is Ruby alone: argument
readers in serde's words, a label lookup, and a dispatch table. The
webview plugin is the opposite. Tokra's `Webview` has `eval` and
`set_background_color`, and nearly every webview command is a wry call
Tokra has not bound. Some commands, those that create windows and
webviews or move a webview between windows, need features Tokra does
not have at all.

So this plan has three phases. Phase 1 brings the window plugin whole
except `create`, the two webview commands Tokra can already answer, and
the drag-region script, and proves `onCloseRequested` end to end in a
real window. It is three working sessions, each its own commit:

- **050a** moves the serde readers the menu and tray plugins each carry
  into one module, fixing two places where they disagree with serde.
  Fully specified.
- **050b** gives each argument type its reader and each returned type
  its JSON. Fully specified.
- **050c** adds both plugins, their registration, `drag.js`, a queued
  `Window#destroy`, and the end-to-end test. Its permission check, and
  so what the end-to-end test expects of `destroy`, waits for the
  maintainer's answer to question 1; everything else in it is specified.

Phase 2 binds wry's webview calls and ports the webview commands that
need nothing else. Phase 3 is not this plan's: it lists the commands that
wait for multiwindow and child-webview work, and the plans that would
bring them.

## Decisions

1. **The plugins are `Tokra::Window::Plugin` and `Tokra::Webview::Plugin`,
   registered after `Event::Plugin`.** They live in
   `lib/tokra/window/plugin.rb` and `lib/tokra/webview/plugin.rb`, as
   Tauri's live in `window/plugin.rs` and `webview/plugin.rs`, and are
   named `"window"` and `"webview"`. `App#initialize` registers them
   right after the event plugin, as `register_core_plugins` orders
   `event`, `window`, `webview` before `resources`. Tokra has no `path`
   or `app` plugin; nothing else moves. Their init scripts follow the
   event plugin's, as Tauri collects plugin scripts in registration
   order.

2. **The target is found the way `get_window` finds it.** A `label` that
   is missing, `null`, or the empty string names the window of the
   webview that invoked (`invoke.webview.window`). Any other string goes
   to `Manager#get_window`, and a label it does not find raises
   `Error::WindowNotFound`, `window not found`. The webview plugin does
   the same with `invoke.webview`, `Manager#get_webview`, and
   `Error::WebviewNotFound`, `webview not found`. Both errors are new
   `Tokra::Error` subclasses with Tauri's messages. A Tokra app has one
   window and one webview, both labeled `main`, so a page that asks for
   another label gets Tauri's rejection, as a Tauri app does for a label
   it never created.

3. **Arguments are read before the window is looked up.** Tauri's
   generated command deserializes every argument, in the signature's
   order, before its body runs `get_window`. So a bad `label` rejects
   before a bad `value`, and a bad `value` with an unknown label rejects
   with the value's message, not `window not found`. `set_icon` and
   `set_overlay_icon` resolve their `JsImage` against the calling
   webview's table after the lookup, as `into_img` runs after
   `get_window`. `monitor_from_point` reads `label`, then `x`, then `y`.

4. **050a: one module holds serde's visitors, and reads as serde does.**
   The menu and tray plugins each carry private copies of serde's
   readers, and a window plugin would be the third. The copies already
   disagree with serde twice:

   - Too many elements. `Menu::Plugin#struct_fields`
     (`menu/plugin.rb:769-780`) rejects a sequence longer than the struct
     with `invalid length N, expected struct X with M elements`. serde's
     derive reads the fields it wants and serde_json then rejects what
     is left with `invalid length N, expected fewer elements in array`,
     as `Menu::Plugin#position_fields` and `Tray::Plugin#options`
     already say (serde_json `src/value/de.rs:195-211`).
   - Order. `struct_fields` and `Tray::Plugin#options` check a
     sequence's length before reading any element. serde reads element
     by element, so a bad first element in a short sequence fails with
     that element's error, and only a sequence that runs out of good
     elements fails with `invalid length i, expected struct X with M
     elements`, where `i` is the index it ran out at.

   050a writes a failing test for each, then moves the visitors into
   `Tokra::Ipc::Serde` (`lib/tokra/ipc/serde.rb`, `:nodoc:`), reading as
   serde does, and the two plugins call it. The module holds serde's
   concepts and nothing of any one type:

   - `unit_variant(value, variants)`: a string, or a one-key map whose
     value is `null` (`invalid value: map, expected map with a single
     key`; `invalid type: ..., expected unit`); anything else is
     `invalid type: ..., expected string or map`.
   - `enum_variant(value, variants, newtype: [])`: an externally tagged
     enum, a one-key map (or a bare string, which a newtype variant
     rejects with `invalid type: unit variant, expected newtype
     variant`), answering the variant and its content; a variant not in
     `newtype:` is a unit variant, whose content must be `null`.
   - `internally_tagged(value, tag, enum_name, variants)`: the tag, read
     as a variant identifier when it is reached, from a map, or
     from a sequence's first element, as `EventTarget.read` reads `kind`
     (plan 047, decision 2), with `missing field `tag`` and `invalid
     type: ..., expected internally tagged enum Name`. `EventTarget`
     moves onto it.
   - `known_variant(name, variants)`: serde's `unknown variant `x`,
     expected ...`, its list worded as `OneOf` words it (one, `a or b`,
     `one of a, b, c`).
   - `struct_fields(value, name, fields, optional: [], deny_unknown:
     false) { |field, raw| ... }`: from a map, each present field read
     in the map's key order, then the first missing required field;
     from a sequence, element by element, then serde_json's leftover
     error. With `deny_unknown:`, a map key that is no field raises
     `unknown field `x`, expected one of ...`. The block reads each
     field. The fields in `optional:` are Rust `Option`s: `null` is
     `nil` without the block, an absence from a map is `nil`, and an
     absence from a sequence is the length error.
   - `tuple(value, size) { |index, raw| ... }`: element by element,
     `invalid length i, expected a tuple of size N`, then serde_json's
     leftover error (added in 050a; see its Results).
   - Scalars: `string` (`a string`), `borrowed_str` (`a borrowed
     string`), `boolean` (`a boolean`), and `f64` (an integer or a
     float). Integers stay in `Ipc::CommandItem.integer`.

   The fixes (four, see 050a's Results) change messages a page can
   see. Every CHANGELOG entry is still under Unreleased, and the readers
   came in since the last tag, so there is no entry for them.

5. **050b: each argument type reads its JSON as its `Deserialize` does.**
   Tauri's types each own their serde impl; `JsImage.deserialize`
   (plan 042) and `EventTarget.read` (plan 047) are Tokra's precedent.
   Each type the window plugin takes gains a `:nodoc:`
   `self.deserialize(value)`, built on `Ipc::Serde`, that answers the
   Ruby value or raises `Ipc::CommandItem::Mismatch` with serde's words.
   Each integer is read as its Rust type, since the type is in the
   message:

   | Reader | Form | Integers |
   |---|---|---|
   | `UserAttentionType` | internally tagged on `type`; other keys ignored | none |
   | `CursorIcon`, `Theme`, `TitleBarStyle` | a string, lowercased; an unknown name falls back to `Default`, `Light`, `Visible`; a non-string is `expected a string` | none |
   | `ResizeDirection` | unit enum, Tauri's names | none |
   | `ProgressBarStatus`, `Effect`, `EffectState` | unit enums, camelCase (`"none"`, `"hudWindow"`, `"followsWindowActiveState"`) | none |
   | `ProgressBarState` | struct `status`, `progress`; unknown keys ignored | `progress`: `u64` |
   | `WindowSizeConstraints` | struct, camelCase `minWidth` and so on, each an `Option<PixelUnit>` | through `PixelUnit` |

   Tokra has no `Size` or `Position` class (a `LogicalSize` or
   `PhysicalSize` stands for one), so the three dpi readers are `Dpi`
   functions. `Menu::Plugin#position` moves onto
   `Dpi.deserialize_position`. `CommandItem.integer` gains `"i64"` and
   `"u64"`, for `set_badge_count` and `progress`. So `{"Physical":
   {"width": -1, ...}}` is `invalid value: integer `-1`, expected u32`,
   while the same `-1` in a position is accepted and `2147483648` is
   `expected i32`.

6. **050b: returned values serialize as serde writes them.**
   `PhysicalPosition`, `PhysicalSize`, `PhysicalRect`, `Monitor`, and
   `Theme` gain public `to_json` (and `:nodoc:` `as_json`), as `Rect`
   has: `{"x","y"}`, `{"width","height"}`, `{"position","size"}`,
   `Monitor` with Tauri's camelCase keys (`name`, `size`, `position`,
   `workArea`, `scaleFactor`), and `Theme` as `"light"` or `"dark"`. A
   Float stays a Float (`cursor_position` is `f64`), an Integer an
   Integer. `Ipc::Invoke` already runs `JSON.generate`, which calls
   `to_json`.

7. **`set_background_color` reads `value`, as Tauri's does.** The JS
   sends `{ color }` with no label (`window.ts:1593-1595`,
   `webview.ts:607-609`, `webviewWindow.ts:222-226`), and the command
   reads `value: Option<Color>`. A missing key is `None`
   (`ipc/command.rs:134-145`), so at the pinned commit the page's
   `setBackgroundColor` always resets the color to the default, on the
   calling window. Tokra does the same: precedence 2 says wire formats
   match the Rust source, and the Rust source is what reads them. The
   plugin's RDoc says so.

8. **`get_all_webviews` answers snake-case keys.** `WebviewRef` derives
   `Serialize` without `rename_all`, so Tauri writes
   `{"window_label": ..., "label": ...}`. The JS reads `w.windowLabel`,
   which is `undefined`, and builds `new Window(undefined, { skip: true
   })` (`webview.ts:77`); that window sends no label, so its commands
   act on the caller's window. Tokra writes what Rust writes, for the
   reason in decision 7, and the RDoc says what the page gets.

9. **`drag.js` is the window plugin's init script.** `rake sync:tauri`
   vendors `crates/tauri/src/window/scripts/drag.js` as
   `lib/tokra/js/drag.js.erb`, its `__TEMPLATE_os_name__` an ERB tag.
   `App#os_name` is private (`app.rb:592`); it becomes a `:nodoc:`
   public reader the plugin calls, so the OS name has one source.
   `Window::Plugin#initialization_script` renders the script with that
   name, JSON-encoded. It sends `plugin:window|start_dragging` and
   `internal_toggle_maximize` with no label. The webview plugin has no
   init script in phase 1: `print.js` replaces `window.print` with a
   command phase 1 does not answer, so it arrives with `print` in
   phase 2.

10. **Platform-only commands are answered only on their platform.**
    Tauri compiles `set_badge_label` into the handler only on macOS, and
    `set_overlay_icon` only on Windows. Tokra defines those `Window`
    methods only there (plan 045, decision 5), so the plugin answers
    each only when `Window.method_defined?` says the method exists.
    Elsewhere the command is unclaimed and rejects with `Command
    set_badge_label not found`, as in Tauri.

11. **The permission check is the maintainer's to choose (question 1).**
    In Tauri every plugin command is checked against the ACL before its
    plugin sees it (`webview/mod.rs:1801-1830`). `core:event`,
    `core:menu`, and `core:tray` grant every command by default, which
    is why plans 043 and 047 had nothing to decide. `core:window:default`
    grants only the getters and `internal_toggle_maximize`, and
    `core:webview:default` only its getters and
    `internal_toggle_devtools` (`build.rs:43-153`). A Tauri app on
    `core:default` alone cannot `destroy`, `close`, `setTitle`, or drag
    (`start_dragging` is not default). Plan 047's Risks already took
    that reading: a page listening for `tauri://close-requested` stays
    open "as a Tauri app without the window plugin's permission" does.
    Answering every command would relax a safety default, which
    precedence 1 and ADR 011's amendment keep off unless the app opts in
    by name. So 050c does not decide it. The three options, and what
    each makes of 050c:

    - **(a) The default sets only.** `App#route_invoke` rejects a
      `plugin:window|` or `plugin:webview|` command outside them, after
      the origin check, with Tauri's release-build message, `Command
      plugin:window|destroy not allowed by ACL` (`webview/mod.rs:1829`),
      as ADR 010 §6 already uses it. The debug build's longer text
      (`ipc/authority.rs:229-380`) names capabilities Tokra has none of,
      so it is not ported. The end-to-end test then proves that
      `destroy` rejects with that message and the window stays open;
      the setter tests call the plugin directly, below the check.
    - **(b) Every command**, for the app's own pages, as every other
      Tokra core plugin answers. The end-to-end test proves the window
      closes. The RDoc records the relaxed default.
    - **(c) The default sets, plus a code-level opt-in named after the
      capability**, such as granting `core:window:allow-destroy` on the
      `Builder`, off by default, per ADR 011's amendment. The end-to-end
      test runs twice: without the grant `destroy` rejects as in (a);
      with it the window closes. The opt-in's name and shape would be
      the first piece of the capabilities plan, so it should match that
      plan's eventual API.

    Until the answer, 050c can land everything but the check and the
    end-to-end test's `destroy` expectation.

12. **`Window#destroy` queues the native close for a later turn, as
    Tauri does.** Tauri's `destroy` never takes `send_user_message`'s
    main-thread shortcut; it always sends `WindowMessage::Destroy`
    through the proxy (`lib.rs:2151-2158`, handled at `:4232-4234`). A
    page's `destroy` invoke is answered over `ipc://` by wry's async
    responder (ADR 010 §1), which Tokra delivers at once on the loop's
    thread (`ext/tokra/src/proxy.rs:232-246`). So in Tauri the reply goes
    out before the window goes, and Tokra's current `Window#destroy`,
    which closes at once on the main thread, would reverse that: the
    window would close, and then the reply would go to a webview whose
    window is gone. `RuntimeContext` gains a `:nodoc:` method that
    always queues a task through the proxy, the off-main-thread branch of
    `send_user_message` taken from any thread, and `Window#destroy` uses
    it. Its RDoc's "on the main thread the window closes at once" goes.
    No real-window test has ever called `Window#destroy`; 050c's
    end-to-end test is the first, and under question 1's (a) a stub
    test and a real-window call from Ruby in that fixture stand in for
    it. The CHANGELOG's Unreleased entry for `Window#destroy` says
    nothing about timing, so it does not change.

13. **`onCloseRequested` runs in Tauri's order.** A close request, from
    the close button or the page's `close()` (`Window#close`, a request
    through the loop), reaches the window's listeners first. The
    manager's listener sees the page's listener on this window, prevents
    the close, and emits `tauri://close-requested` (plan 047, decision
    13); the builder's listeners and then the run callback hear
    `CloseRequested`; the window stays. The page's handler runs, and
    unless it called `preventDefault` it invokes `plugin:window|destroy`
    (if question 1 allows it). The invoke resolves and the reply goes
    out; on a later turn the queued close runs; then the platform's
    `Destroyed` reaches the run callback, the window's listeners
    (`tauri://destroyed`), the webviews close, and `RunEvent::ExitRequested`
    follows with no code, as plan 038 ported it.

14. **Commands run on the main thread, as every Tokra invoke does.**
    Tauri's window commands are `async`, so they run on its async
    runtime and reach the window through the event loop. Tokra routes
    every invoke on the main thread (`App#dispatch_ipc` and
    `#route_invoke`, from the loop's `Native::IpcEvent`), so a getter
    answers at once. With `destroy` queued (decision 12), the page sees
    the same results as in Tauri, and its invokes settle in the order it
    sent them, one of the orders Tauri allows.

15. **Unported commands are left unclaimed.** `create`, and in phase 1
    the webview commands phases 2 and 3 bring, reject with `Command
    create not found`, the rejection a Tauri app gives for a command its
    build lacks. The RDoc lists them and the plan that brings each.

## Risks

- `destroy` from the page now closes the window on the turn after its
  reply, as Tauri's does (decision 12). The queued close has never run
  in a real window before 050c; Windows runs it only in CI. A failure
  there shows as the end-to-end test hanging until its backstop, which
  its stdout lines locate.
- On macOS, `start_dragging` from a drag region drags with whatever
  `NSApp.currentEvent` is during the IPC turn (`drag_window`,
  `window.rs:932-958`), which may not be the mouse-down. Tauri's async
  command reaches tao on a later turn too, so Tauri has the same
  exposure; only a person at the screen can confirm it works.
- The readers are many and small, and serde's exact words are easy to
  misremember. Each message in decisions 4 and 5 comes from the serde
  and serde_json sources plans 043 and 047 already cite; any not checked
  there is marked UNVERIFIED in the tests' comments until read.
- 050a changes two shipped plugins' messages. It lands as its own
  commit, its two fixes test-first, so a slip shows before anything
  builds on it.
- Whatever question 1 decides, the other core plugins answer every
  command because Tauri's defaults let them; a later capabilities plan
  replaces both choices with Tauri's resolution.

## Questions for the maintainer

1. **Which commands do the window and webview plugins answer until
   capabilities exist?** Tauri checks every plugin command against the
   ACL, and `core:window:default` grants only the getters and
   `internal_toggle_maximize` (decision 11).
   - (a) Tauri's default sets only. A page cannot close, resize, or drag
     its window, and `onCloseRequested`'s `destroy` rejects with
     `Command plugin:window|destroy not allowed by ACL`, as in a Tauri
     app that has not granted `core:window:allow-destroy`.
   - (b) Every command, for the app's own pages. Pages can do
     everything, but a safety default is relaxed with no opt-in.
   - (c) The default sets, plus a code-level opt-in named after each
     capability (such as `core:window:allow-destroy`), off by default,
     per ADR 011's amendment. Closest to Tauri, and the opt-in becomes
     the first piece of the capabilities API, so its shape is yours to
     set.

   050a and 050b do not depend on the answer. 050c's check, its RDoc,
   its CHANGELOG line, and its end-to-end test's `destroy` expectation
   do, as do the commands phase 2 adds.
2. **What stands for Tauri's `debug_assertions` and `devtools` feature
   in Tokra?** `internal_toggle_devtools`, its hotkey script, and wry's
   `devtools` feature all hang on it. Tauri turns devtools on in debug
   builds, and in release only with a feature that macOS's App Store
   rejects. A Ruby app has no debug build. ADR 011 allows a code-level
   opt-in on `Builder` named after the feature, off by default, or
   never porting it. The plan defers it until you choose.
