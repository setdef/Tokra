# ADR 021: Commands Run Where Tauri Runs Them, and an Async Command Answers Through respond_async

## Context and Problem Statement

AGENTS.md's goal 3 says app code never has to block the main thread: a
window that hangs while the app works is a defect. Today `App`
dispatches every command on the main thread
([the IPC design](../design/ipc.md), "Where commands run"), so any slow
command freezes the window, and an app has no supported way out.

Tauri runs a command in one of three places
(`tauri-macros/src/command/wrapper.rs`): an ordinary command on the
main thread, an `async fn` on its async runtime, and an ordinary
function marked `#[tauri::command(async)]` on that runtime's blocking
pool. Its macro expands each of the last two to a call of
`InvokeResolver::respond_async` (`tauri/src/ipc/mod.rs`), which spawns
the work on `tauri::async_runtime` and answers the page when it ends.
The project's first decision record set another target: all of the
app's logic in a worker Ractor.

Where does a Tokra command run, and how does an app say so?

## Decision Drivers

- Fidelity to Tauri (goal 1): the same commands block the window, and
  the same do not.
- No public name Tauri does not have (goal 1).
- App code never has to block the main thread (goal 3).
- Ractor-ready, with Ractors used only where they serve the goals
  (goal 4).

## Considered Options

1. Tauri's places and Tauri's names: an ordinary command on the main
   thread; an async one through `Invoke#respond_async`, on a port of
   `tauri::async_runtime` whose tasks run on Ruby threads.
2. The same, with the runtime's tasks in Ractors from the start.
3. Every command off the main thread, in a worker Ractor, the project's
   first target.
4. A marker of Tokra's own, such as an `async: true` on a handler or a
   per-command registration.

## Decision Outcome

Chosen: option 1. A command answers with `invoke.resolve` or
`invoke.reject` on the main thread, and blocks the window while it
runs, as Tauri's does. A command that must not block calls
`invoke.respond_async { ... }`: the block runs on the async runtime,
its value resolves the invoke, and an exception rejects it. That is the
call Tauri's macro writes for every async command, so it adds no name,
and the page sees no difference. `Tokra::AsyncRuntime` ports the
module under Tauri's names. A plugin command that Tauri marks async
answers the same way.

The runtime's tasks run on Ruby threads in the main Ractor, because
that needs nothing new: the event loop already hands the lock to other
Ruby threads (ADR 012). Option 2 cannot be built yet: no native method
of Tokra's can be called from another Ractor, and before Ruby 4.1 a
worker Ractor stalls at its first garbage collection while the loop
holds the lock. Option 3 departs from Tauri, where an ordinary command
does block the window, and it would require every handler to be
Ractor-shareable. Option 4 invents a name where Tauri has one.

The one place that hands a task to a thread stays small and single,
inside the runtime, so that tasks can later run in Ractors without
touching commands or plugins.

This record replaces the worker-Ractor target of the former ADR 001,
whose other decision is now ADR 020.

Confidence: medium on the shape, which is Tauri's; low on the cost. It
is not built: a first implementation exists and has not landed. What a
CPU-bound task on a thread costs the window is not measured; ADR 012
predicts about one time slice per busy thread per turn of the loop,
where Tauri's task runs in parallel and costs the window nothing.
Revisit when it is measured on Linux and on Windows, whose hand-off
differs, and again when a Ractor can call the event loop's proxy.

### Consequences

- Good, because a Tauri developer's choice between a blocking and an
  async command carries over, with Tauri's name for it.
- Good, because a command that waits on a file, a query, or the network
  no longer freezes the window.
- Bad, because an ordinary command still blocks the window, as in
  Tauri, and an app developer has to choose.
- Bad, because a command that computes still slows the window while it
  shares the main Ractor's lock, which a Tauri app's does not.
- Bad, because work on another thread reaches app state that the main
  thread also uses, so shared state needs the care Tauri enforces with
  `Send` and `Sync` and Ruby does not enforce at all.
- Neutral, because Tokra has no `#[tauri::command]`: the app's handler
  is one block, so "marked async" is a call inside it, not a mark on a
  function.

### Confirmation

When it lands: a real-window test in `test/integration/` shows a
window answering while a slow async command runs, on each system, and
each plugin's tests check that a command Tauri marks async answers from
a task of the runtime. Until then nothing checks it.
