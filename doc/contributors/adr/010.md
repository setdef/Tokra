# ADR 010: The `ipc://` Transport and `withGlobalTauri`

## Status

Accepted

## Date

2026-07-22

## Context

ADR 009 wired the IPC response path and, in §1, chose `postMessage` as the
primary transport: Tokra injected Tauri's own `ipc-protocol.js`, which tries a
`fetch('ipc://…')` first, and — because Tokra served no `ipc://` protocol — let
the client fail that fetch once, log one console warning per page load, and fall
back permanently to `window.ipc.postMessage`. ADR 009 named serving `ipc://` as
a follow-up, not an optimization: it is Tauri's desktop default, and the failed
fetch plus warning were an accepted interim cost.

Two facts made serving `ipc://` also the way to *prove* ADR 008 (that Tauri's
npm packages work unchanged). The `ipc://` request and response format is fixed
by Tauri's `ipc-protocol.js` (client) and `ipc/protocol.rs` (server): a
Tokra-authored test would only encode Tokra's reading of the wire format on both
ends, so it cannot catch a misreading. And the real client exercises the
transport only once it is served — until then it rides `postMessage`. The
transport and its proof therefore ship together.

## Decision

### 1. Serve `ipc://` as the primary transport; keep `postMessage` as fallback

Tokra registers a second asynchronous custom protocol, `ipc`, alongside
`tokra://`. Both forward the same `UserEvent::HttpRequest` (storing the wry
responder by `request_id`); the native binding stays thin (ADR 001/005) — one
added registration, no new event variant and no new response API. `App` routes a
forwarded HTTP request on its URI scheme: `ipc://…` (macOS/Linux) and
`http://ipc.localhost/…` (Windows) go to the `ipc://` transport; everything else
stays the `tokra://` content path.

This supersedes ADR 009 §1. `postMessage` is retained as the fallback the
vendored `ipc-protocol.js` selects on its own when a `fetch('ipc://…')` rejects,
so hand-rolled `window.ipc.postMessage` callers keep working. Once `ipc://` is
served, the real client stays on it and the per-page-load warning disappears.

### 2. One dispatch, two transports — the routing shape of `on_message`

Tauri routes both transports through `webview.on_message`. Tokra extracts the
command routing — the plugin-vs-`invoke_handler` branch and its
`Command NAME not found` rejection — into one private `route_invoke` that both
front ends call. Each transport supplies only what differs: how it reads the raw
invoke key (a JSON member for `postMessage`; the `Tauri-Invoke-Key` header for
`ipc://`), how it parses the payload, its responder, and its drop action.

`on_message` also resolves ACL/capabilities. Tokra has no capability system
(TODO 001 #9), so this dispatch omits it — exactly as the `postMessage` path
already did. Both transports are equally unguarded until the capabilities phase
lands; this ADR neither closes that gap nor widens it.

### 3. The `ipc://` responder answers the request; it does not eval

Per `ipc-protocol.js`, the client reads the HTTP response and calls
`runCallback` itself. So the `ipc://` responder replies over HTTP rather than
evaluating `runCallback` (the `postMessage` path keeps `FormatCallback`). A
resolved or rejected invoke both reply `200` with an `application/json` body,
distinguished by the `Tauri-Response` header (`ok` vs. `error`), mirroring
`ipc/protocol.rs`. Every reply carries `Access-Control-Allow-Origin: *` and
`Access-Control-Expose-Headers: Tauri-Response`, matching Tauri's shared
`respond` closure, so the cross-origin client can read the header.

### 4. Two failure modes, ported distinctly

A **malformed** request — a missing or non-numeric `Tauri-Callback`/
`Tauri-Error`, a missing `Tauri-Invoke-Key` or `Origin`, unparseable JSON, or an
unimplemented content type — replies **500 `text/plain`** with the parse message
(`ipc/protocol.rs`), which the client surfaces as a rejection. A **key mismatch**
on an otherwise well-formed request **logs Tauri's exact message and drops with
no reply** (`webview/mod.rs`). Tauri drops by letting its owned responder fall
out of scope; Tokra's responder lives in a map keyed by `request_id`, so the
faithful equivalent is `Proxy#drop_response(request_id)`, which removes and
drops it. Dropping reproduces Tauri's chain: the client `fetch` rejects, falls
back to `postMessage`, which drops and logs in turn.

### 5. `withGlobalTauri` as the API-delivery mechanism

The way to run `@tauri-apps/api` in a webview with no frontend bundler is
Tauri's own `withGlobalTauri`, which injects the API's prebuilt IIFE
(`bundle.global.js`) as an initialization script, exposing the whole API as
`window.__TAURI__`. Tokra ports it as `Builder#with_global_tauri`: when set,
`App` appends the vendored `bundle.global.js` after the core init scripts,
mirroring `manager/webview.rs`. Tauri gates this at build time from
`config.app.with_global_tauri`; Tokra has no build-time codegen, so the gate
moves to `Builder`/`App` runtime script assembly — a tier-1 language adaptation.
`rake sync:tauri` vendors `bundle.global.js` from the pinned submodule with the
same extract-and-abort discipline as the other scripts; the API package's own
rollup build produces the artifact, so Tokra never hand-bundles Tauri's
JavaScript.

## Consequences

### Positive

- `invoke` rides Tauri's desktop-default transport; the per-page-load `ipc://`
  fetch failure and console warning from ADR 009 are gone.
- The real `@tauri-apps/api`, loaded through `withGlobalTauri`, drives a live
  invoke round trip — the end-to-end demonstration ADR 008 never had.
- One routing shape serves both transports, matching `on_message`.

### Negative

- Two active transports must stay in sync; the shared `route_invoke` and tests
  for both responders and both failure modes guard against regressions.
- The vendored scripts, now including `bundle.global.js`, are pinned to the
  submodule; regeneration is manual and aborts if extraction fails.

### Neutral

- ACL/capabilities remain unimplemented for both transports (TODO 001 #9).
- Raw/ArrayBuffer request bodies and Channels stay out of scope; bodies are
  JSON-only, and `ipc://` answers only JSON responses.
