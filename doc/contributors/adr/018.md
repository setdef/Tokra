# ADR 018: Every Official Desktop Plugin Is Ported, with Tauri's Formats

Supersedes the `fs`, `http`, and `store` rows of ADR 006 §3.2's decision
matrix. Its other rows stand, as ADR 011 amended them.

## Context and Problem Statement

ADR 006 §3.2 sorted Tauri's official plugins by how Tokra would treat
each. It skipped `fs` and `http`, because "Ruby has native filesystem"
and "Ruby has `Net::HTTP`", and gave `store` a Ruby format, "`YAML` or
`PStore`". ADR 008, a day later, decided that Tauri's npm packages work
unchanged against Tokra, and listed `tokra-fs` and `tokra-http` among
the plugins that serve them. The two records disagree, and no plan has
ported any of the three.

Which of Tauri's official plugins does Tokra port, and in whose formats?

## Decision Drivers

- AGENTS.md's design precedence: Tauri fidelity outranks Ruby culture.
  "Names, class structure, error messages, wire formats, and behavior
  MUST match Tauri's Rust source."
- ADR 008: a page written for Tauri runs on Tokra with Tauri's own
  JavaScript packages.
- A plugin has two callers: the app's Ruby, and the page.

## Considered Options

1. Port every official plugin that has a desktop side, with Tauri's
   commands, payloads, and file formats.
2. Skip a plugin where Ruby already does the job for the backend, and
   choose Ruby formats where Ruby has one (ADR 006 §3.2).

## Decision Outcome

Chosen: option 1, because only it keeps ADR 008's promise. Ruby's
`File` and `Net::HTTP` serve the app's Ruby code, and do nothing for a
page that calls `@tauri-apps/plugin-fs` or `@tauri-apps/plugin-http`:
without a plugin to answer, those calls fail. A `store` that wrote YAML
would not read a file Tauri's `store` wrote, and Tauri's stores JSON
values (`plugins/store/src/lib.rs` in `tauri-apps/plugins-workspace` at
`d4613ff0`).

So `fs`, `http`, and `store` are ported like any other plugin: the
plugin's commands answer the page as Tauri's do, and where the plugin
writes a file, it writes Tauri's format. How each reaches its Rust
crate, or uses Ruby instead, is ADR 011's rule, decided in each
plugin's plan. A plugin with no desktop side is out of scope with the
rest of mobile.

Confidence: high. The precedence rule and ADR 008 leave no room for the
other option; what is uncertain is each plugin's size, not whether it
belongs.

### Consequences

- Good, because a Tauri frontend's file, HTTP, and store calls work on
  Tokra unchanged.
- Good, because an app can move between Tauri and Tokra and keep its
  store files.
- Bad, because `fs` and `http` are large plugins, and both need Tauri's
  scopes, which wait on the port of its permissions.
- Bad, because Tokra carries plugins whose Ruby side adds little over
  the standard library.

### Confirmation

Each plugin's plan enumerates the upstream plugin's commands and
formats, and its tests drive them through the IPC as the page does.

## Pros and Cons of the Options

### Skip where Ruby has a counterpart, and prefer Ruby formats

- Good, because there is less to build and maintain.
- Bad, because the page-side packages for those plugins do not work,
  which breaks ADR 008.
- Bad, because a Ruby-only format is a "more Ruby-like" design that the
  precedence rule forbids.
