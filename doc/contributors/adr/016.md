# ADR 016: An App Is in Development Unless tokra build Made It

## Context and Problem Statement

A Tauri app knows whether it is in development from one flag. `tauri
build` turns on the Cargo feature `tauri/custom-protocol`
(`crates/tauri-cli/src/interface/rust.rs:483-490`), which the macro reads
into `ContextData.dev` (`crates/tauri-macros/src/context.rs:155`) and the
crate into `is_dev()` (`crates/tauri/src/lib.rs:313-316`). That flag
picks `devUrl` or `frontendDist`, which origin may invoke commands,
`devCsp` or `csp`, and whether assets are embedded.

A Ruby app has no Cargo features. Tokra's flag is `true` until this is
decided, so an app shipped today whose config names a `devUrl` trusts
its developer's localhost for IPC on its users' computers.

Where does a Tokra app's development flag come from?

## Decision Drivers

- Whoever runs the app cannot switch it (ADR 011, amended 2026-10-28;
  ADR 014 §6).
- A shipped app is not in development.
- A developer works against a dev server without editing code.
- Tauri's rule: development unless the build tool made the app.

## Considered Options

1. Development unless `tokra build` made it: `tokra build` writes a
   packaged context into the copy it ships.
2. Development by default, with packaged an opt-in in code.
3. Packaged by default, with development an opt-in in code, such as
   `Tokra.generate_context(dev: true)`.
4. An environment variable or a command-line flag.

## Decision Outcome

Chosen: option 1, because it is Tauri's rule, and neither a shipped app
nor a developer's code has to say anything.

The marker is the packaged context, `tokra.context.json`, which `tokra
build` writes beside the staged config: `dev` false, and the config as
`tokra build` merged it. `Tokra.generate_context` reads it, when it is
there, in place of the config files. It exists only in the copy `tokra
build` stages, never in the developer's checkout. Writing it into the
checkout was set aside: the checkout would turn packaged during a build,
and stay that way after a crash. [Packaging through
Fledge](../design/packaging.md), "The packaged context", and [the CLI's
design](../design/cli.md), "The dev session", specify both files.

Confidence: high that this matches Tauri's rule. A gem-distributed app
is open (below).

### Consequences

- Good, because an app shipped by `tokra build` loads `frontendDist`,
  trusts only the `tokra://` origin for IPC, and cannot be switched to
  development from outside.
- Good, because `tokra dev` sets no flag, and `--config` patches reach
  the app without an environment variable, so ADR 014 §6 holds.
- Good, because `generate_context` takes no `dev:` keyword, and
  `Tokra.is_dev` answers the context's `dev`.
- Bad, because an app shipped any other way, a hand-run `fledge build`
  included, runs in development and trusts `devUrl`'s origin, as a Tauri
  binary built without the CLI does. The README says to ship with `tokra
  build`.
- Bad, because the marker is only as tamper-resistant as the app's
  files. On macOS the code signature covers it. On Windows the signed
  setup program covers it on the way to the user, and not once it is
  installed; Linux has no signature. Whoever can edit those files can
  already change the app's Ruby code, as ADR 014 reasons.

### Confirmation

Tests run `generate_context` with and without a packaged context and a
dev session, a stale session included. `rake test:package` runs the
app `tokra build` made, which must report `dev` false.

## Pros and Cons of the Options

### Development by default, with packaged an opt-in in code

- Bad, because an app that forgets the opt-in ships in development, the
  risk this decision removes.

### Packaged by default, with development an opt-in in code

- Good, because a shipped app is safe by default, with no build tool.
- Bad, because every developer edits code to work against a dev
  server, and `tokra dev` would need the same keyword anyway.

### An environment variable or a command-line flag

- Bad, because whoever starts the app controls both.

## Question for the maintainer

**Does a gem-distributed app get the marker?** Tauri has no
distribution path for an app crate. Its flag is the Cargo feature
`tauri/custom-protocol`, which `tauri build` always turns on, and
without which Tauri's build script marks the app as development
(`crates/tauri/build.rs:252-255`). So a plain `cargo install` of a Tauri
app runs in development unless its manifest enables the feature.

Recommended: yes. `tokra build --bundles gem` takes the place of
building with the feature: it stages a copy as for Fledge, writes the
packaged context, and builds the gem there, with the gemspec loaded in
the checkout and its `files` replaced by the staged list. The gem is
packaged and the checkout is not, so one rule covers every way an app
ships. Without it, an app installed with `gem install` trusts its
developer's localhost. Agreed?
