# ADR 009: IPC Response Transport and the Unified App Path

## Status
Accepted. Section 1's choice of `postMessage` as the primary transport is
superseded by [ADR 010](010.md), which serves `ipc://` (Tauri's desktop
default) as primary and keeps `postMessage` as the fallback. The response
machinery, invoke-key handling, and unified App path recorded here still stand;
ADR 010 adds a second transport that reuses them.

## Date
2026-07-20

## Context

ADR 008 established that Tokra speaks Tauri's IPC protocol so Tauri's own npm
packages work unchanged, and it covered the *outbound* direction (event emit
scripts extracted by `rake sync:tauri`). It did not cover the *response*
direction: when Ruby resolves or rejects an `invoke`, how does the value reach
the promise the frontend is awaiting?

Wiring that exposed a second problem. The response path lives in
`Tokra::App`, but every real application — the examples and any Rack/Rails app
— reached the WebView through `Rack::Handler::Tokra.run`, which owned its own
event loop and never touched `App`. So `App` (the faithful analog of Tauri's
`App`) was exercised only by tests, and the IPC response machinery was
unreachable in practice. ADR 004 had already decided the intended shape
(`Builder` is porcelain over the `Rack::Handler::Tokra` plumbing, with
`.app(rack_app)`), but `Builder#app` was never implemented, so the second loop
persisted as a stopgap.

This ADR records both the response transport and the collapse to a single
App-owned path.

## Decision

### 1. Response transport: vendor Tauri's scripts, eval `runCallback`

The frontend's `invoke` sends one JSON message —
`{cmd, callback, error, payload, options, __TAURI_INVOKE_KEY__}`
(`ipc/protocol.rs`) — where `callback` and `error` are integer callback IDs.
`App#dispatch_ipc` parses it, dispatches the command (to the plugin store for
`plugin:`-prefixed commands, else the app `invoke_handler`), and delivers the
result by evaluating `window.__TAURI_INTERNALS__.runCallback(id, value)` in the
calling WebView — the callback ID on success, the error ID on failure. The
JavaScript is produced by `Tokra::Ipc::FormatCallback`, a port of Tauri's
`ipc/format_callback.rs`, including the 10 KiB `JSON.parse('...')` heuristic.

The `__TAURI_INTERNALS__` object the frontend needs is built by initialization
scripts. Rather than hand-write JavaScript, `rake sync:tauri` vendors Tauri's
own scripts (`init.js`, `pattern.js`, `ipc.js`, `ipc-protocol.js`, `core.js`,
`process-ipc-message-fn.js`) as ERB templates, and `App` assembles them in
Tauri's injection order (`manager/webview.rs`). This maximizes ADR 008's
guarantee: the injected side is Tauri's code verbatim.

`ipc-protocol.js` attempts a `fetch('ipc://…')` custom protocol first and, when
it is absent — as in Tokra — logs one console warning per page load and falls
back permanently to `window.ipc.postMessage`. Tokra therefore rides the
postMessage transport with no script changes. Serving the `ipc://` custom
protocol (Tauri's desktop default) is a deliberate future optimization; the
one failed fetch is the accepted cost.

### 2. Invoke key: generate, inject, verify, drop

`Tokra.generate_invoke_key` mirrors Tauri's `generate_invoke_key` (16 random
bytes, Z85-encoded via `Tokra::Z85`). The key is held by `AppManager`,
templated into the scripts, and verified on every message. A mismatch is
logged to stderr and the message is dropped without a response — exactly
Tauri's `Webview::on_message` behavior (`webview/mod.rs`).

### 3. One path: `App` owns the loop; `Builder#app` serves Rack

Per ADR 004, `App` is the single owner of the event loop, window, WebView,
script injection, and IPC dispatch. `Builder#app(rack_app)` (and
`Builder#title`/`#size`) complete the porcelain: the Rack app is served over
`tokra://` by delegating to a `Rack::Handler::Tokra` adapter instance, whose
sole job stays request/response translation (ADR 004's "plumbing"). `App`
never learns what Rack is — it holds a protocol adapter, the same way Tauri's
manager holds the asset protocol handler. `Rack::Handler::Tokra.run` collapses
to building a `Builder` and calling `run`, so there is no second event loop.

The consequence that matters: a Rack- or Rails-served WebView now receives the
IPC scripts and working `invoke` responses, which the old bespoke loop never
provided.

### 4. The synchronous responder is interim

ADR 001's target routes commands Main Ractor → Worker Ractor → proxy → eval.
Today `App` dispatches synchronously on the Main Ractor and the responder
evaluates directly. The responder is an opaque callable on `Ipc::Invoke`, so
the Worker-Ractor phase can replace its implementation without touching
handlers. Nothing in this phase may hand the WebView-capturing responder
across a Ractor boundary. The Rack app likewise runs on the Main Ractor for
now; moving it to the Worker Ractor (ADR 001/002) is future work.

### 5. Deviations from Tauri

- `postMessage` responses always evaluate `runCallback`; Tauri sends object
  and array results over a `Channel` on platforms other than macOS
  (`ipc/protocol.rs:371-388`).

  *Amended 2026-10-27 (Plan 033):* a raw `Response` body evaluates as a JSON
  number array, as Tauri's `format_result` writes it on macOS and whenever
  the client reports `customProtocolIpcBlocked`; elsewhere Tauri's Channel
  gives the page an `ArrayBuffer` (`ipc/protocol.rs:390-407`). The
  message's `options.headers` become the command's headers, checked as the
  http crate checks them, and an error is reported as a JSON error without
  serde's line and column. An `options` that is not an object, and a
  `customProtocolIpcBlocked` that is not a bool, are ignored, where serde
  fails the message (`ipc/protocol.rs:223-241`).

  *Amended 2026-10-27 (Plan 037):* the deviation is retired. Off macOS a
  successful object, array, or raw result travels over
  `Channel.from_callback_fn`, as Tauri sends it, unless the command is the
  channel-data fetch or the message reports `customProtocolIpcBlocked`
  (`ipc/protocol.rs:337-407`).
- A malformed `postMessage` is tolerated: unparseable JSON is logged to stderr,
  and a message without integer callback ids is fire-and-forget, so hand-rolled
  `window.ipc.postMessage` calls keep working. Tauri rejects both with a
  `console.error(...)` eval (`ipc/protocol.rs:422-430`).

  *Amended 2026-10-27 (Plan 032):* a message serde_json cannot read, and a
  `cmd` that is present but not a string, are now reported as Tauri reports
  them, with `console.error("JSON error: ...")` evaluated in the webview, and
  the message is parsed with serde_json's grammar (`Ipc::Json`). Tokra still
  parses the message as a whole `Value` rather than Tauri's `Message` struct:
  serde skips the struct's unknown fields with `ignore_value`, which checks
  neither surrogates nor number ranges (serde_json `de.rs:1100-1281`), so
  Tokra rejects a lone surrogate there that Tauri accepts. A non-object
  message is still logged to stderr, a missing `cmd` is still the empty
  command, and a bad `cmd`'s report lacks the line and column serde gives it.
- The event emit function and listener object have fixed names
  (`__TAURI_EMIT__`, `__TAURI_LISTENERS__`); Tauri randomizes them per app
  (`listeners.rs`).
- ADR 010 §6 adds a local-origin check to both transports until capabilities
  exist.

## Consequences

### Positive
- Frontend `invoke` promises resolve and reject; Tauri's npm packages work end
  to end, completing ADR 008 in the response direction.
- A single, faithful App-owned path (ADR 004): Rack apps, static apps, and IPC
  all flow through `App`, and every WebView is configured identically.
- The injected JavaScript is Tauri's own, extracted by the existing sync task.

### Negative
- One failed `ipc://` fetch and console warning per page load until the custom
  protocol transport lands.
- The vendored scripts are pinned to the submodule; `sync:tauri` regeneration
  is manual (the task aborts if extraction patterns stop matching).
- `Invoke#payload` is now the message's `payload` member (was the whole
  message), and `Tokra::Invoke` moved to `Tokra::Ipc::Invoke` — breaking, and
  recorded in the changelog.

### Neutral
- `Rack::Handler::Tokra` keeps its Rack-convention name and `.run` entry (so
  `rackup -s tokra` remains viable); only its implementation changed.
