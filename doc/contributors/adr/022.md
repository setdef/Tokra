# ADR 022: A Ruby Host: the Framework's Logic Is Ruby, over One-to-One Crate Bindings

## Context and Problem Statement

Tokra is a desktop application framework for Ruby: the frontend is
HTML, CSS, and JavaScript, and the backend is Ruby. Tauri, which Tokra
ports, keeps its application lifecycle, commands, state, and security
checks in Rust, over tao for windows and wry for webviews. With Ruby
4.0's Ractors and YJIT, Ruby can carry those responsibilities itself.

Where does the framework's logic live, and how much of it is Rust?

## Decision Drivers

- Rust maintenance stays small in cost and complexity.
- Ruby developers keep their logic, and the framework's, in Ruby.
- The UI stays responsive: the main thread is never blocked.
- A secure barrier stands between the webview and the system.

## Considered Options

1. A Ruby host over one-to-one crate bindings: Rust wraps the crates
   Tauri depends on and passes raw events and messages to Ruby, and
   Ruby implements the lifecycle, command routing, security checks, and
   state.
2. Tauri's model, with its logic in Rust and Ruby for the app's code
   only. (Named in the context as what Tauri does; not weighed at the
   time.)

## Decision Outcome

Chosen: option 1. Rust is a dumb pipe: it binds the crates Tauri
depends on, one to one, and holds none of Tauri's behavior, none of the
framework's state, and nothing of commands. Everything else is Ruby:
what Tauri's own crates do, Tokra does in Ruby. No reason beyond the
drivers was recorded for preferring option 1 to option 2.

The bindings live in Ferro, and Tokra is to ship no native extension
(ADR 020). Where the app's commands run, and how an app keeps a slow
one from blocking the window, is ADR 021.

The code does not yet follow this record. Tokra's extension,
`ext/tokra`, binds the windowing crates and also holds Tauri's own
behavior: an audit on 2026-11-21 found it in about a quarter of the
extension's code, with state of the framework's beside it (the web
contexts, the window labels, the pending responders)
([the Rust in Tokra](../research/2026-11-21-rust-in-tokra.md)). That
logic moves to Ruby, as the first stage of ADR 020. The audit found
nothing among it that Ruby cannot express, apart from the platform
callbacks ADR 020 names.
[The native layer's design](../design/native.md) says what the
extension holds and how it shares threads with Ruby.

Confidence: not recorded when the decision was made. Since then the
framework's IPC, commands, config, plugin system, and menus have been
ported in Ruby.

### Consequences

- Good, because logic changes happen in Ruby, and Rust compiles rarely.
- Good, because a plugin that needs no native code is pure Ruby.
- Bad, because every platform capability needs a native wrapper and a
  Ruby API over it, and a platform issue is traced through both layers.
- Bad, because installing the gems compiles Rust, which needs a Rust
  toolchain and the platform's build libraries.
- Bad, because nothing but review holds the line, and the audit of
  2026-11-21 found it crossed.

### Confirmation

Nothing automated checks it. AGENTS.md's Project section states the
rule for every contributor, that Tauri's logic belongs in Ruby and that
no more of it is added to `ext/`, and a reviewer of a change to `ext/`
checks it.

## More Information

This record restates the former ADR 001, decided on 2026-01-30. What
changed: the bindings' home is ADR 020, the former record's target of a
worker Ractor for the app's logic is replaced by ADR 021, and the
outcome now says what the audit found. The former record's two
consequences of that target, asynchronous messages between Ractors and
the memory of a second Ractor, went with it.
