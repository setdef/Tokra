# ADR 014: The App's Config and `Context`, Read When the App Starts

## Status

Accepted. Supersedes ADR 004 §2's "(or accept a config hash)". Amends
ADR 006 §6.2: the file is `tokra.conf.json`, its schema is Tauri's, and
the loader sketched there gives way to §2 and §5 below. Answers plan 049's
question 1. [Plan 054](../plan/054.md) carries it out.

## Date

2026-11-03

## Context

A Tauri app describes itself in `tauri.conf.json`: its identifier, name,
and version, the windows it opens, its security settings, its tray icon,
how it is built and bundled, and each plugin's settings. Its `main`
function hands that description to the builder through a macro:

```rust
tauri::Builder::default()
  .run(tauri::generate_context!())
  .expect("error while running tauri application");
```

`generate_context!` runs when the app compiles (vendor/tauri `9f0306fbc`,
`crates/tauri-macros/src/lib.rs:76-87`). It takes an optional path,
joins a relative one to `CARGO_MANIFEST_DIR`, defaults to
`$CARGO_MANIFEST_DIR/tauri.conf.json`, and refuses a path where no
config file exists (`crates/tauri-macros/src/context.rs:24-56`,
`:126-133`). It then calls tauri-codegen, which reads the file and the
platform's own file over it with JSON Merge Patch, merges the
`TAURI_CONFIG` environment variable over both, and deserializes the
result into `Config` (`crates/tauri-codegen/src/lib.rs:57-99`;
`crates/tauri-utils/src/config/parse.rs:41-76`, `:166-225`). Last it
writes the code that builds a `Context` (`crates/tauri-codegen/src/context.rs:135-491`):
the embedded frontend, the window, app, and tray icons decoded to RGBA,
the `PackageInfo` from the config or `Cargo.toml`, the pattern, the
resolved capabilities, and the plugins' global API scripts. Every
failure is a compile error. `Context` holds all of it
(`crates/tauri/src/lib.rs:355-369`), and `Builder::build` and
`Builder::run` take it (`crates/tauri/src/app.rs:2094`, `:2298`).

Tokra has none of this. Its `Config` is
`Data.define(:identifier, :product_name, :version)`
(`lib/tokra/config.rb:17` at `821a7e2`), built from a builder hash that no
public method fills (`lib/tokra/app.rb:172-176`), so all three are always
`nil`. The main window comes from `Builder#title` and `Builder#size`, and
the global API from `Builder#with_global_tauri`, three methods Tauri does
not have; ADR 004 invented them, and said Tokra would "load configuration
from standard locations (or accept a config hash)". ADR 006 §6 named
`tokra.conf.json` but sketched a schema of its own (`app.title`,
`app.width`). Work is stacking up behind the gap: plan 049's config tray,
plan 052's `from_config` constructors and its `app.macOSPrivateApi`
question, plan 052e-3's data directory named for the identifier, and
every plugin's configuration.

Ruby has no compile step. Whatever Tokra reads, it reads while the app
starts.

## Decision

### 1. Tokra ports `Context` and the config schema as they are

`Tokra::Context` is Tauri's `Context`, field for field where Ruby gives
the field a meaning, and `Tokra::Config` is Tauri's `Config`, with every
sub-structure Tauri defines. Plan 054 arrives at that in steps: its
first phase types everything but the bundle's inner structs and inline
capabilities, which it keeps as JSON; its fourth phase types the bundle,
and the capabilities plan types the capabilities. Tokra invents no Hash form and no DSL for
configuration. A Ruby DSL would read well, and it would be a "more
Ruby-like" API, which AGENTS.md precedence 2 rules out: Tauri's names,
structure, and behavior come first. That supersedes ADR 004's "or accept
a config hash". `Builder#title`, `#size`, and `#with_global_tauri` go,
since their settings are `app.windows[].title`, `.width`, `.height`, and
`app.withGlobalTauri` in the file.

### 2. `generate_context!` is translated into a loader that runs at start

The macro has no Ruby meaning: it exists because Rust must know at
compile time what the binary embeds. AGENTS.md precedence 1 translates
it into a method, `Tokra.generate_context(path = nil)`, that reads the
file when it is called and returns a `Tokra::Context` for `Builder#build`
or `Builder#run`.

| Tauri, at compile time | Tokra, at start |
|---|---|
| `tauri::generate_context!()` | `Tokra.generate_context` |
| `tauri::generate_context!("path")` | `Tokra.generate_context("path")` |
| A relative path joins `CARGO_MANIFEST_DIR` | A relative path joins the entry script's directory (§5) |
| A compile error | An exception, raised before any window exists, with the same message |
| Icons and assets embedded with `include_bytes!` | Read and decoded when the method runs |
| `TAURI_CONFIG` merged over the file | Not read (§6) |
| `root` argument (the `tauri` crate path) | None: Ruby has no crate paths |
| `capabilities`, `assets`, `test` arguments | Each with the plan that ports what it feeds (plan 054, inventory) |

Tokra keeps the split between the three crates the macro spans, so each
part answers to one source: `Tokra.generate_context` is the macro,
`Tokra::Codegen` is tauri-codegen's `get_config` and `context_codegen`,
and `Tokra::Utils::Config` is tauri-utils' schema and its `parse`
module.

### 3. File names follow Tokra's renames of Tauri's brand

Tokra already renames Tauri's brand strings where they name the
framework: the `tokra://` scheme, the "Tokra" default title, the
"Tokra Window" class on Windows. The config files follow, as ADR 006 §6
began:

| Tauri | Tokra |
|---|---|
| `tauri.conf.json` | `tokra.conf.json` |
| `tauri.conf.json5` | `tokra.conf.json5` |
| `Tauri.toml` | `Tokra.toml` |
| `tauri.<platform>.conf.json`, `.json5` | `tokra.<platform>.conf.json`, `.json5` |
| `Tauri.<platform>.toml` | `Tokra.<platform>.toml` |

`<platform>` is `macos`, `windows`, or `linux`, Tauri's desktop names
(`parse.rs:51-75`). The platform file is merged over the main one as
Tauri merges it, with JSON Merge Patch (RFC 7396, json-patch 3.0.1's
`merge`): an object merges key by key, `null` deletes a key, and
anything else, an array included, replaces what was there
(`parse.rs:180-188`). Error messages that name the framework's config
file rename it the same way: Tauri's "unable to parse JSON Tauri config
file at {path} because {error}" reads "unable to parse JSON Tokra config
file at {path} because {error}", and "`tauri.conf.json > version` must
be a semver string" names `tokra.conf.json`. Every other word stays
Tauri's.

### 4. The schema is Tauri's, unchanged

Every key, alias, default, and refusal is Tauri's: camelCase keys with
their kebab-case aliases, `deny_unknown_fields` on every struct that has
it, `identifier` required, `app.windows` defaulting to none, and serde's
error texts for a missing field, an unknown one, or a value of the wrong
type. Every refusal holds once plan 054's fourth phase and the
capabilities plan have typed the parts its first phase keeps as JSON.
So Tauri's configuration reference and its JSON schema
(`crates/tauri-schema-generator/schemas/config.schema.json`) describe a
Tokra config too, and `"$schema"` may name Tauri's. Fields that drive
something Tokra does not have yet, such as the bundler's, are read and
checked but not acted on; plan 054's inventory says which, and why.

The window config's default title, Tauri's "Tauri App"
(`config.rs:2061-2063`, and the runtime's own default,
`tauri-runtime-wry/src/lib.rs:827`), is renamed by §3's rule to
"Tokra App". Tokra's runtime default today is "Tokra"
(`lib/tokra/window_builder.rb:27`), an earlier rename that dropped the
second word; plan 054 makes both "Tokra App".

### 5. The default path is anchored at the entry script's directory

`CARGO_MANIFEST_DIR` is the directory holding the app's `Cargo.toml`,
which in a Tauri app is `src-tauri/`, beside `tauri.conf.json`. A Ruby
app has no manifest; the file that plays its part is the script Ruby
was started with, so the anchor is that script's directory. Tokra
records it when `tokra` is required, so a later `Dir.chdir` does not
move it: `File.dirname(File.realpath($PROGRAM_NAME))` when
`$PROGRAM_NAME` names a file, resolving a symlinked launcher to the
script beside the config, and the working directory otherwise (as for
`ruby -e` or IRB).

With no argument the loader reads `<anchor>/tokra.conf.json` (or
`.json5`, or `Tokra.toml`, per §3). If none exists it raises Tauri's
`Io` error, "unable to read Tokra config file at {path} because entity
not found", since the macro checks only a path it was given
(`tauri-macros/src/context.rs:126-133`; `parse.rs:327-333`). With an
argument it works as the macro's argument does: a relative path joins
the anchor, an absolute path is taken as given, and a path where no
supported file exists raises the macro's "no file at path {path}
exists, expected tokra config file". That check looks for the
supported names in the path's directory, the platform names if the path
names a platform file and the main names otherwise
(`parse.rs:206-225`). Once it passes, only the directory matters: the
loader reads that directory's `tokra.conf.json` and its platform file
(`tauri-codegen/src/lib.rs:57-81`).

`Rack::Handler::Tokra.run` anchors at `config.ru`'s directory when
rackup hands it the `:config` option, which rackup 2.3.1 sets to the
file's absolute path (`lib/rackup/server.rb:341`, `:404`).

### 6. `TAURI_CONFIG` and `--config` belong to the CLI

`tauri dev --config` and `tauri build --config` merge their patches
into `TAURI_CONFIG` (`crates/tauri-cli/src/helpers/config.rs:176-184`),
and codegen reads that variable while it compiles
(`tauri-codegen/src/lib.rs:83-87`). It shapes the binary the developer
ships; the person who runs the binary cannot change it. Tokra reads its
config when the app starts, so reading a variable then would hand the
app's configuration, its security settings included, to whoever starts
the process. ADR 011's amendment of 2026-10-28 keeps that kind of switch
out of the environment. `Tokra.generate_context` reads no environment
variable. The `--config` merge waits for a Tokra CLI.

### 7. JSON5 and TOML are built in

Tauri gates JSON5 and TOML behind the `config-json5` and `config-toml`
Cargo features (`parse.rs:21-28`). They add behavior and relax no
default, so under ADR 011 Tokra builds both in: it reads
`tokra.conf.json5` and `Tokra.toml`, and it tries a `tokra.conf.json`
as JSON5 first, reporting serde_json's error if both fail, as Tauri
does with the feature on (`parse.rs:281-302`). Plan 054 decides the
parsers and records what each reproduces of Tauri's json5 0.4.1 and
toml 0.9.10.

### 8. The Ruby surface

```ruby
# <entry script's directory>/tokra.conf.json, with tokra.macos.conf.json
# (on macOS) merged over it.
context = Tokra.generate_context

# A relative path joins the entry script's directory; an absolute one is
# taken as given.
context = Tokra.generate_context("src-tokra/tokra.conf.json")

Tokra::Builder.default
  .setup { |app| puts app.config.identifier }
  .run(context)

app = Tokra::Builder.default.build(context)
app.run { |handle, event| }

context.config           #=> Tokra::Config (Tokra::Utils::Config::Config)
context.config.plugins["log"]  #=> {"level" => "info"}: String keys, JSON values
context.config = context.config.with(identifier: "com.example.beta")
context.package_info     #=> Tokra::PackageInfo: name, version, authors, description, crate_name
context.pattern          #=> Tokra::Pattern::Brownfield

app.config.app.windows   #=> [Tokra::Utils::Config::WindowConfig, ...]
app.package_info.version #=> "1.2.0"
Tokra::WebviewWindowBuilder.from_config(app, app.config.app.windows[0]).build
```
<!-- SPDX-SnippetEnd -->

`config.plugins` holds each plugin's JSON as Tauri's `JsonValue` holds
it, with String keys. ADR 006 §6.2's sketch symbolized them; that
sketch is superseded. §6.3 and §6.4 stand: a plugin still takes a
config Hash in its constructor and may be given one in code, until the
plan that ports `Builder#plugin` hands each plugin its slice of
`config.plugins` as Tauri's builder does.

`Context#config=` and `#package_info=` translate Tauri's `config_mut`
and `package_info_mut`: Ruby has no mutable borrow, and the values are
frozen, so a caller builds a changed copy with `Data#with` and stores
it. Plan 054 adds the icon accessors (`default_window_icon`,
`set_default_window_icon`, `tray_icon`, `set_tray_icon`) with the phase
that decodes icons.

## Consequences

- An app needs a config file, and the file needs an `identifier`, as a
  Tauri app does. A Tokra app without one fails at
  `Tokra.generate_context` with Tauri's words. The examples gain config
  files.
- An app opens the windows its config lists, and none when it lists
  none, as Tauri's does. Today every Tokra app opens `main`.
- `Builder#build` and `Builder#run` take a `Context`, and the three
  builder methods ADR 004 invented go. `Rack::Handler::Tokra.run` takes
  a `context:` and loses `title:`, `width:`, and `height:`, which it
  has shipped since v0.0.1.pre.2.
- Tauri's configuration reference applies to Tokra word for word, but
  for the brand renames in §3.
- Errors a Tauri developer meets at compile time, a Tokra developer
  meets at start, with the same message. A config mistake no longer
  fails a build; it fails the first launch.
- Reading and decoding at start costs time on every launch that
  compile-time embedding does not. For a config file and a few icons
  this is milliseconds; embedded frontend assets are a later plan's
  concern.
- Whoever can edit the files can change the config. That is no new
  exposure: they sit beside the app's Ruby source, which that person
  can edit too. No environment variable reaches the config (§6).
- The anchor is the entry script, not the file that calls
  `generate_context`. For an app the two agree. A library that called
  it with no argument would read the app's config, where a Rust library
  crate calling the macro reads its own; nothing in Tokra does that.
  Under a launcher that is not a symlink, such as a binstub in `bin/`,
  the entry script is the launcher, so pass a path; under rackup the
  Rack handler anchors at `config.ru` (§5).
- The development and packaged configs differ in Tauri by a Cargo
  feature the CLI sets (`custom-protocol`, which codegen reads as
  `ContextData.dev`; `tauri-macros/src/context.rs:155`;
  `tauri::is_dev`, `crates/tauri/src/lib.rs:313-316`). Tokra has no CLI
  and no bundler. How a Tokra app tells the two apart is plan 054's
  question 1, and plan 054 is written so either answer fits.
