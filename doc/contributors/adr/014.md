# ADR 014: The App's Config and Context Are Tauri's, Read When the App Starts

## Context and Problem Statement

A Tauri app describes itself in `tauri.conf.json`: its identifier, name,
and version, the windows it opens, its security settings, its tray icon,
how it is bundled, and each plugin's settings. Its `main` hands that
description to the builder through `generate_context!`, a macro that
reads the file when the app compiles and embeds a `Context` built from
it; every failure is a compile error.

Ruby has no compile step. Tokra's config was three always-`nil` fields,
and its windows and global API came from builder methods Tauri does not
have. Plugin configuration, the config tray, window constructors, and
the data directory were all waiting on the answer. Where does a Tokra
app's configuration come from, in what form, and when is it read?

## Decision Drivers

- Tauri fidelity (AGENTS.md precedence 2): Tauri's names, structure,
  and behavior, so Tauri's configuration reference describes a Tokra
  app.
- Ruby the language (precedence 1): a macro that exists because Rust
  must know at compile time what it embeds has no Ruby meaning.
- Whoever runs a shipped app must not be able to change its
  configuration, its security settings included.

## Considered Options

1. Tauri's `Config` and `Context`, ported as they are, and a
   `Tokra.generate_context` that reads the config file when the app
   starts.
2. A Ruby DSL for configuration.
3. A config Hash handed to the builder, which Tokra's first builder
   design had said it would accept.

## Decision Outcome

Chosen: option 1, because only it keeps Tauri's schema, file, and
errors, and it translates the macro into the one thing Ruby can do,
reading when the app starts. A DSL or a Hash would read well, and each
is a "more Ruby-like" API that precedence 2 rules out.

`Tokra.generate_context(path = nil)` reads `tokra.conf.json`, Tauri's
file under Tokra's name, with Tauri's schema, and returns a
`Tokra::Context` for `Builder#build` and `Builder#run`. Its errors are
the macro's, raised before any window exists. It reads no environment
variable: Tauri's `TAURI_CONFIG` shapes the binary at compile time,
where reading one at start would hand the configuration to whoever
starts the process. The builder methods that duplicated the config
(`#title`, `#size`, `#with_global_tauri`) are gone.
[The config's design](../design/config.md) holds the loader's table,
the file names, the schema rules, where the loader looks, and the
formats.

Confidence: high that this matches Tauri. The cost of reading at every
start is assumed small for a config and a few icons; it has not been
measured.

### Consequences

- Good, because Tauri's configuration reference applies to Tokra word
  for word, but for the brand renames.
- Good, because errors a Tauri developer meets at compile time, a Tokra
  developer meets at start, with the same message.
- Bad, because a config mistake no longer fails a build; it fails the
  first launch.
- Bad, because every app needs a config file with an `identifier`, and
  every launch reads and decodes it, which compile-time embedding does
  not.
- Bad, because whoever can edit the files can change the config. That
  is no new exposure: the files sit beside the app's Ruby source, which
  that person can edit too.
- Bad, because the anchor for a relative path is the entry script, not
  the caller, so a launcher that is not a symlink, such as a binstub,
  has to pass a path.

### Confirmation

`test/test_generate_context.rb` checks where the loader looks, what it
checks, and what it raises, that no environment variable reaches it,
and the anchor. `test/utils/config/` checks the schema against the answers
Tauri's own crates give for each fixture (`rake config:fixtures`).
