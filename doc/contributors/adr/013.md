# ADR 013: The Windowing Stack Stays in Tokra, and Windows Name Their Handles

## Status

Accepted. Settles the windowing question ADR 011 §1 deferred, and amends
plan 023's decision 3.

## Date

2026-10-26

## Context

ADR 011 moved standalone crate bindings to Ferro and left tao and wry in
Tokra's extension "until a later ADR settles where the windowing stack
lives". It named three candidates: keep the stack in Tokra; move it into
one Ferro gem behind a single native library; or bind wry and muda in
Ferro and hand them Tokra's window as a raw handle.

The question came back from the other side. `tokra-dialog` (plan 023)
shows rfd's dialogs through `ferro-rfd`, and Tauri parents each dialog to
the calling window: `set_parent(&window)` takes anything that is
raw-window-handle's `HasWindowHandle + HasDisplayHandle`
(plugins-workspace `d4613ff0`, `plugins/dialog/src/lib.rs:287-302`,
`460-478`; `commands.rs:129-132`, `229-232`, `281-284`). Tokra's windows
named no handle, so plan 023 shipped every dialog without a parent.

What Tauri does:

- `Window` implements `HasWindowHandle` by asking its dispatcher
  (`crates/tauri/src/window/mod.rs:943-949`). The dispatcher sends
  `WindowMessage::RawWindowHandle` through `getter!`, so the handle is read
  on the main thread whichever thread asks (tauri-runtime-wry
  `src/lib.rs:196-210`, `234-254`, `1852-1856`, `3320-3326`), and any
  failure of the getter becomes `HandleError::Unavailable`
  (`lib.rs:2012-2018`). A closed window has `inner: None`, so the message
  matches nothing, the channel drops, and the caller gets that same error
  (`lib.rs:3244-3253`, `4293-4299`).
- `Window`, `WebviewWindow`, `App`, and `AppHandle` implement
  `HasDisplayHandle` through the runtime handle, which reads the event
  loop's target directly, on the calling thread (`window/mod.rs:951-957`,
  `webview/webview_window.rs:1410-1426`, `app.rs:2353-2367`;
  tauri-runtime `src/lib.rs:295-298`, `750-753`; tauri-runtime-wry
  `lib.rs:2656-2660`).

What tao 0.34.5, the version Tokra and Tauri both lock, answers
(`src/window.rs:1422-1437`, `src/event_loop.rs:344-350`):

| Platform | Window handle | Display handle |
|---|---|---|
| Windows | `Win32 { hwnd, hinstance }` (`platform_impl/windows/window.rs:438-457`) | `Windows`, empty |
| macOS | `AppKit { ns_view }`, the content view (`macos/window.rs:1494-1510`, `1561-1563`) | `AppKit`, empty |
| Linux, X11 | `Xlib { window, visual_id: 0 }`, GDK's XID | `Xlib { display, screen }` from a new `XOpenDisplay` (`linux/window.rs:948-999`) |
| Linux, Wayland | `Wayland { surface }` | `Wayland { display }`, GDK's |

tao never answers Xcb, and an X11 window lacks a GDK window only before it
is realized, when tao answers `Unavailable`.

Two problems in that table matter here. tao's X11 display handle opens a
connection to the X server on every call and never closes it. And when
`XOpenDisplay` fails, which it does once the server refuses another client,
tao 0.34.5 passes the null pointer to `XDefaultScreen`, which faults inside
libX11 before the pointer even reaches `NonNull::new_unchecked`: undefined
behavior either way. tao 0.37.2's `Window::display_handle` checks the
pointer first (`linux/window.rs:984-992`).
Tauri copes with neither: each `set_parent` on Linux reads the display
handle, so each save or message dialog leaks a connection.

ferro-rfd (0.1.0.pre.2, plan 002 decision 6 in Ferro) takes a parent as any
object answering `window_handle` and `display_handle` with its own `Data`
values, and binds only the kinds rfd never follows as a pointer: Win32,
whose `HWND` Windows validates, and Xlib and Xcb, whose window ID rfd's
portal backend formats as text (rfd 0.17.2
`xdg_desktop_portal/window_identifier/mod.rs:23-43`, `70-83`). It checks
each value's class (`lib/ferro/rfd/handles.rb`, `parent_pair`), so a value
from another gem raises `TypeError`. It binds no AppKit or Wayland handle:
rfd retains the `NSView` and asks it for its window (`backend/macos/utils.rs:34-45`),
and wayland-backend reads the surface and display
(`window_identifier/wayland.rs:25-44`). An Integer from Ruby could point
anywhere.

## Decision

### 1. tao and wry stay in Tokra's extension

Of ADR 011's three candidates, Tokra keeps the stack. wry builds its
webview from the tao window inside Tokra's own Rust, so no handle crosses
a gem boundary and nothing trusts an Integer. Moving both into one Ferro gem
would give the same native library another name and add a release step to
every windowing change. Binding wry or muda in Ferro and passing them
Tokra's window as an Integer is the unsound case ferro-rfd refuses: both
follow the `NSView` pointer, and a stale or forged one crashes the process.
muda and tray-icon, when Tokra ports menus and trays, join this extension,
keeping ADR 011's rule of one native home per stateful crate.

A raw handle crosses into another gem only when that gem's crate never
dereferences it, which is the rule ferro-rfd already follows.

### 2. Windows answer Tauri's handle traits

`Tokra::Window#window_handle` and `#display_handle`,
`Tokra::AppHandle#display_handle`, and `Tokra::App#display_handle` port the
four impls. Tokra has no `WebviewWindow`, so its impl has nothing to land
on yet. Each returns a raw-window-handle value or raises its error, as
ADR 011's table maps `Result`.

The values live in `Tokra::RawWindowHandle`, one `Data` class per struct tao
can answer with: `Win32WindowHandle(hwnd, hinstance)`,
`WindowsDisplayHandle`, `AppKitWindowHandle(ns_view)`, `AppKitDisplayHandle`,
`XlibWindowHandle(window, visual_id)`, `XlibDisplayHandle(display, screen)`,
`WaylandWindowHandle(surface)`, and `WaylandDisplayHandle(display)`, with
raw-window-handle 0.6.2's field names (`src/windows.rs`, `src/appkit.rs`,
`src/unix.rs`). The crate's `RawWindowHandle` and `RawDisplayHandle` enums
wrap one struct per variant; in Ruby the struct is the variant. The
borrowed `WindowHandle<'a>` and its `as_raw` drop with the lifetime they
carry. `HandleError` is a `StandardError` with a subclass per variant,
`NotSupported` and `Unavailable`, whose messages are the crate's Display
text (`src/lib.rs:346-388`).

These are the shapes ferro-rfd's handles have, but not its classes, so
ferro-rfd's `set_parent` does not take a `Tokra::Window` as it stands.
Tokra cannot return ferro-rfd's classes without its core depending on a
dialog gem. `tokra-dialog` copies each kind ferro-rfd binds into
ferro-rfd's value (decision 6). A shared home for the types is a Ferro
follow-up (Consequences).

*Amended 2026-10-27 (Plan 035):* `AppKitWindowHandle` also carries
`window_number`, the window's `-[NSWindow windowNumber]`, read natively on
the main thread beside `ns_view`. raw-window-handle has no such field
(`src/appkit.rs:86-91`); it is the translation the AppKit follow-up below
named, tier 1, because a number names a window AppKit can look up, where
an address from Ruby can point anywhere. `ns_view` keeps the crate's
meaning. ferro-rfd 0.1.0.pre.3 reads handles by kind and field name, so it
takes Tokra's values as they are, and nothing is copied.

### 3. Every handle is read on the main thread

Tauri reads the window handle on the main thread through its dispatcher,
and so does Tokra, through `RuntimeContext#getter`. A getter that cannot
reach the loop, or whose answer never comes, raises
`HandleError::Unavailable`, as Tauri maps its getter's failure.

Tauri reads the display handle on the calling thread. Tokra cannot: its
event loop is moved into `run_return` while the app runs, and its native
objects answer only the main thread (ADR 012). So `AppHandle#display_handle`
asks the app's first window for tao's `Window: HasDisplayHandle`, through
the same getter. tao builds both answers the same way, from the same
default display. Deviation, tier 1: what Ruby's GVL and Tokra's ownership
rules allow. Before `App#run` builds the window, as in the setup hook,
there is nothing to ask, and the call raises `Unavailable`; Tauri's setup
hook runs after its event loop exists.

A Tokra window closes only when its event loop ends: a close request ends
the loop (ADR 012). After that, a call from another thread raises
`Unavailable`, matching what Tauri raises for a closed window. On the main
thread, in a `RunEvent::Exit` handler or an `at_exit` hook, the call still
runs, and the window it names still exists until Ruby frees it.

### 4. One X11 display for the life of the process

Tokra asks tao for the X11 display handle once and answers every later
call with that first display, which stays open as long as the process
runs. Without it, a page that opens dialogs in a loop leaks one X
connection each time until the server refuses one, and then reaches tao's
undefined behavior. The value keeps its meaning, the default display and
its screen, and the connection behind it stays valid. Deviation from
Tauri, which leaks; it avoids undefined behavior reachable from the
frontend. Wayland's display is GDK's own, so it needs no cache. The cache
is set only from a successful answer.

The cache makes every consumer share one Xlib connection, where tao gave
each its own. Xlib is not thread-safe unless the process calls
`XInitThreads` first, and nothing in Tokra does, so sharing is sound only
under decision 5's rule: use the display on the main thread.

### 5. A handle is safe to read and unsafe to use

The native layer copies each field out of tao's answer: a pointer becomes
its address, an ID its number. Nothing reads through a pointer, so
exposing the value is sound, and the native code needs no `unsafe`.

The danger is a consumer that turns the Integer back into a pointer, such
as Fiddle or another gem's Rust. raw-window-handle promises a borrowed
handle's pointers only for the borrow's lifetime
(`src/borrowed.rs:200-257`), and Ruby has no lifetime to hold it to.
`RawWindowHandle`'s RDoc says so: use a handle on the main thread, while
the window is open, with a library that says it takes one. An XID or
`HWND` that outlives its window names nothing, or a later window; an
`NSView` or `wl_surface` address that outlives it points at freed memory.

### 6. Dialogs take the calling window as parent where ferro-rfd can

`tokra-dialog`'s builders take a `Tokra::Window` (or any object with the
two methods) in `set_parent` and `parent`. They keep the parent only when
both handles answer, raising nothing when either raises `HandleError`, and
leave an earlier parent in place otherwise, as Tauri's `if let (Ok, Ok)`
does. Win32 and Xlib handles become ferro-rfd's values; AppKit and Wayland
handles are no parent. The commands pass the calling window as Tauri's do:
save, message, ask, and confirm everywhere, and open only on Windows and
macOS (`commands.rs:129-132`).

*Amended 2026-10-27 (Plan 035):* ferro-rfd 0.1.0.pre.3 binds
`AppKitWindowHandle` by window number and reads handles by kind, so
`tokra-dialog` passes Tokra's handles through unchanged and parents
dialogs on macOS as well; on macOS each is a sheet on the window. Only a
Wayland handle is still no parent, which the rest of this section
describes.

So the dialog has its parent on Windows, and on X11 rfd names it to the
desktop portal as `x11:` and the window ID in hex. rfd's zenity fallback
takes no parent (`backend/linux/zenity.rs:40-44`), and neither do its Linux
message dialogs. On macOS and Wayland the dialog stays parentless:
deviation, tier 1, since ferro-rfd cannot take those handles soundly. File
dialogs on macOS still attach to the app's main window as sheets
(`backend/macos/modal_future.rs:71-75`); message dialogs there remain system
alerts.

### Alternatives rejected

- **Bind AppKit in ferro-rfd from the Integer.** rfd would retain whatever
  the address points at. One wrong value ends the process.
- **Return ferro-rfd's classes from Tokra.** Tokra's core would depend on a
  dialog gem to describe its own windows.
- **Duck-type the handle in ferro-rfd.** ferro-rfd checks classes on purpose,
  standing in for Rust's trait bound; loosening it is Ferro's call.
- **Call tao for every X11 display handle, as Tauri does.** Fidelity to a
  leak that ends in undefined behavior.
- **Answer the display handle from the event loop.** The loop lives inside
  `run_return` while the app runs; borrowing it from a callback would need
  the loop to hand out its target, which tao gives only to its own closure.

## Consequences

- Libraries can parent to, draw into, or inspect a Tokra window, on the
  main thread, while it lives.
- On Windows a dialog keeps the window from taking input until it closes,
  as in Tauri. On X11 the portal can place it over the window.
- An app on X11 holds one extra X connection once anything asks for the
  display handle, and every library that asks shares it. Xlib calls on it
  belong on the main thread, since Xlib without `XInitThreads` is not
  thread-safe.
- Ferro follow-ups, recorded here because ferro-rfd is not Tokra's to
  change:
  - A shared home for raw-window-handle's types, so a `Tokra::Window` is a
    ferro-rfd parent with no copying: a `ferro-raw-window-handle` gem of
    plain `Data` classes that ferro-rfd and Tokra both use, or ferro-rfd
    reading the fields of any value named for a kind it binds.
  - A sound AppKit parent. rfd needs an `NSView` it can retain; an Integer
    cannot prove one. A handle that names the window by its
    `windowNumber` can: AppKit looks it up with
    `-[NSApplication windowWithWindowNumber:]`, which answers `nil` for a
    number that names no window of this app, and the binding takes the
    window's `contentView` from the live window, on the main thread. rfd
    has no such entry point, so the binding would build the `NSView`
    handle itself from the looked-up window. Tokra would then add the
    window number to `AppKitWindowHandle`, or a handle of its own for it.
    *Done 2026-10-27 (Plan 035):* ferro-rfd 0.1.0.pre.3 binds it this
    way, and reads any value named for a kind it binds, which also
    settles the shared-home follow-up above.
  - A sound Wayland parent. The portal takes an exported `xdg-foreign`
    handle as text (`wayland:<handle>`), which rfd builds from the raw
    surface. A binding that takes the exported string, which GDK can make
    (`gdk_wayland_window_export_handle`), never follows a pointer.
- When Tokra moves to tao 0.37 or later, the X11 null check is tao's, and
  decision 4 remains only for the leak.
