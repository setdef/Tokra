# ADR 015: A tokra-cli Gem Ports tauri-cli, and tokra build Packages Through Fledge

## Context and Problem Statement

A Tauri developer works through tauri-cli. `tauri dev` runs the
frontend's dev server and the app. `tauri build` runs the build hooks,
compiles the app, and bundles it into installers with tauri-bundler.
Tokra has neither command, so a Tokra app runs only from its sources,
and nobody without Ruby can install one.

Fledge, a separate project by the same maintainer, packages Ruby
programs for people who have no Ruby: a Ruby runtime, the app's locked
gems, and each platform's installers. Its interface is its command,
`fledge build`, and the `fledge.yml` it reads, which refuses any key it
does not know (Fledge ADR 029). `fledge.yml` names things in Fledge's
own words, for no framework in particular. Tauri's `bundle` section has
close to a hundred keys.

How does a Tokra developer run an app in development, and ship it, as
tauri-cli lets a Tauri developer do?

## Decision Drivers

- Tauri fidelity: the commands, flags, hooks, messages, and what a
  bundle carries match tauri-cli and tauri-bundler.
- A Ruby app has no binary and no Cargo features, and it ships with a
  Ruby runtime.
- Nothing the developer does not ship reaches the user: no dev server,
  file watcher, frontend sources, or tests.
- A config's bundle values are there for a reason; none is dropped
  without a word.
- Tokra relies only on what Fledge promises: its command, `fledge.yml`,
  exit statuses, and standard output.

## Considered Options

1. A `tokra-cli` gem whose `tokra build` stages what Tauri's bundle
   carries, writes `fledge.yml`, and runs `fledge build`.
2. A `tokra-cli` gem that ports tauri-bundler too.
3. A `tokra-cli` gem that calls Fledge's Ruby classes in its own process.
4. A `tokra` executable in the `tokra` gem.

## Decision Outcome

Chosen: option 1, because it ports tauri-cli as a package of its own,
which an app keeps in its `development` group with the dev server and
the file watcher, and because Fledge already does the packaging, with
the Ruby runtime that tauri-bundler has no notion of.

`tokra dev` and `tokra build` come first; tauri-cli's other commands
wait for plans of their own. Two rules hold for `tokra build`:

- **It ships what a Tauri bundle carries, and no more.** It stages the
  app's files, the frontend's assets, `bundle.resources`,
  `bundle.externalBin`, and the icons into a copy, at Tauri's relative
  paths, and runs Fledge there.
- **It drops no `bundle` key.** Each key maps onto Fledge, or
  `tokra build` refuses it, naming the key and what Fledge lacks. A key
  Tauri reads only for an installer this build does not produce, or one
  left at Tauri's default, is not refused, but for the three defaults
  below.

[The CLI's design](../design/cli.md) specifies the commands, and
[packaging through Fledge](../design/packaging.md) specifies what
`tokra build` hands Fledge, key by key, and how an app tells development from packaged.

Confidence: medium. Fledge builds windowed apps with native and Rust
gems on macOS, Linux, and Windows, but no Tokra app has gone through it,
and many `bundle` keys wait for Fledge releases after its 1.0.

### Consequences

- Good, because a Tauri developer's commands, flags, hooks, and hook
  variables carry over, and frontend tooling written for Tauri reads
  `TAURI_ENV_*` unchanged.
- Good, because the app ships with its own Ruby, and its user needs none.
- Good, because a shipped app carries what a Tauri bundle carries, so
  frontend sources, tests, and tooling stay home without an exclusion
  list. Without a gemspec, the config folder ships whole.
- Good, because a Tauri config builds unchanged when every key it sets
  maps, and one that sets another key fails, naming it.
- Bad, because many keys are refused for now. Fledge has shipped the
  description, homepage, license text, `.deb` changelog, file
  associations, macOS build number, Linux icon sizes, and a Windows
  signing command. It plans the category, `infoPlist`, the `.deb`
  control fields, the setup program's look, downgrade refusal, and
  WebView2 for its 1.1.0, after a 1.0 that waits for Ruby 4.1.0. The RPM,
  the timestamp server, and `.deb` maintainer scripts come later, and the
  MSI, per-machine installs, the Start menu folder, and disk image
  layout have no date. Some keys never map: `nsis.template`,
  `installerHooks`, `desktopTemplate`, extra files at system paths,
  macOS frameworks, a second bundle name, and `hardenedRuntime: false`.
- Bad, because Tokra follows a 0.x dependency. Each Fledge minor may
  change its command or `fledge.yml`, so each one is a Tokra change. A
  gem cannot depend on a git source, and Fledge is not on RubyGems.org
  before its 1.0, so `tokra-cli` checks Fledge's version when it runs.
- Bad, because Fledge decides the app's Ruby: the app gets the runtime of
  the Ruby minor that runs `tokra build`. Fledge 0.12 and later need Ruby
  4.1; Tokra supports 4.0.1 and later.
- Bad, because the dev tools ship unless `tokra build` keeps them out.
  Fledge's trunk ships the `development` group unless Bundler's
  `without` names it, so `tokra build` names it.
- Bad, because each build copies the project, which costs disk and
  time, and a path gem outside the project fails there, as Fledge
  refuses one already.
- Bad, because `tokra build` downloads Microsoft's WebView2 installers at
  build time for a Windows installer that needs one, as Tauri's bundler
  does.
- Neutral, because Tokra's releases gain a seventh gem, after `tokra`.

### Confirmation

Core tests cover each command's flags, hooks through a real shell, the
staging tree file by file, and every `bundle` key's path with its
refusal message, checking `fledge.yml` against the pinned Fledge's
schema. A `rake test:package` task, outside the default gate, runs the
real `tokra build` with the pinned Fledge in CI on Linux, macOS, and
Windows, and runs the built app. A review of each Fledge minor before
the pin moves keeps the key table true.

## Pros and Cons of the Options

### A tokra-cli that ports tauri-bundler

- Good, because no key would wait on another project. (Noted
  2026-11-13; not weighed at the time.)
- Bad, because tauri-bundler bundles a compiled binary, and knows
  nothing of shipping a Ruby runtime and gems, which Fledge does.

### A tokra-cli that calls Fledge's Ruby classes

- Good, because it saves a process and a Ruby start. (Noted 2026-11-13;
  not weighed at the time.)
- Bad, because Fledge's classes are not its interface (Fledge ADR 029),
  and may change in any release.

### A tokra executable in the tokra gem

- Good, because there is one gem fewer to release. (Noted 2026-11-13;
  not weighed at the time.)
- Bad, because every app would ship the dev server and the file
  watcher, and tauri-cli is a crate of its own.

## More Information

Each rule in the outcome set an alternative aside:

- Warning on, or ignoring, a key Fledge lacks. A packager that drops a
  setting without failing ships an app its developer did not ask for.
- Copying the whole project less an exclusion list, or a
  `.tokraignore`. Tauri ships what its bundle names, not what a
  developer forgot to exclude.
- `TOKRA_ENV_*` for the hook variables. Frontend tooling written for
  Tauri reads `TAURI_ENV_*`, a contract [the config's design](../design/config.md) keeps.

Fledge answered Tokra's requests key by key on 2026-11-05
([bundle keys against Fledge](../research/2026-11-05-bundle-keys-vs-fledge.md),
[app metadata and installer needs](../research/2026-11-05-fledge-app-metadata-and-installer-needs.md),
[Fledge's answer](../research/2026-11-05-fledge-answer-to-requests.md)).
Fledge's rule: plain keys for what every packager states, and three
seams for the rest, a fragment in each system's own format, one NSIS
include, and the file-association key. [Packaging through
Fledge](../design/packaging.md), "What Fledge has", holds each
capability's state on Fledge's trunk. Revisit this ADR when Fledge
reaches 1.0, which puts it on RubyGems.org, and when it ships 1.1.0.

Related: ADR 009 and ADR 010 (Tauri's frontend names), ADR 011 (no
safety switch in the environment), ADR 014 (the config, its renames, and
`--config`).

## Defaults That Ask for More Than Fledge Has

Three of Tauri's defaults are not inert. `targets: "all"` includes an
MSI on Windows and an RPM on Linux, which Fledge defers past its 1.0. A
file association's `rank` defaults to `Default`, and Fledge never makes
an app a file's default (Fledge ADR 052). `webviewInstallMode` defaults
to `downloadBootstrapper`, and Fledge's NSIS include, the only way to
install WebView2, is planned for its 1.1.0.

Decided 2026-11-13 by the orchestrating agent session, from the second
rule above: a default is a value like any other, so the build gives
Tauri's result or refuses, and never gives a different result without
a word.

- `targets: "all"` builds every installer `tokra build` can make on the
  host, and prints each of Tauri's targets it left out, with what
  Fledge lacks. `all` means all there is. A target named outright that
  cannot be built is refused.
- An unset `rank` is refused, as `Default` is when written. The refusal
  names the key and the value that builds, `Alternate`.
- An unset `webviewInstallMode` refuses a Windows setup program, since
  the app would fail to open on a computer without WebView2, where
  Tauri's installer installs it. `"type": "skip"` builds one, and says
  so in the config.

This ADR stays proposed until the maintainer accepts packaging through
Fledge.
