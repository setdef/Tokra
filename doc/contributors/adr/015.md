# ADR 015: A Tokra CLI That Ports tauri-cli and Packages Through Fledge

## Status

Proposed. Answers plan 054's question 1. Takes up what ADR 014 §6 and
plan 054's "Out of scope" left for a Tokra CLI. Rewrites plan 054's
054a-5 (§5). Revised 2026-11-05 with the maintainer's decisions on
fidelity to Tauri's `bundle`, staging, hook variables, WebView2, Linux
icons, and the Fledge pin, and with Fledge's answer on each bundle key.

## Date

2026-11-05

## Context

A Tauri developer works through two commands. `tauri dev` runs
`build.beforeDevCommand`, waits for `build.devUrl` or serves
`build.frontendDist` itself, and runs the app; `tauri build` runs
`build.beforeBuildCommand`, compiles, runs `build.beforeBundleCommand`,
and bundles. The difference between the two runs reaches the app as a
Cargo feature: `tauri build` turns on `tauri/custom-protocol`
(`crates/tauri-cli/src/interface/rust.rs:483-490`), which the macro reads
into `ContextData.dev` (`tauri-macros/src/context.rs:155`) and the crate
into `is_dev()` (`crates/tauri/src/lib.rs:313-316`). That one flag picks
`devUrl` or `frontendDist`, which origin may invoke commands, `devCsp` or
`csp`, and whether assets are embedded.

Tokra has neither command. Every Tokra app runs from its sources, the way
`tauri dev` runs one, and plan 054 left the flag at a provisional `true`
until someone decides where it comes from (its question 1, and the risk
that an app shipped in that state trusts its developer's localhost on its
users' machines). ADR 011 rules out an environment variable: whoever runs
the app could flip it.

Fledge packages Ruby programs for people who have no Ruby. Its 0.5
contract (Fledge ADR 019 §2, widened by ADR 029) is a command, not a
library: `fledge build [--out DIR] [--sign IDENTITY] [PATH]`, exit 0, 1,
or 2, one written path per line on standard output, and a `fledge.yml`
whose schema (`lib/fledge/config.schema.json`) refuses any key it does not
know. Its Ruby classes, its standard error's wording, and `fledge.cfg` are
not part of that contract (ADR 029 §3). It has no build hooks. It ships
the whole project, the nearest folder holding a `Gemfile`, `gems.rb`,
`fledge.yml`, or gemspec, as the app's `app/` folder, less `.git`,
`.bundle`, `vendor/bundle`, `vendor/cache`, and any folder holding a
`CACHEDIR.TAG` (`lib/fledge/app.rb:88-91`, Fledge ADR 005). Since 0.5.0
the app's Ruby is the Ruby that runs `fledge build`. Fledge's ADR 030
added `linux: system_libraries` for gems that link a desktop's
libraries, and named Tokra as the reason.

Tauri's `bundle` section has close to a hundred keys, and `fledge.yml` has
twelve. Fledge answered, key by key, which it supports, which it could
add, and which it never will, and proposed neutral capabilities for the
middle group ([bundle keys against Fledge](../research/2026-11-05-bundle-keys-vs-fledge.md),
[app metadata and installer needs](../research/2026-11-05-fledge-app-metadata-and-installer-needs.md)).
Fledge knows no framework's words, so each capability carries Fledge's
own name; Tokra owns the mapping from Tauri's keys.

## Decision

### 1. A `tokra-cli` gem whose `tokra` command ports tauri-cli

`tokra-cli` is a gem of its own, in `cli/` beside `plugins/`, with one
executable, `tokra`, as tauri-cli is a crate of its own beside `tauri`.
An app's `Gemfile` puts it in the `development` group with Fledge, so
neither it, its dev server, nor its file watcher ships with the app (§4).
It depends on `tokra` at the same version. Its classes live under
`Tokra::Cli`, one file per tauri-cli module it ports (`dev`, `build`,
`helpers/app_paths`, `helpers/config`, `helpers/mod`'s `run_hook`).

`tokra dev` and `tokra build` come first. tauri-cli's other commands
(`init`, `bundle`, `info`, `add`, `remove`, `plugin`, `icon`, `signer`,
`completions`, `permission`, `capability`, `inspect`, `migrate`) each wait
for a plan of their own; `android` and `ios` stay out with mobile. The
global `-v`/`--verbose`, `--help`, and `--version` are ported.

Both commands find the project as tauri-cli's `app_paths` does
(`helpers/app_paths.rs:93-175`): the config's folder is the current one or
its `src-tokra/` when either holds a config file, else the first found
three levels down; the frontend's folder is the nearest with a
`package.json`, else the config folder's parent. `TAURI_APP_PATH`,
`TAURI_FRONTEND_PATH`, and `TAURI_CLI_CONFIG_DEPTH` become `TOKRA_APP_PATH`,
`TOKRA_FRONTEND_PATH`, and `TOKRA_CLI_CONFIG_DEPTH` by ADR 014 §3's rule:
they are the developer's instructions to the framework's own tool, and
nothing outside Tokra reads them. They steer that tool, not the app, so
ADR 011 does not reach them. The app's entry is the program Fledge would
build: the project root's gemspec executable, else its `main.rb`.

Hooks run as `run_hook` runs them (`helpers/mod.rs:71-127`): `sh -c` or
`cmd /S /C`, in the frontend's folder or the hook's `cwd`, failing with
"{name} `{script}` failed with exit code {code}". Their environment gets
`command_env` and the interface's variables (`helpers/mod.rs:35-48`,
`interface/rust.rs:290-321`) under Tauri's own names:
`TAURI_ENV_PLATFORM_VERSION`, `TAURI_ENV_DEBUG`, `TAURI_ENV_TARGET_TRIPLE`,
`TAURI_ENV_ARCH`, `TAURI_ENV_PLATFORM`, and `TAURI_ENV_FAMILY`. These are
a contract with the frontend's tooling, not the framework's brand: a Vite
config from Tauri's templates reads `TAURI_ENV_DEBUG` and
`TAURI_ENV_PLATFORM` to pick its target and minification. ADR 014 §3
keeps such names as Tauri spells them, as it keeps `__TAURI_INTERNALS__`
(ADR 009) and `@tauri-apps/api` (ADR 010). The triple is the host's as
Rust names it, since Fledge builds only for the host.

### 2. `tokra dev`

It does what `dev::setup` does (`crates/tauri-cli/src/dev.rs:136-322`):
runs `beforeDevCommand` (in the background, or to completion with
`wait`), kills its process tree when the app exits for good or on Ctrl-C,
starts the built-in server on `frontendDist` when there is no `devUrl`,
waits for the dev server, then runs the entry with Ruby from the config's
folder. With watching on, a change under that folder or an additional
watch folder restarts the app, as a Rust change rebuilds and reruns a
Tauri app; `.tokraignore` stands in for `.taurignore` by ADR 014 §3's
rule for the framework's own file names, and Tauri's
`tauri-dev-watcher.gitignore` is ported as it is. An app in development
reads `bundle.resources` and `bundle.externalBin` where they are, as plan
054 recorded.

| tauri-cli flag | Verdict |
|---|---|
| `-r`, `--runner` and `build.runner` | translated: the command that runs the entry instead of `ruby` |
| `-t`, `--target` | deferred: Tokra runs on the host only |
| `-f`, `--features` and `build.features` | not ported: Tokra has no Cargo features to choose (ADR 011) |
| `-e`, `--exit-on-panic` | translated: an app that exits with a nonzero status ends `tokra dev` instead of waiting for a change (`dev.rs:324-332`) |
| `-c`, `--config` | ported, through the dev session (§5) |
| `--release` | not ported: there is no compile profile |
| `-- [runner args] -- [app args]` | ported: Ruby's arguments, then the app's `ARGV` |
| `--no-dev-server-wait`, `TAURI_CLI_NO_DEV_SERVER_WAIT` | ported; the variable renamed `TOKRA_CLI_NO_DEV_SERVER_WAIT`. The wait keeps Tauri's 90 tries, 2 s apart, and its messages (`dev.rs:268-313`) |
| `--no-watch`, `--additional-watch-folders` and `build.additionalWatchFolders` | ported |
| `--no-dev-server`, `--port`, `TAURI_CLI_PORT` | ported, the variable renamed `TOKRA_CLI_PORT`: the server binds 127.0.0.1 from port 1430 up, or exactly `--port` (`builtin_dev_server.rs:32-52`), and reloads the page when a file changes |

The plan that builds the server and the watcher picks their libraries.
They ship in `tokra-cli` only, so an app never carries them.

### 3. `tokra build`

It runs `build::setup`'s checks and hook (`build.rs:140-260`), then
`bundle::bundle`'s hook (`bundle.rs:163-202`), then Fledge:

1. Reads the config with the platform file and every `--config` patch
   folded in by tauri-cli's `merge_patches`, in which `null` keeps a key
   (`helpers/config.rs:176-184`, `:278-294`).
2. Refuses `com.tokra.dev` and an identifier with characters other than
   alphanumerics, `-`, and `.`, and warns on one ending in `.app`
   (`build.rs:160-186`; plan 054, decision 11).
3. Checks every `bundle` key against §6 for the installers this build
   produces, and refuses, naming each key that stops it, before any hook
   runs.
4. Runs `beforeBuildCommand`, then checks `frontendDist` as Tauri does:
   it exists, it is not a folder named `src-tokra`, and it holds no
   `node_modules` or `src-tokra` (`build.rs:188-248`).
5. Stages what Tauri's bundle carries (§4) into `.tokra/stage/`, which
   gets a `CACHEDIR.TAG`, so neither tool ever ships `.tokra/`.
6. Writes the packaged context (§5) beside the staged config, and
   `fledge.yml` (§6) at the staged root.
7. Runs `beforeBundleCommand` when an installer is to be built, as
   `bundle.rs:189-200` runs it when a bundle is.
8. Runs `RbConfig.ruby Gem.bin_path("fledge", "fledge") build --out
   PROJECT/.tokra/bundle [--sign IDENTITY] ENTRY` in the staged root,
   where `ENTRY` is the staged entry, passes Fledge's standard error
   through, prints each path Fledge prints, and exits with Fledge's
   status.

A project with its own `fledge.yml` may name extra libraries under
`linux: system_libraries`, for gems other than Tokra's; `tokra build`
adds them to its own list. Any other key there is refused, naming it,
because the Tokra config owns it.

| tauri-cli flag | Verdict |
|---|---|
| `-r`, `--runner` | deferred: it replaces the compiler, and nothing compiles the app |
| `-d`, `--debug` | translated: hooks get `TAURI_ENV_DEBUG`; what else it changes waits on plan 050's question 2 (devtools) |
| `-t`, `--target` | deferred: Fledge builds for the computer it runs on (Fledge ADR 010) |
| `-f`, `--features` | not ported (ADR 011) |
| `-b`, `--bundles` | translated into `installers` (§6) |
| `--no-bundle` | translated: `installers: []`, so Fledge writes the archive alone, the counterpart of Tauri's bare binary |
| `-c`, `--config` | ported, into the packaged context |
| `-- [args]` | deferred with `--runner` |
| `--ci`, `CI` | ported; `tokra build` asks nothing yet |
| `--skip-stapling` | ported with notarization (§7) |
| `--ignore-version-mismatches` | deferred: the npm and Cargo package check (`info::plugins::check_mismatched_packages`) waits for `tokra info` |
| `--no-sign` | ported: `--sign` is left off |

### 4. What ships is what Tauri's bundle carries

Staging is a question of fidelity, not an exclusion list. A Tauri
bundle carries the app's binary, with the frontend's assets and the
config compiled into it (`tauri-codegen/src/context.rs:184-196`); the
files `bundle.resources` names, copied into the resource folder by
`resource_relpath`, which writes `..` as `_up_`
(`tauri-bundler/src/bundle/settings.rs:1146-1153`,
`tauri-utils/src/resources.rs:17-24`); the `bundle.externalBin`
programs, copied beside the binary with their `-TARGET` suffix removed
(`settings.rs:1127-1143`); a `fixedRuntime` WebView2 folder, added to the
resources (`tauri-cli/src/interface/rust.rs:1434-1440`); and the icons,
desktop file, and platform files each installer writes
(`macos/app.rs:75-105`, `linux/debian.rs:115-140`). Nothing else from
the project reaches the user. `tokra build` stages the same set, at the
same relative paths, so Fledge's copy of the staged root ships exactly
that:

- **The app, standing in for the binary.** A Ruby program has no binary;
  its sources and its locked gems are what Ruby runs. When the project
  root has a gemspec, the app is the files that gemspec lists, the
  gemspec, `Gemfile`, and `Gemfile.lock`: a gem's `files` is how Ruby
  already says which files a program is. `tokra build` loads the gemspec
  in the developer's checkout, where its `files` expression runs as it was
  written (often `git ls-files`), and copies what it names. Without a
  gemspec Tokra cannot tell the program's files from the rest, so the app
  is the config folder's tree, the counterpart of the crate beside
  `tauri.conf.json` (ADR 014 §5), with `Gemfile` and `Gemfile.lock`, less
  what Fledge never ships, `.tokra/`, every `node_modules`, and the
  `frontendDist` folder, which ships as assets. A project that wants less
  writes a gemspec. Fledge installs the gems from the lockfile, not from
  the developer's computer.
- **The config, compiled in.** The config files do not ship. The
  packaged context (§5) takes their place, as Tauri's binary carries its
  config and reads no file.
- **The frontend's assets.** Tauri embeds `frontendDist`; Tokra serves it
  from files, so `tokra build` copies the folder, or the files a
  `frontendDist` list names, into `tokra-packaged/assets/` beside the
  staged config, and the packaged context's `build.frontendDist` names
  that folder. A `frontendDist` URL ships nothing, as in Tauri.
- **`bundle.resources`**, a list or a map, into
  `tokra-packaged/resources/` by Tauri's rules. That folder is the app's
  resource folder: the path resolver, when it is ported, answers it for
  `resource_dir` in a packaged app.
- **`bundle.externalBin`**, the host triple's file of each, into
  `tokra-packaged/bin/` with the suffix removed. The shell plugin's
  sidecar lookup, when it is ported, looks there in a packaged app, as
  Tauri's looks beside the binary. Fledge has not verified that a shipped
  file keeps its executable bit; `rake test:package` checks it.
- **The icons**, under the names Fledge reads (§7), in
  `tokra-packaged/icons/`.

Plugin files a Tauri plugin compiles into the binary, such as
capabilities once they are ported, ship inside the app by the same rule
as its sources.

### 5. Development unless `tokra build` made it, sealed by signing

This answers plan 054's question 1 with its option (a): an app is
packaged when `tokra build` produced it and in development otherwise.

The marker is the packaged context, the file `tokra.context.json` that
step 6 writes beside the staged config. It is Tokra's counterpart of
codegen's output: `dev` false and the config as `tokra build` merged it
for this platform, `--config` patches included, with `frontendDist`
naming the staged assets. `Tokra.generate_context` looks for it in the
folder it would read the config from, before it looks for a config file.
When it finds the marker it builds the `Context` from it, with `dev`
false, and reads no `tokra.conf.json`; otherwise it reads the config
files as ADR 014 says, with `dev` true. The file exists only in the
staging copy, never in the developer's checkout.

`fledge build --sign` seals it. On macOS codesign covers every file in
the `.app` bundle, so removing or editing the marker breaks the
signature Gatekeeper checks. On Windows signtool signs programs and
libraries, so the signed setup program covers the marker on its way to
the user but not once it is installed; Linux has no signature. There the
marker is exactly as tamper-resistant as the Ruby source beside it. That
matches ADR 014's reasoning: whoever can edit the app's files can already
change its code. No environment variable decides it (ADR 011).

`tokra dev` sets no flag, since development is the default. It hands
the app its `--config` patches and the built-in server's `devUrl` in a
dev session, `.tokra/dev.json`, which holds the merged patch and the
`tokra dev` process's id. `generate_context` merges it over the config
only when no packaged context exists and the recorded id is
`Process.ppid`. A stale file left by a crash, or a plain `ruby main.rb`,
then changes nothing. Merging it changes no more than editing
`tokra.conf.json` would.

### 6. Every key in Tauri's `bundle` is honored

A Tauri config's bundle values exist for a reason, so `tokra build`
drops none of them. Each key takes one of three paths:

- **Mapped.** Fledge has it, and `tokra build` writes it into
  `fledge.yml`, onto `--sign`, or into the staged files (§4).
- **Pending.** Fledge can have it and does not yet. Tokra asks for the
  capability (Requests to Fledge, below). Until Fledge ships it,
  `tokra build` refuses a config that sets the key away from its default
  for an installer this build produces, with a message naming the key and
  the capability, such as "`tokra.conf.json > bundle > homepage` needs
  Fledge's A2, a homepage for the app, which Fledge 0.5.1 lacks". When
  the capability lands, the key becomes mapped and the refusal goes.
- **Never.** Fledge will not have it. The table says why and what Tokra
  does instead.

A key that Tauri reads only for an installer this build does not produce
is not refused, since `tauri build` would not use it either: `homepage`
for an app and disk image, `windows.wix` without an MSI, `linux.rpm`
without an RPM. Settings left at Tauri's defaults are not refused (but see
question 2).

`tokra build` writes `kind: windowed` and the keys below.

### 7. Platform specifics

**Linux libraries.** Tokra's extension needs eleven libraries that
Fledge's baseline (auditwheel's manylinux_2_39 list, Fledge
`lib/fledge/linkage.rb:79`) does not cover. On an aarch64-linux build of
trunk (`readelf -d`, 2026-11-05), they are `libwebkit2gtk-4.1.so.0`,
`libgtk-3.so.0`, `libgdk-3.so.0`, `libsoup-3.0.so.0`,
`libjavascriptcoregtk-4.1.so.0`, `libgio-2.0.so.0`,
`libgdk_pixbuf-2.0.so.0`, `libpango-1.0.so.0`, `libcairo.so.2`,
`libcairo-gobject.so.2`, and `libxdo.so.3` (muda's `libxdo` feature).
`libglib-2.0.so.0`, `libgobject-2.0.so.0`, and libc's own libraries are
in the baseline. Fledge refuses a listed library that no gem needs, so
the list has to be exact: Tokra keeps it as a constant, and a Linux test
compares it with the built extension's `DT_NEEDED` entries minus that
baseline. Each Tokra plugin that links a desktop library declares its own
list the same way, and `tokra build` writes the union for the plugins in
the bundle. libappindicator is opened with `dlopen` and cannot be listed
(Fledge ADR 030 §2).

**Icons.** Tauri sorts `bundle.icon` by kind and reads each PNG's pixel
size; Fledge reads no image and takes a size from a file's name
(`app.icns`, `app.ico`, `app-16.png` through `app-512.png`). Tokra and
Fledge split the work there. `tokra build` reads each PNG's width and
height from its header, as Tauri's Linux bundler does with a decoder
(`linux/freedesktop/mod.rs:44-83`), and copies the first PNG of each
size, in the list's order, to `app-SIZE.png`. A `@2x` file is named by its
pixels, so `128x128@2x.png` becomes `app-256.png`; Tauri puts it in
hicolor's `256x256@2` folder, which Fledge has no name for. The list's
first `.ico` becomes `app.ico`, and Windows refuses a list without one,
as `tauri-build` does. The first `.icns` becomes `app.icns`; with none,
`tokra build` packs the PNGs into one as `create_icns_file` does,
resizing a size that is not a power of two to the next one down
(`macos/icon.rs:21-99`), with macOS's own `sips` and `iconutil`, since a
macOS app builds only on a Mac. Fledge's agreed side is C1: a Linux
build takes at least one of its six sizes, ships those present, makes
the AppImage's top icon the 256 or else the largest, and names the
missing sizes on standard error. Until C1 lands, a Linux build missing
one of the six is refused, naming the sizes and C1. A PNG of a size
outside the six is refused, naming it, since Tauri would ship it; Fledge
counts a new size an optional, compatible addition (its ADR 029 §4), so
Tokra asks for it when an app needs it.

**Windows WebView2.** Tauri's default `webviewInstallMode` is
`downloadBootstrapper` with `silent: true`
(`tauri-utils/src/config.rs:943-985`), not `skip`, and its NSIS
installer acts on every mode (`windows/nsis/mod.rs:510-560`,
`installer.nsi:522-607`). Tokra honors them all with that default,
through Fledge's B1, `windows: prerequisites`. Tokra supplies the
installer file, downloaded at build time from Microsoft's links as
Tauri's bundler downloads it (`tauri-bundler/src/bundle/windows/util.rs:13-55`);
Fledge installs it when the `pv` value under
`EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}` is empty,
before it copies the app, and stops the install when it fails, as
Tauri's section does.

| Mode | Tauri's installer | Tokra |
|---|---|---|
| `skip` | installs nothing | mapped: no prerequisite |
| `downloadBootstrapper` (default) | downloads Microsoft's bootstrapper at install time and runs it | pending B1. Fledge never downloads at install time, so Tokra embeds the bootstrapper it downloaded at build time, about 1.8 MB, which then downloads the runtime as Tauri's does |
| `embedBootstrapper` | embeds the bootstrapper | pending B1, the same entry |
| `offlineInstaller` | embeds the standalone installer, about 127 MB, for the target's architecture | pending B1, with the standalone installer Tokra downloads at build time for the host's architecture |
| `silent` | `/silent` before `/install` | mapped to the entry's `arguments` |
| `fixedRuntime` | ships the folder as a resource; the app sets `WEBVIEW2_BROWSER_EXECUTABLE_FOLDER` before its first web view (`crates/tauri/src/app.rs:2167-2185`) | mapped: §4 stages the folder as a resource, and Tokra's runtime sets the variable from the packaged context, which retires plan 054's deferral. Like Tauri, Tokra does not grant the folder the permissions Microsoft asks for under Windows 10 from Fixed Version 120 |

`tokra-cli` downloads each Microsoft file at build time, as Tauri's
bundler does, and hands Fledge the file, so no checksum is pinned by
hand and nothing of Microsoft's is republished.

**macOS.** Without `--sign` Fledge signs ad hoc. With a signing identity
it signs every Mach-O file, the bundle, and the disk image, with the
hardened runtime and a timestamp. Tauri notarizes the signed app when
Apple's credentials are in the environment, then staples the ticket
unless `--skip-stapling` (`macos/app.rs:124-139`,
`macos/sign.rs:76-120`). Fledge never notarizes; that stays Tokra's job,
and `tokra build` ports it in a plan of its own. Until then it refuses to
build when those credentials are set, naming them, since Tauri would
notarize.

### 8. Fledge is pinned at 0.5.x from its tag

An app's `Gemfile`, and Tokra's own for CI, name Fledge as its README
says:
`gem "fledge", git: "https://github.com/setdef/Fledge", tag: "v0.5.1", group: :development`.
A gem cannot depend on a git source, so `tokra-cli` does not declare
Fledge; `tokra build` runs `fledge --version` instead and refuses
anything outside 0.5.x, naming the version it knows. Fledge is 0.x, and a
minor version may change its command or `fledge.yml`, so each new minor
version is a Tokra change, with its CHANGELOG read first. Each Fledge
release that ships a requested capability moves the pin and turns that
capability's pending keys into mapped ones. The app's Ruby is the Ruby
running `tokra build`, which Fledge 0.5 has a runtime for at 4.0 only.

### 9. Testing

Unit tests never run a real `fledge build`, which downloads a runtime and
compiles Tokra's extension. They cover argument parsing; the config
merge; the identifier and `frontendDist` checks; every `bundle` key's
path in §6, each refusal message included; hooks run through a real
`sh -c` or `cmd /S /C`, with the `TAURI_ENV_*` variables; the dev-server
wait against a real local socket; the built-in server over real HTTP;
the staging tree, file by file, with and without a gemspec, resources,
and sidecars; icon naming from real PNG headers; `fledge.yml` checked
against a copy of Fledge v0.5.1's schema; the command line `tokra build`
would run; and `generate_context` with and without a packaged context
and a dev session, a stale session included. A test app under
`test/fixtures/` prints its `Tokra.is_dev` and `devUrl` without opening a
window, so `tokra dev` runs it in the core tests.

A `rake test:package` task, outside the default gate, runs the real
`tokra build` on that fixture with Fledge v0.5.1, and on Linux also
checks the soname list (§7) and the `.deb`'s `Depends`, and everywhere
that a sidecar keeps its executable bit. CI runs it on Linux under Xvfb,
macOS, and Windows, then runs the built app, which must report `dev`
false. `rake test:linux` runs it in Plan 058's container.

## Consequences

- An app shipped by `tokra build` loads `frontendDist`, trusts only the
  `tokra://` origin for IPC, and cannot be switched to development from
  outside. 054a-5 lands on this: `Tokra.is_dev` answers the context's
  `dev`, no `dev:` keyword is added, and its tests cover the packaged
  context and the dev session instead.
- An app shipped any other way, including a hand-run `fledge build`,
  runs in development and trusts `devUrl`'s origin, as a Tauri binary
  built without the CLI does. The README says to ship with `tokra
  build`. Gems are question 1.
- `--config` merges reach an app without an environment variable, so
  ADR 014 §6 holds.
- A Tauri config builds unchanged when every key it sets is mapped or
  never needed. One that sets a pending key fails `tokra build`, naming
  the key and the Fledge capability it waits on, until a Fledge release
  ships it and Tokra's pin moves. No setting is dropped without a word.
- A shipped app carries what a Tauri bundle carries and no more, so
  frontend sources, tests, and tooling stay home without a
  `.tokraignore`. Without a gemspec, the config folder ships whole.
- Frontend tooling written for Tauri reads `TAURI_ENV_*` from Tokra's
  hooks unchanged.
- `tokra build` downloads Microsoft's WebView2 installers at build time
  for a Windows installer that needs one, as Tauri's bundler does.
- Plan 059 gains a seventh gem, released after `tokra`.
- The staged copy costs disk and time on each build, and path gems
  outside the project fail there, as Fledge already refuses them (Fledge
  ADR 019, Consequences).

## Requests to Fledge

Each request below is Fledge's own plan story, quoted from its note
([app metadata and installer needs](../research/2026-11-05-fledge-app-metadata-and-installer-needs.md)
§1.5, §2.5, §3.3), so it can be sent as it is. Fledge's ids follow the
note and its [key table](../research/2026-11-05-bundle-keys-vs-fledge.md).

- **A1. A description for the app.** "A windowed app may say what it does. `fledge.yml` takes `description` (one line) and `long_description`. A Linux desktop entry shows the first as its `Comment`; a `.deb` carries them as its `Description` (synopsis and extended lines, per Debian Policy 5.6.13); a Windows program carries the first as its `Comments` version string. Done when: the example app sets both, and Delivery reads each back with `desktop-file-validate`, `dpkg-deb -f`, and `(Get-Item).VersionInfo`; a project without them builds the files it builds today. Size S to M. Compatible (new keys)."
- **A2. A homepage for the app.** "`fledge.yml` takes `homepage`. A `.deb` states it as `Homepage`; Windows lists it as the app's information, help and update links in Settings. Done when: Delivery reads `Homepage` and the uninstall key's `URLInfoAbout`. Size S. Compatible."
- **A3. A category for the app.** "`fledge.yml` takes `macos: category`, `linux: categories` and `linux: section`, each the string its system takes; Fledge writes `LSApplicationCategoryType`, `Categories=`, and `Section:`. Done when: `desktop-file-validate` accepts a known and refuses an unknown category (it warns on values outside the registry), and `plutil` reads the key. Size S. Compatible."
- **A4. A license text with the app.** "`fledge.yml` takes `license_file`. The Windows setup program shows it on a page before the install, and a `.deb` installs it as `/usr/share/doc/PACKAGE/copyright`. Size M. Compatible. The disk image's agreement is a later story."
- **B1. A Windows setup program installs what the app needs first.** "`fledge.yml` takes `windows: prerequisites`, a list of components. Each names a file (in the project, or a `url` with its `sha256`), the arguments to run it with, and a registry value that is non-empty when it is already installed. The setup program, which needs no administrator, runs each missing one silently before it copies the app and stops with the component's name when one fails. Done when: on every Windows platform Fledge builds for, a Delivery run installs an app whose prerequisite is a fake installer that sets the registry value; a second install skips it; a failing one stops the install; `/S` shows no window. Size M to L. Compatible (new object)."
- **C1. A Linux build takes the icon sizes a developer has.** "A Linux build needs at least one of `ICON-16.png`, `-32`, `-64`, `-128`, `-256`, `-512`. It ships those that exist in the hicolor folders, makes the AppImage's top icon the 256-pixel one or else the largest, and says on standard error which sizes are missing. A project with all six builds exactly what it builds today. Done when: a project with only `-32`, `-128` and `-256` builds, its `.deb` and AppImage hold three hicolor icons, `desktop-file-validate` accepts the entry, and a project with none still fails with today's message. Size S. Compatible (a refusal removed)."

Fledge named these further capabilities as first estimates, without
stories yet. Tokra requests each, in Fledge's words, and asks Fledge to
write the story:

- **D3.** "More Windows setup-program settings: signing timestamp server and custom sign command, installer images, installer icon, languages, compression, Start menu folder."
- **D4.** "More macOS bundle settings: bundle version, bundle name, extra `Info.plist` keys from a file, entitlements, extra files and frameworks in the bundle, disk image window and background." Tokra adds a minimum macOS version above the runtime's floor, which Fledge's table answered only for lowering it.
- **D5.** "A second installer format: an MSI (WiX) or an RPM (rpmbuild)."
- **D6.** "A setting that refuses an older version over a newer one in the Windows setup program."
- **D7.** "A per-machine Windows installer (elevated, Program Files, HKLM)."
- **D8.** "More `.deb` and AppImage settings: extra `Depends`, `Recommends`, `Provides`, `Conflicts`, `Replaces`, `Priority`, changelog, extra files, maintainer scripts."
- **A4's later story.** "The disk image's agreement."
- **File associations.** The key Fledge reserves, `file_associations` (Fledge ADR 029 §5, its ADR 032 draft).

## Rejected alternatives

- **An environment variable or a command-line flag to mark packaged or
  development.** Whoever starts the app controls both (ADR 011, ADR 014
  §6).
- **`generate_context(dev: true)`, plan 054's option (c).** It is safe by
  default, but every developer would edit code to work against a dev
  server, and `tokra dev` would need the same keyword anyway.
- **Calling Fledge's Ruby classes.** They are not its API (Fledge ADR 029
  §3).
- **Writing `fledge.yml` and the marker into the developer's checkout.**
  The checkout would turn packaged during a build, and stay that way
  after a crash.
- **Porting tauri-bundler.** Fledge already does the job, with the Ruby
  runtime tauri-bundler has no notion of.
- **`tokra` as an executable in the `tokra` gem.** Every app would ship
  the dev server and watcher, and tauri-cli is a crate of its own.
- **Warning on, or ignoring, a key Fledge lacks.** A config's bundle
  values are there for a reason; a packager that drops one without
  failing ships an app its developer did not ask for.
- **Copying the whole project less an exclusion list, or a
  `.tokraignore`.** Tauri ships what its bundle names, not what a
  developer forgot to exclude.
- **`TOKRA_ENV_*` for the hook variables.** They are read by frontend
  tooling written for Tauri, a contract ADR 014 §3 keeps.

## Questions for the maintainer

1. **Does a gem-distributed app get the marker?** Tauri has no
   distribution path for an app crate: its development flag is the
   Cargo feature `tauri/custom-protocol`, which `tauri build` always
   turns on (`crates/tauri-cli/src/interface/rust.rs:484`) and without
   which Tauri's own build script marks the app as development
   (`crates/tauri/build.rs:252-255`), so a plain `cargo install` of a
   Tauri app runs in development unless its manifest enables the
   feature. Tokra's equivalent is this ADR's rule, development unless the
   build tool made it, with `tokra build --bundles gem` in the role of
   building with the feature: it stages a copy as §4 does, writes the
   packaged context, and builds the gem there, with the gemspec loaded in
   the checkout and its `files` replaced by the staged list, so the gem
   is packaged and the checkout is not. Recommended, pending the
   maintainer's word.
2. **Defaults that ask for more than Fledge has.** Two Tauri defaults are
   not inert: `targets: "all"` includes an MSI on Windows and an RPM on
   Linux, and `webviewInstallMode` defaults to `downloadBootstrapper`.
   The draft applies the default exemption to `all`, which builds
   Fledge's installers, since D5 may never come. It recommends refusing
   a Windows installer with the mode unset until B1 lands, since without
   it the app fails to open on a Windows 10 computer that lacks WebView2,
   where Tauri's installs it. Agreed?

The WebView2 installers are settled by Tauri's own bundler: it downloads
them from Microsoft's links at build time (`WEBVIEW2_BOOTSTRAPPER_URL`
and the offline installer links,
`crates/tauri-bundler/src/bundle/windows/util.rs:13-17`, fetched by
`download_webview2_bootstrapper` and
`download_webview2_offline_installer`, `:42-55`) and embeds them. `tokra
build` does the same and hands Fledge's B1 the downloaded file, so no
checksum is pinned by hand and nothing of Microsoft's is republished.
