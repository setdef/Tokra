# ADR 015: A tokra-cli Gem Ports tauri-cli, and tokra build Packages Through Fledge

## Context and Problem Statement

A Tauri developer works through tauri-cli. `tauri dev` runs the
frontend's dev server and the app. `tauri build` runs the build hooks,
compiles the app, and bundles it into installers with tauri-bundler.
Tokra has neither command, so a Tokra app runs only from its sources,
and nobody without Ruby can install one.

Fledge, a separate project by the same maintainer, packages Ruby
programs for people who have no Ruby: a Ruby runtime, the app's locked
gems, and each platform's installers. Its interface is its command,
`fledge build`, and the `fledge.yml` it reads, which refuses any key it
does not know (Fledge ADR 029).

How does a Tokra developer run an app in development, and ship it, as
tauri-cli lets a Tauri developer do?

## Decision Drivers

- Tauri fidelity: the commands, flags, hooks, messages, and what a
  bundle carries match tauri-cli and tauri-bundler.
- A Ruby app has no binary and no Cargo features, and it ships with a
  Ruby runtime.
- Nothing the developer does not ship reaches the user: no dev server,
  file watcher, frontend sources, or tests.
- Tokra relies only on what Fledge promises: its command, `fledge.yml`,
  exit statuses, and standard output.

## Considered Options

1. A `tokra-cli` gem whose `tokra build` stages what Tauri's bundle
   carries, writes `fledge.yml`, and runs `fledge build`.
2. A `tokra-cli` gem that ports tauri-bundler too.
3. A `tokra-cli` gem that calls Fledge's Ruby classes in its own process.
4. A `tokra` executable in the `tokra` gem.

## Decision Outcome

Chosen: option 1, because it ports tauri-cli as a package of its own,
which an app keeps in its `development` group with the dev server and
the file watcher, and because Fledge already does the packaging, with
the Ruby runtime that tauri-bundler has no notion of.

`tokra build` ships what a Tauri bundle carries and no more, and drops
no `bundle` key: each maps onto Fledge, or the build refuses it, naming
the key and what Fledge lacks. [The CLI's design](../design/cli.md)
specifies the commands, and
[packaging through Fledge](../design/packaging.md) specifies what
`tokra build` hands Fledge, key by key, and how an app tells development
from packaged.

Confidence: medium. Fledge builds windowed apps with native and Rust
gems on macOS, Linux, and Windows, but no Tokra app has gone through it,
and many `bundle` keys wait for Fledge releases after its 1.0.

The maintainer accepted packaging through Fledge on 2026-11-21.

### Consequences

- Good, because a Tauri developer's commands, flags, hooks, and hook
  variables carry over, and frontend tooling written for Tauri reads
  `TAURI_ENV_*` unchanged.
- Good, because the app ships with its own Ruby, and its user needs none.
- Good, because a shipped app carries what a Tauri bundle carries, so
  frontend sources, tests, and tooling stay home without an exclusion
  list.
- Good, because a Tauri config builds unchanged when every key it sets
  maps, and one that sets another key fails, naming it.
- Bad, because many keys are refused until Fledge ships them, and some
  never map. Packaging through Fledge, "What Fledge has", keeps the
  list.
- Bad, because Tokra follows a 0.x dependency. Each Fledge minor may
  change its command or `fledge.yml`, so each one is a Tokra change, and
  `tokra-cli` checks Fledge's version when it runs, since Fledge is not
  on RubyGems.org before its 1.0.
- Bad, because Fledge decides the app's Ruby: the app gets the runtime of
  the Ruby minor that runs `tokra build`.
- Bad, because the dev tools ship unless `tokra build` keeps them out of
  the gems Fledge installs.
- Bad, because each build copies the project, which costs disk and
  time, and a path gem outside the project fails there.
- Neutral, because Tokra's releases gain a gem.

### Confirmation

Core tests cover each command's flags, hooks through a real shell, the
staging tree file by file, and every `bundle` key's path with its
refusal message, checking `fledge.yml` against the pinned Fledge's
schema. A `rake test:package` task, outside the default gate, runs the
real `tokra build` with the pinned Fledge in CI on Linux, macOS, and
Windows, and runs the built app. A review of each Fledge minor before
the pin moves keeps the key table true.

## Pros and Cons of the Options

### A tokra-cli that ports tauri-bundler

- Good, because no key would wait on another project. (Noted
  2026-11-13; not weighed at the time.)
- Bad, because tauri-bundler bundles a compiled binary, and knows
  nothing of shipping a Ruby runtime and gems, which Fledge does.

### A tokra-cli that calls Fledge's Ruby classes

- Good, because it saves a process and a Ruby start. (Noted 2026-11-13;
  not weighed at the time.)
- Bad, because Fledge's classes are not its interface (Fledge ADR 029),
  and may change in any release.

### A tokra executable in the tokra gem

- Good, because there is one gem fewer to release. (Noted 2026-11-13;
  not weighed at the time.)
- Bad, because every app would ship the dev server and the file
  watcher, and tauri-cli is a crate of its own.
