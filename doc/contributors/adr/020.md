# ADR 020: Tokra Ships No Native Extension: Tauri's Logic Is Ruby, and Ferro Binds the Windowing Crates

## Context and Problem Statement

ADR 001 chose a thin Rust layer under a Ruby host, and in January that
layer was estimated at about 500 lines for the whole port. ADR 011 moved
the standalone crate bindings to Ferro and kept the windowing stack
(tao, wry, muda, tray-icon) in Tokra's own extension.

An audit on 2026-11-21 read every line of `ext/tokra/src`
([the Rust in Tokra](../research/2026-11-21-rust-in-tokra.md)). The
extension is 14,480 lines. About a quarter of its code is Tauri's own
behavior written in Rust: the runtime's event mapping, window placement,
web-context store, window-id map, undecorated resizing, and more. The
rest is one-to-one wrappers, their tests, the glue between the event
loop and Ruby's threads, and guards against panics. AGENTS.md's goal 6
asks for as little Rust as possible in Tokra, with Tauri's own crates
ported to Ruby and only the crates Tauri depends on bound, one to one.

Where does the Rust that Tokra needs live, and what of it is Tokra's?

## Decision Drivers

- Fidelity to Tauri (goal 1): whatever moves, an app developer sees no
  difference.
- As little Rust as possible in Tokra (goal 6). Rust in Ferro, whose job
  is binding crates, does not count against it.
- Each layer has one answer key: a crate for a binding, Tauri for
  Tokra (ADR 011).
- No crate with process-wide state is linked twice in one process
  (ADR 011).

## Considered Options

1. Tokra ships no native extension. Tauri's logic becomes Ruby in
   Tokra, and one Ferro library binds tao, wry, muda, tray-icon, and
   window-vibrancy one to one.
2. Keep Tokra's extension as the binding (ADR 011's choice), and move
   only Tauri's logic out of it into Ruby.
3. Leave the extension as it is.

## Decision Outcome

Chosen: option 1, before 1.0, in three stages.

- **Short term:** Tauri's logic leaves Rust for Ruby, over today's
  extension, which exposes the one-to-one calls each piece needs. About
  1,750 lines need only such calls. This stage is also option 2's whole
  work, so it is right under either.
- **Mid term:** Ferro builds the windowing gem, in parallel: one native
  library for the five crates, with the loop's glue (thread affinity,
  the GVL hand-off of ADR 012, signals, exceptions) beside the loop.
- **Long term:** Tokra's Ruby reaches its native layer through one
  seam, and a process loads the Ferro gem in place of `ext/tokra`,
  never beside it, since tao and tray-icon crash as a second copy. Then
  the extension is deleted.

Option 1 over option 2, because option 2 leaves Tokra with a binding to
maintain that answers to the crates, not to Tauri, which is the split
ADR 011 made for every other crate. ADR 011 kept the stack in Tokra
because moving it "would give the same native library another name and
add a release step to every windowing change". With Tauri's logic in
Ruby, a windowing change to Tokra rarely touches the binding, so that
cost falls. Option 3 leaves goal 6 unmet and Tauri's logic in two
languages.

About 990 lines are code where Tauri itself is the function the
platform calls inside the native loop: window and subclass procedures,
COM handlers, GTK signal handlers. Ruby cannot soundly be those
callbacks with what it ships (the audit, section 2). They stay Rust,
in the windowing library, as a recorded exception to Ferro's rule
against adding what a crate lacks, unless a spike of the `ffi` gem
shows Ruby can hold them.

This record supersedes ADR 011's choice of option a for the windowing
stack, and ADR 001's sentence that the Rust layer is a dumb pipe that
wraps tao and wry and knows nothing of state. The rest of both stands:
a Ruby host, standalone crates bound in Ferro, one native home per
crate with process-wide state. Both records stay until the switch,
since the code cites them.

Confidence: medium that the stages are sound, low on their size. No
stage is built. The gem's size is an estimate (about 11,000 to 15,000
lines of non-test Rust, more than the extension it replaces), the cost
of delivering every raw event to Ruby is unmeasured, and the audit
lists nine unknowns. Revisit at the end of each stage, and at once if
the short-term stage shows a piece of Tauri's logic that Ruby cannot
express over a one-to-one call.

### Consequences

- Good, because Tokra's code answers to Tauri alone, in one language,
  and a port of Tauri's runtime logic needs no Rust.
- Good, because the windowing binding gets Ferro's standards: every
  call guarded against panics, every item bound or deferred with a
  reason.
- Bad, because the total Rust grows: Ferro's gem will be larger than
  the extension it replaces.
- Bad, because a Tokra change that needs a new windowing call waits for
  a Ferro release, as plugin changes already do (ADR 011).
- Bad, because the switch cannot be gradual within a process, so two
  backends live behind one seam until the Ferro one passes the whole
  suite.
- Bad, because the platform callbacks stay Rust that is Tauri's logic,
  outside Tokra's repository, until Ruby can hold them.
- Bad, because the work is large against a 1.0 that also needs the
  rest of Tauri ported.

### Confirmation

Nothing automated checks the first two stages; a reviewer checks that
no change adds Tauri's logic to `ext/tokra`, as AGENTS.md's Project
section asks. At the switch, the packaging check proves the gem loads
with no compiler, and a test asserts the gem ships no extension, as
each plugin's packaging test does today.
