# ADR 020: Every Crate Binding Lives in Ferro, and Tokra Ships No Native Extension

## Context and Problem Statement

Tokra's plugins first carried their own Rust: `tokra-clipboard` shipped
a magnus binding over arboard, and the dialog, notification, and
global-shortcut plugins would each have done the same. That put two
jobs in one gem. The binding answers to the crate: its types, errors,
and edge cases. The plugin answers to Tauri: its commands, wire
formats, and messages. Mixed together, neither had a clean answer key,
and an audit of the clipboard plugin found bugs in exactly that seam: a
zero-size image reached arboard's macOS backend unchecked and panicked
the VM, and malformed payloads hung the invoke instead of rejecting with
Tauri's message.

Ferro is a separate project of gems that bind Rust crates to Ruby 1:1,
adding no Ruby-isms and no functionality the crate lacks. Two technical
limits shape what can move there. A Rust value cannot enter another
gem's Rust API, since magnus checks every wrapped object against its own
gem's type record; only plain Ruby values, byte strings, and raw handles
passed as Integers cross. And some crates keep state the operating
system holds once per process, so a second copy of them in one process
crashes or misroutes: tao, tray-icon, wry before 0.54.3, muda with
objc2 0.6.3, global-hotkey, and notify-rust on macOS among them.

The windowing stack (tao, wry, muda, tray-icon) is bound in Tokra's own
extension, `ext/tokra`. An audit of it on 2026-11-21
([the Rust in Tokra](../research/2026-11-21-rust-in-tokra.md)) found
14,480 lines, and about a quarter of its code is not binding at all but
Tauri's own behavior written in Rust, against ADR 022.

Where does each Rust crate binding live: in each plugin, in Ferro, or in
Tokra's own extension?

## Decision Drivers

- Each layer has one answer key: the crate for a binding, Tauri for
  Tokra and its plugins.
- No crate with process-wide state is linked twice in one process.
- No raw pointer crosses a gem boundary to a crate that follows it.
- As little Rust as possible in Tokra (AGENTS.md goal 6, ADR 022), and a
  port of Tauri's code needs no Rust. Rust in Ferro, whose job is
  binding crates, does not count against that goal.

## Considered Options

For standalone crates:

1. Ferro binds the crate, and the plugin is pure Ruby over the Ferro
   gem.
2. Each plugin carries its own binding, as the first plugins did.

For the windowing stack (tao, wry, muda, tray-icon):

- a. Move it into Ferro, behind a single native library.
- b. Keep it in Tokra's own extension.
- c. Bind wry and muda in Ferro, and hand them Tokra's window as a raw
  handle.

## Decision Outcome

Chosen: option 1 with option a. Ferro binds every crate, and Tokra
ships no native extension.

For the standalone crates, option 1, because each layer is then checked
against one source, and Ferro stands on its own for Rubyists who want a
clipboard and nothing of Tokra.

For the windowing stack, option a, because option b leaves Tokra a
binding to maintain that answers to the crates and not to Tauri, the
split this record removes everywhere else, and because Tauri's logic
collected in Rust beside that binding. Option b was the choice
from 2026-10-26 until 2026-11-21, on the ground that moving the
stack "would give the same native library another name and add a
release step to every windowing change". Once Tauri's logic is Ruby
(ADR 022), a windowing change to Tokra rarely touches the binding, so
that cost falls. Option c is unsound: wry and muda follow the `NSView`
pointer, and a stale or forged Integer crashes the process.

The stack stays one native library, whatever Ruby gems sit over it:
wry builds its webview from the tao window as a Rust value, muda and
window-vibrancy follow the window's pointers, and tray-icon takes
muda's menus as Rust values, so no handle crosses a gem boundary and
nothing trusts an Integer.

A crate with process-wide state gets exactly one native home: no two
gems that one app might load link it. A raw handle crosses into another
gem only when that gem's crate never dereferences it.
[The native layer's design](../design/native.md) lists which crates
keep such state and how a crate's API is translated into Ruby;
[the plugins design](../design/plugins.md) says how a plugin builds on
a Ferro gem.

The windowing move is staged, before 1.0:

- **Short term:** Tauri's logic leaves `ext/tokra` for Ruby (ADR 022),
  over one-to-one calls the extension exposes.
- **Mid term:** Ferro builds the windowing gem, with the loop's glue
  (thread affinity, the GVL hand-off of ADR 012, signals, exceptions)
  beside the loop.
- **Long term:** Tokra's Ruby reaches its native layer through one
  seam, a process loads the Ferro gem in place of `ext/tokra`, never
  beside it, and the extension is deleted.

About 990 lines of the extension are code where Tauri itself is the
function the platform calls inside the native loop: window procedures,
COM handlers, GTK signal handlers. Ruby cannot soundly be those
callbacks with what it ships. They stay Rust, in the windowing library,
a recorded exception to Ferro's rule against adding what a crate lacks,
unless a spike of the `ffi` gem shows Ruby can hold them.

Confidence: for the standalone crates, not recorded when the decision
was made; five plugins are since built on Ferro gems, and the crate
table rests on reading each crate's source at the versions it names.
For the windowing move, medium that the stages are sound and low on
their size: no stage is built, the gem's size is an estimate (about
11,000 to 15,000 lines of non-test Rust, more than the extension it
replaces), the cost of delivering every raw event to Ruby is
unmeasured, and the audit lists nine unknowns. Revisit at the end of
each stage.

### Consequences

- Good, because plugin ports need no Rust, and a reviewer checks each
  layer against one source.
- Good, because the windowing crates, which share process-wide state,
  are linked once.
- Good, because the windowing binding gets Ferro's standards: every
  call guarded against a panic, every item bound or deferred with a
  reason.
- Bad, because a Tokra change that needs a Ferro API waits for a Ferro
  release: Tokra depends only on released Ferro versions, a published
  gem or a release tag named as a git source, never a path or an
  unpushed commit, since a Tokra contributor clones Tokra alone. That
  now holds for windowing changes too.
- Bad, because a window handle Tokra hands another gem is only as safe
  as that gem's use of it, so Tokra's handles are values to copy, not
  pointers to follow.
- Bad, because the windowing crates cannot be split across libraries:
  that would first need wry 0.54.3 or later and objc2 0.6.4 or later,
  the releases that stopped panicking on a second copy, and tao and
  tray-icon crash as a second copy at every version.
- Bad, because the total Rust grows: Ferro's windowing gem will be
  larger than the extension it replaces.
- Bad, because the switch cannot be gradual within a process, so two
  backends live behind one seam until the Ferro one passes the whole
  suite.
- Bad, because the platform callbacks are Tauri's logic kept in Rust,
  outside Tokra's repository, until Ruby can hold them.
- Bad, because the work is large against a 1.0 that also needs the rest
  of Tauri ported.

### Confirmation

A plugin's packaging tests check that its gem ships no native extension
and depends on its Ferro gem, as
`plugins/clipboard/test/test_clipboard.rb` does. At the switch, the
packaging check proves the `tokra` gem loads with no compiler. No
automated check enforces one native home per crate.
