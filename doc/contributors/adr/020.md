# ADR 020: Tokra Is Ruby, and Every Crate Binding Lives in Ferro

## Context and Problem Statement

Tokra ports Tauri, which keeps its lifecycle, commands, state, and
security checks in Rust, over tao for windows and wry for webviews.
Tokra's backend is Ruby, and Ruby can carry those responsibilities
itself. Rust is still needed to reach the crates Tauri depends on.

Ferro is a separate project of gems that bind Rust crates to Ruby one
to one, adding no Ruby-isms and nothing the crate lacks. Two limits
shape what a binding can do. A Rust value cannot enter another gem's
Rust API, since magnus checks every wrapped object against its own
gem's type record; only plain Ruby values, byte strings, and raw
handles passed as Integers cross. And some crates keep state the
operating system holds once per process, so a second copy in one
process crashes or misroutes: tao, tray-icon, wry before 0.54.3, muda
with objc2 0.6.3, global-hotkey, and notify-rust on macOS among them.

Tokra's extension, `ext/tokra`, binds the windowing stack (tao, wry,
muda, tray-icon). An audit on 2026-11-21
([the Rust in Tokra](../research/2026-11-21-rust-in-tokra.md)) found
14,480 lines there, about a quarter of the code Tauri's own behavior
written in Rust.

Where does the framework's logic live, and where does each crate
binding live?

## Decision Drivers

- Fidelity to Tauri (AGENTS.md goal 1): wherever code lives, an app
  developer sees no difference.
- As little Rust as possible in Tokra (goal 6): Tauri's own crates are
  ported to Ruby. Rust in Ferro, whose job is binding crates, does not
  count against it.
- Each layer has one answer key: the crate for a binding, Tauri for
  Tokra and its plugins.
- No crate with process-wide state is linked twice in one process, and
  no raw pointer crosses a gem boundary to a crate that follows it.

## Considered Options

1. Tokra ships no native extension. Tauri's logic is Ruby, and Ferro
   binds every crate, the windowing stack as one native library.
2. Ferro binds the standalone crates, and Tokra keeps one extension
   for the windowing stack.
3. Each gem carries its own binding: Tokra its extension, and each
   plugin its own Rust.
4. Tauri's model: the framework's logic in Rust, and Ruby for the
   app's code only.

## Decision Outcome

Chosen: option 1. It was reached in three decisions, and stands as one.

**The framework's logic is Ruby** (2026-01-30): lifecycle, command
routing, security checks, and state. Rust passes raw events and
messages and knows nothing of commands. No reason beyond the drivers
was recorded for preferring this to option 4, which was named and not
weighed.

**Ferro binds the standalone crates, and a plugin is pure Ruby over
its Ferro gem** (2026-10-26), over option 3, because a plugin that
carried its own binding answered to two keys at once, and the
clipboard audit found bugs in exactly that seam: an unchecked image
size that panicked the VM, and malformed payloads that hung the invoke.
A crate with process-wide state gets exactly one native home: no two
gems that one app might load link it. A raw handle crosses into another
gem only when that gem's crate never dereferences it.

**The windowing stack moves to Ferro too, and Tokra's extension goes**
(2026-11-21), over option 2, which stood for a year. Option 2 leaves
Tokra a binding to maintain that answers to the crates, not to Tauri,
and it let Tauri's logic collect in Rust beside the binding. It was
chosen because moving the stack "would give the same native library
another name and add a release step to every windowing change"; with
Tauri's logic in Ruby, a windowing change to Tokra rarely touches the
binding, so that cost falls. The stack stays one native library,
whatever Ruby gems sit over it: wry builds into tao's window, muda and
window-vibrancy follow its pointers, and tray-icon takes muda's menus
as Rust values. Binding those crates in separate libraries and passing
the window as an Integer is unsound: a stale or forged one crashes the
process.

The move happens before 1.0, in stages. Short term, Tauri's logic
leaves `ext/tokra` for Ruby, over one-to-one calls the extension
exposes; about 1,750 lines need only such calls. Mid term, Ferro
builds the windowing gem, with the loop's glue (thread affinity, the
GVL hand-off of ADR 012, signals, exceptions) beside the loop. Long
term, Tokra's Ruby reaches its native layer through one seam, a
process loads the Ferro gem in place of the extension, never beside
it, and the extension is deleted.

About 990 lines are code where Tauri itself is the function the
platform calls inside the native loop: window procedures, COM
handlers, GTK signal handlers. Ruby cannot soundly be those callbacks
with what it ships. They stay Rust, in the windowing library, a
recorded exception to Ferro's rule against adding what a crate lacks,
unless a spike of the `ffi` gem shows Ruby can hold them.

[The native layer's design](../design/native.md) lists which crates
keep process-wide state and how a crate's API is translated into Ruby;
[the plugins design](../design/plugins.md) says how a plugin builds on
a Ferro gem.

Confidence: high for the standalone crates, which five plugins are
built on. For the windowing move, medium that the stages are sound and
low on their size: no stage is built, the gem's size is an estimate
(about 11,000 to 15,000 lines of non-test Rust, more than the
extension it replaces), the cost of delivering every raw event to Ruby
is unmeasured, and the audit lists nine unknowns. Revisit at the end
of each stage.

### Consequences

- Good, because Tokra and its plugins answer to Tauri alone, in one
  language, and a port needs no Rust.
- Good, because each binding is checked against one source, and Ferro
  stands on its own for Rubyists who want a clipboard and nothing of
  Tokra.
- Good, because the windowing crates, which share process-wide state,
  are linked once.
- Bad, because the total Rust grows: Ferro's windowing gem will be
  larger than the extension it replaces.
- Bad, because a Tokra change that needs a Ferro API waits for a Ferro
  release: Tokra depends only on released Ferro versions, a published
  gem or a release tag named as a git source, never a path or an
  unpushed commit, since a Tokra contributor clones Tokra alone.
- Bad, because the switch cannot be gradual within a process, so two
  backends live behind one seam until the Ferro one passes the whole
  suite.
- Bad, because the platform callbacks are Tauri's logic kept in Rust,
  outside Tokra's repository, until Ruby can hold them.
- Bad, because a platform issue is traced through two projects, and
  installing a Tokra app's gems still compiles Rust.
- Bad, because the work is large against a 1.0 that also needs the
  rest of Tauri ported.

### Confirmation

A plugin's packaging tests check that its gem ships no native
extension and depends on its Ferro gem, as
`plugins/clipboard/test/test_clipboard.rb` does. Until the switch,
nothing automated keeps Tauri's logic out of `ext/tokra`: a reviewer
checks it, as AGENTS.md's Project section asks. At the switch, the
packaging check proves the `tokra` gem loads with no compiler. No
automated check enforces one native home per crate.

bindings) and the former ADR 011 (crate bindings live in Ferro, and
the windowing stack stays in Tokra), with the windowing choice changed.
