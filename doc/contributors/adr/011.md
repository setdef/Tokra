# ADR 011: Crate Bindings Move to Ferro

## Status

Accepted. Amends ADR 006 §3.2, §4, §5.5, §5.6, and §7.2.

## Date

2026-10-24

## Context

ADR 006 told every first-party plugin that wraps a Rust crate to carry its own
Rust: `tokra-clipboard` ships `ext/tokra_clipboard`, a magnus binding over
arboard, and the planned dialog, notification, and global-shortcut plugins
would each do the same. That puts two jobs in one gem. The binding answers to
the crate: arboard's types, errors, and edge cases. The plugin answers to
Tauri: `clipboard-manager`'s commands, wire formats, and messages. Mixed
together, neither has a clean answer key. The clipboard audit (plan 016) found
bugs in exactly that seam. A zero-size image reached arboard's macOS backend
unchecked and panicked the VM, and malformed payloads hung the invoke instead
of rejecting with Tauri's message.

Ferro is a separate project of gems that bind Rust crates to Ruby 1:1:
`ferro-arboard`, `ferro-rfd`, `ferro-notify-rust`, and so on. Its gems add no
Ruby-isms and no functionality the crate lacks. If Tokra's plugins build on
Ferro, every plugin port becomes pure Ruby, which is the end state ADR 005
describes, and each layer gets one answer key: the crate for Ferro, Tauri for
Tokra. Ferro also stands on its own, for Rubyists who want a clipboard in a
command-line tool and nothing of Tokra.

Two technical limits shape how far this goes. Research against each crate's
latest release tag, and against Tokra's locked versions where they differ,
settled what each limit covers.

1. **A Rust value cannot enter another gem's Rust API.** magnus checks every
   wrapped object against its own gem's type record, so handing a `ferro-tao`
   window to a `ferro-wry` method raises `TypeError` (magnus
   `r_typed_data.rs:380-400`). Plain Ruby values and byte strings cross
   freely. So do raw window handles passed as Integers, and several crates
   take exactly that by design: wry and rfd take any `HasWindowHandle`, and
   muda takes an `isize` HWND or a GTK window. A raw handle is unsafe, though:
   nothing tracks the window's lifetime, and the handle works only on the
   thread that owns the window.
2. **Some crates keep process-wide state.** Each extension keeps its Rust
   symbols private (rustc exports only `Init_*` and `ruby_abi_version`), so two
   copies of a crate never share code. The danger is state the operating
   system keeps once per process:

   | Crate | A second copy in the process |
   |---|---|
   | tao, every version | crashes: fixed Objective-C class names, and NSApp's one delegate |
   | tray-icon, every version | crashes: the fixed `TaoTrayTarget` class |
   | wry before 0.54.3 (Tokra locks 0.54.1) | crashes: fixed class names |
   | muda, with objc2 0.6.3 in either lockfile | crashes; on Windows, menu IDs also clash on a shared window |
   | global-hotkey | misroutes: on macOS the last copy swallows every hotkey |
   | notify-rust (macOS) | misroutes: each copy undoes the other's bundle hook and steals its delegate |
   | crossterm | misroutes: two copies race on stdin and terminal mode |

   arboard, rfd, open, os_info, sys-locale, auto-launch, keyring, image, and
   dirs keep no such state. A second copy of them, even at another version, is
   harmless.

Two pairs only work together. tray-icon takes muda's menu objects, and ratatui
takes crossterm's backend and shares its terminal state. One more coupling
reaches into the event loop: muda's keyboard accelerators on Windows need the
loop that owns the window to call `TranslateAcceleratorW`. The rest of the
windowing crates need an OS event loop on the right thread, not tao's, and
global-hotkey on Linux runs its own thread.

## Decision

### 1. Ferro binds standalone crates first; the windowing stack waits

Phase 1 covers crates with no colliding state and no coupling: arboard, rfd,
and similar. global-hotkey and notify-rust also qualify, because nothing else
links them: Ferro becomes their one native home. tao and wry stay in Tokra's
own extension, and muda and tray-icon wait with them, until a later ADR
settles where the windowing stack lives. That ADR weighs three candidates:
keep the stack in Tokra; move it into one Ferro gem behind a single native
library; or bind wry and muda in Ferro and hand them Tokra's window as a raw
handle, accepting the lifetime and thread risks above.

A crate in the table above gets exactly one native home: no two gems that one
app might load link it. tray-icon and muda share one gem, as do ratatui and
crossterm. RatatuiRuby links both today, so a Ferro gem for them waits until
RatatuiRuby can build on it instead.

Ferro binds crates that add something Ruby lacks. It skips crates that
duplicate the standard library or a popular gem, such as `serde_json`.

### 2. A Ferro gem mirrors its crate

Ferro follows Tokra's precedence with the crate in Tauri's place: Ruby the
language first, then fidelity to the crate, then Ruby culture. Rust constructs
with no Ruby meaning are translated, never ported.

| Rust | Ruby |
|---|---|
| crate `arboard` | gem `ferro-arboard`, `require "ferro/arboard"`, module `Ferro::Arboard` |
| type, method, and variant names | kept: `Clipboard#get_text`, `ImageData`, `Error::ContentNotAvailable` |
| `Result<T, E>` | returns `T`, or raises |
| an error enum | an exception class per variant under the crate's `Error < StandardError`, with the crate's `Display` text as the message |
| `Option<T>` | `T` or `nil` |
| `String`, `&str`, `Cow<str>`, `impl Into<Cow<str>>` | `String` |
| `Vec<u8>`, `&[u8]`, `Cow<[u8]>` | binary `String` |
| `PathBuf`, `&Path`, `impl AsRef<Path>` | `String` |
| a struct with public fields | `Data.define` |
| a borrowing builder (`clipboard.get().text()`) | an object that holds its clipboard: `clipboard.get.text` |
| lifetimes, `self` consumption, `Send`/`Sync` bounds | dropped; documented where they change behavior |
| a Cargo feature | supported, built in |
| a `#[cfg(target_os)]` item or platform trait | defined only on that platform, so `respond_to?` answers |

The crate's rustdoc, examples, and tests are the answer key. Tests run
against the real crate, never a stub. A deviation the table does not cover is
a design call and gets written down in the gem's docs.

### 3. Each gem builds alone and links the same pins

Each gem is its own Cargo workspace with a committed `Cargo.lock`, built with
`--locked`, as Tokra's gems are (plan 017). An installed gem compiles from its
packaged files alone, so `workspace = true` inheritance and a root lockfile
would not ship. During development the root Rakefile points every gem at one
shared target directory through `RB_SYS_CARGO_TARGET_DIR`, which rb-sys's
generated Makefile honors, so a dependency compiles once. A root check fails
the gate when two gems pin different magnus or rb-sys versions.

### 4. One repository of plain folders

Ferro is one repository with one gem per folder under `gems/`. Submodules
would split the history without making a gem clonable on its own, since each
gem still needs the root tooling. Commits use scoped Conventional Commits,
such as `fix(arboard): …`, so `git log -- gems/arboard` reads like the gem's
own history.

### 5. Each gem versions and releases on its own

A gem's version answers to its own API, not the crate's, and the crate
version it binds appears in its README and gemspec metadata. Release tags
carry the gem name: `ferro-arboard/v0.1.0`. A root release task replaces
`bundler/gem_tasks`, whose `v0.1.0` tags would collide between gems.
Releasing stays a human step.

### 6. Each gem takes its crate's license; the shared code takes the copyleft one

A gem's Ruby and Rust code takes the license of the crate it binds:
`ferro-arboard` is `MIT OR Apache-2.0` because arboard is. That keeps a
binding as reusable as the code it binds.

Code that belongs to no crate follows RatatuiRuby's split. Shared code that
apps link at runtime is `LGPL-3.0-or-later`, so an app may use it without
taking on copyleft. Tooling that apps never link, such as the root Rakefile,
the gate's tasks, and any devtools gem, is `AGPL-3.0-or-later`. Docs are
`CC-BY-SA-4.0`, code snippets in docs are `MIT-0` so readers can paste them
freely, and lockfiles are `CC0-1.0`.

Tokra stays AGPL-3.0-or-later and depends on Ferro gems the way it depends on
any permissively licensed library.

### 7. Ferro owns no Ractor design

A Ferro gem exposes the crate's types as plain Ruby objects. It marks the
extension Ractor-safe only where the crate's types allow calls from any
thread, and it freezes and shares objects only where the crate's types are
`Sync`. Tokra's Ractor rules (ADR 007) stay in Tokra's plugins, which decide
where a Ferro object lives.

### 8. Ferro supports every Ruby that still gets fixes, from 4.0 on

Ferro gems require Ruby 4.0 or later, as Tokra does, and CI runs on each
supported release. When a new Ruby ships, Ferro adds it and keeps the older
ones until they reach end of life. Only then does the floor rise. Ferro uses
no Ruby 4.0 feature, so the floor could drop to 3.x later; dropping it never
breaks anyone, while raising it does.

### 9. Tokra plugins become pure Ruby

This amends ADR 006:

- **§3.2:** "Port" now means a pure Ruby plugin over a Ferro gem. The plugin
  maps Tauri's commands, payloads, and error messages onto the Ferro gem's
  API.
- **§4 and §5.6:** a third-party plugin that wraps a crate builds on a Ferro
  gem, or contributes one to Ferro, rather than shipping its own extension.
- **§5.5:** the Thin Binding type becomes "Ferro-backed": no Rust in the
  plugin gem.
- **§7.2:** first-party plugins stay in `plugins/`. Plugin gems carry no
  `ext/` once their Ferro gem exists.

`tokra-clipboard` goes first, once `ferro-arboard` is released. It depends on `ferro-arboard`, loses
`ext/tokra_clipboard`, and keeps its Tauri behavior and tests. The plan 016
fixes move to the layer each belongs to. `ferro-arboard` refuses an image
arboard would panic on, raising the crate's `ConversionFailure`. The plugin
validates Tauri's payloads and turns `Ferro::Arboard::Error` subclasses into
`clipboard-manager`'s messages.

## Consequences

- Plugin ports need no Rust, and a reviewer checks each layer against one
  source.
- Tokra depends only on released Ferro gems, never on a git or path source. A
  Tokra change that needs a Ferro API waits until that Ferro version is
  published, so Ferro work comes first and Tokra keeps its current code until
  then. `tokra-clipboard` keeps `ext/tokra_clipboard` until `ferro-arboard`
  ships.
- Ferro needs its own gate, docs, and agent instructions. Its pilot copies
  Tokra's: tests, RuboCop, Steep, RBS parity, RDoc coverage, REUSE, Clippy,
  fmt, and the packaging check.
- Any windowing option that splits crates across gems first needs Tokra on
  wry 0.54.3 or later and objc2 0.6.4 or later, the releases that stopped
  panicking on a second copy.
- The windowing stack stays where it is, so Tokra keeps one Rust extension
  until the later ADR.
