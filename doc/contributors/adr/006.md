# ADR 006: Plugin Architecture

## Status
Accepted. Amended by [ADR 011](011.md): crate bindings move to Ferro, and
plugins that wrap a crate become pure Ruby.

## Date
2026-01-31

## Context
Tokra needs a plugin system to extend functionality beyond the core WebView/Window/EventLoop infrastructure. This ADR documents:
1. How Tauri's plugin system works (for reference)
2. Tokra's strategy for porting vs. wrapping Tauri plugins
3. The Ruby plugin API design
4. First-party plugin distribution strategy

---

## Decision

### 1. How Tauri's Plugin System Works

Tauri plugins follow a well-defined architecture with three distinct layers:

### 1.1. The `Plugin` Trait

The core abstraction is the `Plugin<R: Runtime>` trait ([tauri/crates/tauri/src/plugin.rs](https://github.com/tauri-apps/tauri/blob/9f0306fbcc091148602c04df7286ddec154d4150/crates/tauri/src/plugin.rs#L37-L112)):

```rust
pub trait Plugin<R: Runtime>: Send {
    fn name(&self) -> &'static str;                         // Required: unique identifier
    fn initialize(&mut self, app: &AppHandle<R>, config: JsonValue) -> Result<(), Error>;
    fn initialization_script(&self) -> Option<String>;      // JS to inject
    fn window_created(&mut self, window: Window<R>);
    fn webview_created(&mut self, webview: Webview<R>);
    fn on_navigation(&mut self, webview: &Webview<R>, url: &Url) -> bool;
    fn on_page_load(&mut self, webview: &Webview<R>, payload: &PageLoadPayload);
    fn on_event(&mut self, app: &AppHandle<R>, event: &RunEvent);
    fn extend_api(&mut self, invoke: Invoke<R>) -> bool;    // Handle IPC commands
}
```

**Key Insight:** Plugins hook into the application lifecycle at multiple points, receiving events and optionally handling IPC commands.

### 1.2. The Plugin Builder

Tauri provides a `plugin::Builder` ([tauri/crates/tauri/src/plugin.rs](https://github.com/tauri-apps/tauri/blob/9f0306fbcc091148602c04df7286ddec154d4150/crates/tauri/src/plugin.rs#L264-L756)) that wraps the trait with a fluent API:

```rust
Builder::new("my-plugin")
    .invoke_handler(tauri::generate_handler![cmd1, cmd2])  // IPC commands
    .setup(|app, api| { /* setup logic */ Ok(()) })
    .js_init_script("window.__my_plugin = {};")
    .on_event(|app, event| { /* handle events */ })
    .on_page_load(|webview, payload| { /* handle page loads */ })
    .register_uri_scheme_protocol("myscheme", |ctx, req| { ... })
    .build()
```

### 1.3. The `#[tauri::command]` Macro

For IPC, Tauri uses a procedural macro to generate command handlers:

```rust
#[tauri::command]
fn my_command(app: AppHandle<R>, state: State<'_, MyState>) -> Result<String, Error> {
    Ok("result".into())
}
```

The `generate_handler![]` macro creates a dispatch function that routes commands to the appropriate handler.

### 1.4. Plugin Registration

Plugins are registered on the main `Builder`:

```rust
tauri::Builder::default()
    .plugin(my_plugin::init())
    .run(tauri::generate_context!())
```

## 2. How Plugin Authors Write Rust Tauri Plugins

Looking at official plugins (`global-shortcut`, `dialog`, `clipboard-manager`), the pattern is:

### 2.1. Standard File Structure

```
my-plugin/
├── Cargo.toml
├── build.rs           # Permission generation
├── src/
│   ├── lib.rs         # Plugin init() + Builder
│   ├── commands.rs    # #[tauri::command] functions
│   ├── desktop.rs     # Desktop-specific implementation
│   ├── mobile.rs      # Mobile-specific implementation
│   └── error.rs       # Error types
├── guest-js/          # JavaScript API for frontend
├── permissions/       # Capability definitions
└── package.json       # NPM package for JS bindings
```

### 2.2. The `init()` Convention

Every plugin exports an `init<R: Runtime>() -> TauriPlugin<R>` function:

```rust
// From clipboard-manager/src/lib.rs
pub fn init<R: Runtime>() -> TauriPlugin<R> {
    Builder::new("clipboard-manager")
        .invoke_handler(tauri::generate_handler![
            commands::write_text,
            commands::read_text,
            commands::clear,
        ])
        .setup(|app, api| {
            let clipboard = desktop::init(app, api)?;
            app.manage(clipboard);  // Register state
            Ok(())
        })
        .on_event(|app, event| {
            if let RunEvent::Exit = event {
                app.clipboard().cleanup();
            }
        })
        .build()
}
```

### 2.3. Extension Traits

Plugins expose functionality via extension traits that work on `AppHandle`:

```rust
pub trait ClipboardExt<R: Runtime> {
    fn clipboard(&self) -> &Clipboard<R>;
}

impl<R: Runtime, T: Manager<R>> ClipboardExt<R> for T {
    fn clipboard(&self) -> &Clipboard<R> {
        self.state::<Clipboard<R>>().inner()
    }
}
```

This allows `app.clipboard().read_text()` anywhere you have an `AppHandle`.

## 3. Tokra Plugin Strategy: Wrap, Port, or Case-by-Case?

### 3.1. Analysis

| Factor | Wrap | Port | 
|--------|------|------|
| **Definition** | Use Tauri plugin crate directly, wrap with Ruby API | Rewrite functionality using underlying crate directly |
| **Maintenance** | Inherits Tauri updates automatically | Must manually track upstream changes |
| **Dependencies** | Brings in `tauri-*` crates | Only brings in `global-hotkey`, `arboard`, etc. |
| **Binary Size** | Larger (includes Tauri runtime code) | Smaller (only what we need) |
| **API Surface** | May expose unnecessary complexity | Tailored to Tokra's Ruby-Host model |
| **Ractor Safety** | Unknown—may require extensive adaptation | Can be designed Ractor-safe from scratch |

### 3.2. Recommendation: Case-by-Case with a Bias Toward Porting

**Default: Port** — Tokra uses underlying crates directly (`global-hotkey`, `arboard`, `rfd`, `muda`, `tray-icon`, `notify-rust`) rather than Tauri plugins.

**Rationale:**
1. **Thin Binding Principle (ADR 001/005):** Tokra's architecture deliberately minimizes Rust code. Tauri plugins contain significant Rust logic that we don't need.
2. **Ruby-Host Model:** Tauri plugins expect `AppHandle<R>` and the Tauri runtime. Tokra's model passes raw events to Ruby where all logic lives.
3. **Ractor Safety:** Tauri plugins aren't designed for Ractor isolation. Porting allows us to ensure all callbacks are Ractor-shareable.
4. **Binary Size:** Each Tauri crate brings its own dependencies. Direct crate usage is leaner.

**Decision Matrix:**

| Plugin | Strategy | Rationale |
|--------|----------|-----------|
| `global-shortcut` | **Port** | Uses `global-hotkey` crate directly. Simple API. |
| `dialog` | **Port** | Uses `rfd` crate directly. Straightforward file picker. |
| `clipboard-manager` | **Port** | Uses `arboard` crate directly. Already in ADR 005. |
| `notification` | **Port** | Uses `notify-rust`. Already in ADR 005. |
| `fs` | **Skip** | Ruby has native filesystem. No Rust needed. |
| `http` | **Skip** | Ruby has `Net::HTTP`. No Rust needed. |
| `updater` | **Pure Ruby** | Uses `Net::HTTP` + `OpenSSL`. No Rust needed. |
| `log` | **Pure Ruby** | Uses Ruby `Logger`. No Rust needed. |
| `store` | **Pure Ruby** | Uses `YAML` or `PStore`. No Rust needed. |

**Exception: When to Wrap**
If a Tauri plugin provides complex platform-specific behavior that would be costly to reimplement (e.g., `deep-link` on Windows/Linux), consider wrapping. However, even then, prefer extracting just the platform crate if one exists.

## 4. How Other Devs Can Wrap or Port Tauri Plugins for Tokra

Third-party plugins should be packaged as **separate gems** that depend on `tokra`. This section explains how to create a Tokra plugin gem.

### 4.1. Plugin Gem Structure

Create a new gem with a Rust extension:

```
tokra-global_shortcut/
├── Gemfile
├── tokra-global_shortcut.gemspec
├── ext/
│   └── tokra_global_shortcut/
│       ├── Cargo.toml
│       ├── extconf.rb
│       └── src/
│           └── lib.rs           # Magnus bindings
├── lib/
│   ├── tokra-global_shortcut.rb # Main require
│   └── tokra/
│       └── plugins/
│           └── global_shortcut.rb  # Plugin class
└── test/
```

### 4.2. Porting Guide (Recommended)

To port a Tauri plugin to a Tokra plugin gem:

1. **Identify the underlying crate** — Tauri plugins are wrappers. Find what they wrap:
   - `global-shortcut` → `global-hotkey`
   - `dialog` → `rfd`
   - `clipboard-manager` → `arboard`
   - `notification` → `notify-rust`

2. **Create a new gem** with `bundle gem tokra-<feature> --ext=rust`

3. **Add dependencies to your gem's `Cargo.toml`**:
   ```toml
   [dependencies]
   magnus = "0.7"
   global-hotkey = "0.6"
   ```

4. **Create Rust bindings** in `ext/tokra_<feature>/src/lib.rs`:
   ```rust
   use magnus::{define_module, prelude::*, Error, Ruby};
   use global_hotkey::{GlobalHotKeyManager, hotkey::HotKey};

   #[magnus::wrap(class = "TokraGlobalShortcut::Native::Manager")]
   struct RbManager { /* ... */ }

   #[magnus::init]
   fn init(ruby: &Ruby) -> Result<(), Error> {
       let module = ruby.define_module("TokraGlobalShortcut")?;
       let native = module.define_module("Native")?;
       // ... define classes and methods
       Ok(())
   }
   ```

5. **Create the Plugin class** in `lib/tokra/plugins/global_shortcut.rb`:
   ```ruby
   require "tokra"
   require "tokra_global_shortcut/tokra_global_shortcut" # Load native extension

   module Tokra
     module Plugins
       class GlobalShortcut < Tokra::Plugin
         def name = "global-shortcut"

         def initialize(app, config = {})
           super
           @native = TokraGlobalShortcut::Native::Manager.new
           @shortcuts = {}
         end

         def register(accelerator, &handler)
           raise Tokra::Error, "Handler must be Ractor-shareable" unless Ractor.shareable?(handler)
           id = @native.register(accelerator)
           @shortcuts[id] = handler
           id
         end

         def on_event(app, event)
           return unless event.is_a?(GlobalShortcutEvent)
           @shortcuts[event.id]&.call(event)
         end
       end
     end
   end
   ```

6. **Add `tokra` as a runtime dependency** in your gemspec:
   ```ruby
   spec.add_dependency "tokra", "~> 0.1"
   ```

### 4.3. Pure Ruby Plugin Guide

For plugins that don't need native code:

```ruby
# lib/tokra/plugins/my_logger.rb
module Tokra
  module Plugins
    class MyLogger < Tokra::Plugin
      def name = "my-logger"

      def initialize(app, config = {})
        super
        @logger = Logger.new(config[:path] || $stdout)
      end

      def on_event(app, event)
        @logger.info("Event: #{event.class}")
      end
    end
  end
end
```

### 4.4. Wrapping Guide (When Necessary)

If you must wrap an existing Tauri plugin crate directly:

> [!CAUTION]
> This approach is discouraged. Only use if the underlying platform crate is not directly usable.

1. Add the Tauri plugin crate to your gem's `Cargo.toml`
2. Create Magnus wrappers that expose the Rust API
3. Handle the mismatch between Tauri's `AppHandle` and Tokra's Plugin model
4. Ensure all callbacks are Ractor-shareable

## 5. Tokra Plugin System: Ruby and Ruby+Rust Plugins

### 5.1. Plugin Trait (Ruby)

Based on Tauri's `Plugin` trait, adapted for Ruby idioms:

```ruby
# lib/tokra/plugin.rb
module Tokra
  # Base class for Tokra plugins.
  #
  # Plugins extend application functionality through lifecycle hooks.
  # All hook methods receive immutable, Ractor-shareable arguments.
  class Plugin
    # @return [String] unique plugin identifier
    def name
      raise NotImplementedError, "Subclass must implement #name"
    end

    # Called when the plugin is registered.
    # @param app [AppHandle] the application handle
    # @param config [Hash] plugin configuration from tokra.conf.json
    def initialize(app, config = {})
      @app = app
      @config = config
    end

    # JavaScript to inject into all webviews.
    # @return [String, nil] initialization script or nil
    def initialization_script
      nil
    end

    # Called when a window is created.
    # @param window [Window] the new window
    def window_created(window)
    end

    # Called when a webview is created.
    # @param webview [Webview] the new webview
    def webview_created(webview)
    end

    # Called when a page load event occurs.
    # @param webview [Webview] the webview
    # @param payload [PageLoadPayload] load details
    def on_page_load(webview, payload)
    end

    # Called on each run loop event.
    # @param app [AppHandle] the application handle
    # @param event [RunEvent] the event
    def on_event(app, event)
    end

    # Handle IPC commands for this plugin.
    # @param invoke [Invoke] the invocation details
    # @return [Boolean] true if handled, false to pass to next handler
    def extend_api(invoke)
      false
    end
  end
end
```

### 5.2. PluginApi (Ruby)

Mirrors Tauri's `PluginApi` struct—passed to plugins during setup:

```ruby
# lib/tokra/plugin_api.rb
module Tokra
  # Api exposed to plugins during initialization.
  #
  # Wraps the app handle and plugin-specific configuration.
  # Future: may include permission scopes.
  PluginApi = Data.define(:app, :config, :name)
end
```

Plugins receive this in their setup hook:

```ruby
def setup(api)
  @app = api.app
  @config = api.config
  @logger = Logger.new(api.config[:path])
end
```

### 5.3. Plugin Builder (Ruby)

For convenience, provide a builder pattern similar to Tauri:

```ruby
# lib/tokra/plugin/builder.rb
module Tokra
  class PluginBuilder
    def initialize(name)
      @name = name
      @invoke_handler = nil
      @setup = nil
      @on_event = nil
      @js_init_script = nil
    end

    def invoke_handler(&block)
      @invoke_handler = block
      self
    end

    def setup(&block)
      @setup = block
      self
    end

    def on_event(&block)
      @on_event = block
      self
    end

    def js_init_script(script)
      @js_init_script = script
      self
    end

    def build
      # Return a Plugin subclass instance with configured hooks
      BuiltPlugin.new(
        name: @name,
        invoke_handler: @invoke_handler,
        setup: @setup,
        on_event: @on_event,
        js_init_script: @js_init_script
      )
    end
  end
end
```

### 5.4. Plugin Registration

Extend `Tokra::Builder` to accept plugins:

```ruby
# In lib/tokra/builder.rb
def plugin(plugin_instance)
  @plugins ||= []
  @plugins << plugin_instance
  self
end
```

### 5.5. Plugin Types

Tokra will support three types of plugins:

| Type | Description | Example |
|------|-------------|---------|
| **Pure Ruby** | No Rust code. Uses Ruby stdlib or gems. | Updater, Logger, Store |
| **Thin Binding** | Minimal Rust wrapper + rich Ruby API. | GlobalShortcut, Clipboard, Dialogs |
| **Full Rust** | Complex native code with Ruby interface. | (Reserved for future needs) |

### 5.6. Ruby+Rust (Magnus) Plugin Example

For plugins requiring native code:

```ruby
# lib/tokra/plugins/global_shortcut.rb
module Tokra
  module Plugins
    class GlobalShortcut < Plugin
      def name
        "global-shortcut"
      end

      def initialize(app, config = {})
        super
        @shortcuts = {}
        @native = Native::GlobalShortcutManager.new
      end

      # Register a shortcut with a handler.
      # @param accelerator [String] e.g., "CmdOrCtrl+Shift+P"
      # @param handler [Proc] Ractor-shareable callback
      def register(accelerator, &handler)
        raise Error, "Handler must be Ractor-shareable" unless Ractor.shareable?(handler)
        id = @native.register(accelerator)
        @shortcuts[id] = handler
        id
      end

      def on_event(app, event)
        return unless event.is_a?(GlobalShortcutEvent)
        @shortcuts[event.id]&.call(event)
      end
    end
  end
end
```

### 5.7. State Management and Extension Traits

This section clarifies three patterns that ensure 1:1 API parity with Tauri.

#### 5.7.1. How Plugins Add Methods to Manager

Tauri uses Rust extension traits to add convenience methods like `app.clipboard()`:

```rust
// Tauri: compile-time extension trait
pub trait ClipboardExt<R: Runtime> {
    fn clipboard(&self) -> &Clipboard<R>;
}

impl<R: Runtime, T: Manager<R>> ClipboardExt<R> for T {
    fn clipboard(&self) -> &Clipboard<R> {
        self.state::<Clipboard<R>>().inner()
    }
}
```

**Ruby Recommendation: `Module#include` at require time**

```ruby
# lib/tokra/plugins/clipboard.rb
module Tokra::Plugins::Clipboard
  module ManagerExt
    def clipboard
      state(TokraClipboard::Native::Clipboard)
    end
  end
end

# Extend Manager when the plugin is loaded
Tokra::Manager.include(Tokra::Plugins::Clipboard::ManagerExt)
```

This approach:
- **Matches Tauri semantics** — methods are available after `require`, just like Rust `use`
- **Zero runtime overhead** — Ruby's `include` is O(1) and permanent
- **Pure Ruby** — no additional Rust needed
- **Idiomatic** — standard pattern for extending modules (e.g., ActiveSupport)

#### 5.7.2. Plugin Instance vs. Managed State

Tauri distinguishes between the **plugin instance** and **managed state**:

```rust
// Tauri: Plugin registers STATE, not itself
.setup(|app, api| {
    let clipboard = desktop::init(app, api)?;  // Create Clipboard struct
    app.manage(clipboard);                      // Register as state
    Ok(())
})

// Extension trait retrieves STATE by type
fn clipboard(&self) -> &Clipboard<R> {
    self.state::<Clipboard<R>>().inner()
}
```

**Ruby mirrors this exactly:**

```ruby
class Clipboard < Tokra::Plugin
  def initialize(app, config = {})
    super
    # Create managed state (the Ractor-shareable native clipboard)
    clipboard_state = TokraClipboard::Native::Clipboard.new
    Ractor.make_shareable(clipboard_state)
    
    # Register state by CLASS, not by plugin instance
    app.manage(clipboard_state)
  end
end
```

Key distinction:
- **Plugin instance** — receives lifecycle hooks (`on_event`, `on_page_load`, etc.)
- **Managed state** — the data accessible via `app.state(klass)` and extension methods

#### 5.7.3. State Storage Architecture

| Concept | Tauri | Tokra |
|---------|-------|-------|
| **Plugin storage** | `PluginManager` internal vec | `@plugins` array |
| **State storage** | `TypeId`-keyed `StateManager` | `@state` hash keyed by class |
| **State registration** | `app.manage(instance)` | `app.manage(instance)` |
| **State retrieval** | `app.state::<T>()` | `app.state(T)` |
| **State panics if missing** | Yes | Yes |
| **Optional retrieval** | `app.try_state::<T>()` | `app.try_state(T)` |

**Implementation:**

```ruby
# lib/tokra/app.rb
class Tokra::App
  def initialize
    @plugins = []     # Plugin instances (for lifecycle hooks)
    @state = {}       # Managed state (keyed by class)
  end
  
  def register_plugin(plugin)
    @plugins << plugin
    plugin.initialize(self, config_for(plugin.name))
  end
  
  # Registers state, keyed by its class
  def manage(state_instance)
    @state[state_instance.class] = state_instance
    true  # Returns true if newly registered (Tauri compat)
  end
  
  # Retrieves state by class, panics if missing
  def state(klass)
    @state.fetch(klass) do
      raise "state() called before manage() for #{klass}"
    end
  end
  
  # Optional retrieval
  def try_state(klass)
    @state[klass]
  end
end
```

This design enables:
1. **Stateless plugins** — A logger plugin might not `manage` anything
2. **Shared state** — Plugin A can register state that Plugin B reads
3. **State survives plugin hot-reload** — (future capability)
4. **Cross-Ractor state** — ADR-007 `frozen_shareable` state works with this model

## 6. Plugin Configuration: `tokra.conf.json`

Tokra follows Tauri's configuration pattern: applications can define a `tokra.conf.json` file, and plugin-specific configuration lives under the `plugins.<name>` key.

### 6.1. How Tauri Does It

In Tauri, `tauri.conf.json` contains a `plugins` object where each key is a plugin name and the value is that plugin's configuration:

```json
{
  "plugins": {
    "cli": {
      "description": "My CLI",
      "args": [{"name": "verbose", "short": "v"}]
    },
    "log": {
      "level": "info"
    }
  }
}
```

When a plugin is initialized, Tauri passes the plugin's config slice as a `JsonValue`:

```rust
fn initialize(&mut self, app: &AppHandle<R>, config: JsonValue) -> Result<(), Error>
```

### 6.2. Tokra's Approach

Tokra mirrors this pattern using Ruby's stdlib `JSON`:

```json
// tokra.conf.json
{
  "app": {
    "title": "My App",
    "width": 800,
    "height": 600
  },
  "plugins": {
    "log": {
      "level": "info",
      "path": "logs/app.log"
    },
    "clipboard": {}
  }
}
```

The `Tokra::Builder` reads this file and passes each plugin's config hash to its constructor:

```ruby
# In lib/tokra/builder.rb
def load_config(path = "tokra.conf.json")
  return {} unless File.exist?(path)
  JSON.parse(File.read(path), symbolize_names: true)
end

def build
  config = load_config
  @plugins.each do |plugin|
    plugin_config = config.dig(:plugins, plugin.name.to_sym) || {}
    plugin.send(:initialize, @app_handle, plugin_config)
  end
  # ...
end
```

### 6.3. Plugin Constructor Signature

The `initialize` method receives the config as a Hash—matching Tauri's `JsonValue` semantics:

```ruby
def initialize(app, config = {})
  @app = app
  @config = config
end
```

**Why Hash and not kwargs?**

1. **Tauri parity**: Plugins receive a config object (`JsonValue`), not named arguments
2. **Subclass flexibility**: Subclasses receive config through `super`, not redeclared kwargs
3. **Unknown keys**: Plugins may define config keys the base class doesn't know about

Plugins should document their expected config keys and validate at initialization time.

### 6.4. Programmatic Override

If no config file exists, or for testing, config can be passed programmatically:

```ruby
Tokra::Builder.new
  .plugin(Tokra::Plugins::Log::Plugin.new(app, level: :debug, path: "test.log"))
  .run
```

Both approaches work because `initialize(app, config = {})` accepts any Hash.

## 7. First-Party Plugin Distribution Strategy

### 7.1. Options Considered

| Approach | Description | Pros | Cons |
|----------|-------------|------|------|
| **In-core monolith** | All plugins in `lib/tokra/plugins/` as one gem | Simple; single install | Bloated binary; all-or-nothing |
| **Separate monorepo** | `tokra-plugins/` repo with multiple gems | Coordinated releases | Context-switching; extra repo to maintain |
| **Individual repos** | Each plugin in its own repo | Focused PRs/issues | Version coordination; repos go stale |
| **Rails pattern** | One repo, multiple gemspecs | No context-switching; atomic commits | Slightly more complex release process |

### 7.2. Recommendation: Rails Pattern (One Repo, Multiple Gems)

First-party plugins should live **in the main Tokra repo** with their own gemspecs:

```
tokra/
├── tokra.gemspec                # Core gem (~500 LOC Rust)
├── lib/tokra/                   # Core Ruby API
├── ext/tokra/                   # Core Rust extension
│
├── plugins/
│   ├── clipboard/
│   │   ├── tokra-clipboard.gemspec
│   │   ├── ext/tokra_clipboard/     # Rust bindings for arboard
│   │   └── lib/tokra/plugins/clipboard.rb
│   ├── dialog/
│   │   ├── tokra-dialog.gemspec
│   │   ├── ext/tokra_dialog/        # Rust bindings for rfd
│   │   └── lib/tokra/plugins/dialog.rb
│   └── global-shortcut/
│       ├── tokra-global_shortcut.gemspec
│       ├── ext/tokra_global_shortcut/
│       └── lib/tokra/plugins/global_shortcut.rb
│
├── TOKRA_VERSION                # Shared version for all gems
└── Rakefile                     # Delegates to each plugin
```

### 7.3. Rationale

**Why not separate repos?**

Real-world experience with the ratatui_ruby ecosystem showed that separate repos (`ratatui_ruby/`, `ratatui_ruby-tea/`, `ratatui_ruby-devtools/`) led to the devtools repo going stale. The friction of context-switching caused development to consolidate in the main repo.

**Why the Rails pattern works:**

1. **No context-switching** — You're always in `tokra/`; no `cd ../tokra-plugins`
2. **Atomic commits** — Cross-plugin refactors are one commit, one PR
3. **Single CI workflow** — One `.github/workflows/` directory for everything
4. **Shared version** — `TOKRA_VERSION` keeps all plugins in sync
5. **20+ years proven** — Rails has maintained this pattern since 2004

**Precedents:**

| Project | Structure | Gems | Success |
|---------|-----------|------|---------|

### 7.4. Rake Task Organization

Root Rakefile delegates to each plugin:

```ruby
# Rakefile
PLUGINS = Dir["plugins/*"].select { |f| File.directory?(f) }

desc "Test all (core + plugins)"
task test: ["test:core", "test:plugins"]

namespace :test do
  task :core do
    sh "rake test:unit"
  end

  task :plugins do
    PLUGINS.each do |plugin|
      sh "cd #{plugin} && rake test"
    end
  end
end

desc "Build all gems"
task :build do
  sh "gem build tokra.gemspec"
  PLUGINS.each do |plugin|
    sh "cd #{plugin} && gem build *.gemspec"
  end
end

desc "Release all gems"
task :release do
  version = File.read("TOKRA_VERSION").strip
  # Coordinated release logic
end
```

Each plugin has its own simple Rakefile:

```ruby
# plugins/clipboard/Rakefile
require "rake/testtask"
require "rb_sys/extensiontask"

RbSys::ExtensionTask.new("tokra_clipboard") do |ext|
  ext.lib_dir = "lib/tokra/plugins"
end

Rake::TestTask.new do |t|
  t.pattern = "test/**/*_test.rb"
end

task default: [:compile, :test]
```

### 7.5. Version Coordination

All gems read from a shared `TOKRA_VERSION` file:

```ruby
# plugins/clipboard/tokra-clipboard.gemspec
version = File.read(File.expand_path("../../TOKRA_VERSION", __dir__)).strip

Gem::Specification.new do |s|
  s.name    = "tokra-clipboard"
  s.version = version
  s.add_dependency "tokra", "= #{version}"  # Exact version match
  # ...
end
```

## 8. Comparison Summary

| Aspect | Tauri | Tokra |
|--------|-------|-------|
| **Plugin trait** | Rust trait with 8+ methods | Ruby class with same 8+ methods |
| **Plugin builder** | `plugin::Builder` fluent API | `PluginBuilder` fluent API |
| **PluginApi** | `PluginApi<R, C>` struct | `PluginApi = Data.define(:app, :config, :name)` |
| **Config file** | `tauri.conf.json` with `plugins.<name>` | `tokra.conf.json` with `plugins.<name>` |
| **IPC commands** | `#[tauri::command]` macro + `generate_handler!` | Ruby blocks/procs |
| **State management** | `app.manage(state)` + `State<T>` extractor | `app.manage(state)` + `app.state(klass)` |
| **Manager trait** | Rust trait on `AppHandle`, `Window`, `Webview` | Ruby module included by `AppHandle`, `Window`, `Webview` |
| **Extension traits** | `impl<T: Manager<R>> MyExt<R> for T` | `module MyExt` included in `Manager` |
| **JS injection** | `initialization_script()` | `initialization_script()` |
| **Rust code** | Required for all plugins | Optional—Pure Ruby plugins possible* |
| **First-party distribution** | Separate `plugins-workspace` repo | In-repo `plugins/` directory |

\* The **only intentional difference**: Tokra's Ruby-Host architecture (ADR 001) enables pure Ruby plugins when no native code is needed. This is a feature, not a deviation—Ruby plugins for logging, storage, or updaters don't require Rust wrappers.
