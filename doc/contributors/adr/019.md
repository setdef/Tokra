# ADR 019: Tauri's Access Control Is Resolved When the App Starts

Supersedes ADR 010 §6's stopgap once the check is on. Until then the
stopgap stands.

## Context and Problem Statement

Tauri decides which page may call which command with capabilities,
permissions, and scopes. Most of that work happens before a Tauri app
runs. A plugin's build script generates its permission files. The app's
build script finds every plugin's files through Cargo's `links` key,
reads the app's `capabilities/` folder, and validates them
(`crates/tauri-build/src/acl.rs`). The `generate_context!` macro
resolves the result into the authority the app starts with
(`crates/tauri-codegen/src/context.rs`). At run time every `plugin:`
command is refused unless a capability grants it, from the app's own
pages too (`crates/tauri/src/webview/mod.rs:1801-1831`).

Tokra has no build step: it reads its config when the app starts
(ADR 014), and its plugins are gems. It has none of Tauri's access
control, only a stopgap that refuses every command from a remote origin
and answers every command from the app's own pages (ADR 010 §6). That
is stricter than Tauri for remote pages and looser for local ones.

Where does Tauri's build-time access control run in Tokra, and how does
an app's start find each plugin's permissions?

## Decision Drivers

- Tauri fidelity: the same files, names, validation errors, and
  refusals, so Tauri's documentation describes a Tokra app.
- Ruby has no compile step and no Cargo. A plugin is a gem.
- ADR 014: a failure Tauri reports when the app compiles, Tokra raises
  from `Tokra.generate_context`, before any window.
- Every plugin an app depends on contributes its permissions in Tauri,
  whether or not the app registers it.

## Considered Options

Where the build-time work runs:

1. In `Tokra.generate_context`, at start.
2. In `Builder#build`, from the plugins the builder holds.
3. In a rake or CLI task that writes a resolved file the app reads.

How a plugin's permissions are found:

- a. Gem metadata: each plugin gem names its manifest key and permission
  folder in its gemspec, read from the gems RubyGems activated.
- b. A declaration on each `Tokra::Plugin` subclass, gathered from the
  plugins the builder holds.
- c. A list passed to `generate_context`.

## Decision Outcome

Chosen: option 1 with option a, because together they are the closest
translation of what Cargo does. `generate_context` is where Tokra
already stands in for Tauri's compile step, so its `Context` arrives
resolved, as Tauri's does. Gem metadata stands in for the `links` key:
every plugin gem the app depends on contributes, registered or not.

What follows from it:

- An app's `capabilities/` and `permissions/` folders sit beside its
  config file, where every Tauri project keeps them.
- A plugin gem commits and packages its permission files, generated by
  a rake task, as Tauri's plugins commit theirs. The core plugins'
  permissions are built in memory from Tauri's table
  (`crates/tauri/build.rs:16-225`), since Tauri commits none of those.
- A plugin mirrors its Tauri original's permission files exactly, the
  ones for commands Tokra does not implement included, so a capability
  written for Tauri validates.
- The check turns on in one commit, which also gives every example,
  fixture, and test the capabilities it needs. Before that commit the
  authority is resolved and held, and checks nothing. From it on, an
  app needs a capability to call any plugin command, as in Tauri.
- A refusal carries Tauri's debug text in development and its release
  text in a packaged app (ADR 016 says which an app is).
- Tauri's behavior is ported as written where it surprises: a deny in
  any capability refuses that command everywhere
  (`crates/tauri/src/ipc/authority.rs:446-452`), a remote page may call
  app commands when the app defines no app permissions
  (`webview/mod.rs:1802`), and `add_capability` numbers a runtime
  capability's scopes from 1 again (`authority.rs:198-223`).
- tauri-build's `Attributes` (a capabilities path pattern, an app
  manifest of commands, inlined plugins) are not ported yet. A plugin
  that is not a gem has no permissions until they are.

Confidence: high that this matches Tauri for an app made of gems, which
every Tokra app is today. Lower for start-up cost: resolving on every
start has not been measured, and option 3 remains open as the form a
packaged app carries.

### Consequences

- Good, because a capability file, a permission name, and an error
  message from Tauri's documentation mean the same in Tokra.
- Good, because a broken capability stops the app before a window
  opens, where Tauri would stop the build.
- Good, because the special cases go: no rule of Tokra's own says which
  window commands a page may call.
- Bad, because every existing app breaks when the check turns on, until
  it gains a `capabilities/default.json`.
- Bad, because every start reads and resolves the files again.
- Bad, because a gemspec gains a contract: a plugin whose gem leaves
  the metadata out contributes nothing, and its commands are refused.
- Bad, because Tokra carries Tauri's surprises, the scope numbering
  above among them, until Tauri changes them.

### Confirmation

Tests resolve capabilities through `generate_context` from fixture
folders and compare each validation error with Tauri's text. Each
plugin's tests compare its committed permission files with what its
rake task generates. The real-window origin test covers a local page, a
remote page, and a command no capability grants.

## Pros and Cons of the Options

### In `Builder#build`

- Good, because the builder knows which plugins the app registered.
- Bad, because `generate_context`'s `Context` then has no authority,
  unlike Tauri's, and a plugin added in `setup` has no manifest.

### In a rake or CLI task

- Good, because start does no resolving.
- Bad, because it is a build step, which ADR 014 chose against, and a
  developer who forgets to run it starts with stale permissions.

### A declaration on the plugin class

- Good, because no gemspec contract is needed.
- Bad, because a plugin the app depends on but registers late, or not
  at all, contributes nothing, which is not Tauri's behavior.

### A list passed to `generate_context`

- Good, because it is explicit.
- Bad, because it is an API Tauri does not have, and every app repeats
  what its Gemfile already says.
