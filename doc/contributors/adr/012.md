# ADR 012: Main-Thread Dispatch and the GVL Hand-off

## Status

Accepted. Amends the thread-safety model of ADR 001 and ADR 005.

## Date

2026-10-25

## Context

tao's `EventLoop` and wry's `WebView` belong to the thread that built them,
the main thread. Tauri marks its main-thread types `Send` and keeps the
promise with a dispatcher: a call on the main thread runs at once, and a
call from any other thread travels through the event loop proxy and runs
there (tauri-runtime-wry `send_user_message`, `src/lib.rs:234-254`).

Tokra copied the `Send` impls without the dispatcher (Plan 019's finding).
App code on another Ruby thread reached wry directly through
`Tokra::Webview#eval`, and Ruby's garbage collector frees an object on
whichever thread sweeps it (Ruby v4.0.1 `gc.c:1182-1222`,
`gc/default/default.c:2062-2120`).

Porting the dispatcher exposed a second problem. tao's loop runs inside
`EventLoop#run`, holding the GVL. While it waits for an event, no other Ruby
thread runs at all: a probe thread that ticked every 200 ms never ticked in
20 s of idle loop. A background thread that sends a call to the main thread
and waits for the answer would wait until some unrelated event woke the
loop.

## Decision

1. **The native layer enforces the invariant.** `ThreadBound<T>` holds each
   platform value, the loop, every window, and every webview, with its
   thread's id, hands it out only there, and leaks it rather than drop it
   anywhere else. Every `EventLoop`, `Window`, and `WebView` method raises
   `ThreadError` on another thread. A window or webview that Ruby frees on
   another thread is sent to the loop and dropped on the main thread. The
   two `unsafe impl Send` blocks that trusted the invariant are gone;
   `ThreadBound`'s one impl rests on what its own methods do. tao calls its
   `Window` `Send + Sync`, but on macOS dropping one closes it with a
   synchronous dispatch to the main thread (`platform_impl/macos/window.rs:1734-1739`,
   `util/async.rs:242-249`), which deadlocks when the dropping thread holds
   the GVL the main thread waits for; so windows get the same wrapper.

2. **`Tokra::RuntimeContext` is Tauri's dispatcher, in Ruby.** `Window`,
   `Webview`, and `AppHandle` send every native call through it, and
   `run_on_main_thread` lands on all of them, as in Tauri. Ruby blocks stay
   in a Ruby queue; the native event (`UserEvent::Task`) only wakes the
   loop, so Rust never holds a Ruby object across threads.

3. **The loop keeps the GVL and hands it over once per iteration.** A
   READY thread-event hook (`rb_internal_thread_add_event_hook`, public in
   `include/ruby/thread.h`) fires whenever a thread starts waiting for the
   GVL, which includes every time-slice switch (`thread_pthread.c:1128-1141`).
   It only marks a hand-off owed, and wakes the loop when the mark was clear,
   so a busy thread cannot flood the loop. The loop clears the mark and calls
   `Thread.pass`, through magnus's protected `funcall`, at
   `MainEventsCleared`, after the platform's events are in. Installing the
   hook marks a hand-off owed at once, for threads that were already waiting.
   Ruby has no such hook on Windows, where the loop instead wakes every 10 ms
   while other Ruby threads exist.

4. **Ruby's events wait for the end of the iteration.** tao drains its
   user-event channel until it is empty before it ends an iteration
   (`platform_impl/macos/app_state.rs:110-121`). A Ruby callback inside the
   drain loses the GVL for a full time slice whenever another thread wants
   it, so a busy thread and a steady sender kept the drain, and the
   iteration, from ever ending: the window froze and `exit` never took
   effect. The drain now only queues the events Ruby needs, and
   `MainEventsCleared` delivers that batch. A window's close request joins
   the same queue in arrival order, so Ruby still sees the user events
   that came before it first, as in Tauri: tao's macOS `cleared()` hands
   over user events, then the window events it held
   (`app_state.rs:394-398`).

5. **An interrupt ends the loop the Ruby way.** `Thread.pass` runs pending
   interrupts. A `SignalException` from Ruby's default handler for TERM,
   HUP, or QUIT, an `Interrupt`, a `Thread#raise` aimed at the main thread,
   or any other exception that is not a `StandardError`, raised there or in
   a callback, ends the loop and is raised again by `EventLoop#run` once the
   loop is down. A `StandardError` from a callback is still reported and the
   loop keeps running; `SystemExit` still ends it with its status. The loop
   keeps an exit already set instead of resetting the flow for the next
   event, as Tauri does (tauri-runtime-wry `lib.rs:4029-4031`).

6. **Protocol answers from other threads go through the loop.** WebKit
   answers a scheme task on the main run loop and makes any other thread
   wait (`-[WKURLSchemeTaskImpl didReceiveResponse:]` calls
   `callOnMainRunLoopAndWait`). A Ruby thread waiting there holds the GVL
   the main thread needs, so neither moves. `Proxy#respond` on another
   thread sends the answer to the loop, which answers on the main thread.
   Tauri needs no such step: it has no GVL.

### Alternatives rejected

- **Release the GVL around the whole loop** (`rb_thread_call_without_gvl`)
  and take it back for each event (`rb_thread_call_with_gvl`). On its way
  out, `rb_thread_call_with_gvl` re-enters the blocking region through
  `unblock_function_set(..., FALSE)`, which runs pending interrupts
  (`thread.c:320-343`, `2063-2091`). A signal trap such as
  `trap("TERM") { exit }`, or a `Thread#raise` that a time-slice switch
  lets in, would `longjmp` across tao's and AppKit's frames. Ruby's public
  API has no way to mask trap interrupts there.
- **Pump the loop**: run `run_return` without the GVL until a batch of
  events arrives, return, and deliver the batch in Ruby. Tauri's
  `App::run_iteration` does this and deprecates it as a busy loop
  (`app.rs:1342-1344`). `run_return` does not return during macOS live
  resize or a modal session, so Ruby would stall then, and every batch
  would tear down and restart the platform loop.
- **Poll everywhere**: wake every few milliseconds and pass the GVL. It is
  sound, but it caps a background thread at one GVL hand-off per tick, and
  it burns wake-ups on every platform. It remains the Windows fallback.
- **Pass the GVL on every hook event.** The first version did, inside tao's
  user-event drain. Every time-slice switch fires READY, so a CPU-bound
  thread turned each hand-off into the next request, the drain never ended,
  and the window froze.

## Consequences

- Background Ruby threads run while the window is idle, and can drive the
  window and webview through `Tokra::Window`, `Tokra::Webview`, and
  `run_on_main_thread`. A CPU-bound thread gets one time slice per turn of
  the loop, so each busy thread adds about one time slice (measured near
  108 ms) to how long an event waits, and `exit` still ends the app.
- Calling a `Tokra::Native` window, webview, or event loop from another
  thread raises `ThreadError`. Only `Proxy` crosses threads.
- A main-thread callback that waits on a thread which waits on the main
  thread deadlocks, as in Tauri.
- Ruby signals other than `SIGINT` (which the loop takes) run when the
  loop next hands over the GVL or delivers an event, and end the app as
  they would any Ruby program. With no other thread and no events, nothing
  wakes the loop for a signal alone.
  *Amended 2026-10-27 (Plan 034):* a ticker thread now wakes the loop
  every 100 ms, Ruby's default time slice, and the loop hands over
  whenever Ruby has an interrupt pending, so a signal's handler, Ruby's
  default or an app's `trap`, runs within about 100 ms even when nothing
  else happens. The idle loop pays about ten wake-ups a second.
- An exception that is not a `StandardError`, raised in an event callback,
  now ends the loop instead of being reported and ignored.
- On Windows, untested so far, background threads get the GVL within
  10 ms instead of at once.
- *Amended 2026-10-28 (Plan 042, phase 3):* a context menu blocks the
  main thread in a nested run loop until it closes. That one native call
  releases the GVL (`rb_thread_call_without_gvl` inside magnus's
  `protect`), so other Ruby threads keep running, as Rust threads do in
  Tauri. It is sound because no callback of Tokra's, tao's, wry's, or
  muda's calls Ruby in the nested loop: tao holds back its handler while
  one runs, and muda's and wry's handlers only send through the proxy.
  On macOS tao's `drawRect:`, `open_urls`, and `reopen` skip that check
  and would block on the running handler's lock, as in Tauri, without
  reaching Ruby. A foreign callback the app registers itself (a GLib
  timeout, a Fiddle closure) takes the GVL back through
  `rb_thread_call_with_gvl`, whose interrupt check can `longjmp` across
  the platform's frames, as in any region without the GVL. Events and
  blocks for the main thread wait for the menu to close, as in Tauri, and
  so does a signal.
