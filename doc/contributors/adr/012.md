# ADR 012: The Event Loop Keeps the GVL and Hands It Over Once per Iteration

## Context and Problem Statement

tao's `EventLoop` and wry's `WebView` belong to the main thread. Tauri
keeps that promise with a dispatcher that runs every call from another
thread on the main thread. Tokra had copied Tauri's `Send` impls without
the dispatcher, so app code on another Ruby thread reached wry directly,
and Ruby's garbage collector could free a platform object on whichever
thread swept it.

Porting the dispatcher exposed a second problem. tao's loop runs inside
`EventLoop#run`, holding Ruby's GVL. While it waits for an event, no
other Ruby thread runs at all, so a background thread that sends a call
to the main thread and waits for the answer would wait until some
unrelated event woke the loop.

How do other Ruby threads run, and reach the window and webview, while
the platform's loop owns the main thread?

## Decision Drivers

- Soundness: a platform object is used and dropped only on its own
  thread, and no Ruby exception `longjmp`s across tao's or the
  platform's frames.
- Background Ruby threads make progress while the window is idle.
- The window keeps turning however busy the other threads are.
- Signals and `exit` end the app as they would any Ruby program.

## Considered Options

1. Keep the GVL in the loop, and hand it over once per iteration when a
   thread-event hook says a thread is waiting; bind each platform value
   to the main thread, and send other threads' calls through a Ruby
   dispatcher.
2. Release the GVL around the whole loop (`rb_thread_call_without_gvl`)
   and take it back for each event (`rb_thread_call_with_gvl`).
3. Pump the loop: run `run_return` without the GVL until a batch of
   events arrives, return, and deliver the batch in Ruby.
4. Poll everywhere: wake every few milliseconds and pass the GVL.

## Decision Outcome

Chosen: option 1, because it is the only option that is both sound and
prompt. Option 2 is unsound: on its way out, `rb_thread_call_with_gvl`
runs pending interrupts, so a signal trap such as `trap("TERM") { exit }`
or a `Thread#raise` would `longjmp` across tao's and AppKit's frames, and
Ruby's public API has no way to mask trap interrupts there. Option 3
stalls Ruby during macOS live resize or a modal session, when
`run_return` does not return, tears down and restarts the platform loop
for every batch, and is what Tauri's own `App::run_iteration` deprecates
as a busy loop. Option 4 is sound, but caps a background thread at one
GVL hand-off per tick and burns wake-ups on every platform; it remains
the fallback on Windows, where Ruby has no thread-event hook.

The hook only marks a hand-off owed, and the loop passes the GVL at the
end of an iteration, never inside tao's drain of its user events: the
first version passed it on every hook event, inside the drain, and a
CPU-bound thread kept the drain from ending, so the window froze.
[The native layer's design](../design/native.md) describes the hand-off,
the dispatcher, and how interrupts, protocol answers, and menus fit
around it.

Confidence: not recorded when the decision was made.

### Consequences

- Good, because background Ruby threads run while the window is idle,
  and can drive the window and webview through `Tokra::Window`,
  `Tokra::Webview`, and `run_on_main_thread`.
- Good, because a signal's handler runs, and `exit` takes effect, as in
  any Ruby program.
- Bad, because a CPU-bound thread gets one time slice per turn of the
  loop, so each busy thread adds about one time slice to how long an
  event waits.
- Bad, because calling a `Tokra::Native` window, webview, or event loop
  from another thread raises `ThreadError`; only `Proxy` crosses
  threads.
- Bad, because an exception that is not a `StandardError`, raised in an
  event callback, ends the loop instead of being reported and ignored.
- Bad, because a ticker wakes the idle loop about ten times a second so
  a signal is not left waiting, and on Windows another wakes it every
  10 ms while other Ruby threads exist.
- Bad, because a native call that blocks the main thread, such as a
  context menu, needs its own care: released around the call where
  that is sound, and handed over from a message hook where it is not.

### Confirmation

`test/integration/native_loop_test.rb` drives the loop with other
threads; the keyboard tests in `test/integration/keyboard/` hold a menu
open while another thread runs. Each `unsafe` block in
`ext/tokra/src/` carries a `// SAFETY:` comment citing the source that
makes it sound.
