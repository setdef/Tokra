# ADR 004: Tokra Builder Pattern & IPC

## Status
Accepted

## Date
2026-01-30

## Context
Tokra currently exposes `Rack::Handler::Tokra` as its primary integration point. While this fits the Rack ecosystem perfectly for protocol handling, it lacks a high-level API for configuring desktop-specific features like IPC handlers, menus, and system tray icons.

Developers familiar with Tauri expect a fluent Builder interface:

```rust
// Tauri (Rust)
tauri::Builder::default()
  .invoke_handler(tauri::generate_handler![my_command])
  .run(tauri::generate_context!())
  .expect("error running app");
```

Currently, Tokra developers must manually wire these features into the Rack handler's options hash, which is brittle and less discoverable.

## Decision
We will implement a **Ruby-idiomatic Builder Pattern** (`Tokra::Builder`) that mirrors the Tauri API structure but leverages Ruby's dynamic capabilities to remove boilerplate.

### 1. The Builder API
The `Tokra::Builder` class will be the "Porcelain" (high-level API) that wraps the "Plumbing" (`Rack::Handler::Tokra`).

```ruby
Tokra::Builder.new
  .app(MyRackApp)                         # The "Context"
  .title("My App")                        # Window Config
  .size(800, 600)
  .invoke_handler(my_proc)                # IPC / Command Handler
  .run                                    # Boots the Event Loop
```

### 2. No Macros Needed
In Rust, macros like `generate_handler!` and `generate_context!` are required for compile-time introspection and static asset embedding. In Ruby, we do not need these:

*   **`invoke_handler`**: Instead of a macro that generates a dispatch table, we simply pass a `Proc` or `Method` object. Ruby's runtime reflection handles the dispatch.
*   **`generate_context`**: Instead of a macro that parses `tauri.conf.json` at compile time, `Tokra::Builder` will automatically load configuration from standard locations (or accept a config hash).

### 3. Separation of Concerns
*   **`Rack::Handler::Tokra`**: Remains the **adapter**. It knows how to translate `HttpRequestEvent` to Rack. env.
*   **`Tokra::Builder`**: Becomes the **application definition**. It aggregates configuration, handlers, and the Rack app, then instantiates the Handler with the correct options.

## Consequences

### Positive
*   **Developer Experience:** Provides a familiar, fluent API for Tauri developers migrating to Ruby.
*   **Discoverability:** Methods like `.title`, `.size`, and `.invoke_handler` are easier to find than keys in an options hash.
*   **Extensibility:** The Builder can easily support future features (plugins, menu construction, tray icons) without polluting the `Rack::Handler` signature.

### Negative
*   **Maintenance:** Adds a layer of abstraction that must be maintained in sync with the underlying Handler.
