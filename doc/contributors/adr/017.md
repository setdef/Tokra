# ADR 017: Each Tokra Gem Versions and Releases on Its Own

Supersedes ADR 006 §7.4's release task and §7.5 (version coordination).
ADR 006's other choice in §7, one repository of several gems, stands.

## Context and Problem Statement

Tokra's repository holds several gems: `tokra`, and one plugin for
each folder under `plugins/`. ADR 006 §7.5 gave them one version, read
from a `TOKRA_VERSION` file, with each plugin pinned to exactly that
tokra.
The repository never did this. Each plugin has had a `version.rb` of
its own since the first two were scaffolded on 2026-01-31, the day
after ADR 006, and each gemspec bounds tokra with `~> 0.0`. Nothing
reads `TOKRA_VERSION`. No record says why §7.5 was set aside.

The first release with plugins now needs release tooling, and the
tooling has to follow one rule or the other. How are Tokra's gems
versioned, tagged, and released?

## Decision Drivers

- A tag has to name one gem's release. Bundler's `gem_tasks` tags every
  gem `v0.1.0`, which several gems cannot share.
- A version is a promise about one gem's API (SemVer). A plugin that
  did not change should not get a new version because tokra did.
- A plugin has to say which tokra it works with.
- Tokra and Ferro have one maintainer, who releases both.

## Considered Options

1. Each gem has its own version, changelog, and tag
   (`tokra-dialog/v0.1.0`), released by tasks ported from Ferro; a
   plugin bounds tokra by minor version (`~> 0.1`).
2. One shared version and one release of every gem, each plugin
   pinned to exactly that tokra (ADR 006 §7.5, the Rails pattern).

## Decision Outcome

Chosen: option 1, because it is what the repository already does, and
it is how Ferro releases (Ferro's ADR 001 §5), so one person runs one
kind of release in both repositories. Which option suits Tokra better
was not weighed when the plugins were first given their own versions;
the reasons here were first written down on 2026-11-04, when the
release was planned, and weighed against a shared version on
2026-11-13.

Each gem keeps its version in its own `version.rb` and its changes in
its own `CHANGELOG.md`. `rake bump:<gem>:<part>` releases one gem's
changelog section and commits `chore(<gem>): release X.Y.Z`;
`rake release:<gem>:tag` tags that commit `<gem>/vX.Y.Z`. A tokra
release that moves its minor version raises every plugin's bound to
that minor in the same commit, since each plugin is tested only against
the tokra beside it. The maintainer runs every bump and release task.

Confidence: high that this works, since Ferro has released six gems
this way. That it serves Tokra better than a shared version rests on
the reasons above, not on a trial of both.

### Consequences

- Good, because a tag, a changelog section, and a RubyGems version each
  name one gem's release.
- Good, because a plugin fix ships without a tokra release.
- Bad, because a tokra minor release changes every plugin's gemspec,
  and each plugin then needs a release of its own before its users can
  take the new tokra.
- Bad, because an app's Gemfile can combine a plugin and a tokra that
  were never tested together, within the bound. A shared version would
  have made that impossible.
- `TOKRA_VERSION` and its `REUSE.toml` entry are dead and can go.

### Confirmation

`test/tasks/test_tokra_gems.rb` checks the list of gems against the
repository: every gemspec is listed, each version file matches its
gemspec, each plugin bounds tokra, and no Rakefile loads Bundler's
`gem_tasks`. `test/tasks/test_bump.rb` and `test/tasks/test_release.rb`
pin the tasks.

## Pros and Cons of the Options

### One shared version and one release

Later research, 2026-11-13; not weighed at the time.

- Good, because every published combination of tokra and a plugin was
  tested together.
- Good, because one number answers "which Tokra do I have".
- Bad, because every gem is published at every release, changed or not.
- Bad, because Tauri's own plugins do not work this way: at the commit
  Tokra's plugins were ported from, each has its own version
  (`plugins/dialog` 2.6.0, `plugins/log` 2.8.0, `plugins/notification`
  2.3.3, in `tauri-apps/plugins-workspace` at `d4613ff0`).
