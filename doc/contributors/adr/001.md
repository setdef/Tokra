# ADR 001: A Ruby Host over Thin Rust Bindings to tao and wry

## Context and Problem Statement

Tokra is a desktop application framework for Ruby 4.0.1 and later: the
frontend is HTML, CSS, and JavaScript, and the backend is Ruby. Tauri,
which Tokra ports, keeps its application lifecycle, commands, state,
and security checks in Rust, over tao for windows and wry for webviews.
With Ruby 4.0's Ractors and YJIT, Ruby can carry those responsibilities
itself.

Where does the framework's logic live, and how much of it is Rust?

## Decision Drivers

- Rust maintenance stays small in cost and complexity.
- Ruby developers keep their logic, and the framework's, in Ruby.
- The UI stays responsive: the main thread is never blocked.
- A secure barrier stands between the webview and the system.

## Considered Options

1. A Ruby host over thin Rust bindings: Rust wraps tao and wry and
   passes raw events and messages to Ruby, and Ruby implements the
   lifecycle, command routing, security checks, and state.
2. Tauri's model, with its logic in Rust and Ruby for the app's code
   only. (Named in the context as what Tauri does; not weighed at the
   time.)

## Decision Outcome

Chosen: option 1. The Rust layer is a dumb pipe: a magnus extension,
built with rb_sys, that wraps tao and wry and knows nothing of commands
or state, and everything else is Ruby. The main Ractor runs tao's event
loop and the windows; the target is for the app's logic, file I/O, and
heavy computation to run in a worker Ractor, messages crossing by
`Ractor` ports. No reason beyond the drivers was recorded for preferring
option 1 to option 2.

The worker Ractor is not built: `App` dispatches every command
synchronously on the main Ractor today ([the IPC design](../design/ipc.md),
"Where commands run"). [The native layer's design](../design/native.md)
says what the extension holds and how it shares threads with Ruby.

Confidence: not recorded when the decision was made.

### Consequences

- Good, because logic changes happen in Ruby, and Rust compiles rarely.
- Good, because a plugin that needs no native code is pure Ruby.
- Bad, because every platform capability needs a native wrapper and a
  Ruby API over it, and a platform issue is traced through both layers.
- Bad, because message passing between Ractors is asynchronous, so app
  code that runs in a worker Ractor has to be written for it.
- Bad, because two Ractors cost more base memory than one.
- Bad, because installing the gem compiles a Rust extension, which needs
  a Rust toolchain and the platform's build libraries.

### Confirmation

Nothing automated checks it. AGENTS.md states the rule, that Rust is a
thin binding and Ruby owns all logic, for every contributor.
