# ADR 007: Ractor-Shareable Mutable State via Rust

## Status
Accepted

## Date
2026-02-01

## Context
Ruby 4.0's Ractor model provides thread-safe concurrency through **isolation**: each Ractor has its own GVL, and unshareable objects cannot cross Ractor boundaries. Objects can be made shareable via `Ractor.make_shareable`, which deep-freezes the object graph.

However, some Tokra plugins require **shared mutable state** across Ractors:
- A single instance accessible from both Main and Worker Ractors
- Methods that modify internal state (e.g., write operations)
- Thread-safe concurrent access

### The Ruby Limitation

Ruby's `Mutex` is **unshareable**:

```ruby
m = Mutex.new
Ractor.shareable?(m)  #=> false
Ractor.make_shareable(m)  #=> Ractor::Error: can not make shareable object
```

This is because Ruby cannot statically verify that a Mutex-protected object is safe to access from multiple Ractors. Ruby's Ractor safety relies on **runtime verification**, not compile-time proofs.

Furthermore, frozen objects cannot be mutated:

```ruby
obj = SomeClass.new
Ractor.make_shareable(obj)  # Freezes the object
obj.mutate!  #=> FrozenError
```

This creates an impossible situation for plugins needing shared mutable state: they cannot use Ruby's Mutex (unshareable), and they cannot mutate frozen objects (required for shareability).

### The Rust Solution

Rust's type system provides **compile-time guarantees** of thread safety through the `Send` and `Sync` traits:

- `Send`: Safe to transfer ownership to another thread
- `Sync`: Safe to share references between threads
- `Mutex<T>`: Implements `Send + Sync` when `T: Send`

Magnus (the Rust-Ruby bridge) exposes two mechanisms:

1. **`frozen_shareable()`**: Marks a `TypedData` wrapper as Ractor-shareable when frozen
2. **`rb_ext_ractor_safe(true)`**: Marks the entire extension as safe to call from non-main Ractors

Combined, these allow Rust structs with interior mutability (via `Mutex<T>`) to be:
- Shared across Ractors (frozen, but mutable through the Mutex)
- Called from any Ractor (not just the main Ractor)

## Decision

**Plugins requiring shared mutable state MUST implement that state in Rust using `Mutex<T>`.**

### 1. The Pattern

```rust
use std::sync::Mutex;

pub struct RbSharedResource {
    inner: Mutex<Option<SomeNativeType>>,
}

impl RbSharedResource {
    fn new() -> Self {
        Self { inner: Mutex::new(Some(SomeNativeType::new())) }
    }

    // Note: &self, not &mut self — interior mutability via Mutex
    fn mutate(&self, value: String) -> Result<(), Error> {
        let mut guard = self.inner.lock().unwrap();
        match guard.as_mut() {
            Some(resource) => resource.set(value),
            None => Err("Resource has been cleaned up"),
        }
    }

    fn cleanup(&self) {
        self.inner.lock().unwrap().take();  // Drop the inner resource
    }
}
```

### 2. TypedData Configuration

```rust
unsafe impl magnus::TypedData for RbSharedResource {
    fn data_type() -> &'static magnus::DataType {
        static DATA_TYPE: magnus::DataType =
            magnus::typed_data::DataTypeBuilder::<RbSharedResource>::new(c"MyModule::Resource")
                .free_immediately()
                .frozen_shareable()  // <-- Enables Ractor shareability when frozen
                .build();
        &DATA_TYPE
    }
}
```

### 3. Extension Initialization

```rust
#[magnus::init]
fn init(ruby: &Ruby) -> Result<(), Error> {
    // Mark entire extension as Ractor-safe
    unsafe { rb_sys::rb_ext_ractor_safe(true); }

    // ... define classes and methods
}
```

### 4. Ruby Usage

```ruby
# Create and make shareable
resource = MyModule::Resource.new
Ractor.make_shareable(resource)

# Use from any Ractor
worker = Ractor.new(resource) do |r|
  r.mutate("value from worker")  # Works! Mutex provides thread safety
end
worker.value

resource.read  # Also works from main Ractor
```

## Consequences

### Positive

1. **True 1:1 Tauri Parity** — Tauri uses `Mutex<Option<T>>` for shared plugin state. This pattern is now possible in Tokra.

2. **Ractor-Safe Shared State** — Plugins can be accessed from both Main and Worker Ractors without message passing overhead.

3. **Compile-Time Safety** — Rust's type system guarantees thread safety. If the code compiles, it's safe.

### Negative

1. **Increased Rust Surface** — Plugins with shared mutable state cannot be pure Ruby. This increases the Rust maintenance burden for certain plugins.

2. **ADR 005 Estimate Refined** — The "~20 LOC Rust" estimate for plugins like clipboard assumed stateless wrappers. Shared mutable state requires the Mutex pattern, adding ~20-40 additional lines.

3. **Unsafe Assertions Required** — `rb_ext_ractor_safe(true)` and `frozen_shareable()` require the developer to assert correctness. A bug in the Rust code could violate Ractor safety guarantees.

### Neutral

1. **Pure Ruby Plugins Unaffected** — Plugins that don't require shared mutable state (e.g., dialogs, notifications) remain pure Ruby with thin Rust bindings.

2. **Pattern Matches Tauri** — This is exactly how Tauri implements plugins, so porting patterns are 1:1.

## Classification

| State Requirement | Implementation |
|-------------------|----------------|
| Stateless (single call) | Pure Ruby + thin Rust binding |
| Per-Ractor state | Pure Ruby instance per Ractor |
| **Shared mutable state** | **Rust `Mutex<T>` + `frozen_shareable()`** |
