### Planner Response

This is an excellent architectural question. Let me analyze the tradeoffs:

## Option Analysis

| Approach | Pros | Cons |
|----------|------|------|
| **In-core (`lib/tokra/plugins/`)** | Single gem install; no version coordination; simple for users | Bloated binary with unused features; compile time increases; forces all-or-nothing updates |
| **Monorepo (like `plugins-workspace`)** | Coordinated releases; shared CI; atomic cross-plugin changes; one repo to clone | More complex release process; still all plugins in one checkout |
| **Individual repos** | Independent release cycles; focused issues/PRs; clear ownership | Version matrix complexity; scattered documentation; harder cross-plugin refactoring |

## My Recommendation: **Monorepo**

For Tokra's first-party plugins, I recommend **Option 2: a monorepo** (e.g., `tokra-plugins`) with individual gems. Here's why:

### 1. **Ruby Ecosystem Precedent**
Tauri uses `plugins-workspace` (which you already have checked out). Rails uses a monorepo for `rails-*` gems. This pattern is proven.

### 2. **Thin Binding + Heavy Ruby Split**
Tokra's ADR 005 establishes that plugins are ~50-100 LOC Rust + ~200+ LOC Ruby. The Ruby portion could live in-core, but the **Rust extensions must be separate gems** because:
- Each plugin adds Rust compile time
- Each plugin adds binary size
- Users shouldn't pay for dialogs if they only want clipboard

### 3. **Coordinated Releases Matter**
When Tokra 0.2 ships with breaking changes, all first-party plugins need updates simultaneously. A monorepo with a shared `TOKRA_VERSION` constant makes this trivial.

### 4. **Keeps Tokra Core Minimal**
The main `tokra` gem stays focused on the event loop, Builder, and Rack adapter. No platform dependencies beyond `tao`/`wry`.

Keep all first-party plugins **in the Tokra repo itself**, but as **separate gems with their own gemspecs**:

```
tokra/
├── tokra.gemspec              # Core only (~500 LOC Rust)
├── lib/tokra/                 # Core Ruby
├── ext/tokra/                 # Core Rust
│
├── plugins/
│   ├── clipboard/
│   │   ├── tokra-clipboard.gemspec
│   │   ├── ext/tokra_clipboard/   # Rust bindings for arboard
│   │   └── lib/tokra/plugins/clipboard.rb
│   ├── dialog/
│   │   ├── tokra-dialog.gemspec
│   │   ├── ext/tokra_dialog/
│   │   └── lib/tokra/plugins/dialog.rb
│   └── global-shortcut/
│       ├── tokra-global_shortcut.gemspec
│       ├── ext/tokra_global_shortcut/
│       └── lib/tokra/plugins/global_shortcut.rb
│
└── Rakefile                   # Delegates to each plugin
```

**Why this avoids staleness:**
- You're always in `tokra/` — no context switch
- `git status` shows changes across all plugins
- Single CI workflow, single PR, atomic commits
- Version file like Rails' `TOKRA_VERSION` keeps everything in sync

**Rake tasks:**
```ruby
# Rakefile
PLUGINS = Dir["plugins/*"].select { |f| File.directory?(f) }

desc "Test all"
task :test do
  sh "rake test:core"
  PLUGINS.each { |p| sh "cd #{p} && rake test" }
end

desc "Build all gems"
task :build do
  sh "gem build tokra.gemspec"
  PLUGINS.each { |p| sh "cd #{p} && gem build *.gemspec" }
end
```

This is exactly how Rails works — and it's survived 20 years. The only difference from what I proposed earlier is: **plugins live in the main repo, not a separate `tokra-plugins` repo.**
