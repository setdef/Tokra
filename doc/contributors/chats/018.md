⏺ Verdict: the plan's architecture is sound — the phasing mirrors Tauri's real
  structure and most of its naming mistakes were already corrected during chat
  017. But yes, it warrants three concrete changes, one of which is a parity bug
  already committed to trunk.

  1. The committed error message violates port fidelity (fix regardless of 
  plan). Tauri's error.rs:140 is "The resource id {0} is invalid." — Tokra's
  Error::BadResourceId (from Phase 2.1, commit 7885f70) says "Resource ID #{rid}
  not found". CLAUDE.md rule 2 says error messages MUST match the Rust source,
  and chat 017 never checked the message text, only the class naming. Pre-alpha,
  zero users: change it to the exact Tauri string (affects error.rb, its RDoc,
  and assertions in test_error.rb).

  2. The plan under-scopes Phase 2.2: registration and routing are the actual 
  substance, not just the two plugin classes. Tauri auto-registers these plugins
  during app build (app.rs:1128-1129:
  self.handle.plugin(resources::plugin::init()) then image::plugin::init()), and
  its IPC layer routes by parsing the plugin: prefix — webview/mod.rs:1793
  strips it, looks the plugin up by name in a PluginStore, and only falls
  through to the app's invoke_handler for non-plugin commands (:1842-1888). Plan
  009 asked "How does Tauri register built-in plugins?" as a research question
  but then omitted registration from Phase 2.2's test list entirely. Without it,
  the new plugin classes are dead code — required but never instantiated, and
  dispatch_ipc only calls the user's single invoke_handler_hook. Phase 2.2
  should deliver: a plugin store on the app/handle, auto-registration of these
  two core plugins at build time, and plugin:-prefix routing in dispatch_ipc.
  That's the 1:1 shape, and it's also what Phase 2.4 (clipboard) needs to exist
  anyway.

  3. from_bytes/from_path should be rejecting commands, not unhandled. The plan
  punted on these ("requires image decoding"), and the current code returns
  false. But Tauri built without the image-ico/image-png features — which is
  exactly Tokra's situation — still registers both commands and returns an
  error: "from_bytes is only supported if the image-icoorimage-png Cargo 
  features are enabled". Handling them with invoke.reject(...) and Tauri's
  message (lightly adapted) matches both the port philosophy and this repo's
  established pattern of loud, documented non-implementation (level_for,
  with_colors in the log plugin).

  One design decision worth making consciously now: Tauri's plugins receive the
  bare command (new, not plugin:image|new) because the store routes by plugin
  name first. Tokra's plugins (clipboard included) match the full namespaced
  string inside extend_api. If we're building the store/router in Phase 2.2,
  this is the moment to pick: I'd route by name at the dispatcher (Tauri parity,
  and it makes each plugin's extend_api only see its own commands) but keep
  passing the full command string in Invoke#command, since ADR 006 already
  documents that pattern and the frontend-visible protocol (ADR 008) is
  unaffected either way.

  What doesn't warrant change: the phase ordering, ResourceTable/Image design,
  the Tokra::Image::Plugin / Tokra::Resources::Plugin namespacing (it maps
  cleanly onto tauri::image::plugin / tauri::resources::plugin), the file layout
  mirroring image/plugin.rs, and the in-flight size test — that's just
  unfinished TDD, and the plan correctly specified size all along.

  Want me to proceed on that basis — finish size (GREEN), fix the error-message
  parity, add from_bytes/from_path rejections, then build registration/routing —
  or would you rather I write the revised Phase 2.2 scope down first (plan
  amendment or ADR) before touching code?

❯ Would it be better or worse to port the Tauri documentation with as high of   
  fidelity as the Tauri code?                                                   

⏺ Worse as a blanket policy, better selectively — and the distinction falls
  directly out of your own design precedence.

  Why code fidelity doesn't transfer to prose fidelity. Code parity works
  because there's a mechanical mapping: Error::BadResourceId →
  Tokra::Error::BadResourceId, and a test can verify it. Prose has no such
  mapping. Tauri's rustdoc is saturated with Rust semantics — Arc<Mutex<>>, R: 
  Runtime bounds, ownership transfer, Cargo feature flags, Result types. A
  near-verbatim port would make Ruby users mentally translate concepts that
  don't exist in their language, which is precisely what rule 1 ("Ruby the
  language") says trumps rule 2. Error messages earned their MUST-match status
  because frontend code can observe and match on them at runtime; doc prose has
  no runtime surface. And rule 2's own text scopes fidelity to "method names,
  class structure, error messages, and API shapes" — documentation is
  deliberately not on that list.

  Second problem: you'd import Tauri's gaps. Tauri's doc comments are thin in
  many places — one-liners or nothing, because their real documentation lives on
  the docs site. High-fidelity porting would faithfully reproduce that
  sparseness while your Alexandrian/Zinsser mandate exists exactly because docs
  are the developer UX of the gem. There's also mechanical friction: rustdoc is
  Markdown, RDoc isn't, so "verbatim" is already lossy; and copied prose needs
  SPDX snippet annotations, adding noise to every file.

  Where high fidelity is genuinely better: behavioral contracts. Some Tauri doc
  sentences define semantics rather than describe them. Today's work hit a
  perfect example — PluginStore::extend_api's doc: "The message is not handled
  when the plugin exists and the command does not." That sentence is the
  specification; paraphrasing it risks changing the meaning, and I ported its
  substance into the Ruby doc nearly intact. Same category: take does not call
  close; clear does not call close; the webview→window→app fallback order. For
  those, close-to-verbatim porting with a citation is the more faithful and the
  safer choice.

  So the policy I'd recommend — which is what the codebase already does by
  instinct — is two-tier:

  1. Semantic fidelity is mandatory: every behavioral claim, caveat, and edge
  case in Tauri's docs must have its counterpart stated truthfully in the RDoc.
  A parity reviewer should be able to put the two side by side and find no
  contradiction.
  2. Prose fidelity is selective: contract-defining sentences may be ported
  near-verbatim (with the existing "Matches Tauri x.rs:N" citation); everything
  else is written for Rubyists in the Alexandrian/Zinsser voice, with
  Rust-machinery references translated or dropped.

  That keeps the port honest where honesty is load-bearing and keeps the docs
  useful where Tauri's aren't. If you want, I can add a short paragraph
  codifying this two-tier rule to the Tauri Parity Citations section of
  documentation_style.md — it's about four sentences.
