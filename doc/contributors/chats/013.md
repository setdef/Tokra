### Planner Response

**Ruby's `Mutex` is not shareable**, and objects containing a Mutex cannot be made shareable.

This is a fundamental difference from Rust, where `Mutex<T>` is `Send + Sync`.

---

**So what's the 1:1 Ruby equivalent of Tauri's approach?**

Tauri relies on Rust's `Mutex` being `Send + Sync`. Ruby doesn't have that.

**Options:**

1. **Store the plugin in a single Ractor, communicate via Ports**
   - Only one Ractor owns the Clipboard
   - Other Ractors send requests via `Ractor::Port`
   - Similar to actor model

2. **Use Ractor-local storage**
   - Each Ractor that needs clipboard gets its own instance
   - No sharing, no Mutex
   - But: Linux clipboard ownership issues (multiple owners)

3. **Use a native Rust Mutex (in the extension)**
   - Wrap `arboard::Clipboard` in Rust `Mutex` 
   - The Rust wrapper is shareable (marked `frozen_shareable` in Magnus)
   - Ruby calls into Rust, which has the Mutex

Option 3 is actually what Tauri does—and it's the only way to get the same behavior in Ruby.

---

**So the question becomes:** Does Tokra need to implement the Worker Ractor infrastructure first, or can the clipboard plugin use a Rust-side Mutex (which *is* shareable via Magnus's `frozen_shareable`)?

If we use Rust Mutex, the Rust layer gets thicker. If we want thin Rust + Ruby Mutex, we need to solve the "Mutex isn't shareable" problem.

Here's why:

| Mechanism | Ruby | Rust + Magnus |
|-----------|------|---------------|
| `Mutex` | **Unshareable** — Ruby can't verify it's safe | **Shareable** — Rust's `Mutex<T>` is `Send + Sync` by proof |

1. **Plugins needing shared mutable state must use Rust** — A Ruby `Mutex` cannot be shared across Ractors, but a Rust `Mutex<T>` wrapped via Magnus can.

## 3. Distinction Between Plugin Instance and Plugin-Managed-State

### Tauri's Model

| Concept | Lifetime | Purpose | Storage |
|---------|----------|---------|---------|
| **Plugin** | App lifetime | Lifecycle hooks, IPC handlers | `PluginManager` internal vec |

### Ruby Recommendation: Same model

```ruby
# Tokra core
class Tokra::App
  def initialize
    @plugins = []     # Plugin instances (for lifecycle hooks)
    @state = {}       # Managed state (keyed by class)
  end
  
  def register_plugin(plugin)
    @plugins << plugin
    plugin.initialize(self, config_for(plugin.name))
  end
  
  def manage(state_instance)
    @state[state_instance.class] = state_instance
  end
  
  def state(klass)
    @state.fetch(klass) { raise "state() called before manage() for #{klass}" }
  end
end
```

**Why**:
1. **Plugins can be stateless** — A logger plugin might not [manage](cci:1://file:///Users/kerrick/Developer/tokra/lib/tokra/builder.rb:33:4-39:7) anything

## Research: Tauri's ResourceTable for Image Handling

### How Tauri's Image IPC Works

1. **read_image in clipboard plugin** (commands.rs:53-62):
   ```rust
   let image = clipboard.read_image()?.to_owned();
   let rid = resources_table.add(image);  // Store Image in table
   Ok(rid)                                 // Return just the integer ID
   ```

2. **Frontend receives ResourceId** (JS):
   ```typescript
   const rid = await invoke('plugin:clipboard-manager|read_image');
   return new Image(rid);  // Wraps the integer ID
   ```

3. **Frontend fetches actual bytes** via `@tauri-apps/api/image` plugin:
   ```typescript
   // Inside Image class
   async rgba(): Promise<Uint8Array> {
     return invoke('plugin:image|rgba', { rid: this.rid });
   }
   ```

4. **Backend image plugin** (image/plugin.rs:57-62):
   ```rust
   fn rgba(webview, rid: ResourceId) -> Result<Vec<u8>> {
     let image = resources_table.get::<Image>(rid)?;
     Ok(image.rgba().to_vec())
   }
   ```

### Why ResourceTable Exists

- **Memory efficiency**: Large RGBA byte arrays aren't serialized twice
- **Reference counting**: Image stays alive in Rust while JS holds the ID
- **Lazy loading**: Frontend fetches bytes only when needed

### Does Tokra Have ResourceTable?

**No.** Tokra doesn't have [ResourceTable](cci:2://file:///Users/kerrick/Developer/tauri/crates/tauri/src/resources/mod.rs:75:0-77:1) implemented.

## Options for Tokra

### Option A: Implement ResourceTable for Full Parity

**Effort**: ~100 LOC Ruby + wire into Manager

```ruby
# lib/tokra/resource_table.rb
class Tokra::ResourceTable
  def initialize
    @resources = {}
  end

  def add(resource)
    rid = SecureRandom.random_number(2**32)
    @resources[rid] = resource
    rid
  end

  def get(rid)
    @resources.fetch(rid) { raise Tokra::Error::BadResourceId.new(rid) }
  end

  def close(rid)
    @resources.delete(rid)
  end
end
```

Then clipboard [read_image](cci:1://file:///Users/kerrick/Developer/plugins-workspace/plugins/clipboard-manager/src/desktop.rs:101:4-115:5) returns [rid](cci:1://file:///Users/kerrick/Developer/tauri/crates/tauri/src/resources/mod.rs:80:2-84:3), and we implement the core [image](cci:1://file:///Users/kerrick/Developer/plugins-workspace/plugins/clipboard-manager/src/desktop.rs:101:4-115:5) plugin:
